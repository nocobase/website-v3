# 编写文档中的提示词

文档中的提示词是人写给 Agent 的需求，也是给人看的示例。读者应当能理解每句话，知道它想完成什么，并能自然地换成自己的需求。

适用于本仓库各种文档中的开发、配置、应用内对话、排错和验证提示词，中英文都遵循同一原则。只处理当前任务涉及的内容，不因使用本 Skill 就批量改写其他文章。

## 写读者会说的话

- 从读者的目的出发：想在什么地方做什么、希望看到什么结果。通常一句或几句就够，不套固定模板，也不以字数代替判断。
- 使用日常表达，例如“给任务列表加个搜索框”“成员只能看到分配给自己的任务”。必要的业务规则要明确；人性化不等于只剩“帮我做好”这样的空话。
- 只保留会影响结果、且读者确实需要指定的名称和细节，例如选用的产品、目标项目、文件或业务字段。包名、API、服务端校验机制和目录结构，不应因为作者知道就出现在提示词中。面向开发者的示例也要让上下文足以解释这些术语。
- 不让读者替 Agent 编写实现方案。不要把“遵循 AGENTS.md 和 Skills”“复用公开契约”“报告未验证项”等项目指令变成每段提示词的固定结尾。
- 一次围绕一个目的展开。复杂业务可以用简短清单或自然的后续对话补充；不要只是把同一份技术清单拆成多轮，仍要求新手全部输入后才能开始体验。
- 中文像日常交流，英文像自然的用户请求。翻译时保留意图与业务边界，不照搬生硬句式或术语堆叠。

## 把细节放到合适的位置

提示词负责说明用户需求，正文负责帮助读者准备和理解，项目指引负责指导实现：

正文同样要简洁。移出提示词后，只在相关位置保留读者当前需要的信息；已有说明用链接引用，不要原样搬过去形成另一堵技术文字墙，也不要在多处重复同一要求。

- 安装插件、连接机器、准备账号或配置服务，放在场景前提和操作步骤中。
- 包名、注册入口、公开 API、事务、权限校验和路径限制，放在实现说明或开发约束中，并保留准确的来源。
- 测试命令、失败路径、验证证据和未验证范围，放在结果检查或验收说明中。确需验收提示词时，只写这次要确认的可观察行为。
- 重要业务限制仍可直接说，例如“普通成员只能看自己的任务”或“先帮我看看，别修改文件”。不要为了简短而丢掉这些限制，也不要把从提示词移出的技术要求直接删掉。
- 区分交给开发 Agent 的需求与功能建好后在应用里发出的任务。说明各自在哪里使用，不把两种提示词混在一起。

沿用所在文档的代码块和章节约定；本 Skill 不规定统一的文章结构。原始用户输入、故障复现材料或需要忠实引用的外部提示词保留原文，不伪装成编辑后的示例。

## 改写示例

**快速开始。** 不要求用户一次交代字段、接口、角色矩阵、测试清单和交付报告。先给出能开始体验的需求：

```prompt
帮我在这个应用里加一个任务管理页面，能新建任务、设置截止日期、标记完成。做好后运行起来给我看看。
```

**接入机器上的编程助手。** 不要把开发提示词写成下面这样的内部实施说明：

```text
请使用 @nocobase/app-plugin-agents，复用 Runtimes 和 Machine agents 页面，使用公开会话与任务能力；工作目录由服务端校验，先做只读验证，再做代码修改验证，报告未验证项。
```

面向读者的开发需求可以写为：

```prompt
我想在应用里给机器上的编程助手发任务，能选择项目、看到执行进度和结果。帮我把这个功能接上。
```

把插件要求、机器连接方式、目录授权和执行验证保留在这个场景的正文中。功能接好后，应用内的第一条任务可以另写为：

```prompt
帮我看看这个项目的页面路由写在哪里，先不要改代码。
```

**检查权限。** 用读者能看到的行为说明要检查什么：

```prompt
帮我检查一下：普通成员是不是只能看到分配给自己的任务，而且只能更新进度？
```

服务端授权、直接调用接口和测试覆盖的要求放在旁边的验证说明中。上面的示例用于说明表达方式，不是每篇文档都要套用的固定句式。

## 编辑后检查

站在目标读者的角度读一遍：这像是我会主动说的话吗？我能解释其中每个术语吗？能换成自己的需求吗？如果需要先理解一堆内部实现才能使用，继续改写。

同时检查：需求是否具体，必要业务边界是否保留，移出的技术要求是否有去处，提示词能否在正文给出的前提下使用。不要仅靠删字、换同义词或分段来通过检查。
