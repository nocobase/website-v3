# 文档写作风格

读者是来完成一件事或查一个事实的开发者。每句话都要让读者往前走一步。删掉一句之后，读者什么都没少知道，这句就该删。

这套规则取自 Supabase、Cloudflare、Next.js、Vercel、Stripe、Lovable、Convex 和 Vue 中文文档的共同做法：第一句就是答案，一篇只做一件事，检查跟在步骤后面，导航只给链接和一句话。

## 一篇只做一件事

| 类型 | 读者要什么 | 怎样写 | 例子 |
| --- | --- | --- | --- |
| 入门 | 跟着做，得到能用的结果 | 编号步骤。每步一个动作，接一两句结果。不展开原理，不写检查清单 | 创建应用、开发第一个功能 |
| 指南 | 完成一项具体任务 | 标题写任务。前提、做法、结果，可以讲取舍 | 持续开发应用、部署 |
| 概念 | 弄清是什么、由什么组成 | 先定义，再拆组成部分，用同一个例子贯穿 | 认识 NocoBase Core、应用的代码结构 |
| 示例导读 | 看一个完整的实现 | 按数据流向列出关键代码，每段说明做什么、为什么，链接到完整文件。不写成动手步骤 | 一个功能的完整代码 |
| 参考 | 查准确的事实 | 表格和完整列表 | 命令、配置项、接口 |

遇到属于另一类的内容，链接到对应的页面，不在本篇展开。比如入门教程只写“应该看到什么”，系统的检查方法放在指南里。

## 开头

- 第一段让读者马上知道这篇对自己有什么用。概念页先给定义；入门和指南先说要做的事。
- 用途不明显的页面，例如一个新部分的第一篇、示例导读，第一段写清读者为什么要读、用它来做什么。这是上下文，不是目录。
- 每一页都要能单独读懂。读者可能从搜索直接进来，所以不写“开始使用里”“上一篇”“接着前面的应用”，直接说出所指的东西，或者给出链接。
- 不写目录式的导语，例如“本篇介绍……”“下面说明……”。`description` 会显示在标题下面，一般不写；搜索摘要写进 `metaDescription`，它不显示在页面上。
- NocoBase、Core、Studio、Solution 的定义照用《NocoBase 产品定义与标准表述》，可以缩写，不改逻辑和用词。

## 句子

- 一句话一个意思。并列超过三项，改成列表或表格。
- 主语放在前面，按“谁 + 做什么”写。不把宾语、范围或例子提到句首；条件用“如果……”“……时”开头。
- 先说结论，再说条件和例外。
- 写具体的事。写“销售只能看到自己负责的客户”，不写“数据范围生效”。
- 不写空话，例如“非常强大”“轻松实现”“可以看到”“总之”“这样一来”。
- 一个事实只在一处讲清，别处链接过去。
- 版本说明、例外和注意事项写在用到它的那一步，不为罕见情况写满预防。

## 标题

- 菜单里的标题不依赖示例名称。读者浏览目录时还不知道示例是什么：写“一个功能的完整代码”，不写“读懂客户管理的代码”。
- 一组连续的页面，标题要看得出先后，同一个词不指两件事。例如《创建应用》之后接《开发第一个功能》，不接《搭建第一个应用》。
- 同一篇的小标题用同一种形式。入门和指南用动宾短语，例如“提需求”“拆分需求”“保存项目规范”；概念页可以用问题，例如“哪些代码归应用”。
- 不用条件短语（“需求大时”“上线以后”），也不用文绉绉的说法（“记下长期约定”）。

## 步骤

- 每步先给命令或提示词，再用一两句说明结果，例如“侧边栏出现 **Customers**。”
- 出错时的处理不要打断主线：写一句“没有……时，……”，或者放进 `<details>`。

## 示例和截图

- Core 的示例用读者熟悉的业务，例如客户管理。不用 Studio 的概念做示例：任务、项目、Agent 团队、评审、验收。
- 示例源码放在 `nocobase/docs-examples-v3`，链接到固定提交，见仓库的 `AGENTS.md`。
- 截图来自示例应用时，写“截图来自示例应用”。读者的结果可能不同时，说明哪里会不同。

## 人和 Agent 的分工

写读者要做什么之前，先查应用模板的 `AGENTS.md` 和 NocoBase 的开发 Skill。Skill 已经要求 Agent 做的事，不写成读者的步骤，也不写进示例需求，例如测试、权限检查、迁移规则、启用用户和权限管理、汇报验证结果、保存项目规范。读者只做需要人决定的事：用业务语言提需求，回答 Agent 的问题、确认设计，看报告并在应用里试用。

## 面向全球读者

文档会翻译成多种语言，面向全球用户。不突出某一种语言或地区：

- 不说明截图用的是什么界面语言，也不写“可以切换为中文”这类话。
- 讲界面语言时写“多语言”，不写“中英文”。
- 例子里的时区、货币、节假日不偏向某个地区：写“公司所在的时区”，不写“北京时间”。

## 结尾和导航

- 结尾用“下一步”，放一到三个链接，每个链接后面一句话。不写总结。
- 索引页按读者要做的事列链接，每项一句话。

## 提示框和强调

- 提示框只用在读者不注意就会出错的地方，不用来放背景介绍或版本声明。
- 加粗只用于界面上的按钮和菜单（**System settings → Users**），以及列表项开头的关键词。

## 用词

- 写 Agent、Skill，不写 Coding Agent、技能、Skills。Studio 的界面文字按界面原样写。
- 中文和英文、数字之间留一个空格，引号用“”。

## 改写示例

| 原文 | 问题 | 改为 |
| --- | --- | --- |
| 导语“Core 是什么、一个应用由哪几部分组成，以及开发时你和 Agent 各做什么。” | 只是本文目录 | 删除 |
| “NocoBase Core 是一组 npm 包：创建应用用的模板，应用的运行时，……以及教 Agent 使用这些包的 Skill。” | 自造定义；一句塞进五项，读者要自己拆 | 用标准定义，组成部分另列 |
| 页首的 beta 提示框 | 和读者当前要做的事无关 | 删除；需要时在对应命令旁说明 |
| “开始使用里，代码都由 Agent 来写。” | 从搜索直接进来的读者不知道“开始使用”指什么 | “用 Core 开发应用时，代码通常由 Agent 来写。” |
| 《应用的代码结构》直接从目录树开始 | 读者不知道为什么要看代码 | 先写一句上下文：“……想看懂它写了什么、判断改动是否合理，或者自己动手改，先要了解应用的代码怎样组织。” |
| “新页面或一套完整的交互，例如新建和编辑流程、详情抽屉，Agent 开发前会先给出设计，请你确认：” | 宾语和例子提到句首，读了半句还不知道谁做什么 | “Agent 做新页面或新的交互流程（比如新建和编辑、详情抽屉）之前，会先给出设计，请你确认。” |
| “这段需求说清了四件事：……” | 解释刚给出的内容 | 删除；怎样写需求放在指南里讲 |
| 《逐层实现客户管理》《读懂客户管理的代码》 | 前一个像动手教程，内容却是代码导读；后一个依赖示例名称，浏览目录的读者不知道“客户管理”是什么 | 《一个功能的完整代码》，第一段说明用途：审查 Agent 的改动，或照着写类似的功能 |
| 《创建应用》《搭建第一个应用》《和 Agent 一起开发》 | 应用已经创建，读者分不清“第一个应用”指什么；三篇看不出先后 | 《创建应用》《开发第一个功能》《持续开发应用》 |
| 小标题“需求大时”“记下长期约定” | 和同篇的“提需求”“确认设计”形式不一致 | “拆分需求”“保存项目规范” |
| 入门教程里十几步的手工验收 | 让人以为这些也是搭建步骤 | 写一两句“应该看到什么”，系统的检查方法放在指南里 |
| 让读者按数据、接口、页面拆需求，逐项检查迁移、权限和文案 | 这些是 Skill 要求 Agent 做的事 | 读者按业务拆需求；Agent 完成检查并汇报，读者看报告、试用 |
| 示例需求里写“按 AGENTS.md 和 Skill 实现”“完成后告诉我验证了什么” | Agent 每次启动都会读 AGENTS.md，汇报是固定要求 | 只写业务 |
| 以“团队任务”做 Core 的贯穿示例 | “任务”“项目”是 Studio 的概念，读者会混淆 | 客户管理 |
| “截图来自示例应用，界面是英文，可以在语言菜单里切换为中文。” | 突出中文，不适合翻译给全球读者 | “截图来自示例应用。” |

## 写完检查

- 只读每节的第一句，能知道这节讲什么、要做什么。
- 从搜索直接进来的读者，只读这一页也能看懂。
- 没有目录式导语，也没有介绍文章本身的句子。
- 句子主语在前，没有把宾语或例子提到句首。
- 同一件事没有在两篇里各讲一遍。
- 读者的步骤里没有 Agent 按 Skill 会自己做的事。
