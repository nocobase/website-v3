# 编写文档

先确定读者要完成什么或弄清什么，再决定内容和顺序。删掉一句之后，如果读者不损失有用的信息，就删掉它；必要的前提、步骤、业务边界和解释仍要保留。

## 范围与配合

- 适用于文档站各语言的正文。Core 开发者、Studio 使用者和部署维护人员需要的深度不同，不把所有文章都写成开发教程。
- 遵循用户本次要求与仓库 [AGENTS.md](../../../AGENTS.md)。双语、菜单、链接、资源、示例源码和检查命令以该文件及 [doc/README.md](../../../doc/README.md) 为准。
- 只处理当前任务涉及的文章和必要关联修改。局部改标题、链接或段落时，不因使用本 Skill 就重组整篇、改换示例或迁移代码。
- 编写或审阅读者提示词时，叠加 [write-doc-prompts](../write-doc-prompts/SKILL.md)，由它规定提示词与正文的分工。
- 编写、重组或审阅“开发应用”的功能专题时，叠加 [write-app-development-docs](../write-app-development-docs/SKILL.md)，按一篇专题对应一个可运行 App、每种 API 用法有对应示例的要求组织内容。概览和项目结构等说明性文章不强制配独立 App。
- 编写或重组单个插件使用指南时，叠加 [write-plugin-usage-docs](../write-plugin-usage-docs/SKILL.md)，沿用其四章结构和证据要求。下面的文章类型与导航建议不改变专项结构。

## 选择文章的主要目的

| 类型 | 读者要什么 | 内容组织 |
| --- | --- | --- |
| 首页／导航页 | 判断是否适合自己，找到入口 | 必要的定位与背景，按读者任务组织链接；可以结合产品介绍和阅读导航 |
| 入门 | 跟着做，得到能用的结果 | 必要前提、连续步骤、可观察的结果；只解释完成当前任务所需的概念 |
| 指南 | 完成一项具体任务 | 前提、做法、结果；需要选择时说明取舍 |
| 概念 | 弄清是什么、怎样工作 | 先给定义或结论，再解释组成、关系和边界，用例子帮助理解 |
| 示例导读 | 理解一个完整实现 | 按职责或数据流解释关键代码，说明做什么、为什么，并链接到完整文件 |
| 参考 | 查准确的事实 | 便于查找的参数、默认值、约束、错误和用法；按内容选择表格、列表或代码 |

一篇围绕一个主要目的，可以包含支持这个目的的其他内容。需要展开成另一项独立任务时，链接到对应页面。入门中的结果检查可以简短，但不能省掉判断功能是否可用所需的关键条件。

## 开头与产品表述

- 第一段提供读者当前需要的上下文：要做什么、需要已有的什么，或这个概念是什么意思。标题和第一节已经说明清楚时，可以直接开始。
- 页面应能从搜索结果独立进入。把“上一篇”“前面的应用”等指代换成具体名称或链接，并说明必要的先修条件。
- 不用“本篇介绍……”复述目录。`description` 和 `metaDescription` 都是元数据，不显示为正文导语；当前站点优先使用 `metaDescription`，没有时使用 `description`。
- 产品定位沿用用户已确认的表述。按涉及的产品查阅 [Core 文档首页](../../../doc/content/zh-CN/core/index.md)、[Core 产品页](../../../homepage/content/pages/core.body.html)、[Studio 产品页](../../../homepage/content/pages/studio.body.html)或 [Solutions 产品页](../../../homepage/content/pages/solutions.body.html)。可以为文章用途缩写，保留产品边界，不用依赖包清单替代产品定义。引用其他标准时给出可读取的路径或链接；发现表述冲突时核实依据，不自行拼接成新定义。

## 表达与标题

- 先给读者需要的答案或行动，及时说明适用条件。主语清楚、动作具体；例如用“销售只能看到自己负责的客户”解释数据访问范围。
- 长句拆成容易理解的句子。并列内容适合比较时用表格，适合逐项处理时用列表，不按固定项数决定排版。
- 删除宣传词、空泛过渡和重复总结。共享概念在一处解释，其他页面链接过去；保留独立阅读必需的简短上下文。
- 菜单标题应让不了解示例的人也知道文章用途。连续教程的标题体现不同阶段，例如“创建应用”“开发第一个功能”“持续开发应用”。具体案例的导读可以使用案例名称。
- 同篇标题尽量使用一致形式：操作步骤用动作，概念说明可以用问题。根据内容选择自然的表述，不机械禁止条件式标题或固定句式。
- 提示框用于影响读者正确操作的条件、限制和易错点；版本要求会影响步骤时应保留在相关位置。加粗突出界面名称、关键词或关键条件，避免整段强调。

## 步骤与结果

- 按读者实际执行顺序组织。命令或提示词前说明必要的工作目录、配置、账号和操作条件；已经交代的前提不在每步重复。
- 给出动作后，说明应该看到的界面、数据或文件变化，让读者能判断是否继续。不要把检查命令成功退出等同于业务功能正确。
- 常见失败给出简短处理或链接。较长的可选排错可以放进 `<details>`，影响主流程的前提不能隐藏其中。
- 手动操作指南和开发参考保留必要命令、关键代码、权限边界与验证方法。篇幅与任务相称，不为精简省去可执行步骤。

## 人与 Agent 的分工

介绍 Agent 的开发流程或能力时，先核对适用版本的应用模板 `AGENTS.md` 和相关开发 Skill，区分项目约定与工具实际支持的能力。

Agent 入门教程突出读者的业务需求、必要决策和结果验收；常规实现要求留在项目指引，提示词写法交给 `write-doc-prompts`。读者必须完成的登录、服务配置、业务授权或账号准备仍应说明。

Skill 规定应该做什么，不证明 Agent 已经执行或结果正确。保留读者需要理解的验证方法与业务边界，区分预期结果、源码确认、实际运行结果和未验证部分。仅整理文档时，不自动扩大为重建示例或调用外部服务。

## 示例、截图与语言

- 示例选用读者熟悉、适合当前功能的业务。客户、任务、项目等都可以使用；明确应用中的业务概念，避免与 Studio 的同名产品功能混淆，不因通用文风规则更换已有示例。
- 示例源码、固定提交、截图和验证范围按仓库规范维护。截图说明有助于理解的功能或状态；示例与读者结果会有差异时说明差异，不重复添加无用的截图来源声明。
- 不把实测数据库、模型服务或地区设置变成所有读者的前提。需要具体环境才能复现时，保留明确配置和适用范围。
- 面向各语言读者自然表达。通用例子可以说“公司所在的时区”；代码、兼容性或验证记录需要具体时区、货币、界面语言时，准确保留。
- 行文保持 Agent、Skill 等术语一致；英文按语法使用单复数。界面名称、命令、路径和 API 保持原样，例如 **Skills**、`.agents/skills/`。需要区分开发 Agent 与应用内业务 Agent 时，先解释各自用途。
- 中文与英文、数字之间适当留空格，中文使用中文标点；英文按英文习惯书写，不照搬中文句式。

## 结尾与导航

- 连续教程通常只给一个明确的后续入口；读者已有多个合理选择时，给少量按任务区分的链接，并说明各自用途。
- 需要后续行动时使用“下一步”。参考页可以直接结束；索引页的导航本身就是主要内容。插件指南在现有章节中安排相关链接，不为了统一结尾增加第五章。
- 避免在每篇末尾重复同一组开发、部署、参考链接，也不添加复述正文的总结。

## 改写时的判断

| 情况 | 处理 |
| --- | --- |
| 导语只是复述本篇标题和目录 | 删除；读者缺少前提时补必要上下文 |
| 入门页堆积内部开发与验收清单 | 保留读者要做的动作和可观察结果，将详细方法链接到对应指南 |
| 因为 Skill 要求检查权限，就删去权限边界和验证结果 | 保留业务限制与真实证据，区分要求和已完成的检查 |
| 参考页查完参数即可离开 | 直接结束，确有相关任务时再加链接 |

## 完成检查

- 文章的主要目的清楚；从搜索进入也能识别前提并完成当前任务。
- 精简后仍保留可用步骤、关键限制和结果判断，没有把 Agent 的约定写成已验证的事实。
- 标题和链接符合实际内容，相关页面各有职责；按适用范围核对提示词或插件指南专项规则。
- 各语言的操作、能力边界和验证范围一致，表达自然。
- 按仓库要求完成内容、链接、菜单和构建检查；交付时区分文档检查与应用运行验证。
