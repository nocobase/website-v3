# 编写插件使用文档

面向使用插件构建应用的开发者，说明插件能做什么、怎样用、接入代码如何工作，以及怎样验证 AI 完成的改动。

本 Skill 是 `website-v3` 的文档编写规范。它不属于示例应用的开发 Skills，也不作为应用运行时的业务 Skill 分发。

## 范围与依据

- 目标是 `doc/content/zh-CN/core/using-plugins/` 与 `doc/content/core/using-plugins/` 下的单个插件指南。新写或整体重组时使用下述四章；局部纠错保持本次任务范围，不顺带改写其他文章。
- 先遵循仓库 [AGENTS.md](../../../AGENTS.md) 与 [doc/README.md](../../../doc/README.md) 的双语、菜单、链接和资源约定。中文作为编写参考，示例代码、应用界面和截图使用英文。
- 编写或审阅提示词时，使用 [write-doc-prompts](../write-doc-prompts/SKILL.md)。提示词要像读者自然提出的需求；实现约束和详细验收要求分别放在本指南对应章节中。
- 核实目标插件的包名、版本、公开导出、注册方式、配置和依赖。按问题读取已安装包或对应版本源码、类型、随包开发 Skill 及示例；说明与实现冲突时核实差异，不凭包名推断功能。
- 区分源码确认、片段示意、可运行示例和实际运行验证。既有核验记录见 [plugin-usage-verification.md](../../../doc/notes/plugin-usage-verification.md)，记录中的版本和结论只适用于其原有范围。

## 固定的四章

正文用以下四个二级标题，中英文顺序一致。三级标题按插件实际能力组织，不要求每篇具有相同的小节或场景数量。仅在有助于理解时，在第一章前写简短导语；不要把 frontmatter 摘要复制到正文。

四章用于帮助读者查找内容，不是凑篇幅的要求。按仓库的文档写作规范，直接讲插件能做什么、怎么用，以及必要的实现说明；不在每章重复目标、前提和总结。通用知识链接到已有说明，保留与本插件有关的具体内容。

| 中文标题 | 英文标题 |
| --- | --- |
| 提供的能力 | Capabilities |
| 使用场景与示例 | Scenarios and examples |
| 重要原理与实现 | Key principles and implementation |
| AI 开发的约束与验证 | AI development constraints and verification |

### 1. 提供的能力

说明插件解决的问题、提供的能力和应用需要完成的接入。适合比较时，用“能力 / 插件提供什么 / 应用如何使用”的表格。

明确区分插件直接注册的页面、导出但需要应用组合的页面、Registry 分发的 UI 源码、服务端能力，以及仅分发开发指引的插件。不要把“安装依赖”“注册插件”“出现界面”“业务可用”写成同一件事。

有不同接入方式时在这里解释适用范围与区别，操作步骤放进第二章对应场景。能力介绍以读者能完成的事情为主，完整 API 清单链接到相关参考。

### 2. 使用场景与示例

选择能体现该插件用途的具体任务。每个场景应让读者找到：

- **目标与前提**：谁在什么页面做什么，需要已有的业务、配置或外部服务。
- **开发提示词**：用读者会说的话描述想做的功能、预期效果和必要业务规则。接口、目录、项目规范和测试方案由 Agent 结合项目指引查找；不要把场景的前提、实现约束和验收清单全部塞进提示词。
- **配置与操作**：必要的界面或 CLI 步骤，关联对应代码；通用安装、注册、升级流程引用“管理插件”。
- **结果与验收**：预期的界面或数据变化，以及可观察的完成条件。使用 `**完成的标志**：` / `**Done when**:` 标记。

提示词使用 `prompt` 代码块。只有插件本身提供用户对话时，才另外给出应用内对话提示词，并与交给开发 Agent 的提示词区分。

场景默认沿用应用已有配置。数据库、模型服务等只有影响功能或步骤时才限定；需要具体配置时，可选一种受支持的方案并标明“以此为例”。SQLite 等实测配置写在验证范围中，不作为通用使用前提，也不据此声称其他配置已验证。保留真正的兼容性和版本要求。

有界面且截图能帮助理解时，使用实际应用截图，说明展示的功能和状态。服务端或指引类插件可以用接口响应、代码差异、文件产物等展示结果。不要为了统一版式给不存在的页面补截图，也不要把示意图当作运行证据。

### 3. 重要原理与实现

围绕第二章的同一示例解释实现。让读者能把界面和行为对应到代码：修改了哪些文件、每处做什么、为什么需要，以及它产生了什么可见效果。

按实际情况使用“文件或目录 / 改动内容 / 对应效果”表格，随后解释关键代码与必要的数据流、配置、权限和生命周期。没有界面的插件说明接口、任务、数据或文件产物的变化。

代码片段注明所在文件、前提和省略内容，使用经核实的公开接口。完整示例与局部片段分别说明；不要把建议的接入改动写成已经实施的代码差异。若仅核实了源码，就按接入说明编写。

共享框架原理链接到“框架”或“开发应用”，本章保留理解该插件所必需的机制。不要把完整源码或 API 参考搬进文章。

### 4. AI 开发的约束与验证

这里讨论 **AI 帮助开发者使用该插件时，怎样约束和验证改动**，不要求插件本身具有 AI 功能。

围绕插件特有的问题编写：

- 应读取哪些随包开发 Skills 或公开契约，版本更新后怎样确认兼容。
- 接入中必须保留的权限、数据范围、状态隔离、生命周期或外部服务边界。
- 容易混淆或误用的能力，以及能发现这些错误的检查。
- 与实际改动相称的类型、接口、数据、组件或运行验证；成功结果、失败路径和未验证项分别说明。

例如，文件插件关注上传授权和文件访问，通知插件关注接收人范围和重复发送，Agents 插件关注会话隔离、工具授权和真实执行结果。根据目标插件选择相关内容，不把这些例子全部套入每篇文章。

提示词和 Skill 提供行为指引，代码中的校验、授权及测试才提供可执行的约束。不要声称插件或 Skill 自动保证代码正确、自动完成测试、提供未实现的沙箱或自动回滚。

通用协作方法引用“使用 Agent 开发”，测试方法引用“测试与验收”。保持本章聚焦插件的约束；需要验收提示词时，用自然语言说明本次要确认的行为，把检查方法、测试命令和证据要求留在正文中。

## 示例代码与证据

配套代码仓库为 `nocobase/docs-examples-v3`。每个独立运行的应用放在 `apps/<example-name>/`；贯穿多章的同一应用共用一个目录，其 README 关联章节、代码文件、版本、运行方式和验证步骤。

- 只链接实际存在且与文章匹配的目录、文件和版本。可复现的源码链接优先指向已存在的 commit 或 tag；仓库已创建不代表某个示例已经迁入。
- 既有源码下载、截图和章节链接在迁移完成前保持可用。根据本次任务范围维护示例，单纯整理文档不自动扩大为迁移或发布代码。
- 源码、配置模板和说明可以进入示例仓库；环境密钥、会话、运行数据库、依赖目录和构建产物不进入公开示例。截图也不得暴露凭据。
- 实测结论注明有关版本和执行范围。模型说“已完成”、截图中出现成功提示、测试命令退出成功，都需要与实际验证对象对应；不要用它们代替持久化、权限、工具执行或测试用例的证据。
- 仅修改文章时可以验证文档结构与链接，不必重新创建应用或调用外部服务；报告中区分本次文档检查与原有运行记录。

可参考 [Agents 中文指南](../../../doc/content/zh-CN/core/using-plugins/agents-and-knowledge/agents.md) 与 [Agents 核验记录](../../../doc/notes/agents-plugin-verification.md) 如何关联场景、截图、代码和检查；参考其组织方式，不照搬环境配置或验证结论。

## 完成检查

完成编辑后确认四章内容各司其职，中英文的能力与验证边界一致，菜单、链接、截图和示例源码能对应。移动标题时检查锚点引用；新建或移动文章时同步两种语言的菜单。

删掉不帮助读者操作或理解的铺垫、重复解释和空泛结论；检查精简后是否仍保留必要前提、可用步骤和关键代码说明。不要把简洁写成难懂的术语短句。

逐段检查提示词是否像真实用户会提出的需求，而不是内部开发指令。读者应能理解并替换成自己的需求，且无需输入整套实现方案才能开始使用。

从仓库根目录运行：

```bash
pnpm doc:test
pnpm doc:build
git diff --check
```

交付时简要报告修改了哪些文档、示例与资源是否变化、文档检查结果，以及本次是否做过应用运行验证。网页外壳或样式的检查按仓库指引执行。
