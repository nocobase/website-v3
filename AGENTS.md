# AGENTS.md

## Documentation writing

- Write for the person using the document. Lead with what they can do or need to know, then give the necessary steps and explanation. Match the depth to the article's purpose: a quickstart should get readers to a working result; a reference should make precise details easy to find.
- Use natural language, concrete actions and examples. Explain unfamiliar terms when needed; do not stack jargon or assume readers know internal implementation names.
- Keep examples adaptable to the reader's existing setup. Require a specific database (such as SQLite), model provider, operating system or deployment method only when the user specifies it or the task depends on it. Distinguish example choices and tested environments from prerequisites; preserve real compatibility requirements and do not imply untested alternatives were verified.
- Cut repeated introductions, obvious commentary, generic warnings, empty transitions and summaries that repeat the preceding text. Do not explain the article's organization when the headings already make it clear, or narrate the author's writing and verification process in place of useful instructions.
- Keep docs front matter `description` and `metaDescription` for metadata and summaries. Do not render them in the visible article or copy them into its introduction. Add a body introduction only when it helps the reader.
- Keep prerequisites, usable commands, important business rules, relevant limitations and essential code explanations. Concision means removing material that does not help readers act or understand, not omitting steps or turning prose into cryptic fragments.
- Explain shared concepts once and link to them elsewhere. Do not fill every section with exhaustive lists or move a bloated prompt unchanged into the surrounding prose. Before finishing, remove any paragraph whose deletion would not cost the reader useful information. Apply the same standard to every language.

When writing, restructuring or reviewing reader-facing pages in `doc/content/`, use [write-docs](.agents/skills/write-docs/SKILL.md) for article purpose, organization, language and navigation. It complements the prompt and plugin-guide skills below; use their specialized rules only when the task involves those contents. Keep local edits within their scope, updating related links and menus when necessary; loading a skill does not authorize rewriting unrelated content or migrating examples.

When writing or reviewing reader-facing prompts in any repository documentation, use [write-doc-prompts](.agents/skills/write-doc-prompts/SKILL.md). This applies to quickstarts, tutorials, plugin guides, configuration instructions and verification examples in every language. Prompts must read like something a person would naturally ask: describe the reader's goal and necessary business rules. Put implementation contracts, project instructions and detailed verification procedures in the surrounding documentation instead of packing them into the prompt.

## Docs site (`doc/`)

`doc/` is the source of the NocoBase 3 docs site, an Astro site in the pnpm workspace (see `doc/README.md` for the layout, `docs.config.ts` and the full `meta.json` guide). CI builds it with `pnpm doc:build` on every pull request and push that touches it, and publishes it to `docs.nocobase.com` once merged into `main` (see "CI and publishing" below). When you change the docs, change the content, the menus and the links together so they never disagree:

- For writing, restructuring or reviewing individual plugin usage guides, use [write-plugin-usage-docs](.agents/skills/write-plugin-usage-docs/SKILL.md). It defines the four-chapter format, source/example mapping and plugin-specific AI development verification; it does not apply that format to the section overview or general plugin-management guide. Keep narrow corrections within their requested scope.
- Content is in `doc/content/`: English at the root (`content/index.md`, `content/start/`, `content/core/`, `content/studio/`, served at the site root) and Simplified Chinese in `content/zh-CN/` (served under `/zh-CN/`). Pages are `.md` (not `.mdx`; some contain handwritten HTML). The front matter must be valid YAML (quote values that contain a colon). Both languages must have exactly the same files and the same menu structure; an English page that has not been translated yet contains only front matter (`title`) and `status: placeholder`.
- Menus are `meta.json` files, one per section directory in each language, and the build fails when they and the files disagree. Register every new page in the `meta.json` of both languages with a `page` entry (`{ "type": "page", "path": "dir/name" }`, path relative to that `meta.json`, no `.md`; add a `title` when the sidebar text should differ from the page title). Add a `meta.json` plus a `folder` entry only when a directory should be a collapsible level; otherwise reference the pages by path (a directory without `meta.json` is only storage). `group` entries are headings, `planned` entries are not-yet-written items. Moving or renaming a page means updating both `meta.json` files and every link to it. The two languages' `meta.json` must be identical in structure (same `type`, `path`, nesting); only titles differ.
- Write links between pages as relative `.md` paths (such as `[My tasks](../use/my-tasks.md#views)`); the build turns them into final URLs and checks every in-site link and anchor, so after moving a page update every link to it.
- Figure snippets live in `doc/figures/` (English versions in `doc/figures/en/`) and are referenced from the content with `::figure name | caption`. When you rename or delete a figure, update the content that references it. `> [!NOTE]` callouts and `**Done when**:` are handled by the plugins in `doc/plugins/`.
- Site-wide settings (languages and their interface strings, sections, links, analytics IDs) are in `doc/docs.config.ts`; the Astro app is in `doc/src/`. New sections or languages are described in `doc/README.md`. The header, footer, tokens and fonts come from `packages/shared/`; change them there (and check the website too), not in `doc/`.
- Do not casually change the output conventions: each page is written to `<path>/index.html`, URLs have no extension and end with `/`, links and assets inside the site use root-relative paths, and the root contains `404.html` (English only; no `zh-CN/404.html`), `sitemap-index.xml`, `robots.txt`, `llms.txt` (plus `zh-CN/llms.txt`) and `pagefind/`. The CDN's back-to-origin rules depend on this layout; changing it takes the whole live site down with 404s.
- Top-level directories must not share a name with the old v2 docs URLs (listed in `packages/shared/v2-redirect-prefixes.txt`, such as `guide`, `api`, `cn`), and `en` and `api` are never allowed at the output root. `docs.nocobase.com` redirects those paths with a 301 to `nocode.docs.nocobase.com`, and the build fails on a clash. Do not edit the list to make the build pass: it has to change together with the EdgeScript rule on the CDN, so ask the user first.
- After any change, run `pnpm doc:test` and `pnpm doc:build` from the repository root and make sure both succeed; if you changed the page shell, styles or search, also look at it with `pnpm doc:preview` (port 4321). `doc/dist/` and `doc/.astro/` are build output; do not commit them.
- When you change the docs structure, update `doc/README.md` as well.

## Documentation example projects

- Store documentation example projects in [nocobase/docs-examples-v3](https://github.com/nocobase/docs-examples-v3). Follow that repository's own `AGENTS.md` for implementation, directory layout and validation. Keep documentation content, menus and site assets in this repository.
- `nocobase/app-tutorials` is deprecated. Do not add new examples or new documentation references to it. Existing references may remain during gradual migration; replace them when the corresponding example is available and verified in `docs-examples-v3`. Do not bulk-replace the repository name or assume old paths and commit SHAs exist in the new repository.
- Link example source to its directory or file at a fixed commit in `docs-examples-v3`. When migrating or updating an example, update the affected Chinese and English documentation together, including source links, code excerpts, setup and run commands, version requirements, screenshots when behavior changes, and verification notes. Distinguish checks actually run from checks the reader still needs to perform.
- Each example should include a README with its purpose, corresponding documentation, prerequisites, setup, run and test commands. Verify those instructions before presenting the example as runnable; record any validation that could not be completed.

## Workspace and website (`homepage/`, `packages/shared/`)

The repository is a pnpm workspace (root `package.json` and `pnpm-workspace.yaml`, one `pnpm-lock.yaml`, Node 24, pnpm 11 from `packageManager`): `homepage` (the website), `doc` (the docs site) and `packages/*`. Dependencies are pinned to exact versions. Run `pnpm install` at the root.

The website is an Astro site in `homepage/`; see `homepage/README.md` for details (and `homepage/content/i18n/README.md` for translation).

- Change only source files and never commit build output. Sources: `homepage/content/` (page bodies `pages/*.body.html`, the home page `pages/home.html`, translations `i18n/*.yaml`, blog data `blog/`, NocoReach figure sources `reach/`), `homepage/src/` (the Astro app: `pages/` routes, `layouts/`, `lib/` translation lookup, link rewriting and checks, `styles/`, `scripts/` client JavaScript), `homepage/public/` (files copied as they are) and `homepage/scripts/` (maintenance scripts). `homepage/dist/` is build output and `node_modules/` holds dependencies; neither is committed, and the repository contains no generated HTML.
- `packages/shared/` (`@nocobase/site-shared`) is what the website and the docs site share: `Header.astro`, `Footer.astro`, `Analytics.astro`, `tokens.css`, `shell.css`, the fonts, the 12-language table, `v2-redirect-prefixes.txt`, the GitHub star-count config and an Astro integration that writes `robots.txt`, and for the docs `llms.txt` and per-page `.md` copies. Keep site-specific parts out of it; a change there triggers both `site.yml` and `docs.yml`, and the website's output must not change unless you meant it to (build `homepage` before and after and compare).
- Build and preview, from the repository root: `pnpm homepage:build` (generates `homepage/dist/`, one `<path>/index.html` per page per language, plus `sitemap-index.xml`, `robots.txt`, `404.html`), `pnpm homepage:dev` (Astro dev server) and `pnpm homepage:preview` (serves `dist/` the way the CDN's back-to-origin rules map URLs). The same commands work inside `homepage/` as `pnpm build`, `pnpm preview`, `pnpm test`, `pnpm figs`, `pnpm i18n:extract`, `pnpm i18n:check`. After changing sources, always run `pnpm homepage:test` and `pnpm homepage:build` and make sure they succeed; if you changed the page shell, styles or copy, take a look with `pnpm homepage:preview`.
- Languages: English is at the root, and the other 11 languages are in the `zh-CN zh-TW ja-JP ko-KR es-ES fr-FR de-DE pt-BR ru-RU id-ID vi-VN` directories; NocoReach, the blog, customer stories and release notes exist in English and `zh-CN`; blog posts and customer stories with a Japanese body in the CMS, plus the two lists, also exist in `ja-JP` (see `homepage/README.md`). Do not generate an `/en/` directory (or an `/api/` one): the output directory layout is what the CDN's back-to-origin rules depend on, and changing it takes the whole live site down with 404s. The build checks this.
- When you change Chinese or English copy on a page, run `pnpm homepage:i18n:extract`, add the translations in `homepage/content/i18n/<group>.<language>.yaml`, and check with `pnpm homepage:i18n:check`. Write links inside the site as source file names such as `core.html` or `blog/<slug>.html`; the build turns them into each language's URL, and a link to a page that does not exist fails the build.
- The header, footer and language menu are the shared components, filled by `homepage/src/lib/nav.mjs` for the home page and every other page alike. The home page has no navigation or footer of its own; its own styles are only in `homepage/src/styles/home.css`.
- Interface illustrations are generated by the scripts in `homepage/scripts/figs/` (`pnpm homepage:figs`). To change an illustration, change its script; do not edit `homepage/content/pages/snips/` or the parts of `home.html` and `homepage/src/styles/site.css` that the scripts write. CI regenerates them and compares.
- The GitHub star count in the header is read at build time only: the static default is in `packages/shared/src/config.mjs`, and the environment variable `GITHUB_STARS` (a raw number) overrides it. The browser never requests GitHub.
- When you change the build's conventions (languages, URLs, page list) or commands, update `homepage/README.md`, `homepage/content/i18n/README.md` and this section.

## CI and publishing

This is a public repository. Building and publishing are done by this repository's own GitHub Actions, no longer relayed through an external repository:

- `.github/workflows/docs.yml`: the docs site. It runs on pull requests and pushes to `main` that touch `doc/`, `packages/shared/`, the root `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, this workflow or `scripts/deploy-cdn/`, and can also be run manually. `Docs build` uses pnpm and Node 24 to run, from the repository root, `pnpm install --frozen-lockfile`, `pnpm doc:test` and `pnpm doc:build` (with the star count read by an unauthenticated `curl` into `GITHUB_STARS`, like `site.yml`), checks that `index.html`, `zh-CN/index.html`, `404.html`, `sitemap-index.xml`, `robots.txt`, `llms.txt`, `zh-CN/llms.txt` and `pagefind/` were generated, and uploads `doc/dist/` as an artifact; only runs on `main` go on to `Docs publish`.
- `.github/workflows/site.yml`: the website. Same triggers, with the paths `homepage/`, `packages/shared/`, the root `package.json`, `pnpm-lock.yaml` and `pnpm-workspace.yaml`, this workflow and `scripts/deploy-cdn/`. `Site build` uses pnpm (the version comes from `packageManager` in the root `package.json`) and Node 24 to run, from the repository root, `pnpm install --frozen-lockfile`, `pnpm homepage:test`, `pnpm homepage:figs` (the regenerated interface illustrations must match what is committed) and `pnpm homepage:build`. Before the build it reads the repository's star count from `https://api.github.com/repos/nocobase/nocobase` with a plain unauthenticated `curl` (no token, since a build job must not reference any secret) into `GITHUB_STARS`, and falls back to the static default when that fails. It checks that `index.html`, `zh-CN/index.html`, `404.html`, `sitemap-index.xml` and `robots.txt` were generated, and uploads `homepage/dist/` as an artifact. Only runs on `main` go on to `Site publish`; `www.nocobase.com` is already published by it, so a push to `main` changes the live website directly.
- Publishing: every deployment uploads to a new timestamped directory in OSS (Shanghai time), then `scripts/deploy-cdn/deploy-cdn.mjs` points the CDN's back-to-origin rewrite rules at it, refreshes the cache once the rules take effect, and finally cleans up old versions. `404.html` is also uploaded to the bucket root (the website's 404 page is generated from `homepage/content/pages/404.body.html` and is served at any depth, so its assets and links always use root-relative paths). Only one publish runs at a time, and a running publish is never cancelled; if `main` has moved on and a later commit also touches the directories this workflow is responsible for, the older commit skips publishing and the newer one publishes.
- Version retention and rollback: the docs keep the latest 2 timestamped directories (the script's default `--keep 1`), and the website keeps the latest 3 (`site.yml` passes `--keep 2`). When the website's `SITE_CDN_DOMAINS` is empty, it uses `--cleanup-only`: no CDN switch and no cache refresh, but old versions are still cleaned up. Before cleaning up, the script confirms that the newly uploaded directory is in the bucket; if not, it fails and deletes nothing. To roll back, in the Alibaba Cloud CDN console change the timestamp in each of the domain's back-to-origin rewrite rules (`back_to_origin_url_rewrite`) back to a retained older directory, then refresh the cache. The workflows only publish the latest commit on `main` and cannot be used to republish an older commit.
- Configuration: the publish jobs run in the Environment `production`, and every value they use is a secret of that Environment: `ALI_ACCESS_KEY_ID`, `ALI_ACCESS_KEY_SECRET`, `ALI_OSS_REGION` (such as `cn-beijing`), `DOCS_OSS_BUCKET`, `DOCS_CDN_DOMAINS` (required; publishing fails without it), `SITE_OSS_BUCKET` and `SITE_CDN_DOMAINS` (optional). Separate domains with whitespace or commas.
- Security: trigger only on `pull_request`; never switch to `pull_request_target`. The top-level permissions are only `contents: read`. Build jobs run the pull request's code and must not reference any secret; secrets appear only in the `env` of the publish step in the publish jobs, which only download the artifact and run no code from the repository other than `scripts/deploy-cdn/`.
- When you change the publishing flow, change the publish parts of `docs.yml` and `site.yml` together. If you change the environment variables or dependencies that `deploy-cdn.mjs` reads, update the `Publish` steps of both workflows and `scripts/deploy-cdn/package.json` and `package-lock.json`. If you add or remove a secret or change the triggers, update this section and the description in `doc/README.md`. Before changing the docs site's output directory conventions, read the notes above `REWRITE_RULES` in `deploy-cdn.mjs`. If you change version cleanup or argument parsing (`scripts/deploy-cdn/versions.mjs`), run `node --test scripts/deploy-cdn/versions.test.mjs`; both build jobs run it too.

## Commits and pull requests

Write commit messages and pull request titles in the [Conventional Commits](https://www.conventionalcommits.org/) format: `type(scope): subject`. Pull requests are squash-merged, so the pull request title becomes the commit message on `main` and must follow the same format.

- Types: `feat` (new feature or content), `fix` (bug fix), `docs` (documentation such as READMEs and `AGENTS.md`), `style` (formatting only), `refactor`, `perf`, `test`, `build` (build setup and dependencies), `ci` (workflows), `chore` (maintenance), `revert`.
- Scopes: `homepage` (website), `doc` (docs site and its content), `shared` (`packages/shared/`), `ci` (workflows), `deploy` (`scripts/deploy-cdn/`). Omit the scope when a change spans several of them.
- Subject: English, imperative mood ("add", not "added"), lowercase first letter, no trailing period, at most 72 characters including the prefix.
- Breaking changes: add `!` after the type or scope (`feat(doc)!: …`) and explain them in a `BREAKING CHANGE:` footer. Use the body, after a blank line, to explain why when the subject is not enough.
- Do not add AI attribution (such as `Co-Authored-By` lines or "Generated with" notes) to commits or pull requests.

Examples:

```
feat(doc): migrate the docs site to Astro
fix(homepage): scroll back to the top when the logo is clicked on the home page
ci(doc): install from the workspace root and run vitest
docs: adopt Conventional Commits for commits and pull request titles
```
