Pages coordinate API data, user input and navigation. Identify the source of each kind of state before choosing where it belongs, so searching, paging, editing and returning remain consistent.

This guide follows default template `1.0.0-beta.84`. `useListData` and `useListLocation` are editable application source generated by the template, not exports from `@nocobase/app-client`. The example assumes your server implements the task APIs below; adapt paths and response types to your own contract.

## With an agent

```text
Complete request and state handling for the task list. Inspect existing endpoints and client/hooks/ first.

Keep search and pagination in the URL so reloads and browser history restore them. Reset pagination when search changes.
Reuse useListData and useListLocation; an old response must not overwrite a newer query.
Distinguish loading, empty results, failure and retry. Stop showing old data when access is denied.
Preserve drafts after a failed save and refresh the current query after success without losing search conditions.
Check closing routed dialogs, deleting the last page's final item, out-of-order responses and duplicate submissions.
Use existing shadcn components, translations and themes, and report the verification scope.
```

## Assign ownership to state

| State | Suggested location | When it changes |
| --- | --- | --- |
| Search, sorting, pagination and shareable tabs | URL query parameters | View changes and browser history |
| Records, totals and server-returned operation permissions | Request Hook or query cache | Query changes, successful mutations or refresh |
| Unsubmitted fields and validation errors | Form or page-local state | Input, validation, save and cancel |
| Expansion, hover and temporary selection | Component state | Current interaction |
| Values shared within a component tree | Common ancestor or React Context | Component coordination |
| Business operations and observable state shared across pages | Client business service | Business methods or service events |

Prefer deriving values over storing another copy. For example, derive the current page's selection count from selected IDs and records. A custom Hook reuses logic; separate calls do not automatically share state. See [UI components and interactions](pages-and-interactions.md#use-react-context-and-providers) for Context and Providers, and [Client business services](client-business-services.md) for services.

## Obtain the application's API Client

Use `useApiClient()` in a component or Hook. Pass the client into ordinary functions or inject it into services. Reuse its configuration rather than creating a client or assembling deployment URLs in each page.

The examples assume this contract:

| API | Input | Successful response |
| --- | --- | --- |
| `GET /tasks` | `q`, `page`, `pageSize` | `{ data: Task[], meta: { total: number } }` |
| `PATCH /tasks/:id` | JSON `{ title: string }` | `{ data: Task }` |

These business endpoints are not generated by creating client files. The server owns validation, authentication, authorization and data scopes; see [Routes and HTTP APIs](apis-and-services.md).

Save response types and the update operation in `client/pages/tasks/api.ts`:

```ts
import type { ApiClient } from '@nocobase/app-client';

export interface Task {
  id: string;
  title: string;
}

export interface TaskListResponse {
  data: Task[];
  meta: { total: number };
}

export async function renameTask(
  api: ApiClient,
  id: string,
  title: string,
  signal?: AbortSignal,
): Promise<Task> {
  const response = await api.request<{ data: Task }>({
    method: 'PATCH',
    path: `/tasks/${encodeURIComponent(id)}`,
    json: { title },
    signal,
  });
  return response.data;
}
```

`path` is relative to the API Client's address and usually omits `/api` and the application mount path. `request<T>()` returns the complete response body. The generic describes the expected type without validating runtime data. Here, `response.data` is a field in the business response, not another HTTP-client wrapper.

For Repository data endpoints, use `api.repository(name)` and its protocol rather than assuming the response above. See [API Client](../framework/http/api-client.md) and [Repository data APIs](../framework/http/repository-routes.md).

## Read list conditions from the URL

Combine the existing template Hooks in `client/pages/tasks/use-task-list.ts`:

```ts
import { useListData } from '#hooks/use-list-data';
import { useListLocation } from '#hooks/use-list-location';
import type { TaskListResponse } from './api.js';

export function useTaskList() {
  const { params, setParams, active } = useListLocation();
  const q = params.get('q') ?? '';
  const inputPage = Number(params.get('page') ?? '1');
  const page = Number.isSafeInteger(inputPage) && inputPage > 0 ? inputPage : 1;
  const pageSize = 20;
  const query = new URLSearchParams({ q, page: String(page), pageSize: String(pageSize) });
  const request = useListData<TaskListResponse>(`/tasks?${query}`, { active });

  function setSearch(value: string) {
    setParams((current) => {
      const next = new URLSearchParams(current);
      if (value) next.set('q', value);
      else next.delete('q');
      next.set('page', '1');
      return next;
    }, { replace: true });
  }

  function setPage(value: number) {
    if (!Number.isSafeInteger(value) || value < 1) return;
    setParams((current) => {
      const next = new URLSearchParams(current);
      next.set('page', String(value));
      return next;
    });
  }

  return { ...request, q, page, pageSize, active, setSearch, setPage };
}
```

Connect `q` and `setSearch` to the search control, and `page` and `setPage` to pagination. For debouncing, keep in-progress input locally and update the URL when committing the search; handle IME composition. Search uses `replace` to avoid a history entry per keystroke, while pagination preserves back/forward navigation.

`useListLocation()` relies on the template's routing context. When a child route covers the list, it retains the list's query and pauses reading through `active`; returning resumes reading. `useListData` can report `loading: true` while inactive, which does not mean a request is running. Pages outside this route tree need their own routing integration rather than copying its active-state assumptions.

For sorting, variable page sizes and page correction after deletion, see the template's `client/hooks/use-table-url-state.ts`. Accept only supported sort fields and preserve unrelated parameters. Correct parameters with `replace` to avoid history loops.

## Handle loading, races and errors

`useListData` cancels reads when the path changes or the component unmounts, and uses request generations to reject stale results. `reload()` invalidates the old result synchronously before starting another read. Pages still own presentation:

| State | Page behavior |
| --- | --- |
| First load without data | Show loading feedback |
| Successful response with empty `data.data` | Show an empty state, distinct from failure |
| Refresh with data from the same query | Indicate that it is updating; wait before actions requiring fresh data |
| Network failure or temporarily unavailable server | Offer retry, preserve drafts and call `reload()` to retry the read |
| 401, 403 or 404 | Explain the identity, permission or record condition without displaying old restricted data |
| Cancellation after a query change or unmount | Do not show an error or let the cancelled result overwrite the new page |

By default, a new path does not retain the previous path's data. `keepPreviousData: true` can keep it visible while a query changes, but identify it as old data. Do not use it for the new query's total or bulk operations. This option is not a complete shared query cache.

Branch on HTTP errors using `ApiClientError.status`, `reason` and `domain`. Network failures may be ordinary exceptions. Map known errors to translated messages and field feedback. Use `requestId` for diagnosis; do not display the developer-oriented `error.message` directly. See [API Client](../framework/http/api-client.md).

When writing request Effects yourself, handle cancellation and result ownership, clean up subscriptions and declare actual dependencies. React development mode can repeat Effect setup and cleanup; see [React useEffect](https://react.dev/reference/react/useEffect).

## Refresh after saving and preserve drafts

A form obtains its client with `useApiClient()` and calls `renameTask(api, id, title)`. Validate before submission, show pending feedback and use a synchronous submission lock against rapid duplicate clicks. Release the lock when the operation ends.

After success, use the returned record to update the detail view or call the list's `reload()` for its current query. Creation, deletion and changes to sort fields affect totals and position, so normally reread the list. `replaceData()` only replaces the current Hook's result; it does not update other views or recompute pagination, permissions or aggregates.

After failure, preserve the draft and map field errors according to the API contract. Do not reinitialize an editor whenever its list refreshes. Reset explicitly when editing another record ID. Stop editing if the record disappears or access is revoked.

A list and its editor child route can pass refresh behavior through parent state, Outlet context or callbacks. Restore search conditions when closing or returning. When deleting the last item on the last page, correct pagination using the latest total for the matching query rather than an old total.

Cancelling a browser request does not roll back a server mutation, and a timeout does not prove saving failed. Automatic write retries require explicit idempotency semantics; concurrent edits need server version checks or conflict handling. See [Client business services](client-business-services.md) for operations shared across pages.

## When to use a shared query cache

Start with template Hooks for a single-page list. When views need shared queries, deduplication, background refresh or optimistic updates, use the project's existing query-cache approach and mount its Provider consistently.

Cache keys must cover the resource, parameters and identity or context affecting visible results. Clear old requests and caches on sign-out or identity changes. Avoid separate, unsynchronized copies of the same records in components, services and caches.

## Verify results

Test your pages and Hooks for these behaviors:

- Make the first of two searches finish last; the second query's result must remain visible.
- Reload, navigate back/forward, enter a child route and return; URL conditions and results remain consistent.
- Distinguish read failures, cancellation, 401, 403, 404 and successful empty responses.
- Preserve drafts after failure, send one mutation for duplicate clicks, and refresh the current query after success.
- Correct pagination after deleting its last item while retaining search and sorting.
- Prevent old requests and shared state from affecting the interface after unmounting or identity changes.

The template includes `tests/client/list-recovery.test.tsx` and `tests/client/table-url-state.test.tsx` as references. Run relevant tests using your project's actual paths, plus `pnpm typecheck` and `pnpm build`; see [Testing and acceptance](testing-and-acceptance.md).

Your server must implement the example API contract. Tests that replace the network boundary verify client requests and state behavior; real authorization and persistence still need API and integration tests.
