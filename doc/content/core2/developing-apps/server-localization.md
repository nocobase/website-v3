title: Server localization
description: Organize server language resources and generate text in the right language for HTTP requests and background jobs.

Text shown on pages usually lives in `client/locales/`, while mail, notifications and exports generated by the server live in `server/locales/`. Each side loads its own resources: a key that exists on the client is not automatically available on the server.

This guide follows the structure of `server/locales/` and how it is connected to the runtime in default template `1.0.0-beta.84`; it does not depend on the historical project tutorial.

## Add application text

Add the report text to the existing object in `server/locales/en-US.ts`, keeping other keys and the existing type export. The file below shows only this example's text:

```ts
import type { LocaleResource } from '@nocobase/i18n';

const enUS = {
  reports: {
    ready: 'Report {{name}} is ready.',
    subject: 'Your report: {{name}}',
  },
};
export type AppServerResource = LocaleResource<typeof enUS>;
export default enUS;
```

Add the matching keys to `server/locales/zh-CN.ts`:

```ts
import type { AppServerResource } from './en-US.js';

const zhCN = {
  reports: {
    ready: '报表 {{name}} 已准备好。',
    subject: '你的报表：{{name}}',
  },
} satisfies AppServerResource;
export default zhCN;
```

`LocaleResource` constrains the structure of the keys, not the strings themselves, which naturally differ by language; interpolation variable names must also stay the same. Never build translation keys from user names or report names; pass them in as parameters.

## Check the resource entry

The template's `server/locales/index.ts` already declares loaders for both languages:

```ts
import type { LocaleLoaders } from '@nocobase/i18n';

const locales: LocaleLoaders = {
  'en-US': () => import('./en-US.js'),
  'zh-CN': () => import('./zh-CN.js'),
};
export default locales;
```

`server/runtime.ts` already connects this entry to the application as `locales`, so no new Provider is usually needed. To add a language, add its resource file and loader; installing a plugin that contains a language does not add that language to the application. The default language is set in configuration; see [Application configuration (config.yml)](configuration-and-settings.md). The client and server language lists are maintained separately, so check both sides when offering a language to users.

## Use the current language in requests

The template's `server/app.ts` mounts `i18nHttpMiddleware` after the session middleware. It determines the language in the order session language, then `Accept-Language`, then the default language, and loads the resources. Routes simply use `getRequestTranslator(c)`; there is no need to create a new translation instance for each endpoint.

Below is a public endpoint that only previews text; it neither reads nor generates a real report. Save it as `server/routes/report-message-preview.ts`, then add it to `server/routes/index.ts` as described in [Routes and HTTP APIs](apis-and-services.md):

```ts
import { Hono } from 'hono';
import { z } from 'zod';
import {
  apiErrorHandler, apiValidator, dataResponse,
  defineApiRoutes, describeRoute, apiErrorResponses,
} from '@nocobase/app-server/router';
import { getRequestTranslator } from '@nocobase/i18n/server';

export default defineApiRoutes(() => {
  const router = new Hono();
  router.onError(apiErrorHandler);
  router.get(
    '/report-message-preview',
    describeRoute({
      operationId: 'previewReportMessage',
      summary: 'Preview report wording',
      security: [],
      responses: {
        200: dataResponse(z.object({ message: z.string() })),
        ...apiErrorResponses,
      },
    }),
    apiValidator('query', z.strictObject({
      name: z.string().trim().min(1).max(80),
    })),
    (c) => c.json({
      data: {
        message: getRequestTranslator(c)(
          'reports.ready', { name: c.req.valid('query').name },
        ),
      },
    }),
  );
  return router;
});
```

Request `<APP_BASE_PATH>/api/report-message-preview` with `name=Q3` and `Accept-Language: zh-CN`; without a saved session language overriding it, the response contains the Chinese "report is ready" message. Tests for this route must also install the real i18n middleware; calling it on a bare Hono instance without the middleware leaves it with no request translator.

`security: []` is only a documentation declaration, and this example has no authentication middleware. If you adapt it to read real reports, you must add authentication and data authorization.

## Generate background text in the recipient's language

Background jobs have no HTTP request, so they cannot rely on a request translator, and they must not change the shared instance's global language either. The right approach is to load resources for the recipient's language, then create a translation function fixed to that language. For example, create `server/services/report-message.ts` as needed:

```ts
import metadata from '../../package.json' with { type: 'json' };
import type { I18nRuntime } from '@nocobase/i18n';

export async function renderReportMessage(
  i18n: I18nRuntime,
  recipientLocale: string,
  name: string,
) {
  const locale = i18n.resolveLocale(recipientLocale);
  await i18n.ensureLocaleLoaded(locale);
  const t = i18n.getFixedT(metadata.name, locale);
  return {
    locale,
    subject: t('reports.subject', { name }),
    message: t('reports.ready', { name }),
  };
}
```

A Provider obtains `I18nRuntime` from `i18nToken` in `@nocobase/app-server/i18n` and injects it into the service or passes it to this function. The namespace is the `name` from the application's `package.json`, not a deployment path or any user input. `services/` is a directory you organize yourself, and its files are used through ordinary imports.

`recipientLocale` comes from the recipient's language preference, and unsupported languages fall back through `resolveLocale()`. Always call `ensureLocaleLoaded()` before `getFixedT()`; otherwise resources that are not loaded yet may fall back to default text or even show the raw key. Because each translator has a fixed language, content for recipients in different languages can be generated concurrently without one switching the other's language.

## Override plugin text and handle errors

An application can override a plugin's server text under `overrides` in its server language object, keyed by the plugin's package name. Do not edit `node_modules/`, and do not put overrides for client pages into server resources by mistake.

API errors keep stable `reason` and `domain` values; the developer-oriented `message` is not interface text. Clients translate errors by these identifiers; where necessary, the server can also provide a separate `localizedMessage`, but error types must never be decided from translated strings. See [Request validation and error handling](request-validation-and-errors.md).

## Verify

Run `pnpm nocobase locales check` and the type check. Then, with real resources, check interpolation in both languages, the precedence of request headers and session language, fallback for unsupported languages, and concurrent generation for recipients in different languages. Language checks cannot replace runtime verification, and do not hide missing keys by mocking the translation function.

For client language selection and text organization, see [Localization](localization.md); for declaring a plugin's server resources, see [plugin Server localization](../extension-development/server-localization.md).
