title: Plugin structure
description: Learn where a plugin sits in an App, how its directories and entries connect, and how source relates to build output.
---

This guide assumes an App created with create-app and explains where a local plugin's files go, what each is responsible for, and how the plugin connects to the application. Plugins live under the App's `packages/` directory, and their structure varies with the chosen capabilities; not every plugin needs Client, Server and CLI.

## Where a plugin sits in the App

Take an "announcements plugin" as the example: it provides an announcements page and an API that reads announcements. Below are the main files after development is finished and the plugin is registered with the App, leaving out common configuration and some test files. `client/pages/`, `shared/` and the page components were added on top of the scaffold; the full implementation is in [Write your first plugin](write-your-first-plugin.md).

```text
my-app/
├── client/plugins.ts                          # App registers the Client entry
├── server/plugins.ts                          # App registers the Server entry
├── packages/
│   └── app-plugin-announcements/
│       ├── client/
│       │   ├── components/                    # Page container and header components
│       │   ├── pages/announcements.tsx        # Page: requests and displays announcements
│       │   ├── locales/                       # Menu and page translations
│       │   ├── routes.ts                      # Page route and navigation
│       │   ├── plugin.ts                      # Composes Client contributions
│       │   └── index.ts                       # Public Client entry
│       ├── server/
│       │   ├── routes/index.ts                # Announcement API
│       │   ├── routes/schemas.ts              # API response schema
│       │   ├── plugin.ts                      # Composes Server contributions
│       │   └── index.ts                       # Public Server entry
│       ├── shared/announcement.ts             # Shared data type
│       ├── tests/                             # API, page and route tests
│       ├── package.json                       # Dependencies, exports and scripts
│       └── AGENTS.md                          # Plugin development guidance
├── package.json                               # References the plugin through workspace:*
└── pnpm-workspace.yaml                        # Includes the plugin directory
```

When the page opens, `client/pages/announcements.tsx` sends a request, `server/routes/index.ts` returns the announcements, and the page shows the list. In this example, the page and the API belong to the same plugin; since it only reads fixed sample data, it needs neither database migrations of its own nor a CLI entry.

The plugin's `package.json` makes two entries public, Client and Server, and the App's two `plugins.ts` files register them. The package dependency lets the App find the plugin, while registration makes the App load its capabilities. For using the generator, see [Create a plugin](create-plugin.md); the complete directory below is for reference when you look up other capabilities.

## The complete directory structure

Taking the App's local plugin `demo-full` as the example, the tree below collects the complete directory structure for every kind of capability. `client/`, `server/`, `database/`, `cli/` and `skills/` are all generated according to the chosen capabilities, and a real plugin keeps only what it needs. The tree also marks `client/pages/`, added as needed during development, and `dist/`, generated by the build; for language resources, only the file names of other languages are omitted.

```text
packages/app-plugin-demo-full/

│   ├── components/                             # Plugin components
│   │   ├── plugin-component.tsx
```

The timestamps in migration and seed file names vary with the generation date. `client/pages/` organizes the actual pages, which still need to be connected in `client/routes.ts`; creating the directory alone does not register routes.

The files in the tree fall into three kinds: scaffold generated by the generator, source added as needed during development, and build output. `client/pages/` is of the second kind and `dist/` of the third. Which capability directories are actually generated depends on what you choose at creation; for the options, see [Create a plugin](create-plugin.md).

## How the entries connect

For the specific declaration style, exporting public services and calling across plugins, see [Plugin declarations and public exports](plugin-declarations.md).

The plugin's implementation, its public entries and the App's registration files each have their own responsibility:

| Location | Responsibility |
| --- | --- |
| The plugin's component, route, service or command files | Implement the actual features |
| The plugin's `client/plugin.ts`, `server/plugin.ts` | Combine the contributions for that runtime, such as routes, Providers and database resources |
| The plugin's `client/index.ts`, `server/index.ts` | Export the plugin definition; in the scaffold they usually just re-export `plugin.ts` from the same directory |
| The plugin's `cli/index.ts` | Declares and exports the command-line plugin directly; there is no separate `cli/plugin.ts` |
| The plugin's `package.json` | Declares these entries as the package's public exports |
| The App's `client/plugins.ts`, `server/plugins.ts`, `cli/plugins.ts` | Register the corresponding entries the plugin provides |

The announcements page and the announcements API each have their own path into the App:

```text
Client: pages/announcements.tsx → client/routes.ts → client/plugin.ts
        → client/index.ts → package.json ./client → App client/plugins.ts

Server: server/routes/index.ts → server/plugin.ts
        → server/index.ts → package.json ./server → App server/plugins.ts
```

The plugin's `client/plugin.ts` and the App's `client/plugins.ts` belong to different packages: the former defines what the plugin provides, and the latter decides which plugins the application loads. When adding a page or API, you usually change only the implementation and route declarations inside the plugin; as long as the App has registered the corresponding runtime entry, there is no need to register the plugin again for each page or API.

### Three runtime entries

| The plugin's public export | The App's registration file | How it is connected |
| --- | --- | --- |
| `<package>/client` | `client/plugins.ts` | Call the client factory, optionally passing configuration the plugin supports |
| `<package>/server` | `server/plugins.ts` | Add the server plugin definition |
| `<package>/cli` | `cli/plugins.ts` | Add the command-line plugin definition |

Connect only the entries the plugin actually provides. For example, when only `client.components` was chosen, what is generated is only public component exports, without `client/index.ts` or `client/plugin.ts`, and the application simply uses the components through `import`. Choosing `database`, on the other hand, generates a server entry used to declare the database resources.

The generator creates the entries, and `pnpm nocobase plugin register` connects the runtime entries to the App. For the full steps, see [Write your first plugin](write-your-first-plugin.md).

## Key files

### package.json: metadata, dependencies and public exports

The plugin has its own `package.json`, maintained separately from the one in the App root:

| Field | Role in the plugin |
| --- | --- |
| `name`, `version` | Identify the plugin package and its version |
| `private` | Defaults to `true` for local plugins, which can be used inside the App without being published to npm |
| `exports` | Declares the paths consumers can import; the scaffold uses source entries for convenient local development |
| `publishConfig.exports` | The export mapping for build output, also used when the App build collects local packages |
| `files` | What the package carries, such as `dist/`; with Skills chosen, also `skills/` |
| `scripts` | The plugin's own check, test and build commands |

The App's `package.json` references the local plugin through `workspace:*` in `dependencies`. The package dependency lets the App find the plugin, and runtime registration decides which capabilities the App loads.

Declare each dependency in the package that actually uses it, and keep the categories the scaffold generates: ordinary server runtime dependencies go in `dependencies`; runtimes that must share an instance with the host, as well as client runtime dependencies, go in `peerDependencies`; test and build tools go in `devDependencies`. Do not omit the plugin's own dependency declarations just because the App already installs a package.

Taking the announcements plugin as the example, here are only the Client and Server export fields:

```json
{
  "exports": {
    "./client": {
      "types": "./client/index.ts",
      "import": "./client/index.ts"
    },
    "./server": {
      "types": "./server/index.ts",
      "import": "./server/index.ts"
    }
  },
  "publishConfig": {
    "exports": {
      "./client": {
        "types": "./dist/client/index.d.ts",
        "import": "./dist/client/index.js"
      },
      "./server": {
        "types": "./dist/server/index.d.ts",
        "import": "./dist/server/index.js"
      }
    }
  }
}
```

The App uses `@nocobase/app-plugin-announcements/client` and `@nocobase/app-plugin-announcements/server` respectively and never references the plugin's internal source directly. When adding public components, services or types, keep the source exports and the build output mappings consistent as well.

### database: the plugin's data resources

`database/migrations/` holds migrations and `database/seeds/` holds seed data. The `.ts.example` files the generator creates are only drafts and are never executed; after completing one, remove the `.example` suffix and keep the file name consistent with the exported task name.

`server/plugin.ts` declares these directories through its `database` configuration, with resource paths relative to the plugin's absolute path `baseDir`:

| Code loaded | Where `baseDir` points | Location of database resources |
| --- | --- | --- |
| Source `server/plugin.ts` | The plugin root | `database/migrations/`, `database/seeds/` |
| Compiled `dist/server/plugin.js` | The plugin's `dist/` | `dist/database/migrations/`, `dist/database/seeds/` |

Keep the generated path calculation and database build script. Plugins with database capabilities generate `.manifest.json` files when compiled, and these manifests must stay together with the compiled migration and seed files. The build only produces resources; it does not run migrations automatically.

### UI components and source ownership

`client/components/` holds components the plugin maintains, and you can add `client/pages/` as needed to organize business pages. Pages are connected through `client/routes.ts`, while public components are offered to the App through package exports.

Plugins with client code include `components.json` and `client/styles.css`, which configure shadcn's file locations, in-package aliases and style entry. Both applications and plugins can install components or blocks from the NocoBase UI Library: source installed into the App is maintained by the App, and source installed into the plugin is maintained by the plugin. When consumers use a component through the plugin's public exports, its implementation is still maintained by the plugin.

Aliases such as `#components/*` inside the plugin are defined by the plugin's own `package.json` and do not depend on the App's private aliases. After adding or installing components, keep file locations, import paths and build configuration consistent.

Applications and plugins can both write and organize frontend components freely, with shadcn for primitives; when building modular interfaces, first consult the components and blocks in the [NocoBase UI Library](https://ui.nocobase.com/). The NocoBase UI Library distributes source assets based on shadcn UI Registry, and publishing your own assets uses the same mechanism. For writing components and connecting them to pages, see [Components and styles](frontend-components.md); for organizing, building and locally adding a separate Registry package, see [Optionally distribute UI source assets](frontend-components.md#optionally-distribute-ui-source-assets).

Source assets are maintained in a separate Registry package that sits beside the plugin in `packages/`; they connect to the plugin's capabilities through public package entries or parameters supplied by the consumer, and must not import the plugin's internal files by relative path. Once an asset is installed, the target App or plugin maintains its own copy of the source.

### AGENTS.md and skills/: two kinds of Agent guidance

| File | Who it is for | Purpose |
| --- | --- | --- |
| `AGENTS.md` at the plugin root | Developers and Agents maintaining the plugin's source | Explains the plugin's internal development conventions |
| `CLAUDE.md` at the plugin root | Claude Code working in the plugin | References the same `AGENTS.md` |
| The plugin's `skills/*/SKILL.md` | Application Agents using the plugin | Explains what the plugin provides and how to connect and verify it |
| The App's `.agents/skills/` | Agents used when developing the application | Holds the synchronized copies of the guidance |

The development guidance at the plugin root is a basic file, while `skills/` is generated according to the chosen capabilities. Complete the Skill source in the plugin first, then synchronize; do not maintain the automatically generated copies in the App directly.

For writing the plugin's own maintenance conventions, see [Plugin development guidance (AGENTS.md)](plugin-development-guidance.md); for giving application Agents capability descriptions and usage examples, see [Plugin Skills](write-plugin-skills.md).

### Tests and development configuration

`tests/` organizes tests by capability. `tsconfig.json`, `eslint.config.js` and the `vitest.config.ts` generated as needed handle types and compilation, linting, and running tests respectively. When adding a capability, also add its implementation, declarations, public exports, dependencies and tests; for the check commands, see [Write your first plugin](write-your-first-plugin.md).

## Source, plugin builds and App builds

The plugin's `dist/` and the App's `dist/` are build output at two different levels:

| Location | Contents |
| --- | --- |
| `packages/app-plugin-announcements/client/`, `packages/app-plugin-announcements/server/` | The plugin's client and server source |
| `packages/app-plugin-announcements/dist/` | The plugin's compiled JavaScript and type declarations |
| `dist/` at the App root | The application's build output, including application code and the dependencies it needs to run |

To build only the plugin, run this in the App root:

```bash
pnpm --filter @nocobase/app-plugin-announcements build
```

During development, the App uses the local plugin through the workspace dependency and source exports. When preparing delivery, run in the App root:

```bash
pnpm build
```

The App build builds local packages in dependency order and collects the workspace packages to deliver into `dist/vendor/` in the application output, using exports that point to compiled results and local dependency paths. **Local plugins can be delivered together with the App without being published to npm first.**

All of this output is generated by the build, so change the source and rebuild rather than editing `dist/` directly. After the plugin's own build passes, also verify its actual use in the App and the App's overall build.
