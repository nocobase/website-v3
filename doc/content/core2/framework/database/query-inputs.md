`@nocobase/repository-input` provides a query input contract that works on both the client and the server. Builders turn expressions in code into serializable data, while executing against the database and authorization still happen on the server.

## Building input

```ts
import { buildFilter, buildSelect, buildSort } from '@nocobase/repository-input';

export const orderQuery = {
  filter: buildFilter((f) => f.string('status').eq('paid')),
  select: buildSelect((s) => s.fields('id', 'orderNo', 'amount')),
  sort: buildSort((s) => s.field('id').asc()),
};
const json = JSON.stringify(orderQuery);
```

`buildFilter`, `buildSelect`, `buildSort` and `buildAggregate` accept the corresponding AST or a synchronous callback and return a standalone JSON snapshot. Filter also supports simple equality objects. Building input does not connect to the database, and does not check whether the caller may read those fields.

## Three input forms

| Form | Suitable for |
| --- | --- |
| Equality shorthand | Simple scalar conditions |
| Builder callbacks | Readable composition in development code |
| JSON AST | Conditions that are saved, transmitted or generated dynamically |

Functions cannot be sent directly as JSON; materialize them with the build helpers first. Asynchronous callbacks, objects with circular references, invalid numbers and functions in unsupported positions are rejected; dates become ISO strings and bigints become decimal strings. A native bigint in a numeric Filter is still not a valid JSON value.

## Variables and write input

`context` provides values for variables in a query; it is neither a transaction connection nor a permission object. The server decides which variables come from trusted identity and which from validated user input.

`buildCreateValues` and `buildUpdateValues` materialize write builders; for complete remote Repository requests, use the `build*Options` helpers exported by the API Client. Do not use the `internal/*` entries, which exist for sharing implementation inside the framework.

## Server-side validation

For saved queries, the server still has to check the Collection, field types, relation depth, pagination range and authorization policy. Input generated by the official Builder does not justify arbitrary data access. Exact numeric values must match what the field supports; for example, big integers and DECIMAL use strings to preserve precision.

Tests can compare the execution results of a Builder and an AST, but comparing only the JSON structure cannot verify database semantics. Related topics: [API Client](../http/api-client.md) and [Filtering, sorting and pagination](filtering-pagination.md).
