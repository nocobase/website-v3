After [Create an app](create-app.md), you have an independent application project. Most business development happens in four directories: `client/`, `server/`, `database/` and `tests/`.

## Directory overview

The tree below lists the commonly used directories and files, including those generated by installation, running or building. Exact contents vary slightly by template and version; the test directories follow the latest layout.

```text
my-app/
├── .agents/             # Agent rules and Skills
├── cli/                 # Application commands
├── client/              # Pages and UI
├── database/            # Migrations and seeds
├── dist/                # Build output (generated)
├── node_modules/        # Installed dependencies (generated)
├── packages/            # Local plugins, shared packages and UI assets (optional)
├── public/              # Static assets
├── server/              # APIs and services
├── storage/             # Runtime data (generated)
├── tests/               # Application tests
├── AGENTS.md            # Agent guidance entry
├── config.example.yml   # Configuration example
├── config.yml           # Local configuration
├── package.json         # Scripts and dependencies
└── pnpm-workspace.yaml  # Workspace package directories
```

## Where business code belongs

### client: pages and interactions

| Location | What you write |
| --- | --- |
| `client/pages/` | Pages, registered in `client/routes.ts` with their navigation and access conditions |
| `client/components/`, `client/hooks/` | Reusable components and shared hooks |
| `client/locales/` | Interface text in English and Chinese |
| `client/layouts/`, `client/theme/` | Layouts and themes |

### server: APIs and services

| Location | What you write |
| --- | --- |
| `server/routes/` | Application APIs, registered through `index.ts` in that directory |
| `server/providers/` | Service registration and lifecycle |
| `server/services/` | Business implementations extracted as needed (optional) |
| `server/config/` | Application configuration definitions |

### database: schema and initial data

`database/` is organized by database connection; the default connection is `main`:

- `main/migrations/`: create or change tables and fields.
- `main/seeds/`: prepare the initial data the application requires.

To change a schema, add a new migration rather than rewriting one that has already run. The generated `main/collections/` directory is a schema snapshot; do not edit it.

### cli: application commands

`cli/plugins.ts` registers command-line plugins. Create `cli/commands/` when you need commands of your own.

Client and server plugins are registered in `client/plugins.ts` and `server/plugins.ts` respectively.

### packages: local plugins and source assets

Use `packages/` for local plugins, shared packages or independent UI Registry packages. All three are optional, so create only what you need, and configure the workspace package directories in `pnpm-workspace.yaml`:

```tree
packages/
├── app-plugin-<name>/   # Runtime plugin
├── <name>-ui/           # UI Registry source assets (optional)
└── <shared-package>/    # Shared package (optional)
```

The two kinds of package are delivered differently: a plugin's Client, Server and CLI entries must be connected to the application, while a UI Registry package builds source assets that consumers add as needed. See [Plugin structure](../extension-development/plugin-structure.md) and [Optionally distribute UI source assets](../extension-development/frontend-components.md#optionally-distribute-ui-source-assets).

## package.json: preinstalled plugins

The template brings in plugin dependencies through `package.json` to provide shared capabilities such as users, permissions, files and notifications. The table lists the plugin packages installed in this guide's reference application; templates and versions may differ, so check your own project's dependency list.

The table omits the common `@nocobase/app-plugin-` prefix; for example, `users` stands for `@nocobase/app-plugin-users`.

| Package | Purpose |
| --- | --- |
| `agents` | Agents, model providers, conversations and runs |
| `api-keys` | API key authentication |
| `authentication` | Sign-in and authentication |
| `authorization` | Access control and the permission management interface |
| `authz-default-access` | Default data access scopes |
| `authz-restriction-rules` | Data access restriction rules |
| `authz-sharing-rules` | Data sharing rules |
| `database-explorer` | Read-only browsing of database connections, tables and fields |
| `file` | File storages, upload and access |
| `foundation` | The Core capabilities the application uses and runtime information |
| `i18n` | Interface language switching |
| `knowledge` | Document knowledge spaces, search and versions |
| `mail` | Sending mail and synchronizing mailboxes |
| `notification` | Notification storage, delivery and logs |
| `notification-in-app` | In-app messages and inbox |
| `notification-providers` | Built-in notification channels and delivery services |
| `scheduler` | Scheduled jobs |
| `template-print` | Development Skill for template printing |
| `users` | User management APIs and pages |

**Installed does not mean enabled.** `package.json` only declares dependencies; `client/plugins.ts`, `server/plugins.ts` and `cli/plugins.ts` register a plugin's client, server and command-line parts respectively. A plugin does not necessarily provide all three entries.

In this guide's reference application, `agents`, `knowledge` and `template-print` are not in any of the three registration lists. `template-print` is a `devDependencies` entry that gives Agents development guidance; it is not a printing page that appears automatically after installation.

## tests: where tests belong

The current getting-started example is based on default template `1.0.0-beta.81`. Tests are organized by the code they verify, mirroring the business directories:

```text
tests/
├── client/              # Pages, components and client logic
├── server/              # APIs, services and permissions
├── database/            # Migrations and seeds
├── cli/                 # Commands (optional)
├── project/             # Project configuration and builds
├── fixtures/            # Test data and fixture applications
├── helpers/             # Shared test helpers
├── setup/               # Test environment setup
└── playwright/          # Browser tests (optional)
```

Create `cli/` and `playwright/` as needed; the Examples template already includes both. Test cases go in the matching business directory, and supporting data and functions go in `fixtures/` and `helpers/`.

Run `pnpm test` in the application root for the Vitest tests; browser tests run separately with `pnpm test:e2e`. Prefer real services and isolated databases, and use mocks only where necessary. Older projects may still use `tests/components/` and `tests/logic/`; follow your project's template version and test configuration. See [Testing and acceptance](../developing-apps/testing-and-acceptance.md) for details.

## Configuration and Agent guidance

`config.example.yml` is the configuration example. `config.yml`, generated when you initialize configuration, holds environment settings such as the local database connection and secrets; do not commit it to Git. `package.json` holds the project's scripts and dependencies.

`AGENTS.md` is the Agent's entry point. The application's own development conventions live in `.agents/rules/`; `.agents/skills/` is synchronized from dependencies to provide development guidance, so do not edit it directly.

`node_modules/`, `storage/` and `dist/`, which appear after installing and running, hold dependencies, runtime data and build output respectively.

## Starting from a feature

To add order management, for example, you would change these places in turn:

1. **Schema**: add a migration that creates the orders table in `database/main/migrations/`.
2. **API**: add the order APIs and permission checks in `server/routes/`.
3. **Page**: write the page in `client/pages/` and register it in `client/routes.ts`.
4. **Tests**: verify each behavior in `tests/database/`, `tests/server/` and `tests/client/`.
