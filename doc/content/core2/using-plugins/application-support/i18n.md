## Capabilities

`@nocobase/app-plugin-i18n` provides the application's runtime language switching API and Hooks. Translation resources, namespaces and the translation mechanism are handled by the framework; this plugin lets users choose a language and synchronizes the server-side language preference.

The plugin provides the switching and synchronization behavior; translation resources and the look of the selector remain the application's responsibility.

## Scenarios and examples

### Example: an English and Chinese interface

1. The application provides both client and server resources for `zh-CN` and `en-US`.
2. Connect a language selector in the header, or reuse the one the default template already has.
3. Choose the other language, and check the pages, plugin content and error messages returned by the server.
4. Refresh the page and confirm the browser keeps the choice; synchronization at startup can use `useSyncServerLocale()`.

The APIs are `GET /api/i18n/locales` and `PUT /api/i18n/locale`. If the server does not support the chosen language, it saves `en-US` and returns `fallback: true`, while the browser interface keeps its own language; a network failure does not undo the choice in the browser either.

**Development prompt** (for a coding Agent in the current application directory):

```prompt
Use Localization to add English/Chinese switching. Check client and server

multiple tabs. Do not add automatic business-content translation.
```

**Done when**: after switching, application and plugin text update and the choice survives a refresh; server fallback and network failures are handled clearly.

## Key principles and implementation

The table lists where this example connects and how the interface is expected to change. These are development notes; specific file names follow your application's current structure.

| Integration point | Code or configuration change | Interface and behavior change |
| --- | --- | --- |
| `client/locales`, `server/locales` | Add resources and their loaders | The selectable languages come from resources the application actually has |
| The language selector in the header | Use `useAppLocale`, handling `switching` and failures | Page and plugin text update with the choice |
| Startup synchronization in the layout, and error display | Use `useSyncServerLocale`, and show errors by stable reasons | The server preference is synchronized, and fallback behavior can be explained |

### Integration and where languages come from

Register the Client and Server plugins. The selectable languages come from the loaders the application itself declares in `client/locales/index.ts` and `server/locales/index.ts`, not from a separate language list maintained by the plugin.

To add a language, add the matching resources and loaders to the application. Even if another plugin provides a language, it is not added to the application's language selector automatically. The default language is configured as:

```yaml
i18n:
  defaultLocale: zh-CN
```

`APP_DEFAULT_LOCALE` can override this default. A default language the application has no resources for does not appear as a new option.

### Connect the language selector

The plugin provides the behavior, and the look of the selector is up to the application. Inside `AppClientRoot`, use:

```tsx
import { useAppLocale } from '@nocobase/app-plugin-i18n/client';

const { locale, locales, setLocale, switching } = useAppLocale();
```

This is a call inside a component. Render the options from `locales`, call `setLocale(next)` after a choice, block repeated actions while `switching`, and handle the Promise failing.

Switching loads the resources of each namespace, updates the interface and the HTML language and direction, saves the browser preference and notifies the server. Plugins share one translation runtime, so there is no need to write separate logic that follows the switch.

## AI development constraints and verification

### Development constraints for this plugin

- The language options are decided by the application's loaders; do not hard-code another list that disagrees with the resources.
- Wait for the result of `setLocale` and handle failures; never mistake a server fallback for the browser's switch being undone.
- Test missing text, persistence after refresh, several tabs sharing one session, and server error text; passing type checks cannot replace checking language coverage.

### Verification and limits

Several tabs share the server language of one session, so after one tab switches language, the messages returned by APIs in another tab may change too. Custom interfaces can show text in the matching language based on the stable `error.reason`.

This plugin provides neither automatic translation of business content nor a translation management back office. For writing resources, see [Localization](../../developing-apps/localization.md) and [Server localization](../../developing-apps/server-localization.md).
