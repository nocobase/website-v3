---
title: デプロイ環境を管理する
description: ホスト型子アプリの実行方式、アクセス URL、デプロイのルールを設定し、デプロイ環境を確認・管理します。
---

デプロイ環境では、ホスト型子アプリの実行方式、アクセス URL、デプロイに承認が必要かどうかを決めます。アプリテンプレートやインスタンスの作成時には、利用可能なデプロイ環境を選択します。複数の子アプリで同じ環境を使えます。

## デプロイ環境を追加する

まず[クイックスタート](quickstart.md#メインアプリを設定して起動する)に従って、メインアプリの子アプリホスティング機能を有効にしてください。その後、環境の管理権限を持つアカウントで、メインアプリの**デプロイ環境**（Deploy environments）を開きます。

![実行方式、アプリ数、公開 URL のパターンを表示するデプロイ環境一覧](/assets/core/multi-app/environment-list.png)

1. **環境を追加**（Add environment）をクリックし、名前と一意の識別子を入力します。名前は変更できますが、識別子は作成後に変更できません。
2. 実際の用途に合う環境の用途を選び、現在のメインアプリで利用できる実行方式を選択します。
3. **公開 URL のパターン**（Public URL pattern）を入力します。子アプリの識別子には `{appId}` を使います。たとえば `https://apps.example.com/{appId}/` を指定すると、識別子が `customer-demo` のインスタンスは `/customer-demo/` パスを使います。
4. **接続テスト**（Test connection）をクリックし、成功を確認してから保存します。

![環境設定で名前、実行方式、公開 URL のパターンを設定する](/assets/core/multi-app/environment-settings.png)

URL はユーザーのブラウザーからアクセスできる必要があります。同一ドメインでデプロイする場合、リバースプロキシはメインアプリと子アプリの両方のパスをメインアプリの入口に転送し、WebSocket にも対応する必要があります。内部制御用ポートを公開アクセス URL に指定しないでください。

<details>
<summary>ローカルや内部ネットワークで HTTP を使う場合</summary>

シングルサインオンはデフォルトで HTTPS を使います。管理された環境で HTTP が必要な場合は、メインアプリの `config.yml` で子アプリのオリジンを明示的に許可してください。

```yaml
sso:
  insecureRedirectOrigins:
    - http://127.0.0.1:13510
```

実際のスキーム、ホスト、ポートに置き換えてください。アプリのパスは含めず、ワイルドカードも使いません。`pnpm nocobase config check` を実行してメインアプリを再起動してから、子アプリをデプロイまたは接続します。独立した子アプリの場合も、この例外はメインアプリで設定します。子アプリ側に別のスイッチを設定する必要はありません。

</details>

## 環境が利用可能か確認する

環境名をクリックし、詳細ページで**確認**（Check）をクリックします。結果に応じて、接続や実行に必要な依存関係の問題を修正してください。環境の作成に成功していても、接続確認が成功したとは限りません。

**概要**（Overview）では、環境のアクセス URL のパターンとアプリの稼働状態を確認できます。アプリのデプロイに失敗した場合は、まず環境の確認が成功することを確かめ、その後インスタンスの[デプロイ履歴](management.md#設定を変更し稼働状態を管理する)で原因を調べてください。

## 実行環境とデプロイの設定を変更する

環境の詳細で**設定**（Settings）を開き、変更して保存します。

| 設定 | 利用する場面 |
| --- | --- |
| 保護（Protected） | デプロイのたびに、指定された承認者の承認を必要とする場合 |
| アプリ数の上限 | この環境に配置できるアプリ数を制限する場合 |
| アクセスがないときの停止・休止 | 個別の実行ポリシーを持たないアプリに、デフォルトのアイドル時ポリシーを設定する場合 |
| 初回デプロイ時のサンプルデータ読み込み | デモデータが必要な環境でのみ有効にします。本番の業務環境では有効にしないでください |

![デプロイ承認、アプリ数、アイドル時ポリシーの設定](/assets/core/multi-app/environment-policy.png)

公開 URL のパターンを変更したら、影響を受けるアプリの実際の入口とログインコールバックを確認してください。パターンの変更だけで、既存アプリのドメイン移行が自動的に完了することはありません。環境を削除する前に、その環境内のアプリを処理する必要があります。子アプリの停止や無効化の代わりに、環境を削除しないでください。

メインアプリの保守やコンテナーの再作成時には、メインアプリの設定、データベース、`storage/` を保持してください。これらにはデプロイパッケージとデプロイ履歴だけでなく、ホスト型インスタンスのデータや非公開設定も含まれます。外部データベースやファイルストレージを使う子アプリでは、そちらのデータも別途バックアップする必要があります。メインアプリ自体のデプロイとバックアップについては、[通常のアプリのデプロイガイド](../../deployment/choose-a-deployment-method.md)を参照してください。
