## デプロイ前に準備するもの

<a id="デプロイの準備をする"></a>

テスト済みのアプリのソース、ロックファイル、公開するコミットを用意します。Agent はアプリの `AGENTS.md` と同期済みの `nocobase-deployment` Skill を参照します。アプリで依存関係をインストールすると Skills が同期されます。ない場合は `pnpm nocobase skills sync` を実行します。

サーバーへのアクセス権、OS と CPU、書き込み可能なディレクトリ、空きポート、利用者向け URL を伝えます。ドメイン、HTTPS、リバースプロキシ、データベースとファイルストレージのアカウントも準備します。パスワードは安全な入力や環境変数で渡し、プロンプトやリポジトリに含めません。

コマンド例は beta.85 テンプレートの[商品カタログ](https://github.com/nocobase/docs-examples-v3/blob/51658852e7290b0ed3c0735d2856681850560efb/apps/product-catalog/README.md)を使い、Linux x64/glibc、Node.js 24、単一インスタンスの SQLite を選択しています。自分のアプリでは実際のプラットフォームと導入済みドライバーに合わせてビルドします。

## Agent にデプロイ方法の選択を依頼する

<a id="方法を選ぶ"></a>

アプリのソースディレクトリで、環境と普段の運用方法を伝えます。

```prompt
このアプリを私のサーバーにデプロイしてください。環境は <OS と CPU>、利用者のアクセス先は <URL>、現在の運用方法は <コンテナまたはプロセス管理方法> です。Docker と PM2 の保守に必要な作業を比較し、おすすめの方法と不足している準備を教えてください。
```

| 方法 | 管理するもの | 手順 |
| --- | --- | --- |
| Docker | イメージ、Compose、設定とデータのマウント | [Docker でデプロイする](deploy-with-docker.md) |
| PM2 | Node.js、サービスアカウント、プロセス。インストールと更新は app-installer が管理 | [PM2 でデプロイする](deploy-with-pm2.md) |

## 対象とデータの保持要件を決める

<a id="初回のデプロイと以降のリリース"></a>

初回インストール、更新、移行のどれかを明確にし、サーバー、アプリのディレクトリ、対象バージョンを特定します。空のデータベースで始める操作と既存データの移行は別です。

ビルドにはコード、依存関係、マイグレーション、必須の初期化処理が含まれます。開発データベース、アップロード、利用者が設定したロール、実行時の秘密情報は含まれません。データベースとファイルの保存先、移行するデータ、バックアップ時点、許容するデータ損失を決めます。更新では既存データと安定した鍵を保持し、再初期化しません。

## デプロイ後に確認すること

<a id="確認と復旧"></a>

実際の URL からログインし、ページ更新、静的ファイル、代表的な業務の読み書きを確認します。一般ユーザーの権限も確認します。ファイル操作や WebSocket を使う機能があれば実際に操作します。

プロセスの再起動またはコンテナの再作成後、同じレコード、ファイル、権限を確認します。バージョンと成果物のダイジェスト、データの場所、検証結果、未完了事項を Agent に報告してもらいます。ヘルスチェック通過後もこれらの確認が必要です。

公開後は[更新と復旧](publish-app-release.md)、[日常の保守とトラブルシューティング](maintenance-and-troubleshooting.md)を参照してください。フレームワークの依存関係を変える場合は、開発環境で [NocoBase Core のアップグレード](../developing-apps/upgrade-nocobase-core.md)を済ませてから公開します。
