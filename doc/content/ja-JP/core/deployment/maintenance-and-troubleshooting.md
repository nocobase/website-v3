---
title: 日常の保守とトラブルシューティング
description: Agent と稼働状態、設定、バックアップを確認し、証拠に基づいて障害を調べ、修復結果を検証します。
---

## Agent に稼働状態の確認を依頼する

サーバー、配置方法、ディレクトリ、プロセス名または Compose プロジェクト名を伝えます。ヘルス、再起動回数、リソース、ディスク、マイグレーション、エラーログを調べてもらいます。初回調査は読み取り専用にできます。

```prompt
<サーバーとディレクトリ> のアプリが遅い原因を、まだ変更せずに調べてください。<時刻> から <ページや操作> に影響しています。稼働状態とログをもとに、原因と対処案を教えてください。
```

実際の利用ネットワークとサーバー本体の両方から確認し、アプリとプロキシ、DNS、証明書、ネットワークの問題を切り分けます。

## 設定を変更して再起動する

変更する設定、対象環境、再起動できる時間を伝えます。旧設定を保存し、環境変数の優先設定を確認します。origin に base path は含めません。鍵の変更はログインや暗号化データに影響するため、[設定リファレンス](../reference/configuration.md)に従います。

Docker では設定ファイルの置換や環境変数変更後にコンテナを再作成します。restart だけでは環境が変わらず、単一ファイルのマウントも旧ファイルを参照している場合があります。PM2 ではインストール先の `app.env` と `config.yml` を保持し、同じアカウントでこのアプリだけを再起動します。PM2 に残る環境変数の上書きも確認します。変更後は実際のアクセスと業務操作を確認します。

## バックアップと復元能力を確認する

許容するデータ損失と停止時間から頻度を決めます。データベース、アップロードまたはオブジェクトストレージ、設定、安定した鍵を含めます。イメージや公開用アーカイブだけでは足りません。バージョン、復旧時点、範囲、ダイジェストを記録し、独立したアクセス制限付きの場所に保存します。

SQLite のオフラインバックアップではアプリと他の書き込み元を停止し、データベースと WAL/SHM ファイルを保存します。書き込み中のファイルはコピーしません。外部データベースは整合性を保つバックアップツールを使い、関連ファイルの復旧時点も揃えます。

隔離ディレクトリとポートに復元し、ログイン、レコード、権限、ファイルと復旧時間を確認してもらいます。更新時のスナップショットは定期バックアップの代わりにはなりません。範囲は[更新と復旧](publish-app-release.md)を参照してください。

## Agent に障害と手がかりを伝える

時刻とタイムゾーン、URL、失敗した操作、エラーやリクエスト ID、影響範囲、直近の公開や設定変更を伝えます。該当時間帯のログは匿名化し、パスワード、Cookie、鍵、設定全体を含めません。

```prompt
<時刻とタイムゾーン> から <URL> の <操作> が <エラー> になり、<利用者の範囲> に影響しています。直近では <変更> を行いました。このログから調査し、まず対処案を示してください。データの初期化や再インストールはしないでください。
```

## 対処案と修復結果を確認する

原因の根拠、変更範囲、停止時間、データへの影響、復旧方法を確認してから実行してもらいます。ポート競合では所有プロセスを特定し、無関係なアプリは停止しません。マイグレーションの問題をデータ初期化で回避しません。

元の失敗操作を再実行し、ログイン、権限、既存データ、関連機能を確認します。再起動した場合は永続化も確認します。修正内容、実際の結果、未確定の原因を記録します。

## よく使うコマンドとログの場所

元の配置ディレクトリで、プロジェクト名やプロセス名を置き換えて実行します。
```bash
docker compose -p my-app ps
docker compose -p my-app logs --tail=100 app
pm2 describe nocobase-my-app
pm2 logs nocobase-my-app --lines 100 --nostream
npx --yes @nocobase/app-installer@0.1.0-beta.10 status --dir /srv/nocobase/my-app --json
```

| 場所や症状 | 確認方法 |
| --- | --- |
| Docker 出力 | Compose logs。ホストの設定は `config/config.yml`、永続データは `storage/` |
| PM2 インストール先 | `app.env`、`config.yml`、`logs/`、`storage/`、`backups/`。PM2 の出力先は describe で確認 |
| ヘルス | `curl --fail http://127.0.0.1:13000/shop/api/healthz` が `ok: true` を返すか確認し、公開 URL も試す |
| マウント元なし / EACCES | Docker サーバー上のパスと UID 1000 の権限を確認 |
| START_FAILED / unhealthy | 再起動を繰り返す前に起動、データベース、マイグレーションのエラーを確認 |
| REMOTE_STATE_UNKNOWN | 同じ SSH 引数の status でリモート処理が継続中か確認 |

Docker の設定変更後は `docker compose -p my-app up -d --force-recreate --wait --wait-timeout 180`、PM2 は `pm2 restart nocobase-my-app` を使います。

以下は既定のローカル設定と storage のオフラインバックアップ例です。先にアクセス制限した `/safe/backup` を準備し、外部ストレージは別途保存します。元の Docker 配置ディレクトリで実行します。
```bash
docker compose -p my-app stop app
tar -czf /safe/backup/my-app-before-update.tar.gz config storage compose.yml
docker compose -p my-app start app
```

PM2 では先に `pm2 stop nocobase-my-app`、インストール先で `tar -czf /safe/backup/my-app-before-update.tar.gz config.yml app.env storage`、完了後に `pm2 restart nocobase-my-app` を実行します。独自のデータベースやファイルのディレクトリも含めます。秘密情報を含むバックアップはコミットや公開レポートに添付しません。
