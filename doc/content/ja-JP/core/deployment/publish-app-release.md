---
title: アプリのリリースを公開する
description: コードを変更したらビルドし直し、元のデプロイ方法で既存のアプリを更新します。
---

アプリの新しいリリースを公開するとは、検証済みのコードをビルドし直し、Docker または PM2（app-installer）で既存の本番アプリを更新することです。本番のデータベース、実行時の設定、ファイルストレージは保持します。アプリの URL は通常変わりません。

## エージェントを使う場合

アプリがどこで動いていて、どうデプロイされているかをエージェントに伝えます。たとえば：

```text
現在のアプリの新しいバージョンを、Docker で既存のサーバーにデプロイしてください。
デプロイ先のディレクトリは /srv/nocobase/shop です。既存のデータと設定は残し、更新前にバックアップし、更新後にアプリを確認してください。
```

PM2（app-installer）の場合は、app-installer がアプリを更新できるよう、サーバーと既存のインストール先ディレクトリを伝えます。

## エージェントを使わない場合

コードの変更とテストを終え、リリースするコミットまたはバージョンを確定してから、元のデプロイ方法でビルドし直して公開します。2 つの方法の違いは次のとおりです。

| デプロイ方法 | 更新方法 |
| --- | --- |
| [Docker](../tutorials/deploy-with-docker.md#新しいリリースを公開する) | 新しいタグでイメージをビルドし、Compose のイメージの参照を更新して、元の設定とストレージのマウントを保ったままコンテナを作り直します。 |
| [PM2（app-installer）](../tutorials/deploy-with-app-installer.md#新しいリリースを公開する) | 新しいデプロイ用アーカイブをビルドし、既存のインストール先ディレクトリに対して app-installer の `upgrade` を実行します。開発マシンからリモートにデプロイする場合は、引き続き `deploy --ssh` を使います。 |

コマンドは、各デプロイガイドの「新しいリリースを公開する」を参照してください。

データベースの構造が変わる場合は、新しいマイグレーションをコードに含め、適用済みのマイグレーションは残します。更新の前にデータベースとファイルをバックアップし、以前のアーカイブまたはイメージを保持しておきます。古いコードに戻しても、データベースが元に戻るとは限りません。

更新後は、アプリにアクセスでき、既存のデータと権限が保たれ、新しい機能が動作することを確認します。フレームワークの依存関係をアップグレードするには、先に [NocoBase Core をアップグレードする](../developing-apps/upgrade-nocobase-core.md) に従ってから、同じ手順でデプロイします。
