## 提供する機能

監査ログでは「誰が、いつ、何を行い、どのレコードに影響し、どのような結果になったか」を確認できます。エンタープライズ版の監査ログプラグインを有効にして収集を設定すると、ログがアプリケーションのデータベースに保存されます。権限のあるユーザーはシステム設定で確認、エクスポートできます。

商品変更、注文処理、ユーザー管理などの重要な操作を追跡できます。設定した操作について、成功だけでなく失敗やアクセス拒否の結果も記録できます。

## Agent に監査ログの設定を依頼する

まず、アプリケーションでエンタープライズ版の監査ログを利用できることを確認します。プラグインの導入、保存先の設定、業務操作の監査は、そのアプリケーションを開発する Agent に依頼できます。一般的な導入方法は[プラグインの管理](../../developing-apps/manage-plugins.md)を参照してください。

### 監査が未導入のアプリケーションに追加する

まだ監査を設定していない場合は、既存の機能を調べ、追跡が必要な操作をまとめて対応するよう依頼できます。

```prompt
@nocobase/audit を使って、このアプリケーションに監査ログを導入してください。既存の作成、更新、削除や重要な業務操作を調べ、監査機能のドキュメントとプロジェクトの開発規約に沿って、必要な describeAudit の宣言を追加してください。フレームワークがすでに監査している操作を重複して記録せず、通常の参照操作も記録しないでください。

config.yml の audit.transports に driver: database の保存先を設定し、管理者がシステム設定でログを確認、エクスポートできるようにしてください。各記録には操作者、日時、対象レコード、成功・失敗・アクセス拒否の結果を含めてください。

操作名をアプリケーションが対応するすべての言語に翻訳し、一覧、詳細、新しいエクスポートで対応する言語を使ってください。パスワードや API キーなどの機密情報を記録せず、既存の業務権限も変更しないでください。
```

### 特定の業務に不足している監査を追加する

監査は導入済みでも、新しい機能や一部の操作が記録されていない場合は、対象を限定して依頼できます。

```prompt
アプリケーションに導入済みの @nocobase/audit を使い、商品の作成、更新、削除に不足している監査を追加してください。監査機能のドキュメントとプロジェクトの開発規約に沿って、該当する業務ルートに describeAudit を設定し、誰がいつどの商品を操作したかと、成功・失敗・アクセス拒否の結果を記録してください。

config.yml の audit.transports に driver: database の保存先があるか確認してください。あれば再利用し、なければ追加して、システム設定でこれらの記録を確認、エクスポートできるようにしてください。他の業務の監査設定は維持し、重複して記録しないでください。

これらの操作名をアプリケーションが対応するすべての言語に翻訳し、一覧、詳細、新しいエクスポートで統一してください。パスワードや API キーなどの機密情報を記録せず、商品管理の既存の権限も変更しないでください。
```

「商品管理」を対象の業務に置き換えてください。設定後はテスト用レコードで操作し、監査ログの操作者、対象、結果、表示言語を確認します。

## 監査ログを手動で設定する

データベース保存と管理画面を使う場合は、`@nocobase/app-plugin-audit` のクライアントとサーバーのエントリーをインストール、登録し、アプリケーションのデータベースマイグレーションを実行してから、監査対象のルートと保存先を設定します。既存の認証、権限、入力検証は維持してください。

### `describeAudit` で業務操作を記録する

サーバーの業務ルートファイル（たとえば `server/routes/products.ts`）に `describeAudit` を追加します。以下は商品の更新を記録する例です。`router` と `productUpdateHandlers` は、既存のルーターと、認証、権限、API の説明、入力検証、業務処理を含む処理チェーンを表します。

```ts
import { describeAudit } from '@nocobase/audit';

const auditProductUpdate = describeAudit({
  action: 'products.update',
  resource: 'products',
  operationName: {
    ns: 'my-app',
    key: 'audit.products.update',
    defaultValue: 'Update a product',
  },
  target: (context) => ({
    collection: 'products',
    key: context.req.param('id'),
  }),
  captureBody: false,
});

router.patch('/products/:id', auditProductUpdate, ...productUpdateHandlers);
```

| 設定 | 用途 |
| --- | --- |
| `action` | 操作の識別や絞り込みに使う固定の識別子 |
| `resource` | 操作が属するリソースの識別子 |
| `operationName` | 画面とエクスポートで使う操作名。翻訳への参照と既定の名前を指定できる |
| `target` | 対象のコレクションとレコードの主キー。業務データ全体ではなく識別子だけを返す |
| `captureBody` | リクエストとレスポンスの本文を収集するかどうか。この例では明示的に無効化 |

このルートは URL の `id` から商品キーを取得するため、本文の読み取りは不要です。作成後に初めて主キーが分かる場合は、`resolveTargets` で対象を補えます。特定のルートを除外するには `describeAudit(false)` を使います。ルート全体の書き方は [HTTP ルートと API](../../developing-apps/apis-and-services.md)を参照してください。

### 操作名を多言語化する

`my-app` をアプリケーションの `package.json` にある `name` に置き換えます。プラグイン自身の操作には、そのプラグインのパッケージ名を使います。`key` は各言語リソースの同じ項目を指し、翻訳がない場合は `defaultValue` を使います。

以下の項目を既存の言語リソースに追加し、他の文言を上書きしないでください。クライアント側は一覧と詳細、サーバー側はエクスポートに使うため、両方に必要です。

`client/locales/en-US.ts` と `server/locales/en-US.ts`：

```json
{
  "audit": {
    "products": {
      "update": "Update a product"
    }
  }
}
```

`client/locales/zh-CN.ts` と `server/locales/zh-CN.ts`：

```json
{
  "audit": {
    "products": {
      "update": "修改商品"
    }
  }
}
```

日本語など、他の対応言語にも同じ項目を追加し、リソースが読み込まれることを確認します。操作名は閲覧時、またはエクスポート開始時の言語で表示されます。業務データ自体が自動翻訳されるわけではありません。リソースの組み込み方は[多言語対応](i18n.md)を参照してください。

### `config.yml` で複数の保存先を設定する

`audit.transports` には複数の保存先を設定できます。収集した同じ監査記録が各保存先に送られます。たとえば、アプリケーションのルートにある `config.yml` でデータベースとファイルを同時に有効にします。

```yaml
audit:
  enabled: true
  autoDetect: false
  captureBody: false
  transports:
    history:
      driver: database
    localFile:
      driver: file
      options:
        path: audit/events.jsonl
        maxFileSizeMB: 50
        retentionDays: 180
```

`history` と `localFile` は任意の名前で、`driver` が保存方法を指定します。この設定では、管理画面での検索やエクスポートに使うデータベースにログを保存すると同時に、指定したファイルにも追記します。

| 設定 | 意味 |
| --- | --- |
| `enabled` | 監査全体のスイッチ。`false` にすると収集と書き込みを停止 |
| `autoDetect` | API 文書に宣言された書き込み操作を追加で自動収集するかどうか。既定は `false`。明示的な監査宣言やフレームワークが生成するデータ更新エンドポイントは、この設定に依存しない |
| `captureBody` | 本文の収集。この例では全体で無効にしているため、個別ルートでは再び有効にできない |
| `transports` | 名前付きの保存先。それぞれにドライバーとオプションを指定する |
| `driver: database` | 監査プラグインが提供するデータベース保存。アプリケーションの既定のデータベースを使う。重複書き込みを避けるため、データベース保存先はアプリケーションごとに一つにする |

変更後はアプリケーションを再起動します。この設定では操作情報を保存し、リクエスト・レスポンス本文は保存しません。本文の記録については[機密情報のマスキング](#機密情報のマスキング)を参照してください。

保存先を設定して再起動したら、テスト用の商品を更新します。管理画面に操作名、`products` コレクション、該当する主キーが表示され、ファイルにも記録が追加されることを確認してください。画面の言語を切り替えると、操作名の翻訳が変わります。

### ファイル出力の設定と注意点

`driver: file` を指定すると、次の項目でファイル出力を設定できます。

| 設定項目 | 説明 |
| --- | --- |
| `options.path` | 必須。ディレクトリとファイル名の接頭辞。例：`audit/events.jsonl` |
| `options.maxFileSizeMB` | サイズによるローテーションのしきい値。既定は `50` MB |
| `options.retentionDays` | アーカイブの保持日数。既定は `180` 日 |

相対パスはアプリケーションのストレージが基準で、絶対パスも使えます。ログは UTC の日付とファイルサイズで分割され、一行に一つの記録を持つ JSON Lines 形式で保存されます。

保持期間はファイルの最終更新日時から計算し、期限切れアーカイブをバックグラウンドで削除します。データベースのログ保持設定とは独立しています。複数インスタンスでは出力ディレクトリや接頭辞を分け、旧版の未分割ファイルは別途アーカイブまたは削除してください。

> [!TIP]
> ファイル出力だけなら、上の例の `localFile` を残し、`history` を外します。この機能は `@nocobase/audit` が提供し、Default アプリケーションテンプレートには組み込み済みです。`@nocobase/app-plugin-audit` が必要なのは、データベース保存と管理画面を使う場合です。

## 機密情報のマスキング

JSON のリクエスト・レスポンス本文を記録する場合、パスワードやトークンなどの機密フィールドは、ログの書き込み前に `******` に置き換えられます。業務フィールドにもルールを追加できます。下の詳細画面では、本人確認番号や電話番号がマスクされ、通常の値はそのまま表示されています。

![機密フィールドがマスクされ、通常の値が保持された監査ログの詳細](/assets/core/audit-logs/redacted-detail.png)

### ルート単位の設定：`describeAudit`

業務ルートの既存の `describeAudit` 宣言に次の設定を追加し、操作名と対象の設定は保持します。本文は既定では記録されないため、必要なルートだけで有効にしてください。前の例の全体設定 `captureBody: false` を使っている場合は、その行を削除します。どちらかの設定が明示的に `false` なら、本文は記録されません。

```ts
describeAudit({
  action: 'products.update',
  captureBody: true,
  redact: {
    fields: ['routeSecret'],
    paths: ['payload.members.mobile', 'data.payload.members.mobile'],
  },
});
```

`fields` は階層を問わずフィールド名を完全一致で照合し、`paths` は本文のルートからのパスで配列内のフィールドも指定できます。この例では、すべての `routeSecret` と、リクエスト・レスポンスの `members` 配列にある電話番号をマスクします。

### アプリケーション全体の設定：`config.yml`

複数の API で使うルールは `config.yml` の `audit.redact` に追加します。`audit.transports` などの既存設定は保持してください。

```yaml
audit:
  redact:
    fields: [identityNumber, appSecret]
    paths:
      - payload.profile.mobile
      - data.payload.profile.mobile
```

全体とルートのルールは組み合わせて適用され、組み込みの機密フィールドのルールも維持されます。リクエストとレスポンスの構造が異なる場合は、それぞれのパスを指定してください。変更後はアプリケーションを再起動します。新しいルールは以降の監査記録だけに適用され、業務データや過去のログは書き換えません。

## ログの確認とエクスポート

### ログ一覧を確認する

**システム設定 → 監査ログ** の **ログ** タブを開きます。新しい記録から順に、操作者、操作、対象、結果などを確認できます。

期間を指定し、**その他のフィルター** で操作、結果、主体の種類を絞り込みます。レコード ID、ユーザー ID、IP アドレス、リクエスト ID が分かっている場合は検索欄を使えます。

![監査ログ一覧のフィルター、操作対象、実行結果](/assets/core/audit-logs/list.png)

### 操作の詳細を確認する

レコードをクリックすると、操作者の情報、対象レコード、実行結果、リクエスト ID を確認できます。問題の調査では、リクエスト ID を保守担当者に伝えると同じリクエストを特定するのに役立ちます。

![監査ログ詳細の操作者、対象レコード、実行結果](/assets/core/audit-logs/detail.png)

リクエストとレスポンスの内容は、設定で許可され、実際に収集できた場合だけ表示されます。未保存という表示は、該当する本文が保存されていないことを意味します。操作全体が記録されていないわけではありません。

### ログをエクスポートする

1. 一覧で必要な絞り込み条件を設定します
2. **エクスポート**、続いて **エクスポートを開始** をクリックします
3. バックグラウンドでの生成を待ち、**受信トレイ** の完了通知からファイルをダウンロードします

現在のページだけでなく、条件に一致する記録が対象です。Excel（`.xlsx`）ファイルには日時、操作者、操作、対象、結果などが含まれますが、リクエストとレスポンスの本文は含まれません。翻訳にはエクスポート開始時の言語が使われます。

リンクの有効期間は 24 時間です。ダウンロードできるのはエクスポートを開始した本人だけで、引き続きエクスポート権限が必要です。期限が切れたら再度エクスポートしてください。
