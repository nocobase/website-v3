## 機能

`@nocobase/app-plugin-lifecycle-coordination` はサーバー専用のプラグインで、`@nocobase/lifecycle` に基づく [ワークフロー](../../developing-apps/business-workflows.md) に親子プロセスの連携、結果の集約、協調キャンセル、永続的な復旧を追加します。公開 HTTP ルートやフロントエンド画面は提供しないため、業務テーブル、API、認可、UI はアプリ側で組み立てます。インストールの前に対象パッケージへのアクセス権とライセンスを確認してください。手順は [プラグインを管理する](../../developing-apps/manage-plugins.md) を参照してください。

| 機能 | プラグインが提供するもの | アプリが担うこと |
| --- | --- | --- |
| 連携台帳とマイグレーション | 既定のデータベース接続に `lifecycleCoordinations` 台帳テーブルとマイグレーションを提供 | 参加する業務テーブルにライフサイクル項目と定義バインド項目を持ち、子テーブルに `coordination` JSON 項目を追加する |
| 条件分岐と集約 | `LifecycleCoordinator`、`waitingState()`、`complete()`。条件付き分岐、整数しきい値、バージョン付き独自戦略に対応 | 親子定義、分岐条件、終端状態の報告フック、保護された結論遷移を宣言する |
| 終了方針と協調キャンセル | `retain`（継続）と `cancel`（協調キャンセル）、取り下げ後の再提出における旧ラウンド分離、最大 16 階層の入れ子に対応 | 子プロセスのキャンセル遷移と業務上の補償処理（返金や在庫解放など）を宣言する |
| トランザクション再試行と復旧 | `transaction()` の競合再試行、未確定結果や未配信キャンセルの `recover()` / `resume()`、`inspect()` 診断ビュー | 起動時と永続ジョブ（`onSweep`）から `recover()` を呼び、返却されたエラーを監視する |
| プロセス図のメタデータ | `waitingState()` の第 4 引数で入れ子子定義と結論エッジのメタデータを宣言可能 | 必要に応じてアプリ画面で定義図、実行図、ラウンド別の子プロセス詳細を描画する |

[承認（商用版）](approval.md) とライフサイクル連携は対等な拡張であり、相互の必須依存はありません。子プロセスの内部で承認を使い、最終的な業務結果だけを親プロセスへ報告できます。

## シナリオと例

ライフサイクル連携は、主に次の 2 つのシナリオで使います。

1. **並列分岐**：親プロセスが待機状態に入ったときに条件に応じて複数の分岐を並列起動し、合流時にあらかじめ定めた方針（全分岐の成功、成功しきい値、またはバージョン付き独自戦略）で親の遷移先を判定し、未完了の分岐を継続または協調キャンセルします。
2. **子プロセス**：ある工程を独立した子プロセスとして切り出します（並列分岐を持たない 1 つの子プロセスでも構いません）。子プロセスは独自のライフサイクルを持ち、差し戻し修正、人による承認、外部実行や再試行を経て、業務上の終端状態に達した時点で親へ結果を報告します。子プロセスの中でさらに下位の子プロセスを入れ子にすることもできます。

次のような隣接する要件では、別の仕組みを優先します。

- 1 つの業務レコード内での順次遷移、条件分岐、ガード、エフェクト：[ワークフロー](../../developing-apps/business-workflows.md) をそのまま使います。
- 1 つの申請に対して複数人が合議・承認するだけの場合：[承認（商用版）](approval.md) を使います。各分岐が独立した多段階の子プロセスになるときだけライフサイクル連携を追加します。
- 単発の非同期処理や再試行：[バックグラウンドタスク](../../developing-apps/background-tasks.md) を使います。

各ラウンドで起動する分岐の集合は待機状態に入った時点で固定されます。実行中の動的な分岐追加・削除、複数データベースにまたがる分散トランザクション、全体の一時停止、実行中コードの強制終了は本プラグインの対象外です。

### 例：購買申請の並列レビューと条件分岐

購買申請を提出すると待機状態に入り、法務レビューを常に起動し、財務評価が必要な場合だけ財務レビューも並列起動します。法務・財務はそれぞれ独自の差し戻し修正、再提出、承認、後続実行を持ちます。購買方針に応じて「選択した全部門の成功で発注可」または「いずれか 1 部門の成功で発注可とし他方をキャンセル」を選びます。承認後に後続の外部実行が失敗した場合は、その分岐を失敗として集約します。

前提：購買と部門レビューのコレクション、認証・認可、`@nocobase/lifecycle` とホストの Jobs、および [プラグインを管理する](../../developing-apps/manage-plugins.md) に沿ったライフサイクル連携プラグインのインストールと登録が完了していること。

**開発用のプロンプト**（アプリのディレクトリで作業するコーディングエージェント向け）：

```prompt
購買申請に並列の部門レビューを組み込んでください。提出したら法務レビューを必ず開始し、財務評価にチェックがある場合だけ財務レビューも同時に開始します。法務と財務はそれぞれ差し戻し修正、再提出、承認、実行完了を行えます。購買申請の設定に応じて、全部門成功で発注可にするか、いずれか 1 つ成功した時点で発注可にして未完了の分岐へキャンセルを要求するか選べるようにし、承認後の実行失敗は分岐の失敗として扱ってください。詳細画面に実行図と各分岐の進捗を表示します。
```

プラグイン自体は UI を持ちません。以下のスクリーンショットは付属のサンプルプラグインをホストアプリに組み込んだ購買連携の詳細画面で、法務レビューが実行成功し、財務レビューが進行中で、親の購買申請が待機している状態を示しています。

### 例：多階層の親子プロセスと協調キャンセル

大口顧客の受注履行では多階層の並列連携を行います。親の受注を提出すると「倉庫準備」と「物流手配」の子プロセスが並列起動し、それぞれの配下でさらに「品質検査」と「書類確認」の下位ステップが起動します。各階層ではすべての子が成功して初めて親へ進みます。いずれかのステップが失敗した場合や、履行前に親の受注を取り下げた場合は、未完了の同階層・下位プロセスへ協調キャンセルを要求します。取り下げ後に再提出すると新しいラウンドが始まり、旧ラウンドから遅れて届いた結果は新ラウンドを進めません。

**開発用のプロンプト**（アプリのディレクトリで作業するコーディングエージェント向け）：

```prompt
大口受注の履行を多階層の親子プロセスにしてください。受注を提出したら倉庫準備と物流手配を並列起動し、それぞれの配下で品質検査と書類確認の 2 つの子プロセスを動かします。各階層はすべての子が成功したときだけ親を進め、いずれかが失敗するか親受注を取り下げたら未完了の下位プロセスへキャンセルを通知してください。取り下げ後の再提出は新しいラウンドとして扱い、旧ラウンドの遅れた結果が影響しないようにします。
```

中間階層の子プロセスは親から渡された `coordination` バインドを保ったまま自身の `waitingState()` を開き、下位がすべて完了して自身が業務上の終端状態に達した時点で親へ結果を報告します。

## 仕組みと実装

上記のシナリオを実装するときの主な組み込み先と画面・動作の変化は次のとおりです。実際のファイル名はアプリ構成に合わせてください。

| 組み込みの領域 | コードまたは設定の変更 | 画面と動作の変化 |
| --- | --- | --- |
| `server/plugins.ts` とマイグレーション | ライフサイクル連携の Server プラグインを登録しマイグレーション適用。業務表と子表にバインド項目を追加 | `lifecycleCoordinations` 台帳が作成され、レコードが正確な定義バージョンと連携に紐付く |
| ライフサイクル定義と Provider | `LifecycleCoordinator` を生成し、`waitingState()`、終端の `complete()`、`protect()` を設定 | 待機遷移で条件分岐を起動し、しきい値や戦略の判定で親を確定する |
| ホスト Jobs と起動処理 | 定義と戦略の登録後に起動時と `onSweep` で `coordinator.recover()` を呼ぶ | プロセス停止や親確定の失敗後も未処理結果とキャンセル配信を復旧できる |
| 業務 API と詳細画面 | 競合し得る境界を `coordinator.transaction()` で包み、`inspect()` から進捗を表示 | 楽観ロック競合を安全に再試行し、ラウンド状態と入れ子実行図を表示できる |

### 組み込みと定義のバインド

`server/plugins.ts` に `@nocobase/app-plugin-lifecycle-coordination/server` のデフォルトエクスポートを登録し、マイグレーションを適用します（Client や CLI の登録は不要です）。業務の `LifecycleRuntime` と**同じ `LifecycleStore`・データベース接続**を使って `LifecycleCoordinator(runtime, createRepositoryCoordinationStorage(database, store))` を 1 つ構成します。独立して復旧するランタイムが複数ある場合は、それぞれ別の台帳コレクションを割り当てます。

連携に参加するすべての親子定義は、安定した `key`、数値の `version`、`definitionField`（例：`lifecycleDefinition`）を宣言します。

- レコード作成時にランタイムが正確な定義名（例：`procurement.v1`、`procurement.legal.v1`）を `definitionField` へ書き込み、別定義からの操作を拒否します。
- 分岐の `lifecycle` と `protect()` にはプロセス `key` や `latest` ではなく正確な登録定義名を渡します。
- 子テーブルには作成時に連携器が書き込む `coordination` JSON 項目を持たせ、業務 API から変更できないようにします。
- 仕様を変更するときは新しい定義バージョンや戦略バージョンを追加し、未完了ラウンドやキャンセル配信が残っている間は旧実装を登録したまま保持します。

### 待機状態、結果の集約、終了方針の定義

次の抜粋は連携器の構築、待機状態の宣言、結論遷移の保護、子終端状態での報告方法を示します（業務バリデーションとルート認可は省略）。

```ts
// server/services/procurement.ts（抜粋）
import {
  LifecycleCoordinator,
  createRepositoryCoordinationStorage,
} from '@nocobase/app-plugin-lifecycle-coordination/server';

const coordinator = new LifecycleCoordinator(
  runtime,
  createRepositoryCoordinationStorage(database, store),
);

// 親定義（例：procurement.v1）の states 内で待機状態を宣言
coordinator.waitingState('waiting', 'reviews', ({ record }) => ({
  key: 'reviews',
  success: 'order',
  failure: 'reject',
  remaining: 'cancel',
  branches: (record.financeRequired ? ['legal', 'finance'] : ['legal']).map(
    (department) => ({
      key: department,
      lifecycle: `procurement.${department}.v1`,
      values: { department },
      outcomes: {
        succeeded: ['succeeded'],
        failed: ['failed'],
        cancelled: ['cancelled'],
      },
      cancelTransition: 'cancel',
    }),
  ),
}));

// runtime.register(parent) のあと、処理を受け付ける前に結論遷移を保護
coordinator.protect('procurement.v1', ['order', 'reject']);

// 子定義の終端状態フックから結果を報告
{
  name: 'succeeded',
  final: true,
  onEnterState: (context) =>
    coordinator.complete(context, 'succeeded', { receipt: 'business-result' }),
}
```

主な仕組み：

- **結論遷移の保護**：`success` と `failure` の遷移は待機状態から出て `manual: false` を指定し、`coordinator.protect()` でサーバー許可を付けます。外部呼び出しがラウンド ID を知っていても親を直接確定できません。
- **しきい値とバージョン付き戦略**：`required` 省略時は選択された全分岐の成功が条件になります（0 分岐は待機開始コミット後に成功）。`required: 1` はいずれか 1 つ成功、`required: K` は K 件以上成功を表します。失敗とキャンセルはいずれも達成可能な成功数を減らし、しきい値に届かなくなった時点で即座に失敗へ確定します。分岐の識別子に応じた条件（財務必須など）が必要な場合は、`coordinator.registerStrategy({ name, version, decide })` で純粋関数の戦略を登録し、復旧対象が残る間はそのバージョンを維持します。
- **終了と協調キャンセル**：`waitingState()` は入場と退場の両方のフックを登録するため、取り下げや待機からの離脱で旧ラウンドは無効化されます。`remaining: 'retain'` は未完了の子を継続させ、`remaining: 'cancel'` は宣言された `cancelTransition` を永続配信します。`cancellation: 'delivered'` は遷移コミットを意味するだけで、子がキャンセル終端状態に到達して初めて `outcome: 'cancelled'` になります。返金などの外部補償は子プロセスの状態とエフェクトで実装します。
- **管理再入場と入れ子**：管理リセット・再起動を有効にする親定義では、待機状態の `onReenter` を `management.onReenter` に接続します。入れ子連携は最大 16 階層まで対応し、上限を超えると入場トランザクションがロールバックされます。

### トランザクション境界、復旧、プロセス図の表示

子の完了と結果記録は**子自身のトランザクション**でコミットされ、親の確定は**コミット後の別トランザクション**で実行されます。この分離により、親のガード失敗や次段階のタスク割り当て失敗が起きても子の確定済み業務結果が巻き戻らず、台帳にエラーを残して後から安全に復旧できます。

複数の子完了や親の取り下げが競合し得るサーバー境界では、純粋なデータベース操作を `coordinator.transaction(tx => ...)` で囲みます（楽観ロック競合・直列化失敗・デッドロックを最大 5 回まで全体再試行します。外部呼び出しは通常のライフサイクルエフェクトに置きます）。

プラグインは独自のタイマーを起動しません。すべての定義、結論ガード、戦略バージョンを登録したあと、アプリ起動時とホストの永続ジョブ `onSweep` で `coordinator.recover()` を呼び出し、返却されたエラーを記録・通知してください。個別ラウンドの再試行には `resume(id)`、状態確認には `inspect(id)` を使います。

フロントエンドで入れ子プロセス図を表示したい場合は、`waitingState()` の第 4 引数に `{ nested: true, conclusions: ['order', 'reject'], branches: [...] }` を渡して定義図のメタデータを提供し、実行画面ではラウンドと子レコード ID ごとに履歴を掘り下げて現在・通過済みノードを強調表示します。

## AI 開発の制約と検証

### プラグイン固有の開発の制約

- 組み込み前に、インストール済みパッケージに同梱された `nocobase-app-plugin-lifecycle-coordination` スキルと `docs/coordination.md` を読み、公開契約とストレージ要件を確認してください。
- 本プラグインはサーバー専用の組み込み原語です。業務ルート側で認証・認可を行い、生の `complete()`、任意の遷移、`lifecycleCoordinations` や子レコードの `coordination` / `definitionField` への直接書き込みをクライアントへ公開しないでください。
- 子レコードの作成フック内で同期的に `complete()` を呼ばないでください（作成完了までレコード ID が確定しません）。
- 子プロセスに承認を組み込む場合、一部の承認意見や外部実行前の承認完了だけで子成功を報告せず、最終的な業務終端フックからのみ `complete()` を呼んでください。
- 未完了の子プロセスやキャンセル配信が残る台帳行を自動削除せず、仕様変更時は進行中ラウンドが終わるまで旧定義・旧戦略バージョンを保持してください。

### 復旧と検収のチェック

- **分岐としきい値**：条件分岐で選択された子だけが作られること、3 分岐・`required: 2` で「1 件成功で待機」「2 件成功で即座に成功」「1 件失敗＋1 件キャンセルで即座に失敗」がそれぞれ親を 1 回だけ進めることを確認する。
- **入れ子と取り下げ分離**：多階層で下位完了が中間層を経て親へ伝わること、親の取り下げ後に再提出したとき旧ラウンドの遅れた結果が新ラウンドを進めないことを確認する。
- **協調キャンセルと冪等性**：`retain` と `cancel` の動作（`delivered` と終端 `cancelled` の区別を含む）および、重複リクエストや重複報告で子や結論が増えないことを確認する。
- **並行処理と復旧**：子プロセスの同時完了で二重確定しないこと、コミット後通知の欠落、アプリ再起動、親確定の失敗、戦略バージョン欠落からの `recover()` 復旧とエラー可視化を確認する。
