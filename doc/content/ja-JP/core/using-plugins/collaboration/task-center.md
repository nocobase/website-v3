## 機能

`@nocobase/app-plugin-task-center` は、サインイン中のユーザーが対応すべき作業を複数の業務モジュールから 1 つの個人タスクセンターに集約します。承認プラグインへの依存はなく、備品受け取りや注文確認などの通常業務のタスクに単独で使えるほか、[承認（商用版）](approval.md) と組み合わせて承認タスク、CC、その他の業務タスクをまとめて表示できます。インストールの前に対象パッケージへのアクセス権とライセンスを確認してください。手順は [プラグインを管理する](../../developing-apps/manage-plugins.md) を参照してください。

| 機能 | プラグインが提供するもの | アプリが担うこと |
| --- | --- | --- |
| 個人タスクのインデックス | `userTasks` インデックス表とソースごとの書き込み口（`UserTaskWriter`） | 業務トランザクション内で状態を書き込み、受け取り資格と安全なタイトルを管理する |
| 既定のページとヘッダー入口 | サインイン済みユーザー向けの `/task-center` ページと、標準ヘッダーの未処理件数ショートカット | 必要に応じてショートカットの非表示やページの差し替えを行い、業務詳細と処理操作を接続する |
| 照会 API とクライアント部品 | 認証付き `GET /api/userTasks*` API、`createTaskCenterDataSource`、`<TaskCenter />` | ダッシュボード、バッジ、独自ページで同じ範囲の一覧・分類・件数を読み込む |
| 承認との連携 | 承認への逆依存は持たず、共通のインデックスと表示基盤を提供 | 承認定義で `userTasks` の対応付けを有効にし、業務ルート経由で詳細と判断操作を提供する |

タスクインデックスの 1 件は「だれにどの未処理または完了済み項目があるか」を示すだけで、業務レコードの閲覧や更新の権限は与えません。業務詳細の取得、完了操作、状態遷移、認可チェックは各業務モジュールが担い、通知の配信は [通知](../notifications/notification.md) が担います。

## シナリオと例

複数の業務にまたがる個人の作業を 1 か所で処理したいときにタスクセンターを使います。たとえば、購買承認、休暇承認、備品受け取りを 1 つのタスクページにまとめたり、ヘッダーやワークスペースに現在の未処理件数を表示したりする場面に適しています。

次の用途ではタスクセンターを導入する必要はありません。

- お知らせやリマインダーを送るだけの場合：[通知](../notifications/notification.md) または [アプリ内通知](../notifications/in-app.md) を使います。
- 単一の業務詳細ページ内でレコードを直接編集する場合。
- 組織全体の管理レポートを集計する場合：タスクセンターの API はサインイン中のユーザー本人のインデックスだけを返します。
- 「自分が申請した一覧」を追跡する場合：承認タスクの連携は承認担当と CC を対象としており、申請者側の追跡は別の業務ビューまたは独自ソースとして用意します。

### 例：承認と業務タスクをまとめて処理する

社員がサインインしたあと、購買承認、休暇承認、IT 部門からの備品受け取りを同じ画面で確認し、左側のソースと業務カテゴリで絞り込み、各項目から対象業務の詳細へ進んで承認または受け取り確認を完了します。完了後は未処理から完了済みへ移り、ヘッダーとタブの件数が更新されます。

前提：認証機能、対象の承認または業務モジュール（備品受け渡しなど）、および [プラグインを管理する](../../developing-apps/manage-plugins.md) に沿ったタスクセンターのインストールと登録が完了していること。

**開発用のプロンプト**（アプリのディレクトリで作業するコーディングエージェント向け）：

```prompt
購買承認、休暇承認、備品受け取りをタスクセンターに接続してください。項目を開いたら対象の業務詳細へ進んで承認や受け取り確認ができ、処理後にタスクの状態が同期更新されるようにします。各自が自分のタスクだけ見られるようにしてください。
```

プラグインを登録してマイグレーションを適用すると、サインイン済みユーザーはヘッダーのショートカットまたは `/task-center` から既定ページを開けます。左側にはソースと業務カテゴリ別の未処理件数が表示され、上部のタブで未処理・完了済み・すべてを切り替えられます。

![既定のタスクセンター画面とヘッダーの未処理件数ショートカット](/assets/core/task-center/task-center.png)

スクリーンショットは英語のサンプルデータで既定の `/task-center` レイアウトとヘッダー件数入口を示したものです。アプリ側で業務詳細コンポーネントを接続すると、項目クリックからそのまま承認や業務処理へ進めます。

### 例：ダッシュボードやヘッダーに未処理件数を表示する

購買ワークスペースのトップ画面に「自分の承認待ち」カードだけを置き、購買承認の未処理件数と最新 5 件を表示したい場合や、アプリ独自の導線があるため既定のヘッダーボタンを隠したい場合に使います。

**開発用のプロンプト**（アプリのディレクトリで作業するコーディングエージェント向け）：

```prompt
購買ワークスペースのホームに「自分の承認待ち」カードを追加し、購買承認の未処理件数と最新 5 件を表示して、クリックすると対象の発注詳細を開けるようにしてください。独自の導線があるので、ヘッダーの既定タスクボタンは非表示にしてください。
```

クライアントのデータソース関数を使って指定ソースの件数と一覧だけを必要なタイミングで取得し、業務処理後にキャッシュを更新します。既定のヘッダーボタンはクライアントランタイムの設定で非表示にできます。

## 仕組みと実装

上記のシナリオを実装するときの主な組み込み先と画面・動作の変化は次のとおりです。実際のファイル名はアプリ構成に合わせてください。

| 組み込みの領域 | コードまたは設定の変更 | 画面と動作の変化 |
| --- | --- | --- |
| `server/plugins.ts` とマイグレーション | タスクセンターの Server プラグインを登録し `202610190001_user_tasks` を適用 | `userTasks` インデックス表と認証付き照会 API が有効になる |
| `client/plugins.ts` と `client/runtime.ts` | `taskCenter()` を登録し、必要に応じて除外やページ差し替えを指定 | `/task-center` とヘッダー未処理件数入口が有効化、または独自画面へ切り替わる |
| 業務サーバーモジュール | `userTaskServiceToken` を解決してソース登録し、業務トランザクション内で書き込む | 業務の作成・完了・キャンセルと個人タスクインデックスが原子的に同期する |
| ワークスペースや独自画面 | `<TaskCenter sources={...} />` または `createTaskCenterDataSource(client)` を組み合わせる | ソース表示名、範囲一致の一覧・件数、認可された業務詳細への導線を提供する |

### プラグインの登録と既定画面のカスタマイズ

サーバー側で `@nocobase/app-plugin-task-center/server` のデフォルトエクスポートと認証プラグインを登録してマイグレーションを適用し、`client/plugins.ts` に引数なしの `taskCenter()` を追加します。

```ts
// client/plugins.ts（抜粋）
import taskCenter from '@nocobase/app-plugin-task-center/client';

// アプリのクライアントプラグイン配列に追加
taskCenter();
```

登録後、サインイン済みユーザーは `/task-center` を開け、標準ヘッダーに未処理合計数のショートカットが表示されます（アクティブ時は 30 秒ごととウィンドウ再フォーカス時に更新）。独自のシェルでは `<AppHeaderActions />` で登録済みショートカットを描画できます。

既定画面を調整するときは、`client/plugins.ts` の `taskCenter()` を残したまま `client/runtime.ts` の `defineAppRuntime()` で `@nocobase/app-plugin-task-center/client` からエクスポートされた ID を指定します。

| 目的 | `defineAppRuntime()` の設定 |
| --- | --- |
| ヘッダーのショートカットを隠し、`/task-center` は残す | `excludedHeaderActionIds: [TASK_CENTER_HEADER_ACTION_ID]` |
| 既定ページと連動するヘッダー入口を両方外す | `excludedRouteIds: [TASK_CENTER_ROUTE_ID]` |
| `/task-center` とショートカットを残し、画面コンポーネントだけ差し替える | `routeComponentOverrides` で `TASK_CENTER_ROUTE_ID` を指定 |

アプリ独自のルートに埋め込む場合は既定ルートを除外したうえで `<TaskCenter sources={sources} />` を配置し、`TaskCenterSource` に表示名と `renderTask(task, refresh)` を渡します。いずれの方法でもサーバー API とロケールはそのまま利用できます。

### 業務ソースの接続とトランザクションの一貫性

`@nocobase/app-plugin-task-center/server` から `userTaskServiceToken` を解決し、初期化時に業務ごとの一意な `sourceType` を 1 回だけ登録して `UserTaskWriter` を保持します（重複登録はエラーになります）。次の抜粋は備品受け渡しのトランザクション内で未処理タスクを登録する例です（業務テーブルの書き込みと認可チェックは省略）。

```ts
// server/services/deliveries.ts（抜粋）
import { userTaskServiceToken } from '@nocobase/app-plugin-task-center/server';

const userTasks = container.resolve(userTaskServiceToken);
const deliveries = userTasks.registerSource('asset.delivery');

await database.connection().transaction(async (tx) => {
  // 先に tx で業務レコードを書き込み、同じトランザクションで個人タスクを反映する
  await deliveries.put(
    {
      userId: recipientId,
      sourceKey: deliveryId,
      subject: 'equipment',
      title: 'Confirm laptop pickup',
      status: 'pending',
    },
    tx,
  );
});
```

1 件のタスクは `(userId, sourceType, sourceKey)` で一意に識別されます。`sourceKey` は安定した不透明な識別子を使い、`subject` に業務カテゴリを入れ、エントリ自身の `id` を業務レコード ID と混同しないでください。内容が同じ再書き込みは ID と時刻を保ち、完了やキャンセル時は同じトランザクションで `setStatus(..., tx)` を呼びます。受け取り担当が変わった場合は、内部テーブルを直接読まず `writer.listBySourceKey(sourceKey, tx)` で差分を調整します。

[承認（商用版）](approval.md) と連携する場合、`approval.task` と `approval.cc` は承認プラグインの共有コントリビューターが所有するため、通常業務から直接登録や書き込みを行わないでください。承認定義の `userTasks` オプションで同期を有効にします。旧バージョンの承認プラグインに含まれていた `202610190001_user_tasks` から移行する場合は、承認とタスクセンターを同時にアップグレードしてマイグレーション履歴と既存行を保持し、過去の業務レコードは明示的にバックフィルしてください。

### 一覧、分類、統計の照会

プラグインはアプリのベースパス配下に 4 つの認証付き読み取り専用 HTTP ルートを提供します（マウント先が `/main` の場合は `/main/api/userTasks` から始まります）。

| ルート | 主なクエリパラメーター | 用途 |
| --- | --- | --- |
| `GET /api/userTasks` | `status`、`sourceType`、`subject`、`orderBy`、`direction`、`pagination`、`page`、`pageSize`、`after`、`includeTotal` | 本人のタスク一覧をページング取得。`status` と `sourceType` は単一値または配列に対応（同項目は OR、異項目は AND） |
| `GET /api/userTasks/statistics` | `status`、`sourceType`、`subject` | `{ pending, completed, cancelled }` を返す。タブ集計は `status` を省略し、バッジには `status=pending` を指定 |
| `GET /api/userTasks/categoryStatistics` | 任意の `status`（既定 `pending`） | 本人の全履歴から `(sourceType, subject)` カテゴリを抽出し件数を返す。完了のみのカテゴリも件数 `0` で残る |
| `GET /api/userTasks/:id` | なし | 本人所有の 1 件のインデックス情報を返す |

クライアントでは `createTaskCenterDataSource(client)` が `list`、`statistics`、`categoryStatistics` を提供します。

- 「完了済み」タブは `status: ['completed', 'cancelled']`、「すべて」タブは `status` 省略に対応させます。タブ件数は一覧と同じ `sourceType`・`subject` で `status` を省略して取得します。
- 対話的な一覧では `(createdAt, id)` ベースの `pagination: 'cursor'` を優先し、正確な総数が必要なときだけ `includeTotal: true` を付けます。バッジは `status: 'pending'` を指定して過去履歴の走査を避けます。
- 件数は個人のタスクエントリ数であり、業務レコード単位の重複排除は行いません。

## AI 開発の制約と検証

### プラグイン固有の開発の制約

- 組み込み前に、インストール済みバージョンに同梱された `nocobase-app-plugin-task-center` スキル（`references/server.md` と `references/client.md` を含む）を読み、公開契約を確認してください。
- 個人向けルートは常にサーバー認証から所有者を決定します。ブラウザーからの `userId` 上書きや、業務ロジックを通さずにタスクを書き込んだり完了にしたりする汎用 API は作らないでください。
- 業務変更とタスクインデックス更新は同じデータベーストランザクションでコミットし、内部の `userTasks` テーブルへ直接アクセスしないでください。
- `<TaskCenter />` の `sources` アダプターは表示専用であり、他ソースの行を除外しません。タイトルは受け取り手に見せてよい内容に限定し、詳細参照と処理実行は各業務ルートで認可してください。
- 通常の業務タスクはソース書き込み口で直接接続し、不要な承認段階を作ったりタスクセンターを承認に依存させたりしないでください。

### 検収のチェック

- **単独業務の通し確認**：承認を使わずタスクセンターと業務モジュールだけで未処理タスクを作成し、担当ユーザーで一覧・カテゴリ・ヘッダー件数を確認したあと、認可された業務 API で完了処理を行い、完了済みへの移動と件数更新を確認する。
- **トランザクションと冪等性**：業務トランザクションのロールバック時にタスクが残らないこと、同一内容の再書き込みで ID と作成時刻が維持されること、担当者変更時に `listBySourceKey` で正しく整合することを確認する。
- **分離とエラー経路**：未認証の `/api/userTasks*` が `401`、`userId` 指定や空配列フィルターが `400`、他人または存在しない ID が `404` になること、サインアウトやアカウント切替後に前ユーザーのキャッシュが残らないことを確認する。
- **範囲の一致**：ダッシュボードカードや独自データソースで一覧と統計の `sourceType`・`subject` が一致していること、現在実行可能な操作がない未処理項目に誤ったボタンを出さないことを確認する。
