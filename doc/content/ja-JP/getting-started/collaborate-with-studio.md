Studio は要件、エージェントの実行、成果をプロジェクトとタスクにまとめ、チームで開発を進められるようにします。

## Studio を使う理由

### 個人の会話からチームで共有するタスクへ

要件と結果が個人の会話に残っていると、他のメンバーは進捗を人づてに確認することになります。Studio のタスクには要件、責任者、コードの変更、チェック結果がまとまり、業務担当者と開発者が同じ場所でルールの補足、進捗確認、検収を行えます。

### エージェントが開発とチェックを分担する

コーディネーターエージェントが設計、開発、テスト、独立したレビューを実行エージェントに割り振り、問題があれば修正を手配します。引き継ぎと結果はタスクに残るため、人が毎回中継する必要はありません。複数のタスクは別々のブランチで並行して進められます。詳細は[エージェントの実行ルール](../studio/reference/agent-execution.md)を参照してください。

### 判断、検収、プロジェクトの知識を人が管理する

業務ルールの決定と結果の検収は人が行い、コーディネーターエージェントが代わりに PR をマージすることはありません。業務資料はナレッジベースに、合意したルールや設計上の判断はプロジェクトメモリに保存し、次の要件や担当者、エージェントへの引き継ぎに使えます。

## Studio に接続する

### 既存のチームに参加する

[招待を受けてサインイン](../studio/join/sign-in.md)し、管理者が準備したプロジェクトを開きます。先にローカルでアプリを作成する必要はありません。

### チームの環境とプロジェクトを準備する

Studio は商用版で提供されます。管理者は[インストールと設定](../studio/setup/index.md)に従い、利用許可を取得してサービスをデプロイし、Git とエージェントを接続して、プロジェクトとメンバーを準備します。

以下では仕入先ページを追加します。開始前に次を確認してください。

- プロジェクトの **Initialize project** タスクが完了していること。
- コーディネーターエージェントが設定され、少なくとも 1 つのランタイムがオンラインであること。
- リポジトリに[チェックの取得元](../studio/setup/ci.md)が設定されていること。アプリを試す場合は、プレビューまたはテスト環境を用意します。

## 要件を提出して計画を確認する

プロジェクトで **New issue** を選び、目的と確認方法を説明します。例：

```prompt
仕入先の名前、担当者、電話番号、取引状態を管理するページを追加してください。購買担当者が仕入先を追加・編集・閲覧できるようにします。

仕入先を追加し、取引状態を停止中に変更し、状態で一覧を絞り込めることを確認したいです。
```

エージェントが不足するルールを確認し、タスクを作成します。内容を確認して **Start** を選びます。**Fill in manually** で直接作成することもできます。

![会話で目的と業務ルールを定める](https://static-docs.nocobase.com/studio-en-guide-new-task-20261031.png)

タスクは **In progress** になり、コーディネーターエージェントが設計、開発、レビューを手配します。

開始前に、仕入先の状態の種類、購買担当者が操作できる仕入先の範囲、「一時停止」が取引状態だけを変更するのかを確認します。未確定のルールはエージェントと相談し、合意した内容をタスクに残します。購買規定や項目定義はタスクまたは[ナレッジベース](../studio/project/knowledge-base.md)に添付し、設計とレビューに使えるようにします。

## 開発、チェック、レビューを追う

タスク上部に、作業中のエージェント、ランタイム、次のステップが表示されます。**Activity** に引き継ぎ、返信、レビュー結果が残り、**Runs** で実行の詳細を確認できます。

![現在のステップと次の作業を確認する](https://static-docs.nocobase.com/studio-en-guide-task-progress-20261031.png)

コーディネーターエージェントは変更に応じて設計と実装を割り振ります。実行エージェントはタスクのブランチでコードを変更し、PR（プルリクエスト）を作成します。チェックとレビューも同じタスクに紐づきます。失敗や指摘があれば修正し、再チェックとレビューを経て検収に進みます。

たとえば、仕入先の状態で絞り込んでも別の状態のレコードが表示される場合は、修正と検証が必要です。納品レポートでは、実際のチェック結果と未検証の項目を確認してください。「進行中」は、すべての業務動作が検証済みであることを意味しません。仕組みは[チェックとレビュー](../studio/project/checks-and-review.md)を参照してください。

## 質問に答えて結果を検収する

業務上の判断が必要になると、タスクは **Blocked** になり、**My issues › Waiting for you** に表示されます。**Needs you** のカードでルールや不足情報を回答すると、コーディネーターエージェントが続行します。

チェックやプレビューが未設定の場合は、管理者に[チェックと CI](../studio/configure/checks.md)の設定を依頼してください。

タスクが **In review** になったら：

1. 引き渡しレポートで変更、検証、残る問題を読みます。
2. **View changes** で PR を確認します。プレビューがあれば、受け入れシナリオを試します。
3. 要件を満たしていれば **Merge** を選び、対象ブランチと方法を確認します。
4. 修正が必要なら **Send back** で問題と期待する結果を伝えます。

![受け入れ基準と引き渡しレポートを照合する](https://static-docs.nocobase.com/studio-en-guide-accept-20261031.png)

タスクが **Done** になり、変更が既定ブランチに入れば開発完了です。テストとリリースの進捗は[リリース](../studio/release/overview.md)で確認できます。

## 変更をリリースして知識を蓄積する

コードのマージは本番公開の完了を意味しません。自動デプロイを設定したプロジェクトでは、CI からマージ済みコードをテスト環境へデプロイできます。未設定の場合はチームの手順に従います。責任者はリリースに含めるタスクを確認し、本番へのデプロイ後に Studio へ本番バージョンを記録します。操作は[リリース管理](../studio/release/overview.md)を参照してください。

合意した購買ルールや設計上の判断は[プロジェクトメモリ](../studio/project/project-memory.md)に残し、コードと一緒にレビューしてマージできます。購買規定などの原資料はナレッジベースに保存します。後から仕入先機能を変更する際にも、エージェントはこれらの背景を参照できます。

以降の判断や検収は[マイタスク](../studio/use/my-tasks.md)で処理します。チームの設定、プロジェクト管理、各種リファレンスへの進み方は[学習の進め方](learning-path.md)を参照してください。
