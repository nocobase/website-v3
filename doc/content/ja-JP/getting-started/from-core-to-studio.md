NocoBase 3 で実際の業務システムを開発するとき、初日から重いチーム開発プロセスを整える必要はなく、軽く始めてもあとから作り直すコストはかかりません。おすすめの進め方は **2 段階のリレー方式**です。**まずローカルの Coding Agent と Core で素早く MVP を作り、現場試用でフィードバックが集まり始めたら同じリポジトリを移行コストゼロで Studio に接続し、並行改善と品質管理へ切り替えます。**

## 実際のプロジェクト事例から見る

最初に、ある大手製造企業で実際のシステムがどのように立ち上がったかを見てみます。対象は 400 以上の設定パラメータ、各国の規格、商取引条件を扱う複雑な海外向け見積もりシステムでした。

- **最初の 3 日間（業務ヒアリング）**：プロダクトマネージャーが現場の営業・提案担当へヒアリングを重ね、主要パラメータ、見積もりロジック、初版スコープを整理。
- **次の 1 週間（ローカル Coding Agent + Core で MVP 作成）**：開発者が自分の PC で Coding Agent と NocoBase Core を使って動く最小限のバージョン（MVP）を構築。権限・認証・ワークフローなどの基盤を再利用し、画面を見せながらプロダクト担当と高頻度ですり合わせて形を確定。
- **MVP 完成後（プレビュー試用と Studio 接続）**：プレビュー環境を公開して現場メンバーに試用してもらうと要望が一気に集まり始め、同じ Git リポジトリを移行コストゼロで NocoBase Studio に接続。
- **さらに 1 週間（並行改善と本番稼働）**：Studio がエージェントチームを編成して数百件の現場フィードバックを並行処理し、自動チェック・クロスレビュー・検収を経て初版を本番稼働。
- **その後約 2 か月（継続進化）**：同じ Studio のリズムで並行開発を続け、商談、提案、見積もり、受注、ダッシュボード、資料ライブラリ、AI アシスタントなど 10 以上の業務モジュールへ拡張。

実際の期間は業務の複雑さによって変わります。小規模な社内ツールであれば 1 日でフェーズ 1 を終えることもあり、大規模な基幹系はモジュール単位で段階的に進められます。以下では、この 2 段階の進め方を具体的に解説します。

## フェーズ 1：Core で MVP を素早く作る

プロジェクトの立ち上げ期は方向性が最も変わりやすく、高頻度なすり合わせが重要です。この段階ではプロセスを重くするよりも、中核業務を最短で動かせる状態にすることを優先します。

### Coding Agent に任せる前に業務を整理する

AI はコードを素早く書ける反面、業務の境界が曖昧なまま始めると手戻りも高速に膨らみます。最初のコードを書く前に、次の 4 点を整理しておきます。

- 扱う主要な業務データと相互の関係
- 重要な業務ルールとステータス遷移
- 利用するロールと、それぞれの閲覧・操作範囲
- 初版に含める機能と、後回しにする機能

これらを短い設計ドキュメントにまとめておくと（進め方は[まずシステム設計ドキュメントを書く](../guides/write-a-design-doc.md)を参照）、以降の Coding Agent との会話すべてに共通の基準ができます。

### ローカルで Core を使って素早く形にする

開発者が自分のコンピューター上で、普段使っている Claude Code、Codex、Cursor などを使い、NocoBase Core の既定テンプレートからアプリを作成して MVP を構築します（手順は[Core で最初のアプリを開発する](develop-your-first-app.md)を参照）。

- **基盤を再利用して業務に集中する**：ユーザー、権限、ログイン認証、データベース、ワークフロー、承認など 30 以上の共通機能がすぐに使えるため、Coding Agent は自社固有の業務実装に専念できます。
- **動く画面を見ながら素早く合意する**：ローカルで対話しながら改修し、動く画面や API をプロダクト担当者・業務担当者とその場で確認できるため、チケット起票や伝言の待ち時間を省けます。
- **初日からアーキテクチャをそろえる**：試作のようなスピードで進めても、Core が統一されたディレクトリ構成、開発規約、パッケージ同梱の Skill を提供するため、使い捨てのデモではなくそのまま本番へ育てられる標準アプリになります。

## Studio に切り替えるタイミング

MVP が動くようになったら、テスト環境やプレビュー環境へデプロイし（[デプロイ方法を選ぶ](../core/deployment/choose-a-deployment-method.md)を参照）、一部の現場メンバーに実際に試してもらいます。ここで明確な転換点が訪れます。

### 切り替えの目安

次のいずれかが当てはまり始めたら、個人での探索期からチームでの反復開発期へ移ったサインであり、Studio への切り替えに適しています。

- **フィードバックがまとまって届く**：現場試用から数十件〜数百件の改善要望が集まり、1 人のローカルセッションで順番に処理しきれなくなった。
- **複数人・複数モジュールを並行して進めたい**：複数の開発者や業務領域が同時に動くようになり、各自の端末で進捗や背景を追うのが難しくなった。
- **本番投入に向けて品質を守りたい**：機能追加で既存機能が壊れるのを防ぐため、自動チェック、別モデルによる独立レビュー、追跡可能な検収記録が必要になった。
- **業務担当者が直接参加したい**：開発者を介した伝言をやめ、業務責任者が自分で要件を出し、質問に答え、プレビューを確認して検収したい。

### 既存リポジトリを移行コストゼロで接続する

Core から Studio への切り替えに、コードの書き直しや構造変更は不要です。Studio が扱うのは Core で作成した同じ Git リポジトリであり、プロジェクト構成、Skill、動作の仕組みは完全に一致しています。

Studio を用意したら（ローカルでの試用は[Studio をインストールして使う](collaborate-with-studio.md)、チーム向け構築は[インストールの概要](../studio/setup/index.md)を参照）、新規プロジェクト作成時に既存リポジトリを初期化なしでひも付けるだけで、そのまま開発を引き継げます（手順は[プロジェクトを Studio に取り込む](../guides/bring-into-studio.md)を参照）。

## フェーズ 2：Studio で並行改善し継続的に育てる

Studio に接続すると、プロジェクトは個人のローカル開発から、チームで統制された継続デリバリーのリズムへ切り替わります。

### 複数タスクの並行推進とプロセスによる品質管理

- **複数タスクを並行処理する**：現場から集まった要望を個別のタスクに分け、コーディネーターエージェントが得意分野に応じてエージェントチームへ割り振り、独立したブランチで並行開発します。
- **プロセスとレビューで既存機能を守る**：すべての変更に自動チェックと別モデルによるクロスレビューを走らせ、納品レポートと操作可能なプレビューを添えて人の検収に回すことで（流れは[Studio をインストールして使う](collaborate-with-studio.md)を参照）、並行改修によるデグレードを防ぎます。
- **重要な判断は人が握る**：業務ルールの判断が必要なときはタスクが「あなたの対応待ち」で止まり、コードのマージとリリース判断は常に人が行います。

### 本番稼働後も同じリズムでモジュールを広げる

初版の検収が完了すれば本番環境へデプロイできます。リリース後の業務アプリは独立して稼働し、日々の業務リクエストが Studio を経由することはありません。

運用を続けながら合意済みの業務ルールや知見をナレッジベースとプロジェクトメモリーに蓄積していくことで、同じリズムのまま関連モジュールを並行して広げられ、新しく加わる担当者やエージェントもスムーズに引き継げます。

## なぜ先に Core を使い、あとから Studio に接続するのか

| 観点 | フェーズ 1：ローカル Coding Agent + Core | フェーズ 2：NocoBase Studio |
| --- | --- | --- |
| 主な目的 | 要件の境界を探り、動く MVP を最短で作る | 大量の並行要望をさばき、品質を守って本番投入・継続進化する |
| 進め方 | ローカルで対話しながら改修し、分単位ですり合わせる | タスク単位で並行ブランチ開発し、チェックとレビューを経て検収する |
| 主な関与者 | 業務・プロダクト担当者 + 開発者（ローカル Coding Agent） | 業務担当者 + 開発者 + 24 時間稼働のエージェントチーム |
| 強み | 立ち上げ負担ゼロで方向修正が速く、基盤がアーキテクチャを保つ | 高い並行処理力、自動チェックとレビューの防波堤、チームへの知見蓄積 |

## 2 段階を踏まなくてよいケース

多くの新規業務システムには 2 段階方式が合いますが、すべてのケースで必須ではありません。

- **Core 単体のまま運用する**：個人向けツール、小規模アプリ、1 人での低頻度な保守、またはすでに社内のレビュー・進行管理体制が整っている場合は、Core だけで開発から本番運用まで完結できます。
- **最初から Studio で始める**：すでにチームで Studio を運用している場合や、初日から業務部門の要望を標準プロセスで受け付けて新規プロジェクトを立ち上げたい場合は、Studio の[最初のプロジェクトを作成する](../studio/setup/new-project.md)から直接始められます（Studio が同じ Core 既定テンプレートでリポジトリを自動初期化します）。
