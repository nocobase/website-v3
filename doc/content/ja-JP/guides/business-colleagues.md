---
title: 業務担当者と協働する
metaDescription: 営業責任者が顧客引き継ぎの要望を出し、質問に回答して結果を受け入れます。
---

顧客の担当者を管理できる CRM を Studio に接続し、営業責任者 Morgan のアカウントとメンバー招待権限を用意します。Morgan は、担当変更の理由と履歴を残すよう Studio で依頼し、質問に答えて成果を受け入れます。

## 営業責任者を招待する

メンバー管理権限を持つ人が **Settings → Members → Invite members** を開き、Morgan のメールアドレスと CRM プロジェクトを指定します。[メンバー招待](../studio/setup/invite.md)に従って招待を送るかリンクを共有し、参加後にプロジェクトを開けることを確認します。

![CRM プロジェクトの Members にメンバーと責任者が表示されます。](/assets/guides/studio/members.png)

Studio のプロジェクト権限は開発への参加範囲を決め、CRM の営業責任者ロールは顧客へのアクセスを決めます。別々に設定する必要があり、Studio への参加では CRM の権限は付与されません。受け入れには CRM のテストアカウントを使います。

## 顧客引き継ぎを依頼する

Morgan は **My sessions** で会話を作り、チームの Agent と CRM プロジェクトを選びます。

```prompt
営業が異動するとき、顧客を別の営業に引き継ぎたいです。CRM では担当者を変更できますが、引き継ぎの理由、操作した人、日時も残したいです。新しい担当者が元の連絡先、フォロー履歴、商談、見積を引き続き見られるようにしてください。一般の営業が他人の顧客を自分に移すことは認めません。まずルールを相談してからタスクにしてください。
```

合意した内容をタスクにし、Morgan を担当者に設定して開始します。既存の担当者変更とアクセス制御に引き継ぎ記録を追加し、別の顧客所有モデルを作らないようにします。

![会話には議論が残り、右側で関連タスクの状態を確認できます。](/assets/guides/studio/session.png)

**ステップの確認**：Morgan が引き継ぎタスクを担当し、質問と受け入れ依頼を直接受け取れます。

## 顧客の担当とアクセス権を決める

元の担当者が引き続き閲覧できるかを聞かれたら、Morgan はタスク内で回答します。

```prompt
引き継ぎ後は新しい担当者が顧客と関連データを更新できます。元の担当者は担当者としてのアクセス権を失います。協力が必要なら責任者が別途読み取り専用で共有します。元のフォロー記録の作成者と見積履歴を残し、引き継ぎ記録も書き換えられないようにしてください。
```

これは[顧客のアクセス制御](team-permissions.md)を引き継ぐルールです。アクセス喪失を確認するときは、元の担当者に別の共有権限がないかを確認します。共有が残っていれば、閲覧できても引き継ぎの失敗とは限りません。決定をタスク説明にも記録します。

## 引き継ぎ結果を受け入れる

Morgan は交付レポートを読み、プレビューで責任者、Alex、Taylor の CRM アカウントを使います。

1. 責任者として、追加共有のない Alex の顧客を Taylor に移し、理由を記入します。
2. Taylor が顧客を更新でき、既存の連絡先、フォロー履歴、商談、保存済み見積を見られることを確認します。件数、金額、元の作成者は変わりません。
3. Alex の一覧、開いたままの詳細、ワークスペースを更新し、顧客を読めなくなったことを確認します。直接の API 呼び出しにも権限を適用します。
4. Alex が他人の顧客を自分に移したり、引き継ぎ記録を変更したりできないことを確認します。
5. 責任者が Alex に読み取り専用共有を設定すると、顧客と関連データを閲覧でき、更新はできません。

失敗したら、例えば「Alex が詳細を更新しても引き継ぎ済み顧客を編集できる。編集は禁止すべき」と Morgan が差し戻します。再交付後に確認し、合格してからマージします。[受け入れ](../studio/use/accept.md)を参照してください。

**完了の条件**：業務担当者が受け入れ、担当変更に従ってアクセスが変わり、業務データと引き継ぎ履歴が残っています。

依頼で決めたルールを記録するには、[開発方法と経験を蓄積](capture-knowledge.md)を参照してください。
