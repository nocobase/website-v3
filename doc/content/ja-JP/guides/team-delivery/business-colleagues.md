---
title: 業務担当者と協働する
metaDescription: 営業責任者が顧客引き継ぎの要望を出し、質問に回答して結果を受け入れます。
---

業務要件を人づてに伝えると細かなルールが抜け落ちやすく、受け入れ時の認識ずれも起きやすくなります。Studio では業務担当者が直接プロジェクトへ参加し、コードを書いたりローカル Agent を入れたりせずに、同じタスク内で要望起票・ルール決定・プレビュー検収まで進められます。

ここでは営業責任者 Morgan が CRM の顧客引き継ぎを依頼する流れを例に進めます。開始前に、Studio プロジェクト（またはサンプルプロジェクト [`nocobase/doc-demo-crm`](https://github.com/nocobase/doc-demo-crm) を[既存プロジェクトを接続する](open-crm-project.md)で接続したもの）、メンバー招待権限、および Morgan のメールアドレスを用意してください。

## 営業責任者を招待する

管理者が**左ナビゲーション下部のワークスペース設定（Settings › Members）**（プロジェクト内の設定タブではありません）を開き、**Invite members** から Morgan のメールアドレスと CRM プロジェクトを指定して招待を送信します。Morgan がすでにワークスペースアカウントを持っている場合は、CRM プロジェクト上部の **Members** タブから直接追加します（詳細は[メンバー招待](../../studio/setup/invite.md)）。

![参加後は CRM プロジェクトの Members タブでプロジェクトメンバーと責任者を確認できます。](/assets/guides/studio/members.png)

**ステップの確認**：Morgan がサインインして CRM プロジェクトを開け、プロジェクトの **Members** 一覧に表示されています。

## 顧客引き継ぎを依頼する

業務ルールが固まり切っていないときは、まずセッションで相談してからタスク化します。Morgan は左ナビゲーションの **My sessions** で新しいセッションを作成し、チームの Agent を選び、**最初のメッセージを送信する前に CRM プロジェクトを選択**してから入力します。

```prompt
営業が異動するとき、顧客を別の営業に引き継ぎたいです。CRM では担当者を変更できますが、既存の担当者管理の仕組みを活かしたまま、引き継ぎの理由、操作した人、日時も残したいです。新しい担当者が元の連絡先、フォロー履歴、商談、見積を引き続き見られるようにしてください。一般の営業が他人の顧客を自分に移すことは認めません。まずルールを相談してからタスクにしてください。
```

Agent の確認に回答してルールを確定したらタスク化を依頼し、タスクカードの担当者が Morgan であることを確認して **Start execution** をクリックすると **In progress** になります（プロフェッショナル版・エンタープライズ版の役割分担は[複数の担当者でタスクを進める](../../studio/use/multi-role-workflow.md)を参照）。

![会話には議論が残り、右側で関連タスクの状態を確認できます。](/assets/guides/studio/session.png)

**ステップの確認**：引き継ぎタスクが **In progress** になり、Morgan が担当者として質問と受け入れ依頼を直接受け取れる状態です。

## 顧客の担当とアクセス権を決める

開発中に業務判断が必要になると（元の担当者が引き続き閲覧できるかなど）、タスクは **Blocked** になって Morgan の **My issues › Waiting for you** に表示されます（セッション相談ですべて確定していれば、ここで停止せず進みます）。

Morgan はタスク上部の **Needs you** カードで **Reply** をクリックして回答します。

![ブロック中のタスク上部の「Needs you」カードに確認事項が表示され、「Reply」から回答できます（画面はサンプルプロジェクトの例です）。](https://static-docs.nocobase.com/studio-en-req-blocked-20261111-normal-2x.webp)

```prompt
引き継ぎ後は新しい担当者が顧客と関連データを更新できます。元の担当者は担当者としてのアクセス権を失います。協力が必要なら責任者が別途読み取り専用で共有します。元のフォロー記録の作成者と見積履歴を残し、引き継ぎ記録も書き換えられないようにしてください。
```

送信するとタスクは自動的に **In progress** へ戻ります。これは[顧客のアクセス制御](../core-capabilities/roles-and-permissions.md)を引き継ぐルールです。アクセス喪失を検証する前に、元の担当者へ別の共有権限が残っていないか確認します。

## 引き継ぎ結果を受け入れる

タスクが **In review** になったら、Morgan は **My issues › Waiting for you** からタスクを開き、**引き渡しレポート**を読んだうえで **Code & previews** から PR プレビューを開きます。CRM の責任者、営業 Alex、営業 Taylor の 3 つの独立テストアカウントで順に確認します。

1. 責任者として、追加共有のない Alex の顧客を Taylor に移し、理由を記入します。
2. Taylor が顧客を更新でき、既存の連絡先、フォロー履歴、商談、保存済み見積を見られることを確認します。件数、金額、元の作成者は変わりません。
3. Alex の一覧、開いたままの詳細、ワークスペースを更新して読めなくなったことを確認します。あわせて **引き渡しレポート** の権限テストとレビュー記録で、直接 API 呼び出しも拒否されていることを確認します。
4. Alex が他人の顧客を自分に移したり、引き継ぎ記録を変更したりできないことを確認します。
5. 責任者が Alex に読み取り専用共有を設定すると、閲覧のみ可能で更新はできません。

問題があれば **Send back** で現象と期待動作（例：「Alex が詳細を更新しても引き継ぎ済み顧客を編集できる。編集は禁止すべき」）を返します。すべて合格したら **Merge** をクリックし、PR マージ後にタスクが **Done** になることを確認します（[受け入れ](../../studio/use/accept.md)を参照）。

**完了の条件**：業務担当者が受け入れてマージされタスクが **Done** になり、担当変更に従ってアクセスが変わり、業務データと引き継ぎ履歴が残っています。

## まとめと次のステップ

要件の起票からルール判断、プレビューでの検収までを業務担当者自身が 1 つのタスクで完結させたことで、伝言による認識ずれを防ぎつつ、マージ前に権限と履歴の境界を確認できました。

次は[知識と経験を蓄積する](capture-knowledge.md)に進み、今回の依頼で確定した業務ルールと確認手順をナレッジベース、スキル、プロジェクト記憶へ整理しましょう。
