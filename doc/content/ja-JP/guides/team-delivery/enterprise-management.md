複数メンバーや Agent が並行開発すると、個別の PR チェックを通過してもマージ後に権限漏れ、性能劣化、主要フローのデグレが起きることがあります。ここでは見積バージョン比較と顧客引き継ぎをマージして `v1.1.0` の公開を控える CRM を想定し（自分のアプリでは現在のリリース待ち機能に置き換えてください）、リリース前の品質確認を一通り実践します。

始める前に、**Studio Enterprise Edition（EE）**、リリース待ちタスクのある接続済みプロジェクト、有効なプロジェクト責任者、利用可能な Agent とオンライン実行環境、および CRM テストデータ内の独立ロールアカウント（責任者 Morgan、営業 Alex・Taylor など）を用意してください。全体像と権限は[品質の概要](../../studio/quality/overview.md)を参照してください。

## CRM 向けに継続テストとプロジェクト基準を設計する

新規プロジェクトでは自動テストは既定で無効です。開発ペースに合わせて日常の軽量チェックとリリース前の網羅チェックを分けます。

### 開発リズムに合わせて 3 種類のテストを組み合わせる

**左ナビゲーションの「Development › Quality」**（プロジェクト上部タブではありません）を開き、CRM プロジェクトを選んで **Settings** に切り替え、次を設定して保存します（各項目の詳細は[品質設定](../../studio/quality/settings.md)）。

| テストの種類 | CRM での推奨トリガー | 評価項目 | 役割 |
| --- | --- | --- | --- |
| Daily | 毎日定時、完了済みタスクが 3 件以上で実行 | Functional、Permissions、Code quality | 日常マージによるデグレ、権限漏れ、品質低下を早期検出 |
| Release | リリース前に手動実行（またはリリース待ち蓄積で自動実行） | 全 5 項目 | Security と Performance を補完しリリース候補を一括検証 |
| Project | 毎週定時で実行 | Functional、Permissions | コアシナリオ全体を回帰検証し、不足や古いシナリオを自動更新 |

![Quality › Settings でトリガー、テスト種類ごとの評価項目、Skill を設定します（画面はサンプルプロジェクトの例で、実際のプロジェクト名やデータは CRM に応じて異なります）。](https://static-docs.nocobase.com/studio-en-quality-settings-20261111-normal-2x.webp)

定期テストは**プロジェクト責任者**の権限で実行されるため、有効化前に有効な責任者が設定されていることを確認します。

### CRM の業務特性に合わせて既定の基準を調整する

既定指標としきい値は[品質基準](../../studio/quality/standards.md)にあります。正当な業務上の例外（例：見積比較 API の P95 を 800 ms まで緩和しつつ 1 リクエストの SQL 数は 20 本以下を維持）がある場合は、**Quality › Settings** で Performance に紐付く Skill を確認し、**Agent management › Skills** で `budgets.json` を編集して新しいバージョンを保存します（以後のテストから適用。詳細は[プロジェクトの基準を調整する](../../studio/quality/settings.md#プロジェクトの基準を調整する)）。

## CRM コアシナリオの網羅範囲を確認する

**Quality › Core scenarios** をモジュールごとに点検します。コアシナリオは開発タスクと Project テストで `.nb-studio/scenarios/` に自動維持されるため、手動管理は不要です（[コアシナリオ](../../studio/quality/settings.md#scenarios)）。

リリース前に重要な業務ルールが含まれているか確認します。

- 顧客引き継ぎ後、元の担当者は顧客と連絡先・商談・見積へのアクセス権を直ちに失うこと。
- 責任者が明示的に読み取り専用共有を設定した場合に限り、閲覧のみ可能であること。
- カタログ単価を変更しても提出済み過去見積の単価と合計金額は変わらず、新しい下書きのみ最新単価を使うこと。

不足があればタスクで Agent に追加を依頼し、PR をマージして反映します。

```prompt
CRM のコアシナリオを確認し、「顧客引き継ぎ後、元の担当者は関連見積へのアクセスを失い、責任者が読み取り専用共有を設定した場合のみ閲覧できる」というルールを追加してください。コードと一緒にレビューへ出してください。
```

**ステップの確認**：重要な業務ルールがコアシナリオに含まれ、コードとともにリポジトリで管理されています。

## リリース前に Release テストを実行する

**Development › Quality** で CRM プロジェクトを選び、**Run test › Release** で開始します。作成されたテストタスクの進捗は **Quality › Testing issues** で確認でき、完了すると **In review** に移ります（[テストの実行](../../studio/quality/runs.md)）。

実行中は次の 2 点に留意します。

- **独立した実行環境**：各評価項目は実行環境上に独立環境とデータを用意して並行実測し、製品コードや稼働中の環境に影響しません。
- **本来の条件でブロック解消**：テストアカウント不足やルール不明で停止したら、アカウントを補ってテストタスク上で[質問に回答する](../../studio/use/answer.md)で再開します。テスト営業アカウントに管理者権限を付けないでください。

## 納品レポートを確認してフォローアップを振り分ける

テストタスクが **In review** になったら、**Quality › Testing issues** で納品レポートと各評価項目の証拠を確認します（[テストレポート](../../studio/quality/reports.md)）。ここでは 3 種類の典型的な結果が出たと想定します。

| 評価項目 | 結論 | 実測結果の例 | 自動登録されるフォローアップ |
| --- | --- | --- | --- |
| Permissions | 問題あり | Alex が顧客を引き継いだ後、一覧からは消えたが見積比較 API を直接呼ぶと過去見積が返る（読み取り越権 > 0） | 不具合 |
| Performance | 問題あり | 複数明細の見積比較で N+1 クエリが発生し、1 リクエストあたりの SQL 本数が上限超過 | 性能改善 |
| Functional | 一部未検証 | 価格改定後の過去見積サンプル不足で履歴スナップショットが未検証。読み取り専用共有時の見積比較可否も未定義 | テストデータ、確認事項 |

![品質の概要で各評価項目の結論、受け入れ待ちの案内、フォローアップへの導線を確認できます（画面はサンプルプロジェクトの例です）。](https://static-docs.nocobase.com/studio-en-quality-sample-20261111-normal-2x.webp)

### テストの受け入れと不具合修正を区別する

範囲と証拠に漏れがなくフォローアップが紐付いていれば、テストタスクで **Accept** をクリックします。不足があれば **Send back** で差し戻します。

> [!NOTE]
> **テストタスクの受け入れは結論を認めること**であり、修正完了や出荷承認ではありません。**「一部未検証」も合格ではありません**。

### リリースへの影響度に応じてフォローアップを振り分ける

**Quality › Follow-ups**（[フォローアップタスク](../../studio/quality/reports.md#follow-ups)）を開きます。フォローアップは既定で **Backlog** のため、担当者を割り当てて **Start** をクリックすると通常の修正・レビューへ進みます。

1. **リリースを止める項目（不具合）**：読み取り越権は権限のレッドラインです。開発担当者を割り当てて **Start** し、マージまでリリースを止めます。
2. **仕様確定とテストデータ補充（確認事項、テストデータ）**：「確認事項」を Morgan に割り当てて仕様を確定し、「テストデータ」も開始して過去見積サンプルを補います。

```prompt
元の担当者が読み取り専用共有を受けた場合は、対象顧客の見積バージョン比較を閲覧できるようにしてください。ただし新しい下書きの作成、明細の編集、レコードの変更は不可とします。このルールに合わせて権限チェックとコアシナリオを更新してください。
```

3. **影響度に応じた計画（性能改善）**：高頻度画面の N+1 クエリは今回で修正し、軽微なコード整理は次期イテレーションへ回します。

![Quality › Follow-ups で種類・評価項目・状態ごとに絞り込み、元のテストや検出回数を追跡できます（画面はサンプルプロジェクトの例です）。](https://static-docs.nocobase.com/studio-en-quality-follow-ups-20261111-normal-2x.webp)

## 修正後に再テストしてリリース条件を満たす

**フォローアップを閉じても過去のレポートは書き換わりません**。新しいテストで修正を確認します。

1. **個別確認**：ブロッカー修正のマージ直後に **Development › Quality** で **Run test › Custom** を開き、影響する Permissions や Performance だけを選んで素早く確認します。
2. **最終確認**：全ブロッカーとテストデータ補充がマージされたら **Release** テストを再実行し、該当項目が **合格** になったことを確認します。

![Custom テストで対象範囲と影響する評価項目だけを選び、個別修正を素早く再検証できます。](https://static-docs.nocobase.com/studio-en-quality-new-20261111-normal-2x.webp)

最後に **Quality › Metrics**（[指標と推移](../../studio/quality/reports.md#metrics)）で **Release** の推移を比較し、権限違反 `0`、性能が予算内、未検証が解消されたことを確認します。

**完了の条件**：CRM に継続テストとプロジェクト基準が設定され、重要ルールがコアシナリオに入り、リリース前の課題が修正と再テストで合格しています。

## まとめと次のステップ

これで CRM プロジェクトに階層的な継続テスト、業務要件に沿った基準、検証済みのコアシナリオが整い、リリース前のブロッカーと未検証項目も再テストですべて解消できました。

Release テストに合格したら、[本番にリリースする](release.md)へ進み、検証済みの候補コミットをテスト環境へデプロイして `v1.1.0` を本番公開します。
