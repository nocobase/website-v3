すでに NocoBase Core ベースのコードリポジトリがあり、Studio で要件管理・Agent 開発・継続的デリバリーをまとめて進めたい場合は、アプリを作り直さずに既存リポジトリをそのまま接続できます。

ここでは既存の CRM リポジトリを例に進めます（試すだけなら [`nocobase/doc-demo-crm`](https://github.com/nocobase/doc-demo-crm) を Studio の Git 連携からアクセスできるアカウントへフォークして使えます）。開始前に、サインイン可能な Studio 作業環境を用意してください。

## 既存リポジトリを接続する

Studio が接続するのは Git リポジトリのみであり、稼働中の本番サーバーや本番データベースには接続・変更しません。

ローカルの CRM リポジトリディレクトリで、Studio に接続済みのローカル Coding Agent へ直接依頼します（接続手順は[ローカル Coding Agent で Studio を使う](../../studio/join/local-agent.md)）。

```prompt
この CRM リポジトリを Studio に接続して、CRM という名前のプロジェクトを作成してください。既存コードはそのまま残し、初期化しないでください。完了したらプロジェクトの URL を教えてください。
```

Studio の画面から手動で作成することもできます。左ナビゲーションの **Development › Projects** で **New project** をクリックし、**Existing repository** と **Do not initialize** を選んで **Create** をクリックします（初期化タスクは走らず、そのままプロジェクト画面が開きます。詳細は[プロジェクト設定](../../studio/project/settings.md#既存リポジトリを接続する)）。

プロジェクト上部の **Settings › Code repositories**（左サイドバー下部のワークスペース設定ではありません）を開き、リポジトリ URL と **Default branch** を確認します。既存の `AGENTS.md`、カスタム Skills、要件ドキュメントはリポジトリに残したまま Agent が読み込めます。開発・テスト用シークレットはプロジェクトの **Settings › Agent run variables** へ、プレビューやテストアプリ自身の実行時設定（テスト用 DB 接続など）は[ホスト環境](../../studio/admin/environments.md)へ置きます。

![CRM のリポジトリ設定にはデフォルトブランチ、チェック、ブランチルール、バージョン系列、プレビューがまとまっています。](/assets/guides/studio/repositories.png)

**ステップの確認**：対象リポジトリと意図したデフォルトブランチが接続され、既存コードや規約ファイルが上書きされていません。

## チェックと分離プレビューを設定する

### チェック元を選んで設定する

新しく接続したリポジトリは既定で **Agent self-check** が有効なため、そのまま使い始められます。独立した CI パイプラインを使う場合は、プロジェクトの **Settings › Code repositories** で **Checks** 行の **Edit** をクリックします。

| チェック元 | 向いている状況 | 基本の流れ |
| --- | --- | --- |
| **Agent self-check**（既定） | パイプライン管理なしで素早く始める | 既定で有効。実行 Agent がスクリプトを実行して PR プレビューを公開 |
| **コードプラットフォーム CI**（GitHub Actions など） | Agent から独立した統一環境で検証する | プラットフォームとトリガーを選び、プロンプトをローカル Agent に渡して CI PR をマージ |
| **External CI**（Jenkins など） | 既存の外部 CI 基盤を再利用する | リポジトリ用 CI キーを発行し、既存パイプラインから結果報告とプレビュー公開を実行 |

**GitHub Actions** の例：**GitHub Actions** を選び、**Trigger** を **Pull request**、**Environment** を **Preview**、**Directory** を `.`（ルート）に設定します。**Show prompt** でプロンプトをコピーしてから **Save** をクリックし、ローカル Coding Agent に渡してワークフローと `NB_STUDIO_API_KEY` シークレットの PR を作成・マージします。詳細は[チェックとプレビューの設定](../../studio/setup/ci.md)と[リポジトリチェックと CI の設定](../../studio/configure/checks.md)を参照してください。

![Checks パネルでチェック元、トリガー、アプリのディレクトリ、プレビュー環境を設定します。](/assets/guides/studio/checks.png)

採用されるのは現在選択中のチェック元の結果のみで、設定後はタスクの **Code & previews** にチェック状態、ログ、PR プレビューリンクが集約されます。

### プレビューの分離とランタイム要件を確認する

- **プレビューデータの分離**：PR プレビューは初回デプロイ時にサンプルデータを読み込み、本番データは含みません（[PR プレビュー](../../studio/release/previews.md)）。[ホスト環境](../../studio/admin/environments.md)のプレビュー設定に本番 DB 情報を入れないでください。外部テスト DB や必須環境変数が必要な場合は、プレビュー環境またはアプリの **Variables** にテスト用設定を補います。
- **ランタイムの依存条件**：オンラインのランタイムで依存インストールとテスト実行ができることを確認します。

**ステップの確認**：チェック元が保存され（CI 利用時はワークフローをデフォルトブランチへマージ済み）、プレビューデータが本番から分離されています。

## 小さな変更で最初の PR を通す

### タスクを作成し、検収待ちまで進める

まず小さな変更で一連の流れを検証します。プロジェクト画面右上の **New issue** をクリックし、依頼を入力します（自分のアプリの場合は画面と文言を置き換えてください）。

```prompt
顧客一覧の上部に、営業担当者は自分が担当する顧客と共有された顧客のみ閲覧できる旨の短い案内文を追加してください。既存の画面レイアウト、絞り込み操作、権限ルールは変更せず、完了後に顧客一覧の上部で案内文を確認できるようにしてください。
```

Agent が整理したタスクカードを確認して **Start execution** をクリックします（手動入力も可能。詳細は[リクエストを作成する](../../studio/use/raise-a-request.md)）。タスクが **In progress** になり実装・チェック・独立レビューが進みます。途中で確認が入ったら **My issues › Waiting for you** から回答し、**In review** と **引き渡しレポート** の生成を待ちます。

### 成果を確認して PR をマージする

**In review** のタスクを開き、**引き渡しレポート**を読んだうえで次の 3 点を確認します。

1. **既存規約の遵守**：**View changes** で PR 差分を確認し、既存の `AGENTS.md` や規約に従っていることを確かめます。
2. **最新コミットのチェック結果**：**Code & previews** で最新コミットに対するチェック結果を確認します（トラブル時は [PR チェックとコードレビュー](../../studio/project/checks-and-review.md)）。
3. **分離プレビューと回帰確認**：PR プレビューを開き（初期管理者認証情報はタスク画面に表示）、テストアカウントで新しい案内文と主要画面・権限範囲を確認します。

問題があれば **Send back** で現象と期待動作を伝えて修正させます。問題なければ **Merge** をクリックして対象ブランチを確認します（複数担当者フローは[タスクを検収する](../../studio/use/accept.md)を参照）。PR マージ後にタスクは自動的に **Done** になり、PR プレビューも削除されます。

**完了の条件**：既存リポジトリが接続され、チェックと分離プレビューが機能し、最初の小さな PR をマージして既存規約と本番に影響が出ていません。

## まとめと次のステップ

既存プロジェクトを接続して最初の PR を通したことで、以降の改修をブランチ分離・自動チェック・レビュー・プレビュー検収の流れに乗せて進める基盤が整いました。

次は[業務担当者と協働する](business-colleagues.md)に進み、業務側からの要望起票・ルール確認・プレビュー検収も同じ Studio プロジェクトへ統合してみましょう。
