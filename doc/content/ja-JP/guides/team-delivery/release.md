---
title: 本番にリリースする
metaDescription: CRM の変更をテスト環境で確認し、リリース範囲を照合して本番を更新し、実際のバージョンを記録します。
---

変更をデフォルトブランチへマージしただけでは、安全に本番公開できる状態とは言えません。ここでは見積バージョン比較と顧客引き継ぎを含む CRM の候補リリースを想定し（自分のアプリでは現在のリリース待ち機能に置き換えてください）、テスト環境での検証、tag 作成と成果物確認、バックアップ付きの本番更新とバージョン記録を進めます。

開始前に、マージ済みコミットのある接続済みプロジェクト、Studio の[ホスト環境](../../studio/admin/environments.md)で用意したテスト環境、自社の本番サーバーおよびリリース権限を用意してください。

Studio の **Releases** は、PR を確認する **Preview**、マージ後を確認する **Staging**、Git tag と成果物を管理する **Release**、チームが確認した本番バージョンを記録する **Production** の 4 段階に分かれています。Studio はプレビューとテスト環境をホストし、本番デプロイは自社のサーバーで実行します。

![CRM のリリース画面で四つの段階と未公開タスクの位置を確認します（画面はサンプルプロジェクトの例です）。](/assets/guides/studio/releases.png)

## テスト環境にデプロイして業務フローを確認する

CRM プロジェクトの **Releases** タブを開き、**Staging** カードの **Deployment guide** でアプリ ID（例：`crm-staging`）とテスト環境を指定します。**Copy prompt for your agent** をコピーしてローカルリポジトリの Coding Agent に渡すと自動でビルド・アップロードされます（マージごとに自動更新したい場合は **Connect CI** を使用。詳細は[チェックと CI](../../studio/configure/checks.md)）。

![テスト環境への指引は Agent、CI、手動コマンドに対応します。](/assets/guides/studio/staging-guide.png)

デプロイ後、下部の **Staging environments** タブで稼働中のコミット SHA を照合してテストアプリを開きます（必須環境変数が不足していればアプリの **Variables** タブで設定して再起動）。業務責任者（営業責任者 Morgan など）が独立したテストデータで新機能と主要業務フローを検証します。

**ステップの確認**：テスト環境が候補コミットで稼働し、新旧の主要フローが検証を通過しています。

## 公開待ちのタスクを確認する

下部の **Pending release** タブで、完了済みかつ本番に未交付のタスクを確認します。**In staging** はテスト環境に入り、**Not deployed yet** はまだ入っていません。公開予定のタスクが候補コミットに含まれるか確認し、**Done** だけでは判断しません。漏れがあればテスト環境を更新して再検証します。

## バージョンを公開する

初回リリース前に、プロジェクトの **Settings › Code repositories** で **Release lines** の **Edit** を開き、`v*` などの tag パターンを設定しておきます（詳細は[バージョンと公開](../../studio/release/versions.md)）。

準備できたら **Releases** ページの **Release** カードで **How to publish** をクリックします。

1. CRM リポジトリとバージョン系列、検証済みのテスト環境を選び、**Target commit** を照合します。
2. `v1.1.0` など未使用の tag を入力します。
3. **Included issues** と **Omitted issues** で公開範囲を確認します。
4. **Copy commands** をクリックし、ローカルの CRM リポジトリで `git fetch` してからコマンドを実行して tag を作成・push します。

![公開パネルで対象コミット、含むタスク、含まないタスク、tag のコマンドを確認します（画面はサンプルプロジェクトの例です）。](/assets/guides/studio/publish.png)

push 後、下部の **Releases** タブで Studio が tag を認識するのを待ち、デプロイ可能なアーカイブまたはイメージ成果物があることを確認します。**tag だけでは成果物になりません**：タグトリガー CI を設定済みなら自動でビルド・アップロードされ、未設定ならタグトリガー CI を追加するかローカル Coding Agent に該当 tag をチェックアウトさせて `pnpm build --tar` とアップロードを行います（[チェックと CI](../../studio/configure/checks.md)）。

**ステップの確認**：検証済みコミットを指すバージョンに意図したタスクが入り、デプロイ成果物が利用可能です。

## 本番を更新し、実行バージョンを記録する

**Production** カードの **Deployment guide** で `v1.1.0` とサーバーに合う **Docker** または **Installer** を選びます。サーバーにアクセスできる Coding Agent にプロンプトを渡し、次を添えます。

```prompt
このサーバーではすでに CRM が稼働しているためアップグレードとして扱ってください。更新前に本番データベースと永続化ファイルを必ずバックアップし、既存の設定と業務データを保ったまま更新し、完了後にログインと画面表示を確認してください。
```

手動手順・マイグレーション・ロールバックは[本番への交付](../../studio/project/release.md)を参照してください。更新後は本番環境でログイン、既存データ、新機能、権限境界を確認します。

検証に合格したら、権限を持つプロジェクト責任者が **Production** カードの **Record deployment**（またはガイド下部の記録）から `v1.1.0` を記録します。記録すると **Production** カードが更新され、含まれる完了済みタスクが **Pending release** から外れます（記録自体はデプロイを実行しません）。

**完了の条件**：本番と Studio の記録が一致し、対象タスクが **Pending release** から外れ、新機能が使えて既存データも保たれています。

## まとめと次のステップ

これで、既存リポジトリの接続、業務担当者との協働、知識と経験の蓄積、リリース品質の管理、本番リリースまで、Studio でのチーム開発サイクルを一通り完了しました。公開後のフィードバックや新しい要望もプロジェクトのタスクとして起票し、次のイテレーションへつなげられます。

目的に応じて次のドキュメントへ進んでください。

- **業務機能をさらに拡張する**：[テーマ別実践](../core-capabilities/index.md)から、データモデリング、権限、承認、ファイル、通知、メールなど必要な Core 機能を選んで実践します。
- **リリースと運用の仕組みを深める**：環境や成果物パイプラインの詳細は Studio の[リリース管理](../../studio/release/overview.md)、本番アップグレード・バックアップ・ロールバックの手順は Core の[アプリの新しいバージョンをリリースする](../../core/deployment/publish-app-release.md)を参照してください。
