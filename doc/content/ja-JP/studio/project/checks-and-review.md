エージェントの変更を 1 行ずつレビューする必要はありません。作業があなたの検収に届く前に、Studio は 2 つの関門を通します。リポジトリの CI チェックと、別のモデルによるコードレビューです。両方を通過して初めて、タスクは **In review** に移ります。

## チェック

チェックは、GitHub Actions や GitLab CI など、リポジトリ自身の CI で実行されます。lint、型チェック、テスト、ビルドなどです。Studio は各 PR のチェック結果を読み取り、タスクの **Code and deployments** セクションに表示します。

- **チェックが失敗する、またはコンフリクトが発生する**：Studio はコーディネーターエージェントを起動して修正を手配させます。よくある最初のステップは、エージェントに失敗ログを読ませ、変更が原因なのか偶発的なものなのかを判断させることです。
- **3 回連続のコミットでもチェックが失敗する**：Studio はそれについてエージェントを起動するのをやめ、タスク責任者に通知します。
- **必須のチェックがすべて通過する**：Studio はコーディネーターエージェントを起動し、レビューまたは引き渡しを手配させます。

プロジェクトにまだ CI がない場合、PR にはチェック結果がありません。引き渡しの前に、コーディネーターエージェントは CI なしで検収するかどうかをタスク責任者に尋ねます。タスクの説明で最初からそう伝えておくこともできます。CI の設定については、[CI を接続する](../setup/ci.md) を参照してください。

### 必須チェックと参考チェック

**Project settings › Branch rules** で、チェック名を 1 行に 1 つずつ入力すると、そのチェックを参考チェックにできます。

- **参考チェック**：失敗しても注記として表示されるだけです。エージェントを起動せず、Studio でのマージも止めません。不安定なチェックや、パフォーマンスベンチマークなど助言的なチェックに使います。
- **必須チェック**：それ以外のすべてのチェックです。失敗するとコーディネーターエージェントを起動し、Studio での通常のマージを止めます。

GitHub のブランチ保護ルールなど、コードホスト自体が求めるチェックとレビューは引き続き適用されます。コードホストがマージを許可しなければ、Studio でもマージできません。

### コーディネーターエージェントが起動するタイミング

**Project settings › Branch rules** には 3 つのスイッチがあります。

| スイッチ | オンのとき |
| --- | --- |
| Wake when checks fail | 必須のチェックが失敗すると、コーディネーターエージェントが修正を手配します |
| Wake when all checks pass | 必須のチェックがすべて通過すると、コーディネーターエージェントがレビューまたは引き渡しに進みます |
| Wake when the PR has a conflict | PR が対象ブランチとコンフリクトすると、コーディネーターエージェントが修正を手配します |

通常はオンのままにします。スイッチがオフの場合、その状況では人がタスクにコメントするまで、コーディネーターエージェントは作業を続けません。

## レビュー

チェックを通過すると、コーディネーターエージェントはコードを別のエージェントに渡してレビューさせます。

- できるだけ別ベンダーのエージェントを選びます。たとえば Claude が書いたコードを Codex がレビューします。オンラインのエージェントがいなければ、同じベンダーの別のモデルがレビューします。コードを書いたモデルが自分の作業をレビューすることはありません。
- レビューは組み込みの `studio-review` スキルに従います。欠陥、セキュリティ、設計がシンプルかどうか、テストとその CI コストを確認し、指摘の重要度を付け、どれがマージを止めるかを示します。
- レビューの指摘はコードを書いたエージェントに戻され、修正は再びレビューされます。
- レビューは別のコピーで行う読み取り専用のステップなので、ほかの作業と並行して実行できます。

チーム独自の基準でレビューさせるには、`studio-review` スキルを編集するか、チームのレビュースキルをプロジェクトに適用します。[スキル](skills.md) を参照してください。

## マージ時のチェック

タスク責任者が **Merge** をクリックすると、Studio はコードホストで PR とその結果をもう一度確認します。

| 状況 | マージできるか |
| --- | --- |
| PR にコンフリクトがある、下書きである、チェックが実行中 | できません。先に解決してください |
| 必須のチェックが失敗した、またはチェック結果がない | **Merge anyway** を選んで理由を入力できます。Studio は強制マージについてのコメントを PR に投稿し、タスクのアクティビティに記録します |
| コードホストのルールが許可していない | できません。コードホストの要件に従ってください |

エージェントは PR をマージできず、強制マージなどはなおさらできません。

> [!NOTE] コードホストで既定のブランチを保護する
> Studio はブランチを保護しません。GitHub や GitLab で既定のブランチの保護ルールをオンにし、たとえばマージ前にチェックの通過を必須にして、コードホストで直接マージされる場合にも同じ関門が適用されるようにしてください。
