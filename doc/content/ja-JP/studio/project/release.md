このページでは、Studio が管理するリリースの承認とバージョンのロールバックを説明します。デプロイ環境の設定と承認者の決定は、管理者が [デプロイ環境](../admin/environments.md) で行います。CI の接続については、[CI を接続する](../setup/ci.md) を参照してください。

## リリースの流れ

CI を接続した Supplier Management プロジェクトを例にします。

1. タスクが検収されて PR がマージされると、CI が既定のブランチをステージングにデプロイし、タスクに「Staging ✓ b64c3bd」と表示されます。
2. `v1.4.0` などのバージョンタグを作成すると、CI がそのバージョンをビルドして本番にデプロイします。
3. 本番は保護されているため、デプロイは承認者の受信トレイに届くデプロイリクエストになります。
4. 承認者が承認すると本番に反映され、タスクに「Production ✓ 1.4.0」と表示されます。

プロジェクトの概要の **Releases** には、各環境で動いているバージョン、その元になったコミット、デプロイした人と承認した人、承認待ちのリクエストが表示されます。

## 承認者が行うこと

デプロイリクエストは承認者の受信トレイの **To decide** に表示され、次の内容が含まれます。

- アプリと環境。
- デプロイするバージョンと、その元になったコミット。
- CI がビルドに使ったタグまたはブランチと、CI のログ。
- 開始したのはだれか：人、エージェント、CI のいずれか。

リクエストを開いて確認します。承認するには、確認のためにアプリ ID をもう一度入力すると、すぐにデプロイが始まります。デプロイされるのはリクエストに記載されたバージョンそのもので、あとから新しいバージョンが来ても置き換えられません。同意できない場合は、リクエストを却下します。

自分が開始したリクエストを自分で承認することはできません。エージェントはデプロイを承認することも、保護された環境に直接デプロイすることもできません。

> [!WARNING] デプロイの前にバックアップする
> Studio はデプロイの前にアプリのデータベースをバックアップしません。本番のデータベースは、定期的に `pg_dump` を実行したり、データベースサービス自体のバックアップを使ったりして、自分で定期的にバックアップしてください。

## ロールバックする

デプロイ後に問題が見つかった場合は、**Releases › Apps** でアプリを開き、履歴から以前の成功したデプロイを選んで、そのバージョンにロールバックします。保護された環境では、ロールバックも承認者向けのデプロイリクエストになります。

ロールバック後、Studio は各タスクの変更がまだ本番に反映されているかを確認します。

- デプロイされたバージョンに変更が含まれなくなったタスクは、デプロイの表示が取り下げられます。たとえば「Withdrawn with 1.3.0」です。
- 完了していたが変更がロールバックされたタスクについては、ロールバックした人に再オープンの提案が届きます。受け入れることも無視することもできます。

タスクのステータスが自動で変わることはありません。再オープンするかどうかは人が決めます。

## Merged, not released

プロジェクトの概要の **Merged, not released** には、完了しているが、変更がまだ本番に反映されていないタスクが一覧表示されます。こうしたタスクが完了するたびに、プロジェクトリーダーに通知されます。新しいバージョンのリリースを準備するときは、ここを見て今回のリリースに何が含まれるかを確認しましょう。
