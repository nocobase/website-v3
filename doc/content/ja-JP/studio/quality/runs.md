---
title: テストの実行と受け入れ
description: テストを実行し、証拠と納品を確認して、修正後に再検証します。
---

プロジェクトのリポジトリ、有効な Agent、オンラインのランタイムを準備します。自動テストには有効なプロジェクト責任者も必要です。実行者にはプロジェクト管理、タスク閲覧、添付ファイルのアップロード権限が必要です。

## 対象範囲を選ぶ

1. **Quality** でプロジェクトを選びます。
2. **Run test** から Release、Project、Custom を選びます。
3. Custom では完了済みタスク、またはプロジェクト全体のコードを選びます。必要に応じて評価項目を調整します。
4. 確認し、作成されたテストタスクを開きます。

Release は現在のリリース待ちタスクが対象です。対象が空の場合はテストを作成しません。Project とプロジェクト全体の Custom はコアシナリオを使います。

作成時に対象範囲と Skill のバージョンが固定されます。後から設定を変えても実行中のテストには反映されません。新しい範囲や基準を使う場合は別のテストを開始します。

![テストの対象範囲と評価項目を選択](https://static-docs.nocobase.com/studio-en-quality-new-20261111-normal-2x.webp)

## 進捗と阻害要因を確認する

![テストタスクと各評価項目の実行状況](https://static-docs.nocobase.com/studio-en-quality-runs-20261111-normal-2x.webp)

**Testing issues** または **My issues** からテストを開きます。評価項目ごとの進捗、経過時間、確認件数、不足情報が表示されます。

ランタイム、権限、テスト用アカウントが不足している場合は準備してからタスクに返信します。業務上の判断は責任者が行います。[質問への回答](../use/answer.md)を参照してください。

不要になったテストはキャンセルできます。記録は残り、未完了の評価項目はキャンセル済みになります。実行後は[レポートを確認して受け入れ](runs.md#reports)ます。

<h2 id="reports">レポートの確認と受け入れ</h2>

**Quality › Testing issues** からテストを開きます。納品レポートは通常のタスクと同じ手順で受け入れます。

![引き渡しレポートを確認し、受け入れまたは修正を依頼](https://static-docs.nocobase.com/studio-en-quality-report-20261111-normal-2x.webp)

### 結果と証拠

最初に対象範囲、コードのコミット、評価項目を確認します。各項目を開くと詳細レポートと添付ファイルを読めます。

以下はシナリオと確認項目の個別結果です。評価項目全体では問題ありや一部未検証も区別します。[評価項目の結論と個別の結果](metrics.md#評価項目の結論と個別の結果)を参照してください。

| 結果 | 意味 |
| --- | --- |
| Passed | 期待する動作を証拠で確認できた |
| Failed | 実際の動作が期待と異なる。問題と再現証拠を確認する |
| Unverified | 環境やアカウントなどが不足し、判断できない |
| Not applicable | この評価項目と無関係。成功にも失敗にも数えない |

各項目を開いて根拠を確認します。機能検証では自動テストとエージェントが操作したシナリオを区別します。性能は画面と API の測定結果をそれぞれ確認できます。権限の問題は、どのロールで何を操作し、どんな結果になったかを確認します。コードレビューの記録しかない場合は、そのロールでも動作を確かめます。

失敗の証拠、未検証の理由、関連するフォローアップを確認します。スクリーンショットだけでなく、期待する結果と実際の結果を明確にします。

![評価項目の詳細レポートとテスト証拠](https://static-docs.nocobase.com/studio-en-quality-dimension-20261111-normal-2x.webp)

### カバレッジを確認する

自動テスト、エージェントによる操作、未検証の項目を区別します。シナリオを開くと確認項目、実際の結果、証拠を確認できます。

既存の自動テストがシナリオを証明できる場合は再利用し、それ以外は実際に確認します。未検証の理由を残し、環境やデータの不足を補います。シナリオと自動テストの更新は開発で行います。[コアシナリオの管理](settings.md#scenarios)を参照してください。

### 受け入れまたは差し戻し

範囲が適切で、証拠を確認でき、発見事項の対応方針が決まっていれば、タスクから受け入れます。不足するシナリオや証拠があれば差し戻します。

テストケースやコアシナリオの更新は開発タスクで PR を提出し、業務上の修正と分けます。品質テストは発見事項と証拠を記録し、業務修正は[フォローアップタスク](runs.md#follow-ups)で扱います。テストの受け入れだけで修正タスクは完了しません。

<h2 id="follow-ups">フォローアップと再テスト</h2>

**Quality › Follow-ups** に、テストから生じた作業が集まります。通常のタスクと同じ責任者、議論、受け入れの手順を使います。

![フォローアップタスクと元のテストの関係](https://static-docs.nocobase.com/studio-en-quality-follow-ups-20261111-normal-2x.webp)

### フォローアップタスクを作成する

Agent は確認済みの不具合、業務上の確認事項、テストデータ不足、コード整理、性能改善、依存関係の修正を、元のテストと評価項目に関連する作業として登録します。原因ごとにまとめ、不足するデータを明記します。

自動テストとコアシナリオの追加は開発タスクで管理します。品質テストから追加用タスクを自動作成しません。シナリオの不足は機能レポートの更新が必要なシナリオの説明に記録し、要件の変更に合わせて開発で更新します。

| フォローアップ | 対応内容 |
| --- | --- |
| 不具合 | 機能、権限、セキュリティの確認済み問題を再現証拠とともに修正 |
| 確認事項 | 不明確な業務上の期待結果を人が決定 |
| テストデータ | 未検証の確認に必要なレコード、アカウントなどを補充 |
| コード整理 | 新しい複雑な関数、未使用コード、保守性の問題に対応 |
| 性能改善 | 予算超過を原因ごとにまとめて対応 |
| 依存関係の修正 | 脆弱性のあるパッケージごとに対応 |

期待結果、実際の現象、再現条件、証拠を確認し、責任者と優先度を決めます。同じ問題に未完了のタスクがある場合は再利用または関連付けます。

業務上の修正はフォローアップタスクで行います。テストタスクは発見事項と証拠を記録します。業務判断が必要な場合は該当タスクで回答します。

### 修正して再テストする

1. フォローアップタスクで修正を完了し、受け入れます。
2. 影響範囲を含む Project、Release、Custom テストを開始します。
3. 元のシナリオやタスクの新しい結果を確認します。

フォローアップを完了しても過去のテスト結果は変わりません。過去のレポートには当時の証拠が残り、後続のテストで修正後の動作を確認します。
