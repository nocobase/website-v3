症状、関連タスク、エラーをローカルのコーディングエージェントに伝えて調査を依頼できます。プロンプトにパスワードやトークンを含めないでください。Studio に接続したエージェントは `nb-studio` で状態を確認できます。

## インストールとサインイン

| 問題 | 確認すること |
| --- | --- |
| サインイン画面が出ない | `https://studio.example.com/main/` を使い、コンテナの正常性とリバースプロキシを確認 |
| 初期アカウントで入れない | 最初に設定した管理者のユーザー名とパスワードを確認。環境変数の変更では既存アカウントを再設定しない |
| コンテナが再起動を繰り返す | `docker compose logs --tail=100 studio` で設定、DB 接続、保存先の権限を確認 |
| CLI を承認してもログインできない | コマンドを実行したまま承認。期限切れなら新しいコードで再試行 |

[Studio のデプロイ](../setup/install.md)、パスワード再設定は[通知とプッシュ](../admin/notifications.md)を参照してください。

依頼者欄や **Quality** が見つからない場合は、利用中の [Studio のエディション](../setup/index.md#エディションを選ぶ)を確認してください。品質データの閲覧には対象プロジェクトへのアクセス権も必要です。

## Git 接続

GitHub がプライベートな Webhook URL を拒否する場合は、Webhook を無効にしてポーリングを使います。新しいリポジトリに接続できない場合は、GitHub App のインストール範囲を確認します。権限を付与してから[既存リポジトリ](../project/settings.md#既存リポジトリを接続する)として接続してください。

個人の Git アカウントが読み取り専用の場合は、PR をプッシュできません。書き込み権限を付けるか、チームの方針に従ってワークスペース接続を使います。[Git プラットフォーム](../configure/git.md)を参照してください。

### GitLab のリポジトリとパイプラインを調べる

| 症状 | 確認すること |
| --- | --- |
| グループが見つからず接続を保存できない | リポジトリ URL で GitLab の設置先パスとグループの綴りを確認する。トークンを発行したグループ、有効期限、`api` スコープも確認する |
| 接続済みでもチェックアウトで `HTTP Basic: Access denied` になる | 接続のリポジトリ一覧を展開し、プロジェクトが使う接続とクローン URL を確認する。個人の Git アカウントを使う場合は、そのアカウントのアクセス権限も確認する |
| タスクで `glab: command not found` と表示される | 実際にタスクを実行したマシンで、サービスの実行ユーザーとして `glab --version` とサービスの PATH を確認する |
| チェックの失敗はわかるがログが見えない | GitLab CI のチェックかを確認する。エージェントにそのタスク内で MR のパイプラインを調べてもらい、失敗したジョブの ID でログを開く。404 の場合はプロジェクトのパス、番号、実行時のアカウント権限を確認する |
| MR の手動関連付けで読み取りに失敗する | リポジトリのパスと MR 番号を確かめ、Studio の GitLab 接続に MR の読み取り権限があるか確認します。MR が存在しない場合や読み取れない場合、関連付けは保存されません。関連付けはできてもチェックが表示されない場合は、パイプラインの読み取り権限を確認します。 |

次は `inventory-team/warehouse` の MR 12 とジョブ 345 を調べる例です。実際のパスと番号に置き換えてください。

```bash
glab ci get --merge-request 12 -R inventory-team/warehouse
glab ci trace 345 -R inventory-team/warehouse
```

## ランタイムとタスク

| 症状 | 次の操作 |
| --- | --- |
| ランタイムがオフライン | マシンで `nocobase-runner status` を実行し、サービスとネットワークを確認 |
| ツールがない・未ログイン | サービスのシステムユーザーでインストール・サインインし、再検出 |
| ターミナルで使えるがサービスで使えない | 正しいターミナルで `nocobase-runner service install` を実行 |
| タスクが始まらない | 状態、先行タスク、初期化、待機理由を確認 |
| 多数の実行後に停止する | 実行上限と繰り返す失敗を調べてから続行 |
| ツールの利用枠を消費した | 利用枠の確認カードで、回復を待つかエージェント・ランタイムを変更します。未プッシュの変更は元のランタイムに残ります |

Backlog のタスクは **Start** で開始します。共有ランタイムが埋まっている間の待機は正常です。[進捗を追う](../use/follow-progress.md)を参照してください。

モデルが待機し続ける場合は、開発担当者が利用できるランタイムを確認します。対応するツールとモデルにサインイン済みで、空き枠のあるマシンがオンラインになっている必要があります。

Studio のエラー詳細にリクエスト ID が表示されたら、タスク番号、ランタイム、発生時刻とともに管理者に伝えます。管理者は該当時間帯の Studio とランタイムのログをエクスポートできます。GitLab CI のジョブログは GitLab で確認します。

## チェック、プレビュー、マージ

結果がない場合は、リポジトリで選択した取得元を確認します。コードプラットフォームの CI、外部 CI、セルフチェックの結果は合算しません。[リポジトリのチェックを設定する](../configure/checks.md)を参照してください。

プレビューがない場合は、ビルド記録、CI から Studio への接続、必須変数、`no-preview` ラベルを確認します。停止・休止したプレビューは、アクセスすると起動します。

競合、ドラフト状態、チェック待ちはマージ前に解消します。失敗・不足したチェックを無視して続けるには権限が必要で、コードプラットフォームの保護は回避できません。

マージ済み PR がタスクに反映されない場合は、同期を待ち、すべての関連 PR がマージされたか確認してください。

## メールとリリース

招待メールを送れない場合は、招待リンクをコピーします。招待とパスワード再設定は設定済みの mailer を使います。SMTP の認証情報と選択した mailer を[通知とプッシュ](../admin/notifications.md)で確認してください。

デプロイが承認待ちの場合は、環境の承認者に受信トレイでアプリと成果物を確認してもらいます。本番デプロイ後は、責任者が[バージョンを記録](../project/release.md#本番バージョンを記録する)するとリリースの表示が更新されます。
