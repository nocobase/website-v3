Studio での **リリース** とは、リポジトリにバージョンタグを付けることです。タグが付いたコミットが 1 つのバージョンになり、Studio はそれを自動で識別して、そのバージョンに含まれるタスクを算出します。バージョンをどこにデプロイするかは別の話です。テスト環境については [デプロイ環境](../admin/environments.md)、本番については [本番へのデプロイ](../project/release.md) を参照してください。

## リリースラインを設定する

リリースラインは、どのタグをバージョンとみなすかを定めます。**Project settings › Code repositories** で、リポジトリのリリースラインを見つけ、「変更」をクリックします。

- Studio はリポジトリの最近のタグを読み取り、繰り返し現れる接頭辞を見つけてリリースラインを提案します。選ぶだけで使えます。手動で追加することもできます。
- 形式は `*` で終わります。たとえば `v*`、`release-beta/*` です。名前に `beta` や `rc` を含むタグもバージョンとみなされます。
- 1 つのリポジトリに複数のリリースラインを持てますが、一致するタグが重なってはいけません。
- 表示時に接頭辞を外すこともできます。たとえば `release-beta/1.2.0` を `1.2.0` と表示します。

リポジトリにまだタグがない場合は、先に `v1.0.0` などのタグを付けてから設定します。リリースラインを変更または削除すると、そのラインのバージョンとタスクのひも付けが再計算されます。成果物とデプロイ記録は保持されます。

## バージョンをリリースする

1. Releases ページでプロジェクトを選び、「リリース」をクリックします。
2. リリースラインと対応するブランチを選びます。ブランチは既定でリポジトリの既定のブランチで、このブランチにマージされた PR だけが対象になります。
3. 対象のコミットを選びます。テスト用のアプリを選ぶと、そのアプリで動いているコミットが使われます。完全なコミット SHA を入力することもできます。
4. Studio は対象のコミットとこのリリースラインの前のバージョンを比較し、このバージョンに含まれるタスクと、まだ対象のコミットに入っていないリリース待ちのタスクを一覧表示します。
5. 提案されたタグを確認し、必要なら変更して、コマンドをコピーし、リポジトリでタグを作成してプッシュします。

タグをプッシュすると、Studio は新しいバージョンを自動で識別し、含まれるタスクを更新して、バージョンがリリースされたことを通知します。

> [!NOTE] タグの読み取りは Git 接続に依存する
> Studio はコードプラットフォームの Webhook と定期的な照会でタグを読み取ります。GitHub の Webhook が機能せず定期的な照会だけに頼っている場合、古いコミットに付けた新しいタグは読み取れないことがあります。

## リリース待ち

マージ済みだが、まだどのリリース済みバージョンにも含まれていないタスクは、Releases ページの「リリース待ち」タブに一覧表示され、テスト環境にデプロイ済みかどうかも示されます。リリースを準備する前に、ここで今回どの変更が含まれるかを確認します。

プロジェクトで最も古いリリース待ちの変更がマージされてから 3 日が経つと、プロジェクトリーダーにリマインダーが届きます。

## 成果物

バージョンはコードであり、成果物はビルドされたデプロイ可能なものです。`pnpm build --tar` で作成したアーカイブや、イメージレジストリにプッシュしたイメージです。成果物は CI、あなたのエージェント、またはあなた自身が Studio にアップロードし、テスト環境にも本番にも成果物を使ってデプロイします。「バージョン」タブでは、各バージョンの成果物を確認し、アーカイブをダウンロードしたり、バージョン番号をコピーしたりできます。
