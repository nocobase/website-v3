---
title: "結果を検収する"
description: "引き渡しレポートと動作を確認し、マージするか修正を依頼します。"
---

タスクが **In review** になったら、責任者が成果物を確認します。エージェントは報告、検証記録、必要なスクリーンショットを提出し、人が検収を判断します。

## 引き渡しレポートを読む

**My issues › Waiting for you** からタスクを開きます。**Needs you** を読んでから、報告を確認します。

![引き渡しレポートの上に検収操作が表示される](https://static-docs.nocobase.com/studio-en-guide-accept-20261031.png)

| 内容 | 確認すること |
| --- | --- |
| 変更前と合意した方針 | 要件と確定したルールに合っているか |
| 変更点 | 今回の引き渡しに含まれるもの |
| 検証 | テスト、確認環境、独立したレビューの結果 |
| 残る問題 | 未完了の作業と影響 |
| 受け入れ基準 | 確認可能な結果とその証拠 |

添付されたスクリーンショットを開いて確認します。証拠が不足している場合は、判断する前に補足を依頼してください。

## 変更とプレビューを確認する

**View changes** でコードプラットフォームの PR を開きます。**Code & previews** には、関連 PR、チェック、プレビューへの入口がまとまっています。

PR プレビューを設定している場合は、そこで受け入れシナリオを試します。選択したチェック取得元が、先にビルドと公開を完了する必要があります。[PR プレビュー](../release/previews.md)を参照してください。

未使用のプレビューは休止し、開くと起動する場合があります。PR のマージ・クローズ後に削除されます。

## 検収する

PR があるタスクでは **Merge** を選びます。対象ブランチ、方法、コミットタイトルを確認して確定します。確認中に新しいコミットが追加された場合は、再確認が必要です。関連 PR がすべてマージされるとタスクが完了します。

調査や資料整理など PR がない作業では **Accept** を選びます。コーディネーターエージェントも実行エージェントも、人に代わってマージや検収はできません。

マージは個人の Git 接続を優先し、なければワークスペースの接続を使います。コードプラットフォームの権限と保護ブランチのルールも適用されます。

## チェックが通らない場合

競合、チェック待ち、ドラフト PR、コードプラットフォームのルールでマージできない場合があります。

チェック失敗や結果不足の場合、Studio が **Merge anyway** を表示することがあります。理由を入力でき、操作は PR とタスクに記録されます。コードプラットフォームの保護は回避できず、エージェントはこの操作を行えません。

## 修正を依頼する

1. **Send back** を選びます。
2. 実際の動作と期待する動作を説明します。
3. タスクを **In progress** に戻します。

```prompt
停止中の仕入先にも新規注文ができてしまいます。新規注文を禁止し、既存注文の閲覧と入荷処理は引き続き可能にしてください。
```

コーディネーターエージェントが修正を手配し、結果を再提出します。

## コードプラットフォームでマージ済みの場合

Studio は Webhook またはポーリングでマージを取得します。手動の記録が必要な場合は **Mark as merged** を使います。その後のリリースは[リリースの概要](../release/overview.md)で確認してください。
