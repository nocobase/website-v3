description: タスクが引き渡されたら、責任者が結果を確認します。引き渡しレポートとスクリーンショットを読み、必要ならプレビューで試し、問題なければマージし、そうでなければ差し戻します。
---

検収は、人が行う最も重要な判断です。エージェントチームから届くのは PR だけではありません。引き渡しレポートには、以前の状況、変更内容、確認方法、残っている課題が書かれ、検収基準とスクリーンショットが添えられています。CI が接続されていれば、自分で試せるプレビューもあります。コードを読まない業務の専門家でも、これをもとに判断できます。

## 検収が回ってくるとき

コーディネーターエージェントは、PR がチェックとレビューを通過してから、タスクを **In review** にしてあなたに引き渡します。プロジェクトにまだ CI がない場合は、先に CI なしで検収するかどうかを尋ねます。タスクが検収待ちになると：

- **My issues** の **Waiting for you** に、**Needs your acceptance** のラベル付きで表示されます。
- タスクページ上部の **Needs you** カードに、何の確認を求められているかが表示されます。
- その下に、コーディネーターエージェントが提出した引き渡しレポートがあります。

検収できるのは人だけです。コーディネーターエージェントも実行エージェントも、タスクを完了にしたり PR をマージしたりはできません。

## 引き渡しレポートを読む

引き渡しレポートは検収の主な根拠です。コーディネーターエージェントは組み込みの構成に従って書きます。

| セクション | 内容 |
| --- | --- |
| How it was before | 以前の状況と、どこに問題があったか |
| Agreed approach | 今回採った方針と、その範囲の境界 |
| What changed | 変更内容を業務の言葉で |
| How it was checked | エージェントが実行したテスト、どこで確認したか、レビューの結論 |
| Open issues | 今回解決していないもの、リスクのあるもの。それぞれに推奨事項付き |
| Details | PR、コミット、データマイグレーションなどの技術的な詳細 |
| Acceptance criteria | 確認できるチェック項目と、対応するスクリーンショット |

レポートの横には、開発したエージェントが添付したスクリーンショットがあります。クリックすると拡大表示され、ほかのスクリーンショットもめくって見られます。

::figure req-accept | 検収待ちのタスク：Needs you カードにボタンがあり、その下に引き渡しレポートがあります

検収基準は照らし合わせるためのもので、1 つずつチェックを付けるためのものではありません。受け入れるか差し戻すかを、総合的に判断します。

## 変更を見る

- **View changes** をクリックすると、コードホストで PR が開きます。
- **Code and deployments** タブには、タスクにひも付いたすべての PR が、各 PR のチェック結果やコンフリクトとともに表示されます。

コードを読まなくても検収できます。引き渡しレポートの検収基準とスクリーンショットが、ニーズを満たしているかに集中しましょう。疑問があれば、タスクにコメントするか **Ask agent** を使います。

## プレビューで試す

プロジェクトに CI が接続されていれば、PR ごとにプレビューがあります。タスクページから開き、最初の管理者としてサインインして、自分で検収基準を確認します。

::figure req-preview | PR のプレビュー。自分で変更を試せます

- タスクを編集できる人は、タスクページでプレビューの最初の管理者のユーザー名とパスワードを確認できます。
- プレビューはサンプルデータを使い、自社の実データは使いません。
- プレビューはしばらくアクセスがないと停止してスリープし、開くと再び起動します。少しお待ちください。
- PR がマージまたはクローズされると、そのプレビューは自動で削除されます。

CI のないプロジェクトにはプレビューがありません。[CI を接続する](../setup/ci.md) を参照してください。

## 受け入れる

**PR があるタスク**：**Merge** をクリックします。確認画面では、まずコードホストで PR とそのチェック結果を確認してから、次の内容を表示します。

- マージコミットのタイトルとマージ方法。たとえば「Squash and merge into main」です。GitHub ではスカッシュマージを使い、GitLab ではプロジェクトの設定に従います。
- マージ後のタスクのステータス。

::figure merge-dialog | マージ前の確認

確定すると、Studio はあなたが確認したバージョンをそのままマージします。その間に PR に新しいコミットが追加された場合は、もう一度確認を求めます。タスクにひも付いたすべての PR がマージされると、タスクは自動で **Done** に移ります。

**PR がないタスク**（調査やドキュメントなど）：**Accept** をクリックすると、タスクは **Done** に移ります。

> [!NOTE] マージはだれの名前で行われるか
> **Account settings › Git** で自分のアカウントを接続していれば、マージはあなたとして行われます。そうでなければ、ワークスペースの Git 接続が使われます。

## チェックを通過していないとき

次の場合は **Merge** を使えないため、先に解決する必要があります。PR にコンフリクトがある、チェックが実行中、PR が下書き、コードホスト自体のルールがマージを許可していない。

必須のチェックが失敗した場合や、チェック結果がない場合（たとえばプロジェクトにまだ CI がない場合）は、確認画面のボタンが **Merge anyway** と表示され、理由を入力できます。Studio は強制マージについてのコメントを PR に投稿し、タスクのアクティビティに記録します。コードホスト自体のルールは引き続き適用されます。エージェントが強制マージすることはできません。

## 差し戻す

結果が期待どおりでないとき：

1. **Send back for changes** をクリックします。
2. 何を変える必要があるかを、できるだけ具体的に書きます。たとえば「統合後は、最も早い作成日時を残してください。今は最も遅い日時が残っています」です。
3. **Send and return to In progress** をクリックします。

タスクは **In progress** に戻り、コーディネーターエージェントがあなたのフィードバックをもとに修正を手配し、再びあなたに検収を依頼します。

## コードホストですでにマージされた場合

だれかが GitHub や GitLab で直接 PR をマージした場合も、Studio は Webhook またはポーリングでそれを検知し、タスクは同じように自動で完了します。どうしても必要な場合は、Studio で **Mark as merged** をクリックしてマージ済みとして記録することもできます。
