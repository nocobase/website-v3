プロジェクトの **Workflow** タブを開きます。図の左右でタスクを開始する人と検収する人を、中央でエージェントが引き渡しまでに行う作業を確認できます。

## タスクの開始から検収まで

### タスク担当者が開始と検収を行う

コミュニティ版では、タスク担当者がタスクを引き受けて作業を開始します。エージェントが作業を終えたら、担当者が引き渡しレポートを確認し、マージまたは差し戻しを選びます。中央の開発手順には Standard または Simple を選べます。

![コミュニティ版で担当者の作業と Standard の開発手順を確認する](https://static-docs.nocobase.com/studio-workflow-en-ce-20261126-e344b58869.webp)

<span id="requester"></span>

### 依頼者が要件確認と検収を行う

プロフェッショナル版とエンタープライズ版では、依頼者と開発担当者を分けられます。図の左右に要件確認と検収が加わります。依頼者が要件と成果を確認し、開発担当者が作業を開始してコードをマージします。

![エンタープライズ版の画面で依頼者と開発担当者の分担を確認する](https://static-docs.nocobase.com/studio-workflow-en-roles-20261126-af9a0cdf59.webp)

たとえば、取引を停止した仕入先への新規発注を止め、発注済みの注文では引き続き入荷処理できるようにします。購買担当者が依頼者となり、プロジェクトメンバーが開発を担当します。

::figure multi-role-workflow | 依頼者が要件確認と検収を行い、開発担当者がタスクを開始・完了します。

#### 依頼者と開発担当者を指定する

購買担当者がタスクを作成し、プロジェクトを選んで要件と受け入れ条件を入力し、開発担当者を指定します。作成者が依頼者になります。役割を分けた場合、依頼者は開発担当者やフローを変更できず、開発担当者も依頼者を変更できません。プロジェクト責任者またはプロジェクトの管理権限を持つメンバーは、どちらの担当者も変更できます。

開発担当者を省略すると、[プロジェクト設定](../project/settings.md)の既定値が使われます。初期値はタスクの作成者です。同じ人が両方を兼ねる場合は、そのまま開発を開始し、検収できます。

#### 要件を確認して開発を開始する

**開発担当者**は **My issues** で割り当てられたタスクを開きます。**Take over** が表示されたら選択します。

![開発担当者が購買担当者からタスクを引き受ける](https://static-docs.nocobase.com/studio-en-multi-role-handoff-20261119-c9a63c6ba5.webp)

**依頼者**は[受信トレイの Requester decisions](inbox.md#受信トレイの表示) からタスクを開きます。説明と受け入れ条件を確認して **Confirm requirements** を選びます。Backlog の段階で説明を変更した場合は、再度確認が必要です。

![依頼者が受け入れ条件を確認して Confirm requirements を選ぶ](https://static-docs.nocobase.com/studio-en-multi-role-confirm-20261119-bbba66e940.webp)

確認が済んだら、**開発担当者**が **Start** を選びます。コーディネーターエージェントが開発作業を割り振ります。

#### 開発中の質問に答える

たとえば、エージェントから「取引停止前に発注した商品は入荷処理できますか？」と質問が届きます。依頼者は **Requester decisions** で「はい。制限は新規発注だけに適用します」と回答します。回答はタスクのコメントに記録され、エージェントが作業を続けられます。回答待ちの間もタスクは In progress のままです。

![開発中のタスクで依頼者が業務上の質問に回答する](https://static-docs.nocobase.com/studio-en-multi-role-question-20261119-a7eb6f2a79.webp)

開発担当者がルールを把握している場合は、タスク上で代理回答できます。

#### 検収または差し戻しを行う

タスクが **In review** に移ったら、依頼者は **Requester decisions** から引き渡しレポートを開きます。プレビューがある場合は、取引停止中の同じ仕入先で次の操作を試します。

- 新しい注文を作成する。登録が拒否されることを確認します。
- 取引停止前の注文を開く。入荷処理を続けられることを確認します。

両方とも期待どおりなら **Accept** を選びます。既存の注文も処理できない場合は **Send back** を選び、どの操作で問題が起きたかを入力します。必要に応じて画像を添付できます。タスクは **In progress** に戻り、エージェントが修正します。

![依頼者が検収を完了するか、修正を依頼する](https://static-docs.nocobase.com/studio-en-multi-role-accept-20261119-30cc443b04.webp)

#### マージまたはタスクを完了する

検収後、開発担当者は [PR のチェックとコードレビュー](../project/checks-and-review.md)を確認します。条件を満たしたら **Merge** を選びます。PR のないタスクは成果を確認してそのまま完了できます。

![PR のないタスクでは、依頼者による検収後に開発担当者が完了できる](https://static-docs.nocobase.com/studio-en-multi-role-complete-20261119-233bbcfacd.webp)

検収後に別の PR を追加した場合は、依頼者による再検収が必要です。開発担当者が差し戻す際、修正で機能の動きが変わる場合は **Require the requester to accept again** を選びます。

## エージェントの開発フロー

### Standard と Simple の使い分け

| フロー | 用途 | 作業手順 |
| --- | --- | --- |
| Standard | 業務ルールや複数箇所にまたがる変更 | 必要に応じて方針を検討し、実装、別モデルによるレビュー、CI の確認を経て引き渡す |
| Simple | 範囲が明確な小さな変更 | 1 つのエージェントが実装して検収を依頼する |

エンタープライズ版には、品質管理モジュールがテストタスクで使う **Quality test** も表示されます。[テストの実行](../quality/runs.md)を参照してください。

### プロジェクトの既定フローと常時読み込むスキルを設定する

プロジェクトの **Workflow** タブでフローを選び、**Set as project default** をクリックします。既定のフローを使うタスクには次回の実行から反映されます。

![プロジェクトの Workflow タブで Standard を既定に設定する](https://static-docs.nocobase.com/studio-workflow-en-project-default-20261126-ccf2ff2db7.webp)

**Workflow** タブの **Resident skills** で、プロジェクト全体または対象リポジトリを選びます。**Add skill** でチームの規約などの通常スキルを選んで保存すると、次回の実行から読み込まれます。作成や更新の手順は[スキル](../project/skills.md)を参照してください。

### タスクのフローを切り替える

タスクを開いて **Workflow** を選びます。プロジェクトの既定値を使うか、このタスクに使うフローを選択します。たとえば、通常は Standard を使うプロジェクトでも、項目名の修正には Simple を選べます。変更は次回の実行から有効です。実行中の作業は元のフローで続きます。現在の段階はタスクの進捗バーで確認できます。

![項目名を変更するタスクで Simple を選ぶ](https://static-docs.nocobase.com/studio-workflow-en-task-switch-20261126-a1845238be.webp)

<span id="不具合修正用のフローを作成する"></span>

### フローを新規作成する

プロフェッショナル版とエンタープライズ版では、スキルの管理権限を持つメンバーがエージェントとの会話で開発フローを作成できます。空のフローから始めるか、既存のフローを基にします。コミュニティ版では組み込みフローを利用できます。

たとえば、不具合の修正前に失敗したテストが、修正後に通ることを記録したいとします。空のフローから「Bug fix」を作り、不具合の再現から修正の検証までの手順を決めます。

1. プロジェクトの **Workflow** タブで **New workflow** を開き、**Blank workflow** を選びます。

   ![New workflow メニューで Blank workflow を選ぶ](https://static-docs.nocobase.com/studio-workflow-en-blank-menu-20261126-5d2fd06cba.webp)

2. 開いたエージェントとの会話で、不具合修正の手順を伝えます。

   ```prompt
   「Bug fix」というフローを作ってください。まず不具合を再現するテストを書き、失敗することを確認します。原因を特定して修正し、同じテストをもう一度実行してください。テストが通ったら別のエージェントにレビューを依頼し、修正前後のテスト結果を添えて引き渡してください。
   ```

   ![新規フローの会話で不具合修正の手順を伝える](https://static-docs.nocobase.com/studio-workflow-en-blank-chat-20261126-3b7143454e.webp)

3. エージェントの下書きを確認し、フローの作成を依頼します。**Workflow** に戻って **Bug fix** を選ぶと、キャンバスの中央に「再現」「原因の特定と修正」「検証」「独立レビュー」「引き渡し」の順で表示されます。

   ![プロジェクトのキャンバスに表示された Bug fix の 5 つのステップ](https://static-docs.nocobase.com/studio-workflow-en-bug-fix-canvas-20261126-4006b9c4b6.webp)

   **View rules** を開くと、各ステップの指示を確認できます。たとえば、テストがまだ失敗する場合は修正に戻り、通ったら別のエージェントにレビューを依頼します。

   ![回帰テストが失敗した場合の手順を示す Bug fix のルール](https://static-docs.nocobase.com/studio-workflow-en-bug-fix-rules-20261126-766840e532.webp)

4. 発注書の二重送信を修正するタスクを開き、**Workflow** で **Bug fix** を選びます。この選択は対象のタスクにだけ適用されます。

   ![発注書の二重送信を修正するタスクで Bug fix を選ぶ](https://static-docs.nocobase.com/studio-workflow-en-bug-fix-task-20261126-43879dbebd.webp)
