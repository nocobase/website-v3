---
title: 从单应用迁移
description: 为已有 NocoBase 3 应用选择接入方式，在保留业务、用户和权限的前提下接入多应用平台。
---

已有 NocoBase 3 应用可以保留原部署接入平台，也可以迁入平台托管，或在原系统中增加主应用能力。这里不涉及 NocoBase 2 到 3 的迁移。

## 选择迁移方式

| 方式 | 适合的目标 | 是否搬迁数据 |
| --- | --- | --- |
| 保留原部署并接入平台 | 增加统一入口，按需使用平台登录 | 通常不需要；接入 SSO 时处理已有账号关联 |
| 迁入平台托管 | 由平台统一管理版本和运行状态 | 按目标数据库和存储方案迁移或重新配置 |
| 将现有应用扩展为 Main | 原系统继续承载业务，同时管理其他应用 | 不因增加平台能力而必须搬迁原业务数据 |

只需要工作台入口时，可以先登记 Web 链接，不改变原应用的登录方式。需要统一登录时，再安排身份接入；需要统一启停和升级时，再选择平台托管。

可以在现有应用目录中让 Coding Agent 先评估：

```prompt
这个库存应用已经在使用。我想把它接入多应用平台，保留商品、出入库记录、现有用户和权限。请帮我比较保留现有部署、迁入平台托管和让它成为主应用这三种方式，先给出建议，不要修改系统。
```

评估后由系统和数据负责人确定路线。框架或插件版本不兼容时，先完成[框架升级](../../developing-apps/upgrade-nocobase-core.md)，不要用新项目模板覆盖原应用。

## 评估现有应用与准备备份

先确认现有系统的版本、运行环境、业务范围，以及目标平台的商业许可和兼容插件。准备事项随路线变化：只添加链接不需要停机搬数据；修改认证、部署环境或数据库前，需要相应备份和恢复安排。

| 内容 | 需要掌握的信息 |
| --- | --- |
| 业务源码 | 自定义页面、API、插件、当前版本和构建方式 |
| 数据库 | 连接、业务记录、用户关联、历史迁移及执行记录 |
| 文件 | 本地附件、外部对象存储及访问配置 |
| 身份与权限 | 原用户 ID、外部身份绑定、角色分配、本地管理员 |
| 私有配置 | 加密主密钥、签名配置、客户端和第三方凭据 |
| 后台任务 | 定时任务、队列消费者、Webhook、通知及其他写入方 |

需要搬迁或改造时，先备份数据库、文件和配置，并在隔离环境中验证可以恢复。演练环境不要发送生产通知、调用真实 Webhook 或与生产环境争抢队列任务。

## 保留原部署并接入平台

原应用继续在原地址运行，数据库、存储和发布方式保持不变。

1. 只需要统一入口时，按[添加 Web 链接](external-apps.md#添加-web-链接)登记原地址并明确授权。
2. 需要平台登录时，先确定已有用户的身份关联，再按[NocoBase 应用接入](external-apps.md#接入-nocobase-应用的统一登录)添加 SSO。
3. 用原有用户检查业务记录和权限，确认接入后没有产生重复账号或改变数据归属。
4. 保留原部署的备份和故障处理职责。

仅登记链接不需要切换流量或停止原系统写入。撤销平台成员资格或停用入口，也不会停止原服务器。若增加了 SSO，需要额外检查平台身份访问、本地恢复登录和撤权行为。

## 迁入平台托管

托管迁移同时涉及代码、配置和持久数据。子应用部署归档不包含原业务数据，不能用创建一个空实例代替数据迁移。

1. 构建与目标环境兼容的独立部署归档，并发布为平台模板版本。
2. 确定目标实例的数据库、文件存储、运行配置和密钥，以及迁移执行时机。
3. 在隔离环境恢复原数据。数据恢复和核对完成前，不允许目标实例接受业务写入或运行后台任务。
4. 检查原用户 ID、代表性业务记录、关联、附件、角色和历史迁移执行情况。
5. 演练通过后，再安排正式切换窗口。

数据库和文件的恢复方法取决于实际存储方式。使用实例卷、外部数据库或对象存储时，需要分别规划恢复路径和权限，不使用一条通用导入命令覆盖所有环境。

## 将现有应用扩展为主应用

如果原系统适合作为统一入口，可以在保留业务的同时增加多应用管理和身份提供方能力。

1. 在隔离环境安装兼容的多应用管理与身份提供方插件，完成服务端、客户端和配置注册。
2. 将管理页面接入现有导航和权限体系，保留原页面、路由标识和业务 API。
3. 合并认证配置和自定义用户字段，保留原账号、角色与本地登录。
4. 需要托管子应用时，再配置 Releases、Host 和持久化环境。
5. 检查原业务仍可使用，再创建或接入其他应用。

原应用成为 Main，不意味着其业务必须迁入新的 Sub。不要为了套用目录结构重新生成项目或替换原认证系统。

## 保留用户身份与业务权限

接入 SSO 前，明确平台身份应关联到哪些已有用户，以及平台访问角色如何映射到业务权限。NocoBase 使用 issuer 和 subject 绑定身份，不自动按邮箱合并账号。保留原用户 ID 及业务外键；遇到身份冲突时先解决映射，不用同名新账号替代旧账号。

同一平台更换域名或挂载路径时，在新地址首次登录前，将 `PLATFORM_SSO_ISSUER` 更新为实际 issuer，并将 `PLATFORM_SSO_IDENTITY_NAMESPACE` 固定为原始 issuer；如果已设置固定值，则保留该值。同时核对客户端、回调、已保存的环境地址和已有用户绑定。该配置用于保留同一身份源的账号关联，不用于合并不同平台的用户。

给明确用户授予平台成员资格，保留原有合法业务角色。平台角色降权时，还要检查其他角色是否仍提供写权限，不能只根据一个只读角色判断最终权限。

已执行的迁移保留原名称、归属和内容，后续变更新增迁移。原有加密数据需要继续使用兼容的密钥和加密配置；凭据无法解密时先检查配置，不更换主密钥来跳过错误。

## 切换与回退

需要搬迁运行环境时，按演练过的顺序进行：

1. 确认维护窗口、目标环境、最终备份和恢复负责人。
2. 停止原业务写入及相关后台消费者，处理尚未完成的任务。
3. 完成最终数据同步并核对，再将访问流量切到目标应用。
4. 用已有普通用户检查业务记录、附件、权限和登录，确认后台任务只有一个明确的执行方。
5. 在保留期内保存原环境的恢复能力，但避免新旧环境同时写入同一业务数据。

仅添加外部链接时，无需套用上述停写切换步骤；出现问题可撤回授权或停用入口。原地增加主应用能力时，按应用版本发布流程更新，并验证原业务不受影响。

回退前确认旧代码与当前数据库兼容。如果迁移已经改变数据结构，可能需要一起恢复匹配的代码、数据库、文件和配置。先隔离流量与后台任务，再按恢复方案操作，不以重置数据库作为默认补救。具体备份要求见[备份与恢复数据](deployment.md#备份与恢复数据)。
