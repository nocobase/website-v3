## 什么时候使用多应用

当多个业务系统需要独立管理数据、配置和发布版本，同时又希望提供统一入口与登录体验时，可以采用多应用架构。

| 业务需求 | 使用方式 |
| --- | --- |
| 多家门店使用相同的库存功能，各自保存数据 | 开发一个库存应用模板，为每家门店创建实例 |
| 客户管理与采购管理由不同团队维护，发布节奏不同 | 分别开发和部署子应用，通过平台统一访问 |
| 已有系统继续运行，希望加入统一工作台 | 登记外部入口，按需接入统一登录 |
| 多个入口共用同一套应用、数据和版本 | 使用[多门户](../multi-portal/create-app.md)，不必拆成多个应用 |

多应用可以作为租户数据隔离的一种实现方式，但不自动提供租户组织、计费或跨应用业务查询。应用间需要交换数据时，应通过明确的 API 和权限进行集成。

## 主应用与子应用

**主应用（Main）**是平台入口，提供工作台、应用管理和平台身份服务。**子应用**承载具体业务，拥有自己的页面、API、数据库、配置和业务权限。

平台负责决定用户可以进入哪些应用，子应用负责决定用户进入后可以做什么。例如，平台允许某位员工进入库存应用，库存应用再根据其业务角色决定是否允许调整库存。平台管理员不会自动成为子应用管理员。

多应用项目模板将 Main 放在项目根目录，默认子应用放在 `apps/sub/`。两个应用共享依赖安装和锁文件，但分别开发、构建和部署。子应用也可以在独立仓库中开发，不必将业务源码放入 Main。目录和开发命令见[应用开发](development.md)。

## 应用模板、版本与实例

创建项目时使用的**项目模板**生成应用源码。平台中的**应用模板**则用于管理一个业务应用的部署版本。

以门店库存为例：

- **应用模板**：库存管理应用。
- **版本**：某次构建产生的部署归档，包含这一版应用的代码和依赖。
- **实例**：使用某个版本运行的库存应用，例如东区门店和西区门店各自的库存系统。

同一版本可以创建多个实例，每个实例保留自己的数据、配置和运行版本。发布新版本不会自动升级已有实例，可以先升级其中一个，再决定其他实例的升级时间。

## 托管应用与独立接入

| 方式 | 平台负责 | 应用负责人负责 |
| --- | --- | --- |
| 托管应用 | 通过 Releases 与 App Host 创建实例、管理版本及运行状态 | 开发业务、提供部署归档、规划权限和数据保护 |
| 独立接入 | 提供工作台入口和可选的统一登录 | 自行部署、升级、重启和备份原应用 |

两种方式中的应用都独立管理业务数据。是否使用独立进程、容器或服务器，取决于部署方式。

源码位置不决定部署方式：独立仓库的应用可以交给平台托管，`apps/sub/` 也可以独立部署后接入平台。托管时，Main 使用子应用的部署归档，不直接运行其业务源码。

## 使用前提

多应用需要兼容版本的商业插件、有效商业许可和包下载权限。项目模板不包含商业插件的实现，也不提供商业授权。

| 插件 | 使用位置 | 提供的能力 |
| --- | --- | --- |
| `@nocobase/app-plugin-multi-app` | Main | 应用模板、版本、实例和外部入口管理 |
| `@nocobase/app-plugin-identity-provider` | Main | 平台身份服务、OIDC 客户端和成员授权 |
| `@nocobase/app-plugin-platform-sso` | 需要平台登录的 NocoBase 子应用 | 平台登录、会话检查及应用切换 |

托管实例还需要可用的 Releases 与 App Host 环境。统一登录需要可信 HTTPS 地址；仅添加 Web 链接时，目标网站继续使用自己的登录方式。第三方 OIDC 应用使用自身的认证客户端，不安装 NocoBase 子应用插件。
