## 理解门户的权限边界

### 共用登录账号与角色

同一应用中的门户复用应用的登录和权限体系。用户切换门户时继续使用当前身份，不需要为每个门户单独创建账号。

门户有自己的布局和路由，但这本身不会隔离用户权限或数据。可以让同一个用户访问多个门户，也可以让不同用户拥有不同的入口、操作和数据范围。

### 区分安装状态、页面权限与数据权限

| 检查 | 回答的问题 |
| --- | --- |
| 门户安装状态 | 这个门户当前是否可用？ |
| 登录与页面权限 | 当前用户能否打开这个页面？ |
| 业务操作权限 | 用户能否查询、新增、修改或删除？ |
| 数据范围 | 本次操作能访问哪些记录和字段？ |

安装门户不会自动给用户授权；能打开页面也不代表拥有页面中所有操作或全部数据的权限。权限需要分别落实到页面和服务端接口。

## 了解默认访问规则

### 首页、工作台与门户管理

当前多门户模板将 **首页** 和 **工作台** 分开：登录用户保留应用首页，管理员从工作台进入已安装门户。**系统设置 → 门户管理** 用于安装、进入和卸载门户。

| 入口 | 默认访问要求 |
| --- | --- |
| 应用首页 | 已登录；不要求业务页面授权 |
| 门户工作台 | 已登录且具有 `unrestricted` 权限 |
| 门户管理及其目录 API | 已登录且具有 `unrestricted` 权限 |
| 生成的门户页面 | `auth: 'required'`，`authz: 'unrestricted'` |

![管理员工作台中的已安装门户入口](/assets/core/multi-portal/access/workbench.png)

如果使用的是尚未分离首页与工作台的旧模板，以应用实际路由为准。安装和卸载步骤见[管理门户](manage.md)。

### 默认门户页面与切换器

默认切换器展示已安装门户，并提供返回工作台的入口。它和默认 `PortalPage` 都读取管理员门户目录，**不是普通用户的已授权门户列表**。

![管理员在门户内打开切换菜单](/assets/core/multi-portal/access/switcher.png)

只放宽门户页面的 `authz`，并不能让普通用户正常使用这些组件：它们请求的目录接口仍要求管理员权限。面向普通用户时，需要同时调整页面、数据请求和入口展示。

## 为用户开放门户

以下以“用户 A 只访问门户 1，用户 B 可访问门户 1 和门户 2”为配置目标；这是接入示例，不是模板已经提供的角色或普通用户门户目录。

### 配置页面访问权限

为页面声明稳定的权限资源。例如，将门户 1 的 Examples 路由改为检查页面访问权限：

```ts
{
  name: 'portal1Examples',
  path: '/portals/portal-1/examples',
  auth: 'required',
  authz: {
    resource: { type: 'page', id: 'portal1.examples' },
    action: 'access',
  },
  breadcrumb: { title: 'examples.title' },
  componentLoader: () => import('./pages/examples.js'),
},
```

同时在应用授权体系中声明并注册对应的页面资源，让管理员能够分配权限。路由声明是访问要求，不会自动给任何用户授权。门户首页和其他业务页面也需要各自适用的规则，不能只修改一个页面就认为整个门户已开放。

在 **系统设置 → 权限管理** 中配置角色的授权，再通过用户管理分配给目标账号。下图是应用共用的权限管理入口，不是单独的门户角色设置：

![应用的权限管理页面](/assets/core/multi-portal/access/permissions.png)

### 配置操作权限与数据范围

页面访问之外，继续声明查询、创建、修改等业务操作，以及允许访问的记录和字段。给用户 A 的角色授予门户 1 所需能力；给用户 B 的角色增加门户 2 所需能力。不要向普通用户分配 `root` 或 `unrestricted` 来代替业务授权。

一个用户可能获得多个角色或其他授权来源，验证时应检查全部有效权限。具体声明、分配和数据策略用法见[权限管理](../../using-plugins/authorization/permissions.md)与[认证、权限与数据范围](../../developing-apps/authentication-and-permissions.md)。

### 提供符合权限的门户入口与切换

当前模板没有现成的普通用户门户目录。应用需要提供经过登录和业务授权的查询，只返回用户获准访问且已安装的门户及必要信息，再据此构建首页入口、切换菜单和页面可用状态。

用户 A 的入口只应出现门户 1，用户 B 可以看到门户 1 和门户 2。服务端必须根据当前身份生成结果，不能先返回管理员完整目录再仅在浏览器中过滤。保留管理员目录与管理 API 的原有权限要求，不要为了复用切换器而放开它们。

## 检查服务端访问权限

### 校验登录、授权与门户安装状态

业务接口应独立完成登录校验、业务操作授权和门户安装状态检查，再执行允许的数据读写。页面的 `authz` 不会自动保护同名 API。

在已经完成认证和业务授权的处理器中，使用门户服务检查可用状态：

```ts
import { portalCenterServiceToken } from '@nocobase/app-plugin-multi-portal/server';

await app.container
  .resolve(portalCenterServiceToken)
  .requireInstalled('portal-1');
```

`requireInstalled()` 只检查门户是否已安装，不检查用户权限。查询与写入还必须应用授权得到的记录、字段策略；只判断“有查看权限”后执行无限制查询，会丢失数据范围约束。

### 共享数据时保留权限边界

门户 2 可以使用门户 1 提供的服务或数据，但共享不等于授予全部访问权限。明确数据由谁维护、谁可以读取或修改，并在共享服务或接口中落实调用者的授权范围。

门户依赖关系只约束安装与卸载顺序，不替代用户授权。隐藏按钮、过滤导航和自定义布局也不能阻止用户直接调用 API。

## 验证权限配置

### 不同账号访问门户 1、门户 2

用普通测试账号验证目标配置，不要仅使用管理员账号：

| 账号 | 门户入口与页面 | 操作与数据 |
| --- | --- | --- |
| 用户 A | 只能进入门户 1 | 仅执行已授权操作，访问允许的数据 |
| 用户 B | 可进入门户 1 和门户 2 | 两个门户分别遵循授权范围 |
| 未获得门户权限的用户 | 不显示对应入口，直接访问也被拒绝 | 业务接口不能返回受保护数据 |

### 直接访问页面与接口

分别测试未登录、已登录但无权、已授权三种情况。除了点击菜单，还要直接打开页面 URL、调用接口，检查查询、写入、字段及关联数据是否遵循同一套权限。普通业务用户不得因获得门户权限而获得门户管理权限。

### 门户卸载或权限变更后的表现

在测试环境中卸载门户后，再调用业务接口，应被安装状态检查拒绝。撤销用户权限后，重新请求页面和接口应按最新权限处理，入口也应更新；不要把浏览器中保留的菜单当作授权依据。最后检查会话失效、页面刷新和移动端切换。
