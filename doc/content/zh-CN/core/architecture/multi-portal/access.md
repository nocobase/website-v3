门户与应用共用登录身份和角色，不需要另建一套账号。管理员在角色中开放门户和页面；开发者在代码中声明页面权限，并在服务端保护业务接口。

## 门户的两层授权

成员要打开门户中的页面，需要同时满足两层授权：

1. **门户访问**：门户的总开关。关闭时，门户不出现在我的门户和切换器中，直接打开门户地址也会被拦下。
2. **页面访问**：开放了哪些页面。导航只显示已开放的页面，直接打开未开放页面的地址会显示无权访问。

我的门户和切换器只列出已安装、开启了门户访问、并且至少开放了一个页面的门户。点击门户卡片会打开成员有权访问的入口。

页面权限只控制界面。页面读写数据时，接口还要检查业务权限和数据范围，见[保护业务接口](#保护业务接口)。

门户的安装和卸载使用单独的管理权限，开放门户访问不会附带这些能力，见[管理门户](manage.md)。

## 为角色开放门户

使用管理员账号打开 **系统设置 → 权限管理 → 角色与权限**，编辑要授权的角色，进入 **多门户** 标签页。这里列出应用中的所有门户和它们的页面。

### 开启门户访问

勾选门户名称旁的复选框，开启这个角色的门户访问。门户名称旁会显示已开放的页面数，如 **已开放 2/3**。

取消勾选后，门户下的页面选项变为不可操作，但原来的勾选会保留；重新开启后恢复原来的选择。

### 开放部分页面或所有页面

在门户下逐个勾选要开放的页面。页面按[页面清单](develop.md#定义页面路由)中的标题列出；共用授权项的页面显示为一项，勾选后一起开放。

勾选 **所有页面** 会开放门户的全部页面，包括以后新增的页面。勾选后，逐页选项变为不可操作，原来的勾选会保留；取消 **所有页面** 后恢复原来的逐页选择。

新增的页面默认不开放，直到管理员勾选它或勾选了 **所有页面**。

保存后重新打开角色，确认配置已保留。

### 用不同账号验证

用持有该角色的普通账号，在独立的浏览器会话中登录检查。不要用拥有全部权限的管理员账号验收。一个用户可能拥有多个角色，要按其全部角色的授权判断结果。

以库存门户为例，给一个角色开放 Overview 和 Materials，不开放 Stock：

| 检查 | 预期结果 |
| --- | --- |
| 我的门户中显示库存门户 | 显示 |
| 侧栏显示 Stock | 不显示 |
| 直接打开 `/main/portals/inventory/stock` | 显示无权访问 |
| 关闭门户访问后打开 `/main/portals/inventory` | 被拦下，我的门户中不再显示 |

应用使用其他基础路径时，替换地址中的 `/main`。没有任何门户权限的成员打开我的门户时，会看到没有可用门户的提示。

如果只开放了需要记录 ID 的页面（如 `materials/:id`），成员从我的门户进入时会看到提示：此门户通过记录链接打开。

## 为页面声明权限

页面的授权项由[页面清单](develop.md#页面授权)生成，不需要单独注册：

- 顶层页面各自是一个授权项，名称取自 `breadcrumb.title`。
- 使用同一个 `group` 的页面共用一个授权项。
- 子页面默认跟随父页面的授权；加上 `access: 'own'` 后成为单独的授权项。成员要打开子页面，还需要能打开它的所有上级页面。
- 设置了 `authz` 的页面使用自定义检查，不出现在 **多门户** 标签页中。

已经发布的门户，修改页面名或 `group` 会改变授权项，角色中原来的勾选不再对应。需要调整时，保留原来的值作为 `group`。修改门户地址（`nocobase.portal.key`）不影响已有授权。

## 保护业务接口

隐藏导航和页面不能代替服务端授权。门户的业务接口挂在 `/api/portals/<key>` 下，请求到达接口之前，多门户统一检查：调用者已登录（否则 `401`）、门户已安装（否则 `404`）、调用者有门户访问权限（否则 `403`）。页面授权不参与接口的检查。

通过后，接口自己还要检查这个操作所需的业务权限和数据范围。门户的业务操作可以放进 **多门户** 标签页，与页面一起配置。写法见[定义门户接口](develop.md#定义门户接口)。

数据表的通用增删改查接口（`/api/<表名>`）不经过门户的检查，由数据表权限控制。验收时，用没有权限的账号直接请求接口，确认未授权的操作、记录和字段都无法访问。

## API 密钥的门户授权

有范围限制的 API 密钥也可以持有门户访问和页面授权，权限不会超过密钥所有者自己的权限。调用门户业务接口时，接口的检查方式与登录用户相同。

门户管理接口需要用户会话，不能用 API 密钥调用。
