安装门户只代表它在当前应用中可运行，不会自动给用户授予页面、数据或操作权限。门户复用宿主应用的登录和权限体系，不需要单独建立一套用户账号。

## 理解当前模板的默认行为

| 入口或能力 | 默认行为 |
| --- | --- |
| 管理员首页 | 显示门户工作台 |
| 普通用户首页 | 保留标准应用首页 |
| 门户管理及目录 API | 要求已登录且具有 `unrestricted` 管理员权限 |
| 生成的门户首页 | `auth: 'required'`，`authz: 'unrestricted'` |
| 默认门户切换器和 `PortalPage` | 使用管理员门户目录，不是面向普通用户的已授权门户列表 |

管理员可以从工作台进入已安装门户，也可以在门户侧边栏切换门户或返回工作台。普通用户不会因为门户安装成功就看到相同的工作台；仅把首页路由的 `authz` 改为普通业务权限，默认目录请求仍会被拒绝。

## 为业务用户开放门户

以库存管理员只能使用库存管理为例，需要同时完成以下工作：

1. 为库存首页和业务页面声明相应的页面访问要求，保留稳定的路由标识和本地化名称。
2. 声明库存查询、入库、出库等业务动作及数据范围，服务端逐项检查。
3. 在应用的权限管理中配置业务角色，并通过用户管理把角色分配给明确的用户。
4. 为普通用户提供符合授权范围的入口、门户切换和可用状态查询，不直接复用管理员目录 API。

当前模板没有现成的普通用户门户目录。需要这项体验时，应用应提供经过登录和业务授权的查询，只返回用户可访问的门户及必要信息，再调整首页、切换器和页面的状态读取方式。不要通过给所有用户授予 `unrestricted`，或放宽管理 API 的管理员要求来绕过这一限制。

角色、页面权限和数据范围的配置方法见[权限](../../using-plugins/authorization/permissions.md)；应用内的认证与授权接入见[认证与权限](../../developing-apps/authentication-and-permissions.md)。

## 在服务端检查门户是否可用

业务 API 除了检查登录和业务权限，还要检查门户当前是否安装。服务端可通过门户服务执行这一检查：

```ts
import { portalCenterServiceToken } from '@nocobase/app-plugin-multi-portal/server';

// Inside an authenticated and authorized request handler with access to app.
await app.container.resolve(portalCenterServiceToken).requireInstalled('inventory');
```

这段代码只检查门户安装状态，不替代用户身份和业务权限校验。把检查放在执行读写操作之前；门户卸载或不可用时，直接调用 API 也不能继续访问业务功能。

浏览器隐藏按钮、过滤菜单或阻止路由跳转，都不能代替这些服务端检查。

## 验证权限边界

| 验证场景 | 预期结果 |
| --- | --- |
| 未登录访问业务 API | 被拒绝 |
| 已登录但无库存权限 | 不能通过直接 URL 或 API 访问库存业务 |
| 只有库存角色的用户 | 只看到已授权入口，操作和数据范围符合角色配置 |
| 业务用户访问门户管理 API | 被拒绝，不因业务授权获得管理权限 |
| 门户卸载后再次调用业务 API | 被门户安装状态检查拒绝 |

使用普通账号测试，检查其全部有效授权来源，避免管理员或其他继承角色掩盖权限问题。修改入口后还要检查移动端菜单、直接链接进入和会话失效后的表现。
