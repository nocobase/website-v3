开发一个功能时，你负责业务上的决定：要做什么，设计行不行，结果能不能用。Agent 按 NocoBase 的 Skill 写代码、测试和检查。

## 提需求

在应用根目录打开 Agent，用业务语言说清三件事：

- 谁在用。
- 要做什么。
- 有哪些规则：谁能做什么，哪些数据不能动。

还没决定的问题直接说出来，例如“跟进记录写错了能不能修改，还没定”，不要让 Agent 猜。如果手上有设计稿、接口约定或业务资料，一并发给它。不用写页面怎样布局、代码放在哪里、怎样测试。

比如给[开发第一个功能](build-your-first-app.md)里做好的客户管理加上跟进记录，需求可以这样写：

```prompt
给客户加上跟进记录。销售每次联系客户后记一条：日期、方式（电话、拜访或邮件）和内容。
客户详情里按时间倒序显示跟进记录。
销售只能给自己负责的客户记跟进；销售主管能看全部记录；只读用户只能查看。
已有的客户不用补历史记录。
```

要动生产环境、真实数据或账号时，说清是哪个环境，允许它做到哪一步。

## 确认设计

Agent 做新页面或新的交互流程（比如新建和编辑、详情抽屉）之前，会先给出设计，请你确认。设计里有：

- 页面结构和主要交互。
- 设计评审发现的问题，以及处理方式。
- 需要你决定的问题。

你回答问题、确认之后，Agent 才开始开发。如果不想等这一步，在需求里加一句“不用等我确认，一次做完”，Agent 会把设计附在最后的报告里。

如果只是加一列、改文案这类小改动，Agent 不出设计，直接修改。

## 验收

Agent 开发完会自己运行测试，在浏览器里逐项验收并截图，然后交给你一份报告：

- 做了什么：页面、路由和改动的文件。
- 验收中发现的问题和修复结果。
- 关键截图。
- 还没解决或没有验证的部分，以及原因。

验收需要登录应用时，Agent 会请你自己登录，不会替你输入密码。

你要做的是：先看报告里没有验证的部分，再用相关角色的账号，在应用里把主要流程走一遍。不对时，说清你做了什么、看到了什么、期望什么：

```prompt
用只读用户登录，在客户详情里还能添加跟进记录。
只读用户应该只能查看，不能添加。
```

想了解 Agent 按什么规则测试和检查，见[测试与验收](../developing-apps/testing-and-acceptance.md)。

## 拆分需求

如果一次要做的事太多，Agent 给出的设计会很长，等你决定的问题会很多，验收时也很难看出哪里不对。遇到下面任何一种情况，就先拆开：

- 要新增好几类数据，每类都有自己的页面和角色。
- 说不清这一步做完后，大家能用它做什么。
- 还有不少业务问题没想好。

按业务拆，每一步做完都能单独用起来。比如把客户管理扩展成完整的 CRM，可以分成四步：

1. **跟进记录**：销售每次联系客户后记一条。
2. **销售机会**：一个客户可以有多个机会，记录金额和预计成交日期。
3. **报价**：为销售机会生成报价单。
4. **销售报表**：按销售和月份统计成交金额。

每做完一步，大家就可以开始用。使用中发现问题，可以在下一步一起调整。

不要按数据、接口、页面来拆。那是 Agent 内部的开发顺序：只做完数据表时，页面上什么也看不到，你没法验收。

不知道怎么拆时，先让 Agent 出方案，不写代码：

```prompt
我想把客户管理扩展成完整的 CRM，包括跟进记录、销售机会、报价和销售报表。
先不要写代码。请拆成几步，每一步做完都能单独使用，并列出每一步需要我决定的问题。
```

方案定下后按顺序做，每一步都像普通需求一样：提需求、确认设计、验收。提第一步时把整体计划也告诉 Agent，免得前面的设计挡住后面的功能。

## 保存项目规范

定下以后每次都要遵守的规则时，让 Agent 保存到项目规范：

```prompt
以后所有日期都按公司所在的时区计算，保存到项目规范。
```

Agent 会把它写进 `.agents/rules/`，并在 `AGENTS.md` 的索引里登记。之后的会话和其他开发者都按它工作。Agent 改动应用的框架结构时，也会自己在这里记下改了什么、为什么。
