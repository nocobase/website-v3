这些操作用于 App Host 托管的应用。独立运行的应用使用[接入独立应用](external-apps.md)流程，不会因此获得平台部署能力。操作者需要相应的页面、操作和数据范围权限；能看到应用入口不代表能管理它。

## 创建模板与发布不可变版本

准备子应用的构建归档，以及可用的部署环境。制品必须匹配环境的操作系统、架构和运行时要求。

1. 打开**应用模板**，创建模板或选择已有模板。
2. 在模板详情上传子应用的 `dist.tar.gz`。
3. 检查识别出的应用包名和版本，确认归档属于这个模板。
4. 发布该版本，保留版本号与校验和，供后续部署核对。

发布会固定制品身份和内容。发现问题时修改源码并发布新版本，不用不同内容覆盖已发布版本。同一模板的后续版本保持相同应用包名；发布版本不会升级任何现有实例。

停用模板会阻止新的发布和实例开通，不会删除已经发布的版本和现有实例。

## 选择版本和部署环境创建实例

在**应用实例**中创建实例，填写名称和唯一标识，选择模板、明确的已发布版本以及部署环境。只有一个可用环境时可以自动选中；多个环境时仍需确认目标。

实例标识会参与实际运行路径，不应把它当作随时可改的显示名称。开通完成后，检查实例详情中的当前版本、目标版本、运行状态和访问地址。

如果环境要求部署审批，先完成审批，再观察部署结果。目标版本表示期望运行的版本；只有实际部署成功，才能认为当前版本已切换。

启用身份集成后，新实例会登记自己的 OIDC 客户端并获得服务端变量，但不会自动给所有平台用户授权。按照[访问授权](single-sign-on.md)添加成员。

## 启动、停止与配置实例

| 操作 | 作用 | 操作后检查 |
| --- | --- | --- |
| 启动 | 运行已停止的实例 | 访问入口可用，已有数据保留 |
| 停止 | 停止运行，保留持久化数据 | 直接访问不能重新激活实例 |
| 重启 | 先停止再启动 | 新进程或运行状态正常，业务读写可用 |
| 配置 | 修改应用标题、默认语言等受支持的展示配置 | 配置生效且其他配置未被覆盖 |

当前实例配置操作不是任意 YAML 或密钥编辑器。基础设施配置和秘密变量应由有权限的部署配置流程管理，不通过扩大用户的原始 Releases 权限绕过限制。

需要初始管理员凭据时，在实例详情中明确执行查看操作。该操作要求配置权限及实例数据范围权限，不向非用户或受限密钥调用者开放。它只读取最初生成的凭据，无法查回后来修改的密码；不要把凭据放进工单、日志或 URL。

## 按实例升级与查看部署历史

升级前备份实例数据，并确认目标版本的数据库迁移与现有数据兼容。

1. 在实例详情记录当前版本。
2. 选择目标版本并确认升级的是这个实例。
3. 跟踪操作记录和部署历史，等待成功或明确的失败结果。
4. 打开实际应用，检查版本、业务数据、附件和关键操作。
5. 检查未选择升级的实例，确认其版本没有改变。

接口调用需要遵循当前 API 文档中的版本检查、确认字段和提交保护要求。自动化客户端应从 `<应用路径>/api/swagger` 获取接口文档，不能用无权限的服务身份替代真实操作者。

部署历史保留执行记录，不是业务数据备份。选择旧制品之前，先检查它能否读取当前数据库；升级时执行过的迁移不会因切换代码而自动撤销。

## 归档、恢复与处理失败操作

归档会停止实例并保留文件、配置和业务数据；归档应用不能继续通过平台身份进入。恢复归档保留原有成员关系，但仍需明确启动实例。归档和恢复都不等于数据库回滚，普通管理流程也不提供永久删除。

操作失败、超时或中断时，先打开该实例的操作记录，确认：

- 失败发生在哪个阶段。
- 是否已经发出部署或审批请求。
- 是否已有部署标识和实际运行结果。
- 实例是否仍被未完成的操作占用。

结果未知时，使用受支持的协调恢复操作核对已有部署，不重复创建实例、不直接清锁、不改内部数据库状态。自动化重试同一个逻辑请求时保留原提交标识，避免产生另一次外部操作。

数据库迁移失败不能靠反复点击升级解决。保留错误、操作和部署标识，按[备份恢复流程](deployment.md)判断是否恢复数据及兼容代码。
