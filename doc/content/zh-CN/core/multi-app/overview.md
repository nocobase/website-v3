## 什么时候使用多应用

当不同业务需要独立保存数据、发布版本或管理访问权限时，可以把它们组织为多个应用，由一个主应用提供管理和访问入口。

| 需求 | 组织方式 |
| --- | --- |
| 多家门店使用相同的库存功能，但数据分别保存 | 一个库存模板，创建多个实例 |
| 客户管理与采购管理有不同的功能和发布节奏 | 分别开发两个应用模板 |
| 已有系统继续独立运行，只需要统一入口和登录 | 接入独立应用 |
| 只是同一业务系统中的不同模块，不需要独立数据和升级 | 保持单应用，用页面和插件组织功能 |

多应用不自动提供完整的租户组织管理、跨应用业务查询或服务治理。应用之间交换业务数据时，需要设计明确的 API 和访问权限，不能把读取另一个应用的私有数据库当作默认集成方式。

## 主应用、子应用、模板与实例

- **主应用**是管理平台，提供工作台、模板管理、应用管理和平台身份认证。
- **子应用**是完整的业务应用，有自己的页面、接口、数据库迁移和业务权限。
- **模板**是用于部署子应用的应用定义。每个已发布版本对应确定的构建制品，而不是指向随时变化的源码目录。
- **实例**是某个模板版本的实际部署，拥有独立的数据、配置、文件和运行版本。

同一个模板可以创建多个实例。发布新版本不会自动升级已有实例；管理员选择哪些实例升级，其他实例继续运行原版本。

## App Host 托管与独立部署

**托管应用**由主应用通过 Releases 和 App Host 创建、启动、停止和升级。App Host 负责运行实例；实例独立并不表示每个实例都有独立的操作系统进程。

**独立应用**由自己的部署环境运行，平台登记其访问入口，并按接入方式提供统一登录。平台不会替它部署、重启或备份。

源码位置与部署方式无关：子应用可以放在同一个工作区，也可以使用独立 Git 仓库。独立仓库中的应用仍可构建后交给 App Host 托管。

## 三个商业插件及其职责

开发包含应用管理、统一登录和应用切换的多应用系统，依赖以下三个**商业插件**：

| 插件 | 接入位置 | 职责 |
| --- | --- | --- |
| `@nocobase/app-plugin-multi-app` | 主应用 | 模板、不可变版本、托管实例、部署记录及独立应用目录 |
| `@nocobase/app-plugin-identity-provider` | 主应用 | OIDC 身份提供方、应用客户端注册及显式成员授权 |
| `@nocobase/app-plugin-platform-sso` | NocoBase 子应用 | 平台登录、独立会话、访问授权复核及应用切换 |


三个插件分工协作，但不是同一个能力：多应用管理可不启用统一登录；第三方 OIDC 应用使用自己的 OIDC 客户端，不安装 NocoBase 子应用插件。托管部署还依赖 Releases 和配置好的 App Host 环境。

## 数据、身份与权限的隔离边界

主应用决定“谁可以进入哪个应用”，子应用决定“进入之后可以做什么”。平台管理员不会自动成为子应用管理员，创建实例也不会自动给所有平台用户授权。

统一登录通过 OpenID Connect（OIDC）传递已验证的身份。子应用建立自己的本地账号绑定和会话，不共享平台用户表或 Cookie。平台登录与本地恢复登录的行为见[统一登录与访问授权](single-sign-on.md)。

停止和归档实例会保留数据；恢复归档不是恢复备份，回退代码也不等于回滚数据库。

首次体验从[快速开始](quickstart.md)进入。已有业务系统应先阅读[从单应用迁移](migration.md)，不要用示例源码覆盖现有应用。
