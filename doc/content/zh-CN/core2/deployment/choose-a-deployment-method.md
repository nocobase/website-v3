---
title: 选择部署方式
description: 选择用 Docker 或 PM2（app-installer）独立部署生产应用，并准备运行配置、持久化数据和后续的更新。
---

应用开发完成并通过测试后，可以在自己的服务器上，用 Docker 或 PM2 把它独立部署到生产环境。Docker 在容器中运行应用；PM2 托管 Node.js 进程，安装和更新则由 app-installer 完成。

本栏目适用于你自己的 NocoBase Core 应用。两篇指南都以 [搭建第一个应用](../tutorials/build-your-first-app.md) 中的任务应用为例，并分别提供 **使用 Agent** 和 **不使用 Agent** 两条路径。

## 如何选择

| 方式 | 适用场景 | 继续阅读 |
| --- | --- | --- |
| Docker | 用容器运行应用，通过镜像和持久化挂载管理部署 | [使用 Docker 部署](../tutorials/deploy-with-docker.md) |
| PM2（app-installer） | 在 Linux 服务器上直接运行 Node.js 进程，用 app-installer 安装部署包、管理配置和更新 | [使用 PM2 部署（app-installer）](../tutorials/deploy-with-app-installer.md) |

如果已经有容器运维的流程，选择 Docker；如果希望直接在服务器上托管 Node.js 进程，选择 PM2（app-installer）。两种方式都使用独立的生产配置、数据库和文件存储。目标平台、数据库和存储方案应在构建之前确定，具体的准备步骤见相应的指南。

## 部署前要准备什么

- **可以构建的源码**：应用已经通过测试，依赖和锁文件已经确定，构建平台与运行环境一致。
- **明确的运行环境**：确定服务器、应用目录、端口、访问地址以及所需的权限；域名、HTTPS 和反向代理按实际环境配置。
- **独立的运行配置**：准备数据库、管理员和应用所需服务的配置，妥善保存生成的密钥，不要把含有密钥的配置提交到仓库。
- **持久化的数据**：确认数据库和文件存储的位置，并建立备份与恢复的方式。

构建产物包含页面、接口、迁移和运行时依赖，但不会自动带上开发数据库、上传的文件或运行密钥。首次使用新数据库时，会执行迁移和必需的 Seed。当前的入门示例会初始化任务相关的角色，但不会复制开发环境中的任务、团队用户或角色分配；通过管理页面创建的其他角色和授权也不会自动迁入。需要保留这些数据时，请另外安排数据迁移。

直接运行 `node dist/server/standalone.js` 可以检查构建产物是否可用；正式部署还需要安排进程托管、配置管理和数据持久化。

## 首次部署与发布新版本

| 首次部署 | 发布新版本 |
| --- | --- |
| 准备部署目录和生产环境的运行配置 | 沿用已有的应用和部署目录，保留稳定的密钥 |
| 在新数据库中执行迁移和必要的初始化，或按计划迁入已有数据 | 备份已有数据，检查并执行新增的迁移 |
| 验证登录、业务功能、权限和数据持久化 | 同时验证新功能、旧数据和原有的权限 |

之后发布新的业务版本时，修改源码、通过测试、重新构建，再按原来的部署方式更新。每篇部署指南都有“部署新版本”一节；[发布应用新版本](publish-app-release.md) 汇总了两种方式在更新时的差别。

如果要更新框架及相关依赖，请先完成 [升级 NocoBase Core](../developing-apps/upgrade-nocobase-core.md)，验证兼容性之后再部署。

## 发布后的检查与恢复

部署完成后，检查实际的访问地址、登录、主要业务的读写、普通用户的权限，以及重启后数据是否保留。构建成功、上传成功或健康检查通过，都不能单独代替业务验证。

发布之前，保留旧版本的构建、与之匹配的配置，以及可以恢复的数据库和文件备份。回退程序版本不会自动撤销数据库迁移或业务写入；如果旧程序无法使用新的表结构，需要恢复与之匹配的数据，并处理备份之后产生的写入。具体的更新和恢复操作，按所选方式的指南执行。
