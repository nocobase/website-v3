---
title: 和 Agent 一起开发
description: 借助应用的 AGENTS.md 和 Skills，用业务语言描述需求、检查实现，并验证真实结果。
---

和 Agent 一起开发时，你负责说明三件事：希望用户完成什么、有哪些业务限制、怎样算完成。Agent 负责结合项目约定找到相关代码、实现改动并验证结果。你不需要先弄清该调用哪个内部 API，才能把需求讲清楚。

本篇面向已经创建好的应用；如果还没有项目，请先阅读 [创建应用](../getting-started/create-app.md)。这里的 Agent 指帮助你编写应用代码的 Coding Agent，与应用内供业务用户使用的 Agents 是两回事。

## 在应用项目中开始工作

在应用根目录启动 Agent，使它能读取源码、`package.json`、`AGENTS.md` 和 `.agents/`。继续开发已有项目时，说明当前工作目录和已有功能，避免它另建一个应用。

开始时可以这样说：

```text
请在当前应用中继续开发。先阅读项目的 AGENTS.md，并按这次任务查阅相关 Skills。
先了解现有实现和未提交的修改，保留已有功能与我的改动。
如果已有插件或组件能满足需求，优先使用它们。
```

这段话用于建立工作上下文，不必在每次小修改时都完整重复。涉及部署、数据库变更或账号操作时，还要明确目标环境和允许操作的范围。

## 项目指引与开发规则

应用把开发约定保存在项目中。Agent 应读取与当前安装版本对应的约定，而不是套用其他版本或其他项目的规则。

| 位置 | 内容 | 怎样维护 |
| --- | --- | --- |
| `AGENTS.md` | 应用开发的入口规则，以及进一步阅读的索引 | 随应用维护，保持简短 |
| `.agents/rules/` | 本应用特有的结构、业务约定和定制说明 | 应用约定变化时同步更新，并从 `AGENTS.md` 链接 |
| `.agents/skills/` | 依赖包和插件提供的开发、升级、部署及能力使用指引 | 根据已安装的依赖同步生成，不要直接修改 |

跨任务都要遵守的应用约定，写入 `.agents/rules/` 并从 `AGENTS.md` 链接。例如，团队已经确定了业务日期的时区、状态流转规则或权限边界，可以集中记录在 `.agents/rules/business.md`，再在入口文件中添加：

```markdown
## 项目规则

- [业务规则](.agents/rules/business.md)：业务日期、状态流转与权限约定。
```

**应用规则写在应用里，共享规则随包维护。** 已确认的约定应与代码保存在一起，方便下一次会话或其他开发者继续使用；依赖提供的指引则在源包中维护，再同步到应用。

## 使用与同步 Skills

日常功能开发从 `.agents/skills/nocobase-app-development/SKILL.md` 开始，按任务读取相关的参考文件；用到某个插件的能力时，再查阅该插件的 Skill。升级 Core 和部署应用各有专门的指引，按当前任务选择即可。

Skills 来自当前已安装的依赖。安装或升级相关包后，请确认指引已经同步，使 Agent 用到与依赖版本相匹配的说明。当前模板会在 `postinstall` 时自动同步；如果安装时跳过了脚本，或同步目录缺失，可以在应用根目录运行：

```bash
pnpm nocobase skills sync
```

想先查看同步计划，可以执行 `pnpm nocobase skills sync --dry-run`。更多选项见命令行参考中的 [插件与 Skills](../reference/cli.md#插件与-skills)。

同步后，检查命令输出和相应的 `SKILL.md`，让 Agent 重新读取本次任务相关的指引。如果仍然缺少某个插件的 Skill，先确认该插件已安装、已按要求注册，并且它确实提供了 Skill。同步得到的副本会随源包一起更新；应用特有的补充约定继续放在 `.agents/rules/` 中。

## 描述需求与拆分任务

一份可以直接执行的需求，通常回答五个问题：

| 要说明的内容 | 示例 |
| --- | --- |
| 谁在什么地方使用 | 团队成员在任务列表里查看和修改任务 |
| 希望完成什么 | 新建任务时可以选择一位负责人，也可以暂不分配 |
| 规则和边界 | 只能选择已启用的现有用户；旧任务和现有权限保持不变 |
| 失败时怎么办 | 负责人已停用时保留任务标题，并提示重新选择 |
| 怎样判断完成 | 保存后刷新仍能看到负责人；没有权限时，界面和接口都拒绝操作 |

尚未确定的业务决定要直接说出来，例如“旧任务是否需要统一指定负责人还没定”，而不是让 Agent 猜一个默认用户。至于文件位置、组件名称和内部方法，可以交给它从项目指引中查找。

### 一个可以直接使用的需求

下面的需求适用于已有任务列表和新建功能、但还没有负责人功能的应用：

```text
请给现有任务应用增加负责人。

新建任务时可以选择一位启用的现有用户，也可以暂不分配。
任务列表要显示负责人；没有负责人时显示“未分配”。
旧任务继续保留，不自动替它们指定负责人，也不改变任何用户的角色和权限。

如果选择的用户在保存前已经停用，保留我填好的标题，提示重新选择。
保存成功后，刷新页面仍能看到正确的负责人。
沿用当前应用的界面风格，并提供中英文文案。

请按项目指引实现，使用独立测试数据验证新建、未分配、停用用户和无权限的情况。
这一轮不做任务转交、通知或“我的任务”。
完成后告诉我改了什么、验证了什么，以及还有哪些情况没有验证。
```

这段需求描述的都是用户能理解的行为，具体的字段、关联、权限策略和选择器用法交给 Agent 按应用约定处理。如果有必须遵守的接口约定或已有设计，可以把相关文档一并提供，不需要把全部实现细节重新抄进提示词。

### 把较大的需求拆成可验证的改动

“做一个完整的项目管理系统”包含太多尚未决定的业务问题。更好的做法是先完成一个范围小、能闭环的结果，再扩展下一项能力。

以给任务增加项目归属为例，可以按下面的顺序推进：

1. **数据层**：项目与任务的关系、旧任务如何保留、关联约束，先用数据库测试验证。
2. **业务接口**：查询和新建项目、修改任务归属，验证输入和两侧的数据权限。
3. **页面交互**：项目列表、新建弹窗和任务的项目选择，验证加载、保存、失败和键盘操作。

每一步都说明当前范围和完成条件。只完成了数据层时，应明确说明页面还不能操作，不能把“迁移测试通过”说成“用户已经可以管理项目”。如果只是想快速完成一个小功能，也可以一次交付这几部分，不必为每个文件单独发起任务。

## 检查实现与验证结果

先检查可观察到的行为，再确认改动是否符合项目约定。你可以要求 Agent 给出简短的改动说明并指出相关文件，重点回答以下问题：

- 旧数据和原有功能是否保留？数据结构的变化是否通过新的迁移完成？
- 页面访问、业务操作和数据范围是否分别处理？有没有意外给用户增加权限？
- 是否使用了现有插件和组件？有没有改动需求之外的布局、主题或其他功能？
- 字段错误是否显示在对应输入旁？保存失败后输入是否保留？
- 新增接口是否出现在应用的 API 文档中？中英文文案是否齐全？

不要仅凭一张成功截图就判断功能已经完成。隐藏按钮不代表接口会拒绝越权请求，显示成功提示也不代表数据真的保存进了数据库。

### 验证真实结果

让 Agent 把自动检查的结果和实际操作的结果分开报告。验证范围应覆盖本次改动以及受影响的已有行为，不要把无关的全量检查当成每次修改的固定步骤。

| 验证层次 | 要确认什么 |
| --- | --- |
| 静态检查 | 修改的代码符合项目的格式、类型和约定 |
| 数据库与接口测试 | 使用隔离数据检查持久化、迁移、校验、授权，以及失败后的数据状态 |
| 页面与组件测试 | 检查表单、加载、反馈和用户输入行为 |
| 浏览器操作 | 在实际应用中完成操作、刷新确认，并用普通用户检查权限 |

凡是能用真实应用、数据库和权限服务验证的业务规则，就直接验证。只有在外部传输、测试环境缺少浏览器能力等必要的边界上才使用替身，并说明替代了什么；不要 mock 正在验证的业务行为。

浏览器验证应使用应用实际输出的完整入口地址，以及专门的测试账号。数据库测试应使用隔离的数据，不能为了跑通测试而清空当前应用的业务数据。完整的任务示例见 [搭建第一个应用](../tutorials/build-your-first-app-agent-first.md)。

发现问题时，给出复现步骤和预期结果，而不只是说“不对”：

```text
用只读成员登录后，任务列表没有“新建”按钮，但直接提交新建请求仍然成功。
预期是只读成员既不能在页面新建，也不能通过接口新建。
请检查服务端授权，修复后用同一普通账号验证，并确认管理员仍然可以新建。
```

如果 Agent 缺少验证某一步所需的环境或账号，应说明缺什么、已经验证到哪一步，而不能用“代码看起来没问题”代替实际验证结果。

## 交付与继续迭代

每次改动结束时，都应留下可检查的代码和验证记录。让 Agent 简要说明改了什么、通过了哪些检查、还有哪些未验证，以及如何启动或查看结果。应用特有的新约定写入 `.agents/rules/`，业务代码和测试一起维护。

继续迭代时，说明当前已经完成了哪些功能，以及本轮新增或调整的需求。沿用已有的业务规则和验收结果，只补充本次变化的验证；发现问题时，把复现步骤和预期行为一并提供给 Agent。

提交代码、发布版本和部署到具体环境是三个不同的动作，请按本次任务的约定执行；本地测试通过并不意味着已经部署。需要上线时，请继续阅读 [选择部署方式](../deployment/choose-a-deployment-method.md)。

如果选择手动开发，同一套数据、接口、页面和验收约定仍然适用。各专题的“不使用 Agent”部分提供了对应的代码和操作步骤。
