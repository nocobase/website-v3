---
title: 和 Agent 一起开发
description: 用业务语言描述需求，让 Agent 按项目指引实现和测试，再用真实结果验收。
---

和 Agent 一起开发时，分工很清楚：**你**说明要做什么、业务规则是什么、怎样算完成，并做出业务上的决定；**Agent** 按项目指引找到相关代码，完成实现和测试，再如实报告结果。你不需要先弄清该调用哪个内部接口，才能把需求说清楚。

本篇面向已经创建好的应用，还没有项目时先看 [创建应用](../getting-started/create-app.md)。这里的 Agent 指帮你写应用代码的 Agent；在应用里按权限处理业务的业务 Agent 是另一项能力，见 [Agents](../using-plugins/agents-and-knowledge/agents.md)。

## 一轮开发怎样进行

1. 开始前提交当前代码，让这一轮的改动可以单独查看。
2. [描述需求](#描述需求)：要做什么、规则和边界、怎样算完成。
3. Agent 实现并测试，报告改了什么、验证了什么。
4. [检查结果](#检查结果)：在浏览器里试用，再查看代码改动。
5. 有问题就给出复现步骤，让 Agent 继续修改；没问题就提交。
6. 这一轮形成的新约定，[写进项目规则](#让-agent-记住项目约定)，之后的会话会自动沿用。

## 开始一个会话

在应用根目录开启 Agent 会话。编码工具会在会话开始时读取 `AGENTS.md`（模板里的 `CLAUDE.md` 只是引用它，供 Claude Code 使用），再从那里找到项目规则和 Skills。

> [!NOTE]
> 在同一个会话里刚创建完应用时，有些编码工具要到新会话才会加载应用自带的 Skills。如果 Agent 找不到 `nocobase-app-development` Skills，在应用目录重新开启一个会话。

第一次在项目里工作，或者接手别人的项目时，可以这样开场：

```text
请在当前应用中继续开发。先阅读 AGENTS.md，按这次任务查阅相关技能。
先了解现有实现和未提交的修改，保留已有功能和我的改动。
已有插件或组件能满足需求的，优先使用它们。
```

之后的小改动不必每次重复。

**说清楚允许做什么。** 修改代码和本地开发数据库，通常可以交给 Agent 放手去做；部署、修改 `config.yml` 里的密钥、重置或回退数据库、操作真实账号，要明确说明能不能做、在哪个环境做。`db reset`、`db rollback` 等会改动数据的命令，在非交互终端里不加 `--force` 会拒绝执行。遇到这种情况，Agent 应该停下来问你，而不是自己加上 `--force`。

**应用在哪里运行。** 可以在自己的终端里运行 `pnpm dev`，也可以让 Agent 启动；由 Agent 启动的进程会随会话结束而停止。打开应用时使用 `pnpm dev` 打印的 `Local:` 地址，包括末尾的 `/main/` 等路径。

## 描述需求

一份能直接交给 Agent 的需求，通常回答五个问题：

| 要说明的内容     | 示例                                                     |
| ---------------- | -------------------------------------------------------- |
| 谁在什么地方使用 | 团队成员在任务列表里查看和修改任务                       |
| 希望完成什么     | 新建任务时可以选择一位负责人，也可以暂不分配             |
| 规则和边界       | 只能选启用的现有用户；旧任务和现有权限保持不变           |
| 失败时怎么办     | 负责人已停用时保留任务标题，提示重新选择                 |
| 怎样判断完成     | 保存后刷新仍能看到负责人；没有权限时界面和接口都拒绝操作 |

还没定下来的业务决定要直接说出来，例如“旧任务要不要统一分配负责人，还没确定”，不要让 Agent 猜一个默认值。文件放在哪里、用哪个组件、调用哪个内部方法，交给 Agent 按项目指引决定。

### 示例：给任务增加负责人

下面的需求适用于已经有任务列表和新建功能、还没有负责人的应用：

```text
请给现有任务应用增加负责人。

新建任务时可以选择一位启用的现有用户，也可以暂不分配。
任务列表要显示负责人；没有负责人时显示“未分配”。
旧任务继续保留，不自动替它们指定负责人，也不改变任何用户的角色和权限。

如果选择的用户在保存前已经停用，保留我填好的标题，提示重新选择。
保存成功后，刷新页面仍能看到正确的负责人。
沿用当前应用的界面风格，并提供中英文文案。

请按项目指引实现，使用独立测试数据验证新建、未分配、停用用户和无权限的情况。
这一轮不做任务转交、通知或“我的任务”。
完成后告诉我改了什么、验证了什么，以及还有哪些情况没有验证。
```

需求里写的是用户能理解的行为。字段、关联、权限策略和选择器怎么用，交给 Agent 按应用约定处理。已经有接口约定或设计稿时，一并提供即可，不需要把实现细节抄进需求。

### 较大的需求，先拆小

“做一个完整的项目管理系统”里有太多还没决定的业务问题。先做出一个小而完整、可以验证的结果，再扩展下一项。

改动涉及多个部分时，可以先让 Agent 给出计划，确认后再动手：

```text
先不要改代码。请阅读相关实现，列出这次要改哪些部分、需要我决定哪些业务问题，以及打算怎样验证。
```

例如给任务增加所属项目，可以分三步推进：

1. **数据**：项目和任务的关系、旧任务怎样保留、关联约束，用数据库测试验证。
2. **接口**：查询和新建项目、修改任务所属的项目，验证输入校验和两边的数据权限。
3. **页面**：项目列表、新建弹窗和任务的项目选择，验证加载、保存、失败提示和键盘操作。

每一步都说明范围和完成条件。只做完数据这一步时，用户在页面上还操作不了，不能把“迁移测试通过”说成“用户已经可以管理项目”。小功能一次做完也可以，不必每个文件单独发起一轮。

## 检查结果

### 先试用

在浏览器里像用户一样操作一遍：新建、修改、刷新后再看，再换一个普通账号试试权限。不要只凭一张成功截图判断完成：按钮隐藏了，不代表接口会拒绝越权请求；页面提示保存成功，也不代表数据真的写进了数据库。

### 再看改动

用 `git status` 和 `git diff` 查看这一轮改了哪些文件，或者让 Agent 列出改动并说明原因。重点看这几件事：

- **旧数据和已有功能**：是否都保留了；表结构变化是否写成了新的迁移，而不是修改已经合并的迁移。
- **权限**：页面访问、业务操作和数据范围是否分别处理；有没有为了让功能能用，把权限授给所有用户。
- **复用**：是否使用了已有的插件和组件，而不是重写权限、通知这类现成能力；有没有改动需求以外的布局、主题或功能。
- **交互细节**：字段错误是否显示在对应的输入框旁边；保存失败后，已填的内容是否还在。
- **接口和文案**：新接口是否出现在应用的接口文档里（应用基础路径下的 `/api/swagger`，例如 `/main/api/swagger`）；中英文文案是否齐全。

### 让 Agent 分开报告验证结果

让 Agent 把自动检查和实际操作分开报告，并说明每项检查覆盖了哪些范围：

| 层次 | 确认什么 | 常用命令 |
| --- | --- | --- |
| 静态检查 | 代码格式、类型和项目约定 | `pnpm lint`、`pnpm typecheck` |
| 数据库与接口测试 | 用隔离数据检查保存、迁移、校验、授权，以及失败后的数据状态 | `pnpm test --project node` |
| 页面与组件测试 | 表单、加载状态、提示和用户输入 | `pnpm test --project client` |
| 浏览器操作 | 在运行中的应用里完成操作、刷新确认，并用普通账号检查权限 | `pnpm test:e2e`，或手动操作 |

检查只需覆盖本次改动和受它影响的部分。`pnpm check` 会运行全部检查和构建，不必每次小改动都跑。命令成功退出也不等于验证通过：默认模板在没有找到测试时也会正常退出，要看报告里实际运行了哪些文件、多少用例、跳过了什么。

能用真实的应用、数据库和权限服务验证的规则，就直接验证。只有外部服务、测试环境缺少浏览器等确实无法直接验证的部分才用模拟，并说明模拟了什么；不要模拟正在验证的业务行为本身。测试使用隔离数据，不能为了跑通测试清空应用里的业务数据。具体写法见 [测试与验收](testing-and-acceptance.md)，完整的任务示例见 [搭建第一个应用](../tutorials/build-your-first-app.md)。

Agent 缺少环境或账号、没法验证某一步时，应该说明缺什么、验证到了哪里，不能用“代码看起来没问题”代替实际结果。

### 发现问题时

给出复现步骤和预期结果，而不是只说“不对”：

```text
用只读成员登录后，任务列表没有“新建”按钮，但直接提交新建请求仍然成功。
预期是只读成员既不能在页面新建，也不能通过接口新建。
请检查服务端授权，修复后用同一个普通账号验证，并确认管理员仍然可以新建。
```

## 让 Agent 记住项目约定

每次会话开始时，Agent 只知道仓库里写下来的东西，在对话里口头说好的规则，下一次会话就不记得了。需要长期遵守的约定，要写进项目：

| 位置 | 内容 | 怎样维护 |
| --- | --- | --- |
| `AGENTS.md` | 所有任务都要遵守的规则，以及其他规则文件的索引 | 保持精简：每次会话都会完整加载它。模板自带的测试限制它不超过 32 KB，并检查其中的链接 |
| `.agents/rules/` | 这个应用特有的约定。模板已经带了工作区、组件、页面外框、构建与部署几份 | 约定变化时更新，并在 `AGENTS.md` 的索引里登记 |
| `.agents/skills/` | 依赖包随包提供的 Skills | 安装依赖时自动同步，不要直接修改 |

两种情况值得写规则：同一个问题已经纠正过一次，又出现了；团队做了跨任务都要遵守的决定，例如业务日期的时区、状态流转的顺序、权限边界。直接让 Agent 记下来：

```text
把这条约定记到 .agents/rules/business.md：业务日期一律按 Asia/Shanghai 计算；
任务只能按 待处理 → 进行中 → 已完成 的顺序流转。
在 AGENTS.md 的索引里加上这份文件，并写明什么时候需要读它。
```

`AGENTS.md` 的索引里会多出一行，例如：

```markdown
| [.agents/rules/business.md](.agents/rules/business.md) | 涉及业务日期、任务状态或权限边界时 |
```

规则文件和代码一起提交，下一次会话和其他同事都会沿用。

## Skills 从哪里来

Skills 是随包发布的开发说明，告诉 Agent 在当前安装的版本上怎样做事。应用里常用的有：

| Skills | 用途 |
| --- | --- |
| `nocobase-app-development` | 日常开发的入口，按任务指向页面、接口、迁移、测试等参考文档 |
| `nocobase-app-plugin-development` | 在应用里开发插件 |
| `nocobase-app-upgrade` | 升级 NocoBase，合并新版模板的变化，见 [升级 NocoBase Core](upgrade-nocobase-core.md) |
| `nocobase-deployment` | 构建部署包，部署到服务器 |
| 插件自带的 Skills | 例如邮件插件的 `nocobase-app-plugin-mail`。使用插件的能力前，Agent 先读它的 Skills，避免重写插件已经做好的功能 |

运行 `pnpm install` 时会自动同步 Skills，所以它们始终和安装的版本配套。如果安装时跳过了脚本，或者 `.agents/skills/` 缺失、过期，在应用根目录手动同步：

```bash
pnpm nocobase skills sync
```

加 `--dry-run` 可以先查看同步计划，更多选项见 [命令行参考](../reference/cli.md#插件与-skills)。还缺某个插件的 Skills 时，先确认插件已经安装、已经注册，并且它确实提供 Skills。

`.agents/skills/` 里的文件是同步生成的，直接修改会在下次同步时被覆盖。应用自己的补充写进 `.agents/rules/`。

## 交付和继续

一轮结束前，让 Agent 简要说明：改了什么、运行了哪些检查以及覆盖范围、还有什么没验证、怎样查看结果。确认后提交代码，新增的规则文件也一起提交。

下一轮可以开新会话。代码和项目规则都在仓库里，只需说明当前已经完成了什么、这一轮要新增或调整什么。

提交代码、发布版本、部署到某个环境是三件不同的事，本地测试通过不代表已经上线。需要部署时，见 [选择部署方式](../deployment/choose-a-deployment-method.md)。

自己写代码时，同样的需求描述、检查和验收方法也适用；各专题中“不使用 Agent”的部分给出了对应的代码和步骤。
