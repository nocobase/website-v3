title: 管理插件
description: 查看应用实际注册了哪些插件，使用已有能力，并管理插件的注册、更新、移除和扩展。
---

默认模板已经包含多种插件。开发应用时，通常直接使用它们提供的认证、用户、权限、文件等能力；只有确认当前应用缺少所需的能力时，才需要增加插件。任务、项目这类应用自己的业务代码，仍然放在应用目录中，不必先拆成插件。

本篇说明应用如何管理插件，它既不是插件开发教程，也不是全部可用插件的产品目录。命令以示例应用已安装的 CLI 为准，执行前可以用 `--help` 确认当前版本支持哪些选项。

如果需要开发自己的插件，请先阅读 [什么时候写插件](../extension-development/when-to-write-a-plugin.md)，再按 [创建插件](../extension-development/create-plugin.md) 在当前 App 中生成骨架；完整的实践见 [编写第一个插件](../extension-development/write-your-first-plugin.md)。

使用团队发布的插件时，需要先配置私有源和读取权限，再进行安装和注册，见 [构建与发布](../extension-development/publish-plugin.md)。

## 使用 Agent

```text
请检查当前应用已经具备哪些插件能力，以及现有业务实际使用了哪些。

先查看已安装依赖、实际注册和相关使用指引，不要仅凭插件名称判断能力，也不要重复实现已有功能。
本轮先不新增、升级或移除插件。

告诉我每项业务依赖哪些插件、通过什么公开入口使用，以及哪些管理页面或必要配置尚未接通。
如果发现必须变更依赖，请说明具体原因、兼容版本和受影响功能，再给出可检查的改动方案。
不要改变现有用户权限或清理业务数据。
```

需要真正变更插件时，请把目标说清楚，例如“把当前应用的定时任务插件更新到已确认兼容的版本，并验证现有任务定义和执行功能”。注册、更新还是移除，由这次任务本身决定；不要让一次能力检查顺带改变应用的依赖。

## 不使用 Agent

### 查看安装与注册

先查看 `package.json` 中的 `@nocobase/app-plugin-*` 依赖，以及锁文件中实际解析出的版本。再检查三个组合入口：

| 文件 | 注册内容 |
| --- | --- |
| `client/plugins.ts` | 浏览器端的插件贡献 |
| `server/plugins.ts` | 服务端的 Provider、路由等贡献 |
| `cli/plugins.ts` | 命令行贡献 |

包出现在依赖中，并不等于已经注册到运行时；三个入口的内容也不要求完全相同，例如只提供命令的插件，只需要接入 CLI 入口。数组的顺序会影响贡献的顺序，不要为了排序好看而随意调整。

`.agents/skills/` 中存在某个 Skill，同样不能证明插件已经启用，因为 Skills 可能是从直接依赖同步过来的。是否实际注册，以组合入口为准。插件包通常放在应用的 `dependencies` 中，以便进入部署产物；不要误以为客户端插件只能放进 `devDependencies`。

### 使用已有能力

先阅读已安装插件的 Skill，确认它公开了哪些服务 Token、客户端 Hooks、组件、路由和管理能力。业务功能应通过公开导出来调用这些能力，不要直接写插件的内部表，也不要从插件内部的源码路径导入实现。

例如，项目功能使用权限插件来声明“查看、新建、修改任务项目”等操作，并复用用户和角色管理；不需要再安装一套权限包，也不应自己另实现一份角色存储。此外，应用还要把用到的能力接入真实的页面和业务接口；仅仅安装依赖，并不会自动完成业务功能。

### 注册确实缺少的插件

下面以定时任务插件为例演示命令。如果应用已经注册了它，跳过这一步即可；换成其他目标插件之前，请先确认它的可用性、版本要求和所需配置：

```bash
pnpm nocobase plugin register @nocobase/app-plugin-scheduler --dry-run
pnpm nocobase plugin register @nocobase/app-plugin-scheduler
```

这个命令负责安装依赖、接入插件导出的组合入口，并同步 Skills。执行后，请检查 `package.json`、锁文件，以及 Client／Server／CLI 注册的实际变化。需要固定某个兼容版本时，使用 `--version`；不要把新包的默认版本当成一定与当前应用兼容。

单独运行 `pnpm add` 只解决了包的安装，不能代替运行时注册。`--no-install` 要求依赖已经可以被解析；`--disabled` 用于只安装、不接入运行时贡献，并不代表相关功能已经可以使用。请根据命令输出检查实际处理了哪些入口。

### 更新插件

先查看单个插件的更新计划，再执行更新：

```bash
pnpm nocobase plugin update @nocobase/app-plugin-scheduler --dry-run
pnpm nocobase plugin update @nocobase/app-plugin-scheduler
```

包名是位置参数，不是 `--plugin`。不提供包名时，会更新所有已注册的插件；因此，只想更新一项能力时，请明确写出包名。

pnpm 的更新遵循项目声明的版本范围；如果版本范围是固定的，就不保证能得到更高的版本。需要跨范围升级时，先确定兼容的目标版本，调整依赖范围，同步锁文件和 Skills，再检查变化。更新插件并不等于合并新模板，也不能代替 [升级 NocoBase Core](upgrade-nocobase-core.md) 的整体流程。

更新后，检查插件可能带来的迁移、配置和公开接口变化，验证使用它的功能，并重新构建应用。已经部署的旧产物，不会因为开发目录中的依赖更新而自动改变。

### 区分停用功能与移除插件

只是暂时不展示某个功能时，先决定是仅隐藏入口，还是禁止使用。只隐藏菜单并不能阻止直接访问页面或调用 API；停用策略应覆盖所有实际的操作入口，并保留日后恢复所需的代码和数据。

彻底移除插件之前，先查找应用中的 import、Client／Server／CLI 注册、路由、配置、服务、测试，以及其他能力对它的依赖。迁移或移除这些引用之后，才执行卸载。

下面的 `<name>` 是占位符，请替换为已经确认不再使用的插件；不要对仍在承担业务功能的插件直接执行：

```bash
pnpm nocobase plugin unregister '@nocobase/app-plugin-<name>' --dry-run
pnpm nocobase plugin unregister '@nocobase/app-plugin-<name>'
```

也可以通过 `pnpm nocobase package remove <完整包名>` 移除直接依赖的 NocoBase 包；如果它是插件包，会转交给插件注销流程处理。不要只是手动删除 `package.json` 中的一行，否则注册信息和同步文件可能会残留。

注销命令不会替你决定如何处理历史业务数据，它也不是数据库的回滚方案。需要保留、迁移或删除数据时，请单独设计数据处理方案；不要顺手删除插件的目录或数据表来“清理干净”。

### 扩展插件提供的界面

| 需求 | 优先使用 |
| --- | --- |
| 插件已有配置选项 | 注册时传入公开的 options |
| 插件公开了可组合的组件 | 从公开导出引用，由应用自行组合 |
| 需要自由修改界面源码 | 从 [NocoBase UI Library](https://ui.nocobase.com/) 安装组件或区块，由应用维护副本 |
| 替换插件某个页面的呈现 | 已支持的 `client/route-overrides.ts`，或插件提供的覆盖方式 |
| 完全属于应用自己的业务页面 | 在 `client/routes.ts` 中注册自己的页面 |

覆盖页面时，应保持原路由的身份、路径和访问条件，按约定替换懒加载的组件；不要再声明一个相同的路径来制造冲突，也不要在同一条路由上叠加多个覆盖来源。当前模板中的登录、注册等页面属于应用源码，不能仅仅因为使用了认证插件，就把它们当成插件拥有的路由。

不要编辑 `node_modules/` 或 `.agents/skills/` 中的包内容。应用特有的约定放入 `.agents/rules/`；共享插件本身的问题，应在它的源码仓库中修复。

## 验证结果

检查依赖和锁文件、三个组合入口、同步的 Skills，以及实际的使用方。运行受影响部分的类型检查、测试和构建；涉及迁移时，验证升级后的旧数据；涉及 API 时，检查应用的 API 文档。在浏览器中，同时验证正常访问和普通用户的权限边界。

如果手动修改了依赖，或者操作中途失败导致 Skills 不一致，可以重新同步：

```bash
pnpm nocobase skills sync
```

同步只会修复指引的副本，不会自动注册插件，也不会修复应用代码。进一步的内容请阅读 [应用开发概览](overview.md) 和 [测试与验收](testing-and-acceptance.md)。
