## 提供的能力

`@nocobase/app-plugin-authentication` 把 Better Auth 接入应用，提供登录身份、会话、认证客户端和服务端认证中间件。它回答的是“当前用户是谁”；这个用户能执行哪些操作，则由 [权限管理](../authorization/permissions.md) 决定。

三者的分工是：认证插件提供身份与会话机制，登录页面由应用维护，业务操作的权限由授权插件决定。

## 使用场景与示例

### 示例：只允许受邀成员加入

1. 在应用配置中关闭自行注册，保留需要的登录方式。
2. 让应用的注册入口与配置状态保持同步，而不只是隐藏一个按钮。
3. 通过 [用户管理](users.md) 发送邀请，让新成员通过邀请页创建账号。
4. 分别检查访客、已登录成员和被停用用户在页面和接口上的行为。

如果要使用内置的密码找回邮件，请启用 `auth.passwordReset.enabled`，配置应用的公开地址和可以投递的系统邮件渠道，再结合 `usePasswordResetCapability()` 展示入口。仅仅启用了邮箱密码登录，并不代表找回邮件已经可用。应用也可以提供自己的 `sendResetPassword` 实现。跨域部署时，还需要正确配置可信来源；不能靠绕过请求来源检查来解决登录问题。

**开发提示词**（交给当前应用目录中的 Coding Agent）：

```prompt
请用身份认证插件将应用设为仅受邀成员加入。
沿用已有登录、会话和扩展配置，同时关闭服务端自行注册与对应页面入口。
如启用密码找回，先检查公开地址和通知邮件配置，再展示可用入口。
验证访客、受邀成员、停用用户及退出登录后的页面和接口行为。
```

**完成的标志**：直接发起的自行注册请求被拒绝；受邀用户仍然可以登录，并按原有的权限访问。

## 重要原理与实现

下表列出实现本例时的接入位置和预期的界面变化。这些是开发说明，具体的文件名沿用当前应用的结构。

| 接入位置 | 代码或配置的变化 | 界面与行为的变化 |
| --- | --- | --- |
| `client/config/auth.ts`、`server/config/auth.ts` | 保留并组合相匹配的认证扩展，调整注册和找回配置 | 登录方式与可用的入口保持一致 |
| 应用的登录、注册、找回页面 | 沿用模板页面，按实际能力显示操作 | 不再出现不可用的注册或找回入口 |
| 受保护的路由和接口 | 先接入登录检查，再执行业务授权 | 访客被正确引导，直接调用 API 也受到保护 |

### 接入与配置

默认模板已经在 Client 和 Server 两侧注册了认证插件，并在 `client/config/auth.ts`、`server/config/auth.ts` 中组合了认证配置。修改现有配置时，请保留应用需要的扩展，不要用一个示例覆盖整个 `plugins` 数组。

| 配置或文件 | 用途 |
| --- | --- |
| `server/config/auth.ts` | 用 `defineAuthConfig` 组合登录方式和服务端扩展 |
| `client/config/auth.ts` | 注册与服务端相匹配的客户端扩展 |
| `auth.emailAndPassword.enabled` | 是否启用邮箱密码登录 |
| `auth.emailAndPassword.disableSignUp` | 是否关闭自行注册 |
| `secrets.keys` / `SECRETS_KEYS` | 提供持久的密钥，认证插件从中派生签名密钥和加密密钥 |
| `auth.passwordReset` | 配置密码找回及其邮件渠道 |

认证所需的数据表由插件的迁移维护。登录、注册、密码找回等页面属于应用源码，插件不会再额外注册一套相同的页面。使用现有的模板页面时，请先检查它们的路由和实际启用的登录方式。

### 在页面和接口中使用

客户端从 `/client` 使用 `useAuthentication()` 读取会话和加载状态，使用 `useAuthenticationClient()` 调用认证客户端。需要登录的页面用 `auth: 'required'` 声明，访客页面则按应用的路由约定配置。

服务端从 `/server` 取得 `authenticationToken`，用认证服务的 `required()` 中间件保护接口；业务权限在认证之后再检查。只隐藏登录后才显示的菜单，并不能保护 API。

## AI 开发的约束与验证

### 本插件的开发约束

- 客户端扩展和服务端扩展要成对修改；持久密钥和可信来源沿用部署时的配置。
- 关闭注册后，要检查直接发起的注册请求；启用密码找回后，要检查邮件的实际投递和链接，而不只是检查按钮。
- 测试会话的恢复、退出登录和被停用的身份；业务接口在认证之后，仍要继续执行授权。

### 常见问题

- **安装后没有登录页**：登录页由应用负责，请检查应用自身的路由和模板页面。
- **重启后会话异常**：检查各个实例是否使用同一组持久的认证密钥，以及会话存储的配置。
- **登录成功后仍无权访问**：检查业务授权；登录本身不会自动赋予管理权限。
- **需要用脚本调用 API**：参阅 [API 密钥](api-keys.md)，不要照着浏览器会话的处理方式另造一套认证机制。
