## 提供的能力

`@nocobase/app-plugin-users` 提供用户查询、账号管理、成员邀请和个人偏好等能力。登录身份、密码和会话由 [身份认证](sign-in.md) 提供，用户管理复用这些数据；角色与操作权限则由 [权限管理](../authorization/permissions.md) 和应用的业务定义。

插件直接提供邀请接受页；用户列表、管理表单和业务角色范围需要由应用接入。

## 使用场景与示例

### 示例：邀请成员加入应用

1. 在应用的用户管理页中选择“邀请”，填写邮箱和允许分配的角色。
2. 创建邀请后，逐一检查每个地址的处理结果；有权获取链接的邀请者，可以复制返回的 `inviteUrl`。
3. 接收者打开邀请页：新用户填写姓名和密码；已有用户用被邀请的邮箱登录后接受邀请。
4. 在用户列表中检查账号及其角色，再以该用户身份验证业务的访问范围。

邀请邮件依赖可用的邮件投递配置。邮件发送失败并不等于邀请创建失败，请根据响应判断是否可以转发邀请链接。重新生成链接后，旧链接会失效。系统邀请邮件使用通知投递能力，不要求接入 [邮件](../notifications/mail.md) 插件的用户邮箱。

**开发提示词**（交给当前应用目录中的 Coding Agent）：

```prompt
请使用用户管理插件，为现有应用接入成员管理和邀请。
复用 UsersClient 与已有认证、权限配置，提供用户列表、邀请和角色选择。
角色只能从允许分配的选项中选择，显示每个邀请的处理结果。
保留已有用户和权限；用普通成员验证管理操作被拒绝，用受邀账号验证加入结果。
```

**完成的标志**：受邀成员能够加入应用并获得指定的角色；普通成员无法调用管理接口。

## 重要原理与实现

下表列出实现本例时的接入位置和预期的界面变化。这些是开发说明，具体的文件名沿用当前应用的结构。

| 接入位置 | 代码或配置的变化 | 界面与行为的变化 |
| --- | --- | --- |
| 客户端路由和成员页面 | 接入 `UsersClient`，增加列表、邀请和角色选项 | 管理员看到操作入口，受邀者使用插件提供的邀请页 |
| 服务端的角色范围配置 | 按业务接入角色范围和管理授权 | 可分配的角色与后台规则保持一致 |
| 语言资源与测试 | 补齐邀请结果、停用等文案和验证 | 失败的结果可见，原有账号的行为可做回归测试 |

### 接入与入口

在 Client 和 Server 两侧注册插件，并把身份认证、权限管理排在它之前，然后执行应用的数据库迁移。通用操作见 [管理插件](../../developing-apps/manage-plugins.md)。

插件只直接注册了邀请接受页 `/invite/:token`。用户列表和管理页面由应用接入，可以复用 `@nocobase/app-plugin-users/client/user-client` 导出的 `UsersClient`。本节及下文中的页面和 API 路径都相对于应用的挂载路径，例如应用位于 `/main` 时，邀请页为 `/main/invite/:token`。

### 管理用户

| 需要完成的操作 | 公开能力 |
| --- | --- |
| 查找用户 | 分页列表，可按名称、用户名、邮箱、状态和角色筛选 |
| 编辑账号 | 创建用户；修改名称、用户名、邮箱；启用或停用账号 |
| 管理访问 | 分配角色、重置密码、撤销会话 |
| 邀请加入 | 创建、重发、撤销和接受邀请 |
| 保存个人设置 | 通过个人偏好接口保存主题、语言等由应用定义的值 |

管理 API 位于 `/api/users`。调用者需要已经登录，并拥有 `user` 资源上相应操作的权限；创建用户时，还同时要求 `create` 和 `assign-role` 两项权限。插件不会因为某个页面被展示出来，就授予其访问权限。

应用应从 `UsersClient` 读取角色选项，再提交允许分配的角色，不要自行假设所有角色都可以修改。服务端通过 `/server/tokens` 中的 `userManagementServiceToken` 复用管理服务，通过 `userRoleScopeRegistryToken` 接入业务自己的角色范围。

## AI 开发的约束与验证

### 本插件的开发约束

- 根据允许分配的角色选项生成表单，同时接口仍要检查 `create` 和 `assign-role`；隐藏选项不能代替授权。
- 保留邀请按地址逐一返回的结果，区分“邀请已创建”和“邮件投递失败”，避免盲目地重复邀请。
- 分别验证新账号接受邀请、已有账号接受邀请、旧链接失效，以及账号停用后的会话；删除操作不能理解为物理清除用户的历史记录。

### 个人偏好与使用边界

React 页面可以从 `/client/preferences` 使用 `useUserPreference(key, { defaultValue })`。例如，应用可以用 `theme.mode` 保存用户的主题选择；插件只负责保存这个值，并不实现主题切换本身。

停用账号、撤销会话和删除账号各有不同的含义。删除需要明确确认，系统会保留一个用于历史归属的已停用身份，原有的邮箱和用户名仍被占用；业务资源的清理由应用的角色范围钩子处理。验证时，既要检查普通用户的管理操作被拒绝，也要检查邀请、停用和撤销会话之后的实际登录状态。
