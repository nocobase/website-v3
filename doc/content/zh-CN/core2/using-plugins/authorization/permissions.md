## 提供的能力

`@nocobase/app-plugin-authorization` 提供应用的授权服务、权限集、页面和设置项权限，以及针对数据库字段、记录和关联的访问策略。它适合控制“谁能打开某个页面、执行某个业务操作、访问哪些数据”。

两者的分工是：应用声明业务资源和管理界面，插件提供授权决策，以及可以落实到查询中的数据策略。

### 可以配置的权限

| 对象 | 控制的内容 |
| --- | --- |
| 权限集 | 把一组授权分配给用户等主体 |
| `page` | 页面访问，例如打开订单页 |
| `settings` | 设置项的读取、创建、修改等管理操作 |
| `composite` | 业务动作，以及它所依赖的数据、字段和操作 |
| `database.collection` | 已接入权限模型的 Collection 及其数据策略 |

资源和操作必须先由应用或插件声明，才能被正确授权。业务 Collection 必须通过授权服务注册；仅仅存在于数据库中，并不等于已经接入了权限模型。

默认配置中的 `root` 权限集拥有 unrestricted 权限，应与普通的业务角色分开使用。当前实现会把 Member 作为显式角色分配给新建的普通账号，不能把它理解为所有已登录用户永远隐式拥有的权限。

## 使用场景与示例

### 示例：订单的查看与修改

1. 应用声明“查看订单”和“修改订单”两项业务能力，明确各自所需的字段和记录范围。
2. 给客服角色授予查看能力，给订单负责人授予相应的修改能力。
3. 页面通过路由的 `authz` 和 `useCan` 呈现入口和按钮；API 则在服务端重新检查操作权限。
4. 查询通过 `authz.database.policyFor(...)` 或 `authorizeRepository(...)` 等公开接口落实记录和字段策略。
5. 用不同的角色检查列表、详情、关联数据和直接发起的 API 请求。

如果只检查“是否有查看订单的权限”，然后直接执行不受限制的数据库查询，记录和字段的限制就会丢失。隐藏菜单、禁用按钮也都不能代替服务端授权。

**开发提示词**（交给当前应用目录中的 Coding Agent）：

```prompt
请使用权限管理插件，为订单增加查看与修改权限。
声明页面和业务操作，复用当前角色，不给普通用户追加 root 或无限制权限。
页面按权限显示按钮，服务端同时校验操作、记录与字段范围。
用只读、可修改和无权用户验证列表、详情、关联数据及直接 API 请求。
```

**完成的标志**：只读用户能读取允许的订单，但不能修改；其他记录和受限字段不会通过接口泄露。

## 重要原理与实现

下表列出实现本例时的接入位置和预期的界面变化。这些是开发说明，具体的文件名沿用当前应用的结构。

| 接入位置 | 代码或配置的变化 | 界面与行为的变化 |
| --- | --- | --- |
| `server/config/authorization.ts` 与资源声明 | 注册业务 Collection、操作以及字段依赖 | 管理页可以选择真实的业务能力 |
| 业务服务和 Repository 查询 | 应用授权返回的数据策略 | 列表、详情和写入遵循同一个范围 |
| 页面路由和操作按钮 | 使用 `authz` 和 `useCan`，同时保留接口校验 | 页面入口和操作的可见性与角色相符 |

### 接入与入口

在身份认证之后注册 Client 和 Server 插件，然后执行迁移和种子数据。应用在 `server/config/authorization.ts` 中组合配置，通过 `/server` 导出的 `authorizationToken` 使用授权服务。

插件提供 `/api/authorization` 接口，以及 `AuthorizationClient`、`useCan` 等客户端能力，但不会直接注册权限管理页面。应用需要接入自己的管理页，并声明可以分配的业务能力。

### 扩展数据范围

需要统一或细化记录范围时，按业务需要分别配置：

- [默认数据范围](default-access.md)：为已经具备操作权限的主体，增加一份共同的记录范围。
- [共享规则](sharing-rules.md)：为指定的主体追加特定的记录范围。
- [限制规则](restriction-rules.md)：收窄指定主体仍然可以访问的记录。

这些规则都不会创建操作权限。管理界面中的分组只是展示上的组织方式，也不会改变授权结果。相关的安装操作见 [管理插件](../../developing-apps/manage-plugins.md)。

## AI 开发的约束与验证

### 本插件的开发约束

- 先声明业务能力，再进行授权；不能把尚未接入权限模型的数据库查询当作已经受到保护。
- 检查页面、操作、字段、记录和关联的访问，避免在一个布尔型的 `can` 判断之后执行不受限制的查询。
- 用普通角色和直接发起的 API 请求进行验收；涉及角色 Seed 时，检查是否意外扩大了现有用户的权限。

以上检查是接入后的验收要求，并不表示本文已经完成了运行验证。请让 Agent 报告实际的改动、执行过的检查和未验证的部分；项目指引、Skills 和通用的检查流程见 [和 Agent 一起开发](../../developing-apps/develop-with-an-agent.md) 与 [测试与验收](../../developing-apps/testing-and-acceptance.md)。
