## 提供的能力

`@nocobase/app-plugin-authz-restriction-rules` 用于收窄指定主体已经获得的记录范围。规则中的记录选择表示“仍然允许访问的记录”，而不是需要屏蔽的记录；多条匹配的限制规则会同时生效。

规则的管理页由应用负责；除了在运行时注册插件，还需要组合授权工厂，规则才会参与业务的访问决策。

## 使用场景与示例

### 业务示例

例如，实习生已经拥有订单的读取权限，但只能处理非保密的订单。为实习生这一主体配置读取限制，选择“非保密订单”。这样，即使共享规则为他追加了某份保密订单，这份订单也无法越过限制。

请先确认主体拥有目标操作，再配置范围；最后分别检查允许的记录、范围外的记录和直接发起的 API 调用。业务查询必须落实授权服务返回的数据策略，规则才会真正影响查询结果。

**开发提示词**（交给当前应用目录中的 Coding Agent）：

```prompt
请使用 @nocobase/app-plugin-authz-restriction-rules，将实习生已有订单读取范围限制为非保密订单，并验证共享不能绕过限制。
保留已有授权扩展，接入规则管理页面及相应设置权限。
先检查主体是否拥有读取操作，再配置记录范围，不通过新增管理员权限绕过限制。
用普通用户验证允许记录、范围外记录和直接 API 请求。
```

**完成的标志**：实习生只能看到非保密订单；即使有人共享了保密订单，他也无法读取。

## 重要原理与实现

下表列出实现本例时的接入位置和预期的界面变化。这些是开发说明，具体的文件名沿用当前应用的结构。

| 接入位置 | 代码或配置的变化 | 界面与行为的变化 |
| --- | --- | --- |
| 插件数组与 `server/config/authorization.ts` | 注册运行时，并组合 `restrictionRules()` | 规则接口和决策扩展同时生效 |
| 应用的规则管理页面 | 接入选项、记录选择和受保护的保存接口 | 管理者可以维护目标规则 |
| 业务查询与测试 | 保留授权返回的数据策略，并为不同主体增加用例 | 规则实际影响数据结果 |

### 接入与配置

在 [权限管理](permissions.md) 的基础上，注册本插件的 Client 和 Server 入口并执行迁移；此外，还要把工厂加入应用的 `server/config/authorization.ts`：

```ts
import { restrictionRules } from '@nocobase/app-plugin-authz-restriction-rules/server';

// 合并到现有授权配置，保留其他已启用的扩展。
plugins: [restrictionRules()]
```

运行时注册负责语言资源和数据库迁移，配置工厂才负责安装规则能力和 HTTP 接口。漏掉工厂时，即使安装了包，规则也不会生效。

### 配置与使用规则

记录选择支持全部记录、指定的记录 ID，或已经注册的 `recordAccess`。多条限制规则取交集，因此即使某条规则选择了全部记录，也不会取消其他限制。删除一条限制规则可能会扩大访问范围，需要重新验证受影响的主体。

规则管理接口位于 `/api/authorization/restrictionRules`，提供列表、创建、更新和删除，以及选项、主体或记录选择所需的接口。管理页面由应用负责，插件不会自动注册页面。访问这些接口，需要 `settings:authorization.restriction-rules` 上相应的 `read`、`create`、`update` 或 `delete` 权限。

应用通过受保护的接口保存规则。可信的服务端代码也可以直接使用授权服务上的 `restrictionRules` API；自行封装 HTTP 接口时，需要保留权限检查和输入校验。

## AI 开发的约束与验证

### 本插件的开发约束

- 记录选择表示仍然允许访问的记录，多条限制取交集；删除规则可能扩大访问范围，需要重新检查。
- 规则改变的是记录范围，不会授予页面、操作或字段权限；请检查服务端的查询是否真正应用了策略。
- 用非 unrestricted 的身份验证规则的叠加、撤销和直接访问，不能只用超级管理员测试。

### 使用边界

规则不会授予页面、操作或字段权限，也不会自动开放关联的记录。默认范围和共享范围合并之后，仍然受限制规则的约束。unrestricted 身份会跳过这些范围规则，因此不能只用超级管理员来验证普通用户看到的结果。
