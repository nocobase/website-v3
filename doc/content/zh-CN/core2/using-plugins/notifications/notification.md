## 提供的能力

`@nocobase/app-plugin-notification` 是通知投递的运行时，负责消息校验、持久化、队列、幂等处理、投递状态和有限次数的重试。具体的发送方式由 [通知渠道](providers.md)、[站内信](in-app.md)、[浏览器推送](web-push.md) 等插件提供。

通知运行时负责协调投递；收件人、业务的触发时机和具体的渠道，由应用和渠道插件提供。

## 使用场景与示例

### 示例：订单结果同时通过两种渠道通知

订单业务成功后，为同一个事件分别构造站内信和邮件消息。站内信的 `to` 使用用户 ID，邮件的 `to` 使用邮箱地址；找到正确的收件人是业务代码的责任。使用稳定的业务事件标识作为 `idempotencyKey`，避免同一个事件被重复提交。

每个收件人对应一条独立的投递记录，其中一路失败并不等于全部失败。重试时沿用原来的渠道和提供方。业务界面应区分“已排队”“已提交”和“失败”，不能把渠道接受了消息当作用户已经收到或已读。

**开发提示词**（交给当前应用目录中的 Coding Agent）：

```prompt
请使用通知插件，在订单审批成功后发送站内信和邮件。
使用已配置的具名渠道，为每个渠道提供完整消息，分别解析用户 ID 与邮箱地址。
用业务事件标识实现幂等，保留每个接收者的投递结果，并接入受保护的日志查看。
验证重复事件、一路失败及无权查看日志，不把排队成功显示为用户已收到。
```

**完成的标志**：同一业务事件的投递可以追踪，失败的渠道和收件人可以识别，重复提交不会意外地造成重复通知。

## 重要原理与实现

下表列出实现本例时的接入位置和预期的界面变化。这些是开发说明，具体的文件名沿用当前应用的结构。

| 接入位置 | 代码或配置的变化 | 界面与行为的变化 |
| --- | --- | --- |
| 服务端的渠道配置与 Jobs | 注册投递渠道，接入执行器 | 通知可以排队，并由对应的渠道处理 |
| 订单业务服务 | 在业务成功后调用 `send`，关联事件和收件人 | 同一事件有可以追踪的通知结果 |
| 日志页面与权限 | 查询投递记录，区分等待、成功提交和失败 | 管理者能够定位到单个收件人的失败 |

### 接入与配置

注册 Server 插件以及实际需要的渠道插件，执行迁移和种子数据，并确保应用的 Jobs 执行器能够运行。Client 插件提供日志客户端等能力，但不会自动注册日志页面。

在 `notification.channels` 中，为每种用途配置一个渠道名称及其 `type`。例如 `system-email` 是渠道名称，`smtp` 是实现类型，两者不能互换。默认模板通过 `server/config/notification.ts` 中的 `defineMailChannelsConfig` 组合配置。

### 发送通知

业务代码在服务端从 `/server` 解析 `notificationServiceToken`，然后调用 `send()`。下面的示例假设已经注册了站内信插件，并配置了 `inbox: { type: 'in-app' }`：

```ts
await notification.send({
  idempotencyKey: 'order:123:approved',
  source: { type: 'order', referenceId: '123' },
  messages: {
    inbox: {
      to: 'user-123',
      title: '订单已审批',
      body: '可以继续处理订单。',
      target: { type: 'route', path: '/orders/123' },
    },
  },
});
```

`notification` 是解析得到的服务，用户 ID 和订单 ID 应取自实际的业务。`messages` 的键必须是已经配置的渠道名，并且每个渠道都需要一条完整的消息；运行时不会自动把一份通用的内容转换成各个渠道的格式。

## AI 开发的约束与验证

### 本插件的开发约束

- 业务成功和通知投递要分开处理；重试时保留稳定的事件标识，不能在每次重试时生成新的幂等键。
- 每个渠道校验自己的消息结构，不能把用户 ID 当作邮件地址使用。
- 验证部分失败和日志权限；一次性凭据使用 transient 路径发送，不能指望它的持久重试或幂等保证。

### 查看投递结果与发送敏感消息

日志接口位于 `/api/notifications/logs`，需要 `page:notification.logs/access` 权限。应用可以接入日志界面，按发送时返回的通知标识检查投递结果。不要额外暴露一个不受保护的通用发送接口。

一次性凭据、邀请 token 等敏感内容，请使用 `sendTransient({ channel, message })` 发送：它只尝试一次，不写入通知快照、Jobs 或重试状态，也没有持久的幂等保证。发生超时时，提交结果可能未知，应由业务决定安全的恢复方式。

请验证多收件人的结果、重复事件、渠道失败和日志权限。相关文档：[通知渠道](providers.md)、[站内信](in-app.md)、[浏览器推送](web-push.md)。
