从[接入 Studio](bring-into-studio.md)后的 CRM 继续。销售在同一商机下多次调整报价，希望解释每次价格变化，同时保留已经发给客户的版本。这一课，我们把这项改动交给 Agent 团队完成。

## 提出报价版本对比需求

打开 **我的会话**，点 **新会话**。在输入框下选择可用 Agent 和 CRM 项目，再发送第一条消息；项目绑定后，要讨论另一项目就新建会话。使用团队共享运行环境时，业务同事无需在自己的电脑安装编码工具。

![新会话的输入区可以选择 Agent 和 CRM 项目。](/assets/guides/studio/new-session.png)

```prompt
客户经常要求调整报价，我想在 CRM 里比较同一份报价的不同版本，看到产品、数量、单价、折扣和总额的变化，以及谁在什么时候修改。已经发给客户的版本要保留，不能被后来的修改覆盖。先和我确认规则，再整理成任务。
```

和 Agent 确认：哪些操作保存版本、比较哪两个版本，以及谁有权查看。这里采用“已提交版本不可修改，后续调整创建新草稿”的规则；版本对比沿用所属客户的访问范围，不能让无权查看客户的人读取历史报价。把这些规则和验收场景保存在任务说明中。

**步骤检查**：CRM 项目中有“报价版本对比”任务，负责人明确，说明包含版本保留和权限规则。

## 开始执行并跟进进展

确认任务后点 **开始**，由调度 Agent 安排设计、实现、测试和评审。任务从 **待规划** 进入 **进行中**。在任务顶部查看 **现在** 和后续安排，在 **动态** 中查看交接；需要了解具体过程时打开 **运行记录**。

![项目任务可以切换到看板，按状态查看开发进展。](/assets/guides/studio/issues-board.png)

需要补充要求时在任务中评论。私有会话中的结论不会自动成为所有成员可见的项目资料，应检查关键决定是否写回任务。具体入口见[跟进进展](../studio/use/follow-progress.md)。

## 回答业务问题

例如 Agent 需要确定：已有报价没有版本历史，升级后如何处理？需要决策时，任务可能进入 **阻塞中**，负责人在 **我的任务** 中查看 **需要你**，回复：

```prompt
已有报价保留原编号、明细和金额，作为第一个可查看的版本。不要猜测过去的修改历史。从这次上线后开始记录新版本，已经提交的版本不能再修改。
```

回复后确认决定已记录，任务恢复执行。阻塞也可能来自运行环境或检查失败，应按提示处理实际原因，不能只改状态。见[回答提问](../studio/use/answer.md)。

## 检查与评审

打开 **代码与预览**，确认 PR 对应的提交、检查结果和预览。调度 Agent 按项目技能安排独立评审，并将必须修复的问题交回实现者；检查来源以仓库配置为准，不一定是 CI。见[检查与评审](../studio/project/checks-and-review.md)。

![CRM 任务的“代码与预览”区域列出 PR、检查来源及各项检查结果。](/assets/guides/studio/issue-checks.png)

阅读交付报告，重点检查历史报价迁移、金额计算、不可变版本和权限边界的证据。不能用“测试通过”替代实际业务验收。

## 验收历史报价兼容性并合并

任务进入 **待验收** 后，在预览中使用独立测试账号验证：

| 操作 | 应看到的结果 |
| --- | --- |
| 打开升级前已有的报价 | 编号、客户关联、明细及金额保持不变，可以查看初始版本 |
| 提交一个版本，再修改数量或折扣 | 生成新草稿，已提交版本保持不变 |
| 对比前后版本 | 产品增删、数量、单价、折扣、总额差异及修改人、时间可核对 |
| 调整产品目录价格 | 已保存版本不随目录价格变化 |
| 用无客户权限的销售账号打开历史版本或直接调用接口 | 无法读取该客户的报价历史 |

![demo 中已完成的报价修订任务，交付报告保留业务背景、结果和验证记录。](/assets/guides/studio/quote-task.png)

在 **需要你** 中点 **合并**，核对目标分支和提交后确认；不符合预期则点 **退回修改**，写明操作、实际结果和预期结果。关联 PR 合并后，任务完成。合并权限与代码平台的分支保护仍然生效，详见[验收](../studio/use/accept.md)。

**完成的标志**：报价版本对比已验收并合入默认分支，旧客户和报价仍可使用。
