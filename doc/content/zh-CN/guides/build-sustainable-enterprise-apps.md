## 前言

AI 开发或者 Vibe Coding 能够很快写出一个看起来「能用」的系统。如果是作为个人应用，或者是一些简单应用，大部分情况下是够用了。但是如果是开发一个企业级应用，随着持续迭代和维护，就会发现不少问题：

1. 很多底层能力要从零建设，比如权限、工作流、审批等
2. 底层架构可能随着 AI Agent 模型更换、开发人员更迭，而逐渐失控
3. 并行任务太多，Agent 消息太多，人确认不过来
4. 开发过程中的知识和经验难以沉淀和共享

NocoBase 基于上述问题，结合当下 AI Agent 能力发展迅猛的背景，给到了我们自己的一个解决方案：既能够让企业在 AI Agent 时代能够快速开发自己的企业级应用， 同时又能解决上述这些问题。本文将从我们内部的实际经验出发，讲述在 NocoBase 3 的加持下，如何开发可持续迭代的企业应用。

## 前期准备

在我们内部的实践经验来看，一开始并不推荐一上来直接让 ai 开始开发一个 XX 系统。这种「一句话生成一个系统」的方式，在企业级应用开发的视角来说是风险比较大，后期很容易返工或者大改。

因此，我们推荐前期最好是准备一个产品的系统设计文档或者需求文档。核心的点在于先跟 Agent 聊清楚我们要做的是个什么应用，需要有什么功能等。下面是一个参考的例子：

```prompt
帮我写一份 XXX 行业的 CRM 系统设计文档，包括方案概述、设计目标、核心业务对象及关联关系、关键业务流程和主要页面，以及如何设计 AI/Agent 辅助或直接执行日常事务，给业务人员提效。先调研几个市场上主流的优秀产品后再写。
撰写过程中有任何问题，可以随时向我提问。
```

当然也可以借助一些市面上比较出名的 Spec 生成工具辅助你完成这个事情，比如：

- [OpenSpec](https://github.com/Fission-AI/openspec)
- [superpowers](https://github.com/obra/superpowers)

## 开发流程

### 创建应用

有了前期准备的材料之后，我们就可以正式开始基于 NocoBase 3 开发应用了。可以先参考[《创建应用》](../core/getting-started/create-app.md)这篇文档，先安装我们的 skills 和创建一个 NocoBase 3 的应用目录。

```bash
npx skills@latest add nocobase/skills-v3 --skill nocobase-create-app -g
mkdir my-app
cd my-app
```

然后在这个应用目录下打开 coding agent ，可以输入如下提示词（数据库可以用 MySql、Postgresql、SQLite 等）：

```prompt
请在当前目录中创建一个供本地开发使用的 NocoBase 3 应用。
使用默认模板和 SQLite，按创建应用的指引完成准备和检查。
启动后告诉我打开哪个地址，以及如何完成首次登录。
```

初始化完一个 NocoBase 3 应用后，Agent 会告诉你如何打开并登录系统。

![](https://static-docs.nocobase.com/20261029150256019.png)

### 搭建系统

接着，我们可以在这个目录下新开一个 coding agent（确保加载了 nocobase 3 在项目中预置的开发 skills），然后可以输入如下提示词，把我们前置准备里的产物用上。在这里，我们推荐可以把这些产物也放进项目的仓库中。比如放到仓库的 `docs/` 目录下，作为初始的系统框架、需求文档。

如果企业内部有自己的设计规范（品牌色、字号大小、组件样式等），也建议在搭建前跟需求文档放在一起提供给 Agent，并要求 Agent 遵守。如果没有设计规范，那么我们就建议让 Agent 遵循 Nocobase 3 内置的设计规范即可：

```prompt
请你参考我在 xxx 目录里放置的 xxx 设计文档，然后基于 NocoBase 3 提供的能力，遵循 NocoBase 3 的框架能力、设计规范、开发 skills，实现一下这个 PMS 系统。

有任何问题，实施前或者过程中可以问我。
```

AI 在实施过程中，会参考我们之前准备的材料。基于前期准备的材料加上 NocoBase 3 提供的底层能力，就可以在较短做出符合业务需求文档的一个业务系统。在此过程中，你只需要描述你的业务需求即可，而不用过分关注底层的逻辑实现。

基于需求文档，我们可以就可以做出一个业务系统的初版：

![](https://static-docs.nocobase.com/20261028161432844.png)

AI 能够在理解业务需求的基础上，快速搭建一个可靠的业务系统主要来源于我们 NocoBase 3 提供底层基座 —— [NocoBase Core](https://www.nocobase.com/zh-CN/core/)。NocoBase Core 是开发和运行业务应用的基础。它提供应用框架，以及登录、用户、权限、文件、通知等通用能力，供你的应用直接使用。Core 提供了：

- **应用模板与运行框架**：从一个可以启动的项目开始，具备客户端、服务端和运行配置，继续添加自己的功能。

- **通用能力**：通过插件和基础库使用认证、用户、权限、数据访问、文件存储和通知等能力，按应用需要组合。

- **UI 组件库**：复用表格、表单、弹窗等组件及业务区块。组件安装到应用源码后，可以按需要修改。

- **开发工具与 Skills**：命令行工具负责配置、迁移、插件管理和构建；Skills 为 Agent 提供与依赖版本配套的使用指引。

基于这些底座能力，Agent 就能像搭积木一样，快速将一个业务系统搭建出来。

搭建出来的应用，如果你不确定到底用上了哪些 NocoBase Core 的能力，我们还提供了一个 foundation 插件，能够方便你快速看到搭建出来的业务系统用上了哪些能力。默认搭建的应用就会自带这个插件：

![](https://static-docs.nocobase.com/20261028161615621.png)


至此，我们解决了上面提到的两个问题：

1. 很多底层能力要从零建设，比如权限、工作流、审批等
2. 底层架构可能随着 AI Agent 模型更换、开发人员更迭，而逐渐失控

未来持续开发的过程中，Agent 也会遵循 NocoBase Core 的规范、利用已有的能力快速搭建，让不同的开发人员、Agent 都能搭建出可靠、规范统一的应用。

如果你对 Core 提供的能力、底层原理感兴趣，欢迎参考我们的[文档](../core/index.md)。

### UI 组件参考

我们提供了一系列开箱即用的业务组件，可以在 https://ui.nocobase.com/#agent-queue 看到。对于不想重复实现业务组件的用户，可以参考这部分内容，并直接复制业务组件安装命令，然后让 ai agent 使用。

```prompt
请你参考 https://ui.nocobase.com/ 的 agent queue 组件，帮我用 `npx shadcn@latest add @nocobase/agent-queue` 安装组件并在页面上用这个组件实现 XXX 功能。
```

### 升级内核

通常情况下，应用搭建完毕并开始基于它持续迭代之后，升级内核频率将不会太频繁。为了保证业务系统的稳定性，我们推荐大多数场景下继续业务开发系统即可。如果因为内核缺陷、或者内核新增了一些能力，想要对内核进行升级，我们也提供了内核升级的 skills，不再需要人为对内核的各个插件、框架本身进行升级。

可以使用下面的提示词，对项目的内核版本进行升级：

```prompt
请把当前应用使用的 NocoBase Core 升级到当前发布通道的最新版。

先检查并给我一个具体计划，暂时不要修改项目：
- 当前是什么版本，准备升级到哪个版本；如果已是目标版本，说明无需升级，不做降级。
- 这次升级会影响哪些功能、依赖、配置和插件，有哪些变化需要我决定。
- 怎样保留已有业务功能、主题、用户权限和数据，以及出问题后如何恢复。
- 是否有无法撤销的数据变更，或需要修复的历史记录，分别说明原因和影响。

我确认计划后，再按照项目升级指引，在独立分支完成修改。
不要直接覆盖当前应用或清空数据库，也不要只改版本号就算完成。
请在独立测试环境验证旧数据、登录、普通用户权限和任务操作仍然正常。
最后告诉我升级前后的版本、做出的调整、验证结果和未完成事项。
这次只准备并验证升级后的项目，正式环境部署另行确认。
```

升级的过程中，Agent 会遵循 skills 的规范，只升级内核本身的版本，尽可能不会更改你已经实现的业务逻辑。如果遇到确实需要对现有业务代码进行修改从而能适配新内核的情况，Agent 也会将此情况抛出给你做决策。

### 内部团队如何提需求

除了研发团队，企业内部还有别的团队，通常也会有自己的业务需求。我们推荐内部团队给研发团队提需求的时候，也可以做类似上述的「前期准备」。然后给到研发团队一份相对明确的业务需求。

[可选] 如果内部团队能够通过 Agent 生成一份 HTML Demo 辅助描述这个需求，会有助于 Agent

研发团队可以把这些内部团队的需求作为输入交给 agent 去开发

```prompt
请你查看 xxx 业务需求的说明材料，基于 NocoBase 3 提供的能力，遵循 NocoBase 3 的框架能力、设计规范、开发 skills，去开发这个功能。
```

## 使用 Studio 进行团队协同和长期迭代

当一个系统已经搭建出初始的版本之后，接下来就会进入一个持续迭代的阶段：

1. 已经搭建的功能，需要迭代功能、修复存在的 bug
2. 需要给系统增加新的功能模块

如果一个人开发，并行多个任务的时候，就需要在多个 Agent 会话之间来回跳转；Agent 输出速度越快，对人的要求就越高。
如果多人开发，需求背景、业务资料、项目经验可能散落在各个角落。不同的人或者不同的 Agent 接手，很可能就丢失这些上下文。
为此，我们推出了 [NocoBase Studio](https://www.nocobase.com/zh-CN/studio/)，它是为了治理人与 Agent 协同开发而生的。


在 NocoBase Studio 中，我们可以把本地的 Agent（比如 Codex、Claude Code、OpenCode 等）组成一支 Agent 团队，让他们能够自主推进任务，只有在关键的地方才需要由人做决策。每个任务都有清晰的状态（进行中、需要你决策、已完成等等），让你只用关注在需要你决策的任务上。

![](https://static-docs.nocobase.com/20261028173135810.png)


> [!NOTE]
> NocoBase Studio 目前仅在 NocoBase 专业版和 NocoBase 企业版中可用，可以参考 [版本与价格](https://www.nocobase.com/zh-CN/pricing/)。

当完成了这些步骤之后，接下来就可以把一个存量的项目接入 Studio 并在 Studio 里进行迭代和开发了。

### 通过 Agent + nb-studio 接入已有项目

打开 Studio，通过右上角「在 agent 中使用 Studio」的入口，找到如何让你本地的 Agent 能够连上 Studio 的指令。

![](https://static-docs.nocobase.com/20261028173406008.png)

发给你本地的 coding agent，它将会安装 nb-studio 的 CLI 工具，并安装对应的 skills ，让你的 agent 知道如何通过 nb-studio 这个 CLI 工具，直接跟 Studio 系统进行交互，比如：
  
- 创建任务
- 查看任务状态
- 创建项目
- 修改密码
- 等等

大部分能够在 Studio 界面上操作的功能，你都可以让本地 Agent 配合 nb\-studio 这个 CLI 工具通过自然语言描述并完成。（这个功能并不是指你本地的 agent 运行环境接进了 Studio。如果你想要的是在 Studio 里能够调用你的本地 Agent，需要参考上述的 [接入共享运行环境](../studio/setup/shared-runtimes.md) 和 [启用 Agent](../studio/setup/agents.md) 的步骤。）

比如我们现在要把我们基于 NocoBase Core 开发的一个项目接入 Studio，那么可以这样跟本地 Agent 沟通：

```prompt
帮我通过 nb-studio 在 Studio 里创建一个 XXX 的项目并关联当前项目
```

Agent 就会通过 nb-studio 这个 CLI 工具直接在 Studio 里创建并关联这个项目。

![](https://static-docs.nocobase.com/20261028181001387.png)

项目创建完之后，就可以开始创建任务，基于任务对项目进行后续的迭代和维护了。

### 任务管理

#### 创建任务

Studio 里创建任务，有几种方式：

1. 通过任务页面右上角新建任务按钮

![](https://static-docs.nocobase.com/20261029151913059.png)

2. 在「我的会话」里直接描述需求、问题，Agent 会自动拆解成可执行的任务

![](https://static-docs.nocobase.com/20261029151954700.png)

3. 通过本地 Agent 创建任务

```prompt
我在 XXX 项目里遇到了 YYY 问题，具体是这样的：ZZZZ。请你用 nb-studio 给 XXX 项目建个任务。
```

创建完的任务，默认情况下是「待规划」的状态。此时并不会立即开始进行这个任务。要想开始这个任务，可以看下面「任务状态扭转」的章节。

#### 任务状态扭转

在本地开发过程中，我们可能会经常遇到类似的情况：

```text
Agent：XXX 是这样的，要我继续吗？
人：是的，请你继续。
...
Agent：YYY 是这样的，要我继续吗？
人：是的，请你继续。
```

Agent 可能会在明明可以继续的情况下，还来征求用户的同意。不仅任务会中断，而且我们需要花费精力来确认这种「低价值」的决策。

为此，Studio 设计了一套机制来解决这个问题，让任务尽可能自动扭转，并且只有在必要的时候才让人介入决策。我们有一个主要的「调度 Agent」，它会负责分析、拆解任务，并把任务分派给合适的 「执行 Agent」 去干活。一旦执行 Agent 遇到类似的问题，调度 Agent 将会主动让执行 Agent 继续工作。

我们在 Studio 内置了六种任务状态

1. 待规划：这种状态下相当于是需求收集阶段的任务，Agent 还没有正式开始开发。
2. 进行中：Agent 开始正式开发。
3. **阻塞中：Agent 遇到了问题，需要你来确认。**
4. **待验收：Agent 完成了开发，需要你来验收。**
5. 已完成：Agent 完成了开发，验收也通过，代码合入，PR 关闭。
6. 已取消：任务已取消，Agent 不再开发。

![](https://static-docs.nocobase.com/20261028201236304.png)

可以发现，六种任务状态里，只有「阻塞中」和「待验收」这两种状态是需要用户来确认的。上面说了，「调度 Agent」会尽可能推进任务往前走。但是一旦遇到它也无法做决策，必须由人介入决策的时候，它才会将任务的状态扭转为「阻塞中」，要求用户来做决策。因此在 Studio 里，你收到的通知会尽可能少，只有真的需要你做决策的时候才会收到通知：

![](https://static-docs.nocobase.com/20261028203035957.png)

此时你要做的事情就是回复 Agent 你的决策即可，调度 Agent 收到之后，就会继续将任务扭转到「进行中」的状态，直到下次需要你决策变成「阻塞中」状态，或者直接开发完毕之后，变成「待验收」状态。

当任务已经完整开发完毕后，任务就会扭转到「待验收」状态，这个状态当然也是需要人来确认的。如果你确认无误，就可以点击「合并」将代码合入仓库。此时任务也会随机切换到「已完成」的状态。

![](https://static-docs.nocobase.com/20261028201509073.png)

如果你手头有很多任务，但是你比较关心其中一些任务的进展，也可以点击任务的「关注」按钮，这样就会把这些任务加入到你的关注列表中，可以方便查看关注的任务进展。

![](https://static-docs.nocobase.com/20261029152227386.png)

#### 预览环境

部署完 Studio 之后，Studio 会自带一个预览环境，它的作用是为每个任务的代码分支提供一个可以实际运行的预览环境：

![](https://static-docs.nocobase.com/20261028203544307.png)


它可以给 「调度 Agent」用来验收「执行 Agent」的开发结果，执行 Agent 会在预览环境运行并截图实际效果供「调度 Agent」 确认，也可以给到用户验收任务的时候一个很好的参考。

![](https://static-docs.nocobase.com/20261028203712314.png)

同时，用户也可以通过预览环境查看这个任务分支的代码的实际效果，以决定是否通过验收。

![](https://static-docs.nocobase.com/20261028204209835.png)

### 知识库和项目记忆

Studio 内置了一个知识库模块，可以按项目级别和系统级别（所有项目共享）的维度，录入相关的文档、信息。Agent 在开发的过程中，将会按实际需要调用知识库里的知识进行开发参考，知识库将存储在 Studio 的数据库中。如果有一些比较重要的内容（比如团队规范、专业术语等），需要共享给人和 agent，则都可以存到这个知识库中。随着项目不断迭代，知识库的内容将会越来越丰富。

![](https://static-docs.nocobase.com/20261028205037978.png)

项目记忆则是另一个重要功能。它参考 claude code 的 [auto memory](https://code.claude.com/docs/en/memory) 机制，agent 只会在关键的时候（比如用户反复强调某个事实、项目有某些无法通过代码获取的上下文、agent  踩过同样的坑等等）自动记录记忆。项目记忆将会落到项目仓库中（在仓库根目录的 \~/\.nb\-studio/memory/ 里），以实际代码的形式留存。项目记忆会在 Studio 的每次任务上下文中注入（设计上，它非常简洁明了，对上下文占用会做非常严格的限制），避免 agent 后续犯同样的错误。

![](https://static-docs.nocobase.com/20261028205613068.png)


### Skills

Studio 支持标准的 Agent Skills。它能用来做开发规范、评审要点、测试步骤等。写成技能，挂在全局、项目或代码仓库上，Agent 在每次执行任务的时候都会遵循给定的 skills 的要求。

![](https://static-docs.nocobase.com/20261028210018195.png)


Studio 的 skills 支持几个维度挂载：

1. 全局挂载，这样所有的项目都会被应用上。同时还支持「新项目自动挂载」。

![](https://static-docs.nocobase.com/20261028210517252.png)

2. 项目级别挂载

有些技能可能只适合某些项目，那么这个时候就不需要启用全局挂载，而是到项目详情中，找到默认技能面板，对项目级别的技能进行专门的挂载。

![](https://static-docs.nocobase.com/20261029152525192.png)

3. 仓库级别挂载

由于一个项目可以添加多个仓库，所以如果想要做仓库级别的挂载，也可以在项目设置里，对某个仓库进行专门的技能挂载。这样同一个项目，只有指定的仓库才会在执行任务的时候挂载这个 skills。

![](https://static-docs.nocobase.com/20261029152621517.png)

Studio 提供的这三种维度的技能挂载，能够非常大程度上解决团队协作中的规范共享问题。同时也能满足个别项目、仓库有自己自定义的一些技能需求。

### 应用部署

当一个 NocoBase 3 应用已经完成开发之后，我们比较建议 [使用 Docker 部署](../core/tutorials/deploy-with-docker.md) 。可以将一个 NocoBase 3 应用打包成一个 Docker 镜像，然后再到目标服务器上进行部署。可以参考下面的提示词，发给 Agent，将服务器、目录和访问地址等替换为自己的实际值

```prompt
请使用 Docker，把当前任务应用首次部署到下面的环境。

服务器：<我的 Docker 服务器>
服务器平台：linux/amd64
部署目录：<服务器上的绝对路径>/tasks-docker
数据库：新的 SQLite 数据库，不导入开发数据或示例任务
服务器本地监听地址：127.0.0.1:13000
用户访问地址：https://tasks.example.com/tasks/

请按项目的 Docker 部署指引准备应用并启动，只操作这个教程应用。
配置、密码和业务数据需要独立保留，不放进镜像；重建容器后不能丢失。
设置管理员登录信息，妥善保存应用密钥，不在代码或报告中暴露它们。
如果需要的配置或存储位置缺失，请说明问题，不要悄悄用空数据继续运行。

检查登录、任务操作和只读权限，再重建这个应用的容器，确认原来的数据和权限仍然保留。
完成后告诉我访问地址、验证结果，以及域名或 HTTPS 等尚未完成的配置。
```

## 总结

AI 写代码很快，但构建可靠的业务系统依然不简单。AI 从零开始写业务系统，写得越快，问题也越多。通过 NocoBase Core，我们解决了这两个问题：

1. 很多底层能力要从零建设，比如权限、工作流、审批等

2. 底层架构可能随着 AI Agent 模型更换、开发人员更迭，而逐渐失控

但是随着企业项目越来越庞大，团队项目越来越多，我们不可避免会遇到下面这些问题：

3. 并行任务太多，Agent 消息太多，人确认不过来

4. 开发过程中的知识和经验难以沉淀和共享

因此我们推出了 NocoBase Studio。通过智能化的 Agent 团队，规范化的任务状态扭转，持续更新的知识库、记忆和 skills 等，有效解决了企业应用开发中上述难题。希望我们的经验能够对遇到企业应用开发、应用治理难题的团队有所帮助！
