在已有 NocoBase Core 应用中扩展多表业务结构：以给 CRM 增加商机、产品和报价为例，先与 Agent 对齐 ER 图和数据字典，再通过迁移脚本（Migration）安全增量建表，并接入事务保存与数据一致性校验。

你可以直接在包含客户、联系人和跟进记录的应用中实践，或运行最新完整的 `doc-demo-crm` 示例对照体验。操作时使用管理员账号，并保留原有客户数据，便于检查数据库变更是否影响既有业务。

## 梳理 ER 图与数据字典

遇到涉及多张表和复杂关系的业务需求时，不要让 Agent 直接修改数据库，而是先让它输出 ER 图和数据字典，在动库前把业务关系确认清楚。

以 CRM 为例：同一家客户（如 Northstar Labs）可能同时推进团队许可证和咨询服务两笔销售机会，各自有不同的进度和多份报价；每份报价会选多个产品，而产品后续调价不能改变已经保存的历史报价。

在应用根目录的 Agent 会话中发送：

```prompt
我想在现有 CRM 中管理商机和报价。一个客户可以有多个商机，每个商机可以有多份报价。产品目录维护名称、编码和当前单价；每份报价可以选多个产品，分别填写数量和折扣，产品以后调价不能改变已保存的报价。

先帮我画出这些数据的 ER 图，再整理一份简短的数据库字典，说明关键字段的含义、类型、关联和约束。保留已有客户、联系人和跟进记录，先不改数据库。
```

ER 图展示实体和关联路径，数据字典说明每张表保存哪些字段及约束。两者表达的是同一个模型，对照 Agent 的输出重点把关三件事：

![客户到商机、商机到报价、报价到明细、产品到明细均为一对多关系。产品保存当前价，报价明细保存报价时的单价。](/assets/guides/crm-sales-er.svg)

1. **拆分独立业务对象**：客户、商机、报价按一对多逐层归属，同一客户下的多次销售机会互不干扰。
2. **用明细表承载多对多与业务属性**：一份报价包含多个产品，一个产品也会出现在多份报价中，**报价明细**连接两者，并保存“这次卖多少、优惠多少”（数量与折扣）。
3. **区分关联引用与业务发生时的值**：报价明细既保存 `productId` 指向产品目录，也单独保存当时的报价单价；如果只留外键关联，重新打开旧报价就会读到调价后的当前价。

下面是数据字典的节选，可对照完整示例中的[模型与字段说明](https://github.com/nocobase/doc-demo-crm/blob/main/docs/sales-model.md)查看具体的数据库类型和约束定义：

| 记录 | 关键字段示例 | 在业务中的作用 |
| --- | --- | --- |
| 产品 `crmProducts` | 名称、编码、当前单价 | 维护可销售产品及其当前价格 |
| 商机 `crmOpportunities` | 客户关联、名称、阶段 | 区分同一客户的不同销售机会 |
| 报价 `crmQuotes` | 商机关联、名称、总额 | 记录针对某次商机给出的报价 |
| 报价明细 `crmQuoteLines` | 报价关联、产品关联、数量、报价单价、折扣 | 记录这份报价卖什么、卖多少、按什么价格卖 |

如果团队已有 ER 图、数据字典或外部 SQL，也可以直接交给 Agent 读取，让它补齐缺少的关联、类型和约束再进入下一步。优先提供文本或结构化导出；图片中未标出的约束需要人工补充，外部 SQL 也需要结合现有项目转换为增量迁移。

## 通过迁移脚本（Migration）增量建表

NocoBase Core 通过 **Migration（迁移脚本）** 管理主数据源的表结构——它不是“搬数据”或“换数据库”，而是类似代码版本记录一样，按顺序保存每一次建表、加字段和加关联的增量变更。应用已有业务数据、或要把改动同步到测试与生产环境时，手工改库既容易破坏存量数据也难以复现；把每次变更写成脚本，就可以先预览、只增不删，并在不同环境重复执行。主数据源中所有业务表的新增与后续演进都必须通过迁移脚本管理（接入外部数据源不受此限制）。

确认模型无误后，让 Agent 生成迁移脚本并先展示变更范围：

```prompt
这个模型可以。请按确认的 ER 图和字典，给现有 CRM 增加商机、产品、报价和报价明细相关的表，保留原有记录。先让我看一下这次会增加哪些表和关联。
```

Agent 生成的迁移脚本会创建四张新表及关联约束，并补充应用查询关联数据时所需的定义。具体语法和写法见[建表与数据初始化](../../core/developing-apps/data-models-and-migrations.md)和[数据库关联](../../core/framework/database/relations.md)。

核对待执行变更**只新增结构、不删除或清空原有表**，先备份数据库，再在应用根目录执行预览和应用：

```bash
pnpm nocobase db apply --dry-run
pnpm nocobase db apply
```

`--dry-run` 只列出待执行计划，确认无误后再运行第二条命令。若开发服务启动时已自动应用变更，预览会提示无待执行项，核对执行记录即可。`db apply` 完成后会自动刷新本地集合缓存。

执行后立即做两项检查：

- **新结构到位**：四张新表及关联约束已建立。
- **存量业务完好**：打开已有客户，查看联系人和跟进记录，并新增一条跟进，确认原有功能和数据不受影响。

以后需要继续加字段或调整结构时，应新增一份增量迁移脚本，不要回头修改已执行过的文件，详见[新增迁移并保留已有数据](../../core/developing-apps/data-models-and-migrations.md#新增迁移并保留已有数据)。另外，迁移脚本只负责把表结构和约束建好，不会自动把产品单价复制到报价明细，这部分业务规则需要在下一步的写入逻辑中实现。

## 接入业务操作与事务保存

建好数据表后，让 Agent 把模型接到页面和服务端写入逻辑：

```prompt
请把商机、产品和报价接到页面上：能维护产品目录，从客户创建和打开商机，再新建、查看和编辑报价。

选择产品时默认带入当前单价，保存时记下本次报价单价；编辑旧报价时沿用已保存的单价。每行按数量、单价和折扣计算金额，四舍五入到两位小数后相加得到总额，10% 折扣表示减免十分之一。做好后运行起来，我来创建报价验证。
```

这里有两个关键的写入保障（参考完整示例的[报价保存逻辑](https://github.com/nocobase/doc-demo-crm/blob/main/server/providers/sales.ts)）：

- **服务端重算与防篡改**：金额按整数美分在服务端重算，不直接信任浏览器提交的总额；编辑旧报价时沿用明细里已存的单价。
- **事务一致性**：通过[事务](../../core/developing-apps/transactions-and-consistency.md)将报价主表和明细行一起保存，避免某一行校验失败时留下半份脏数据。

接下来用管理员账号在应用中录一组报价数据，验证多层关联路径和明细写入（演示数据沿用英文界面和 USD，暂不涉及税费和运费）：

1. 打开 **Customers → Northstar Labs**；若无该记录，先创建客户并补一条联系人和跟进记录。
2. 在 **Products** 中创建或更新 **Team workspace license**（编码 `TEAM-LICENSE`，单价 `100.00`）和 **Onboarding workshop**（编码 `ONBOARDING`，单价 `250.00`）。
3. 回到客户，通过 **New opportunity** 创建 **Northstar sales workspace**（若已存在则直接打开）。
4. 新建报价 **Annual rollout proposal**，选入上述两个产品并按下表填写，保存后重新打开并刷新页面。

| 产品 | 数量 | 报价单价 | 折扣 | 行金额 |
| --- | --- | --- | --- | --- |
| Team workspace license | 10 | 100.00 | 10% | 900.00 |
| Onboarding workshop | 1 | 250.00 | 0% | 250.00 |
| **总额** | | | | **1150.00** |

若加载过示例数据，商机下可能已有预置报价 **Northstar team rollout**（总额 `2096.00`），保持它不动，另建 **Annual rollout proposal** 完成本次验证。

![Annual rollout proposal 保存两行产品、单价及折扣，总额为 1,150.00 USD。](/assets/guides/quote-details.png)

## 验证关联关系与数据一致性

从关联路径、主数据变更隔离和异常回滚三个方面验收模型与写入逻辑：

1. **检查关联归属路径**：沿 **Northstar Labs → Northstar sales workspace → Annual rollout proposal** 逐层打开记录，确认商机归属、报价归属和两行产品明细全部正确对应。
2. **检查主数据变更不影响历史单据**：在 **Products** 中把 **Team workspace license** 的单价从 `100.00` 改为 `120.00`，然后逐项核对：

| 操作 | 应观察到的结果 |
| --- | --- |
| 查看产品目录 | 许可证当前单价显示 `120.00` |
| 重新打开并刷新旧报价 **Annual rollout proposal** | 许可证单价仍为 `100.00`，总额仍为 `1150.00` |
| 在同一商机新建 **Repriced rollout check**，选同样两个产品、数量和折扣并保存 | 许可证带入新单价 `120.00`，行金额 `1080.00`，总额 `1330.00` |
| 编辑旧报价，将许可证数量改为 `12`（不改单价和折扣）并保存 | 沿用旧单价 `100.00` 重算，行金额 `1080.00`，总额 `1330.00`；将数量改回 `10` 后总额恢复 `1150.00` |

新报价的 10 个许可证和旧报价的 12 个许可证总额碰巧相同，但明细单价不同。核对时看明细行而非只看总额，就能直观看到外键关联（指向哪个产品）和已存业务值（当时按什么价报）各自的作用。

3. **自动化回归与异常测试**：让 Agent 在隔离数据库中运行输入校验、主从保存失败回滚及原有客户/跟进功能回归测试（可参考示例的[验证说明](https://github.com/nocobase/doc-demo-crm/blob/main/docs/verification.md)），并核对实际执行结果。

**完成的标志**：四张业务表和关联约束已通过迁移脚本（Migration）增量创建，原有客户、联系人与跟进数据完好；报价和明细在服务端事务中正确写入与重算，产品调价后历史报价不受影响，隔离库自动化测试通过。
