在 CRM 系统中，销售人员通常会记录客户的采购需求，跟进商机，再从产品目录中选择合适的产品给客户报价。每份报价都需要记下当时的产品单价，这样即使产品目录后来调价，也能查到当初报给客户的价格。你会和 Agent 一起梳理客户、商机、产品和报价之间的关系，再让它为应用建表，保存每份报价的明细。

你可以在自己的 NocoBase Core 项目里跟着做。想先体验效果，也可以按[完整 CRM 示例的运行说明](https://github.com/nocobase/doc-demo-crm/blob/main/README.MD)启动应用。示例已具备报价功能，登录后直接按[报价录入步骤](#接入业务操作与事务保存)开一份报价即可。

## 梳理 ER 图与数据字典

同一家客户可能同时洽谈软件许可和咨询服务。每笔销售机会称为一个**商机**，可以分别跟进，也可以先后给出几份报价。如果应用已有客户记录，就让 Agent 把商机关联到现有客户。若还没有客户管理功能，在下面的需求中补一句“也帮我加上创建和查看客户的功能”即可。

在项目的 Agent 会话中，先说清楚你希望怎样报价：

```prompt
我想在应用里管理商机和报价。一个客户可以有多个商机，每个商机可以有多份报价。产品目录里有名称、编码和当前单价。一份报价可以选多个产品，每行都能填数量和折扣。以后产品调价，已经保存的报价要保留当时的单价。

先画一张 ER 图，让我看看这些记录之间是什么关系，再整理一份简短的数据字典，说明关键字段的含义、类型和限制。这一步先不改数据库。
```

看 ER 图时，可以顺着一份报价找它所属的商机和客户，再看报价里每种产品的数量、单价和折扣存在哪里。

![客户到商机、商机到报价、报价到明细、产品到明细均为一对多关系。产品保存当前价，报价明细保存报价时的单价。](/assets/guides/crm-sales-er.svg)

- **报价属于哪个商机？** 每份报价对应一个商机，每个商机对应一个客户。同一客户的两笔商机可以分别查看各自的报价。
- **这次卖多少，优惠多少？** 同一个产品可以出现在多份报价中。每份报价用自己的明细行记录选了什么产品，以及这次的数量和折扣。
- **产品涨价后，旧报价从哪里取价？** 明细行除了记录选中的产品，还要保存报价时的单价。产品目录更新价格后，仍然可以从明细里读到原价。

再看数据字典，确认每个字段能存什么值、有哪些限制。例如，在 CRM 示例中，产品编码是必填文本，最多 40 个字符，而且同一个编码只能给一个产品使用。下面列出四张表的主要字段，完整类型和约束见示例的[模型与字段说明](https://github.com/nocobase/doc-demo-crm/blob/main/docs/sales-model.md)。

| 表 | 主要字段 |
| --- | --- |
| 商机 `crmOpportunities` | 所属客户、商机名称、阶段 |
| 产品 `crmProducts` | 名称、编码、当前单价 |
| 报价 `crmQuotes` | 所属商机、报价名称、总额 |
| 报价明细 `crmQuoteLines` | 所属报价、产品、数量、报价单价、折扣、行金额 |

如果团队已有 ER 图、数据字典或建表 SQL，可以把它交给 Agent 对照现有项目整理。图中没标明的规则，例如产品编码是否允许重复，可以在确认模型时补充。

## 通过迁移脚本增量建表

NocoBase Core 用**迁移脚本（Migration）**记录主数据源的表结构变更。这次的迁移会建立销售业务表，并把商机关联到客户。以后再加字段时，Agent 可以新增一份迁移脚本，保留已经执行过的变更记录。

确认模型后，让 Agent 在当前开发环境中完成建表：

```prompt
这个模型可以。请按它给应用加上商机、产品、报价和报价明细，保留原有记录。如果库里已经有业务数据，先做好备份。建好后帮我确认这些表和关联都已生效。
```

Agent 负责生成并执行迁移脚本，检查新表及其关联。你可以打开一条原有记录，看看熟悉的数据是否还在，并试一次原有操作。例如，客户原先有联系人和跟进记录，就打开该客户查看联系人，再新增一条跟进。有关建表和关联的具体用法，见[建表与数据初始化](../../core/developing-apps/data-models-and-migrations.md)和[数据库关联](../../core/framework/database/relations.md)。

## 接入业务操作与事务保存

表建好后，还需要让销售能从客户页面开报价，并在保存时记下每一行的单价。继续告诉 Agent：

```prompt
我想在页面上维护产品目录，从客户名下创建或打开商机，再给这个商机新建、查看和编辑报价。

选产品时带入目录里的当前单价，编辑旧报价时沿用上次保存的报价单价。10% 折扣表示减免十分之一。每行先算折后金额，四舍五入到两位小数，再相加得到总额。

整份报价要一起保存。如果有一行保存失败，这次修改就全部取消。做好后运行起来，我来试着开一份报价。
```

完整示例在服务端用整数美分重算每行金额和总额，并用一次[事务](../../core/developing-apps/transactions-and-consistency.md)保存报价和所有明细。这样即使最后一行写入失败，前面几行和总额也会一起撤销。具体实现见[报价保存逻辑](https://github.com/nocobase/doc-demo-crm/blob/main/server/providers/sales.ts)。

用管理员账号登录应用，按下面的示例开一份美元报价，不计税费和运费：

1. 在 **Customers** 中打开客户 **Northstar Labs**。如果还没有这位客户，先创建一条客户记录。
2. 在 **Products** 中准备两种产品：**Team workspace license**（编码 `TEAM-LICENSE`，单价 `100.00`）和 **Onboarding workshop**（编码 `ONBOARDING`，单价 `250.00`）。已有产品可以直接更新单价。
3. 回到客户页面，通过 **New opportunity** 创建商机 **Northstar sales workspace**。如果已有这笔商机，直接打开。
4. 在商机下新建报价 **Annual rollout proposal**，按下表填写并保存。如果商机下已有示例报价 **Northstar team rollout**，保留它，另建这份报价。

| 产品 | 数量 | 报价单价 | 折扣 | 行金额 |
| --- | --- | --- | --- | --- |
| Team workspace license | 10 | 100.00 | 10% | 900.00 |
| Onboarding workshop | 1 | 250.00 | 0% | 250.00 |
| **总额** | | | | **1150.00** |

![Annual rollout proposal 保存两行产品、单价及折扣，总额为 1,150.00 USD。](/assets/guides/quote-details.png)

## 验证关联关系与数据一致性

从客户 **Northstar Labs** 打开商机 **Northstar sales workspace**，再打开刚保存的 **Annual rollout proposal**。如果能在这笔商机下找到报价，并看到两行产品和 `1150.00` 的总额，就可以用这份报价检查调价的影响。

在 **Products** 中把 **Team workspace license** 的单价从 `100.00` 改为 `120.00`，依次试下面三种操作：

| 操作 | 预期结果 |
| --- | --- |
| 重新打开旧报价 **Annual rollout proposal** | 许可证单价仍为 `100.00`，总额仍为 `1150.00` |
| 在同一商机下新建 **Repriced rollout check**，选同样的产品，保持数量和折扣不变并保存 | 许可证单价为 `120.00`，10 个打九折后为 `1080.00`，报价总额为 `1330.00` |
| 编辑旧报价，把许可证数量改为 `11` 并保存 | 仍按旧单价 `100.00` 计算，许可证行金额为 `990.00`，报价总额为 `1240.00`。把数量改回 `10` 后，总额恢复为 `1150.00` |

最后，让 Agent 在独立的测试数据库中验证保存失败的情况。先检查无效输入（例如数量为零）会被拒绝，再模拟保存第二行明细时写入失败。检查回滚时，新建失败的报价应查不到，第一行明细也不应留下。如果编辑的是已有报价，重新打开后应看到修改前的明细和总额。如果项目原先支持客户跟进，请 Agent 一并运行对应的回归测试。示例的测试入口见[验证说明](https://github.com/nocobase/doc-demo-crm/blob/main/docs/verification.md)。

## 小结与下一步

**完成的标志**：客户名下能查到商机和报价，调价后旧报价保留原价，任一明细保存失败会撤销整次修改。

现在，销售可以从客户找到对应的商机和报价。产品目录维护今天的价格，每份报价保留当时谈好的价格。接下来可以学习[搭建业务页面](pages-and-ui.md)，把客户列表、筛选和详情页组织成销售日常使用的工作台。
