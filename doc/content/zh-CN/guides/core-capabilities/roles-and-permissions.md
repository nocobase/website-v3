在 CRM 应用中为销售和销售主管设置不同的操作权限与客户数据范围。开始前做好以下准备：

- 准备一个管理员、两位销售和一位主管的独立测试账号。销售和主管不要兼任管理员，也不要带有额外的广泛授权。
- 没有负责人的旧客户，由主管逐条分配，不能默认向所有登录用户开放。
- 备份数据库。新增权限与数据范围字段的迁移不可自动撤销，回退需要恢复匹配版本的数据库备份。

## 明确角色、操作权限与数据范围

将“能做什么”和“能处理哪些记录”分开确定。能打开客户页面，不代表能修改任意客户；获得某个客户的共享，也不代表能修改它。

| 行为                                   | 销售                                     | 销售主管             |
| -------------------------------------- | ---------------------------------------- | -------------------- |
| 新建客户                               | 可以，新客户归自己                       | 可以，并可分配负责人 |
| 查看客户及相关记录                     | 自己负责的客户，以及明确共享给自己的客户 | 全部客户             |
| 修改客户、联系人、商机和报价，添加跟进 | 仅自己负责的客户                         | 全部客户             |
| 查看共享客户                           | 只读                                     | 可以管理             |
| 分配负责人、建立或撤销共享             | 不可以                                   | 可以                 |
| 查看产品目录                           | 可以                                     | 可以                 |
| 维护产品目录                           | 不可以                                   | 可以                 |

Core 的[权限管理](../../core/using-plugins/authorization/permissions.md)同时限制操作和记录范围。例如，销售可以修改客户，但只能修改自己负责的客户。主管可以维护全部客户。

联系人、跟进、商机和报价都遵循所属客户的权限。工作台数量、搜索结果和最近跟进也只能包含有权查看的数据。这些规则需要由应用接入，不能只隐藏页面按钮。

角色把一组职责赋予用户，操作权限决定能做什么，数据范围决定能对哪些记录执行该操作。读取和修改的范围可以不同：销售能读取共享客户，却只能修改自己的客户。共享只追加记录范围，不授予操作权限。

[默认数据范围](../../core/using-plugins/authorization/default-access.md)用于给已有操作权限的用户追加共同可访问的记录范围，例如公开客户；它不是“只能访问自己的客户”的同义词。本专题按角色和负责人限定范围，再向指定销售共享客户。

## 配置用户与角色

通过[用户管理](../../core/using-plugins/authentication/users.md)分配角色。[登录认证](../../core/using-plugins/authentication/sign-in.md)识别当前用户，权限规则再决定他能查看和修改什么。页面和服务端接口都要检查权限。完整示例中的[权限配置](https://github.com/nocobase/doc-demo-crm/blob/main/server/providers/crm-permissions.ts)和[访问控制接口](https://github.com/nocobase/doc-demo-crm/blob/main/server/routes/crm-access.ts)实现了这些规则。

在应用根目录向 Agent 发送：

```prompt
给 CRM 增加销售和销售主管两种角色。

- 销售只能维护自己负责的客户，新建客户归自己。
- 主管可以维护全部客户、分配负责人，也可以把客户只读共享给指定销售，再撤销共享。
- 只读共享的客户可以查看，不能修改。联系人、跟进、商机和报价都遵循所属客户的访问范围。
- 销售可以查看产品，主管可以维护产品。
- 管理员能给选定用户分配角色。不要让所有登录用户自动获得 CRM 权限。
```

完成后，由管理员在 **系统设置** 的用户管理中给测试用户分配对应角色。角色应能从用户详情中查看和调整；检查账号已有角色，确保没有额外授权扩大访问范围。不要把销售角色批量分配给所有登录用户。

下面的验证步骤用 Alex 和 Taylor 表示两位销售，Morgan 表示主管。名称可以替换，但验收时要使用三个不同用户和独立浏览器会话。在自己的测试环境中设置密码，不写入源码或截图。

## 验证销售与主管的操作权限

分别登录 Alex 和 Morgan，使用一条练习用产品，避免修改已有报价演示的产品价格。

| 操作 | 应有结果 |
| --- | --- |
| Alex 打开产品目录 | 可以查看，但不能新增产品或修改价格 |
| Morgan 新增一条练习产品，再修改价格 | 可以保存；Alex 刷新后能看到最新价格 |
| 管理员暂时移除 Taylor 的 CRM 角色，Taylor 重新登录并直接打开客户页面 | 不能进入客户业务；恢复销售角色并重新登录后再继续练习 |

如果结果不符，先在用户详情中检查角色分配，再检查角色的操作授权。不要通过授予管理员角色让测试通过。菜单或按钮是否可见还不足以证明权限正确，最后还需检查接口是否拒绝未授权操作。

## 配置并验证客户数据范围

准备一条包含联系人、跟进与报价的客户记录（例如 **Northstar Labs → Northstar sales workspace → Annual rollout proposal**，可参考[数据建模与表结构变更](data-modeling.md#接入业务操作与事务保存)和[工作台与业务页面搭建](pages-and-ui.md#继续跟进客户并查看报价)准备，或直接使用示例数据）。

使用 Morgan、Alex 和 Taylor 的独立浏览器会话，按顺序完成每一行的操作和验证，再进入下一行。开始时确认 Northstar Labs 没有额外共享；如已有其他客户，主管也应明确分配负责人，列表验收以各客户的实际归属为准。

| 操作 | 立即验证的结果 |
| --- | --- |
| Morgan 打开 Northstar Labs 的 **概览**，将负责人设为 Alex；另建或选择 **Harbor Design**，分配给 Taylor | Alex 能打开 Northstar Labs 及其商机、报价，不能打开 Harbor Design；Taylor 的访问范围相反 |
| Alex 新建 **Cedar Studio** | 负责人自动为 Alex；Taylor 不能查看，Morgan 可以查看 |

Alex 打开自己负责的 Northstar Labs，修改一项客户资料并保存；Morgan 应能看到变化。再让 Alex 直接打开 Harbor Design 的地址，应无法读取。检查工作台数量、搜索结果与最近跟进，确认它们也遵循客户归属。

## 检查只读共享、撤销与交接

保持 Northstar Labs 的负责人为 Alex，并先确认 Taylor 不能读取它，再按顺序执行：

| 操作 | 立即验证的结果 |
| --- | --- |
| Morgan 在 Northstar Labs 的 **只读共享** 中选择 Taylor 并保存，负责人仍为 Alex | Taylor 能查看该客户、已有跟进记录和 Annual rollout proposal，但没有可用的编辑或新增入口；Harbor Design 仍可维护 |
| Morgan 撤销 Northstar Labs 对 Taylor 的共享 | Taylor 刷新已打开的客户与报价页面后不能读取；搜索、工作台数量和最近记录也不再包含该客户的业务。Alex 仍可维护 |
| 确认撤销检查通过后，Morgan 将 Northstar Labs 的负责人从 Alex 改为 Taylor，不再给 Alex 共享 | Taylor 可以维护客户及其关联记录；Alex 刷新后失去访问。Taylor 能看到原联系人、跟进记录和报价，报价总额仍为 `1150.00` |

[共享规则](../../core/using-plugins/authorization/sharing-rules.md)让 Taylor 能查看 Northstar Labs 及其相关记录，但不能修改。Taylor 仍需先拥有查看客户的角色权限。

先检查撤销共享，再转移负责人。因为 Taylor 一旦成为负责人，即使没有共享也能访问客户。转移后，Alex 失去访问，原跟进作者和报价内容保持不变。

## 让 Agent 检查接口权限

让 Agent 用独立账号和数据测试，不能用管理员代替销售。除了页面操作，还要检查直接向接口提交请求的结果：

| 检查 | 应有结果 |
| --- | --- |
| 销售尝试新增产品或修改价格 | 请求被拒绝；主管执行相同操作可以成功 |
| 没有 CRM 角色的用户或未登录访客请求客户接口 | 请求被拒绝 |
| Alex 请求读取或修改 Taylor 负责且未共享的客户 | 请求被拒绝，数据不变 |
| 只读用户尝试修改共享客户 | 请求被拒绝，数据不变 |
| 撤销 Taylor 的共享，再访问原客户和报价 | 不能继续读取 |
| Alex 保存客户和报价后，将客户转给 Taylor，再由 Alex 重发原保存请求 | 重新检查权限并拒绝，不能沿用以前的成功结果 |
| 查看工作台及客户相关记录 | 与客户的访问范围一致 |
| 分配角色、升级数据库 | 不意外扩大权限，原业务字段和报价金额保留 |

重发请求时，Agent 应保留原登录身份和完整请求，包括请求标识，确认旧请求不能绕过变更后的权限。

## 小结与下一步

**完成的标志**：已分别使用销售、主管和只读共享账号检查页面及接口权限；共享撤销和客户交接后，访问范围立即按新权限生效，旧请求不能绕过权限，原联系人、跟进与报价金额保持完整。

要为报价设置审批流程，可参考[审批流程与待办中心](approval-workflows.md)。
