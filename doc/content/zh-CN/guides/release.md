准备一个已接入 Studio 的 CRM 项目、测试与生产环境，以及发布权限。本例的候选提交包含已合并的报价版本对比和客户交接功能。先在测试环境验证，再将更新发布到生产，保留已有业务数据。

Studio 的 **发布** 将交付分为四个环节：**预览** 验证 PR，**测试** 验证合并后的应用，**发布** 记录 Git tag 与制品，**生产** 记录团队确认的生产版本。Studio 可托管预览和测试应用；生产部署在自己的基础设施执行。

![CRM 发布页展示四个交付环节和待发布任务所在的位置。](/assets/guides/studio/releases.png)

## 部署到测试环境并验证业务流程

打开 CRM 项目的 **发布**，在 **测试** 卡片点 **部署指引**，填写独立应用 ID，例如 `crm-staging`，选择已有测试环境。

可以复制提示词，让本地 Agent 构建并上传制品；希望每次合并后自动更新时，使用 **接入 CI** 配置流水线。测试环境准备见[托管环境](../studio/admin/environments.md)，构建与上报见[检查与 CI](../studio/configure/checks.md)。

![测试部署指引支持 Agent 构建上传、接入 CI 和手动命令。](/assets/guides/studio/staging-guide.png)

核对测试应用实际运行的提交，再请 Morgan 使用独立测试数据走完：查看已有客户与历史报价、创建新报价版本并对比、交接客户并检查新旧负责人的权限。保留前序已有的功能；应用已经接入审批、通知或邮件时，同时检查这些功能未被破坏。

**步骤检查**：测试应用运行的是本次候选提交，新功能和已有流程都通过验证，失败项已修复或明确排除出发布范围。

## 核对待发布任务

在 **待发布** 查看已完成但尚未交付生产的任务。**已在测试环境** 表示改动已进入测试环境，**还没部署** 表示尚未部署到测试环境。核对报价版本对比和客户交接是否包含在候选提交中，不能只看任务状态为 **已完成**。

有依赖的改动应一起检查。任务尚未进入候选提交时，先更新测试环境并重新验证，不把未验证的默认分支最新提交直接作为发布目标。

## 配置版本线

在 **设置 → 代码仓库 → 版本线** 配置发布 tag 的匹配格式，例如 `v*`。已有版本线时沿用团队约定；多条版本线的匹配范围不能重叠。见[版本与发布](../studio/release/versions.md)。

## 发布版本

在 **发布** 卡片点 **如何发布**：

1. 选择 CRM 仓库和版本线。
2. 选择刚验证的测试环境，核对 **目标提交**。
3. 填写尚未使用的发布 tag，例如 `v1.1.0`。
4. 检查 **包含的任务** 和 **未包含的任务**，确认本次范围。
5. 复制生成的命令，在自己的 CRM 仓库中创建并推送 tag。

![发布面板列出目标提交、包含和遗漏的任务，以及创建 tag 的命令。](/assets/guides/studio/publish.png)

等待 Studio 识别新 tag，并检查该版本有可部署的压缩包或镜像。tag 本身不是制品；需要由流水线或 Agent 构建并上传。创建版本也不代表已经上线，生产记录在实际部署后更新。

**步骤检查**：版本指向已验证提交，包含预期任务，部署制品可用。

## 升级生产并记录运行版本

在 **生产 → 部署指引** 选择目标版本，按现有环境使用 **Docker** 或 **安装器**。将指引交给可以访问服务器的 Coding Agent 时，说明服务器已经运行 CRM，要按升级处理，保留配置与业务数据。

升级前保存数据库和持久化文件备份，确认迁移与恢复方案。升级后检查登录、旧客户和历史报价、版本对比与交接权限。具体步骤见[生产交付](../studio/project/release.md)；需要回退时，代码回滚和数据库恢复分别按该版本的兼容性处理。

验证通过后，由有权限的项目负责人记录实际部署版本。这个记录不会执行部署，也不能替代运行检查。

**完成的标志**：生产实际运行的版本与 Studio 记录一致，Morgan 能使用新增功能，旧业务记录完整。后续反馈继续建为 CRM 项目任务，进入下一轮开发。
