当你已经有一份基于 NocoBase Core 的代码仓库，希望用 Studio 统一组织需求、Agent 开发和持续交付时，可以直接把现有仓库接入 Studio，无需重建应用。

下面以已有 CRM 仓库为例（想先练手，可将 [`nocobase/doc-demo-crm`](https://github.com/nocobase/doc-demo-crm) Fork 到 Studio Git 连接可访问的账号中操作）。开始前，确认已具备可登录的 Studio 工作台。

## 关联已有代码仓库

Studio 只连接代码仓库，不会连接或改动你的生产服务器与生产数据库。

在本地 CRM 仓库目录中，直接告诉已接入 Studio 的本地 Coding Agent（接入方式见[在本地 Coding Agent 中使用 Studio](../../studio/join/local-agent.md)）：

```prompt
帮我把当前目录的 CRM 仓库接入 Studio，新建名为 CRM 的项目，保留现有代码，不要初始化。完成后把项目地址发给我。
```

也可以在 Studio 网页中手动创建：打开左侧 **开发 › 项目**，点 **新建项目**，**代码位置** 选 **已有仓库**、初始化方式选 **不初始化** 后点 **创建**（不会跑初始化任务，直接进入项目页；详见[项目设置](../../studio/project/settings.md#接入已有仓库)）。

打开项目顶部的 **设置 › 代码仓库**（注意是项目内的设置页，而非左下角的工作区设置），核对仓库地址与 **默认分支**。仓库里原有的 `AGENTS.md`、自定义 Skills 和需求文档保持不动即可让 Agent 直接读取；测试或开发脚本所需的密钥放项目 **设置 › Agent 运行变量**，预览与测试应用自身的运行配置（如测试数据库连接）放[托管环境](../../studio/admin/environments.md)。

![CRM 项目的代码仓库设置，集中展示默认分支、检查、分支规则、版本线与预览。](/assets/guides/studio/repositories.png)

**步骤检查**：项目已关联目标仓库和正确的默认分支，仓库中原有的代码与规范文件未被覆盖。

## 配置检查与独立预览

### 选择并配置检查来源

新接入的仓库默认使用 **Agent 自检**，无需额外配置即可跑通。想接入独立流水线时，在项目 **设置 › 代码仓库** 点目标仓库 **检查** 一行右侧的 **编辑**：

| 检查来源 | 适合情况 | 基本做法 |
| --- | --- | --- |
| **Agent 自检**（默认） | 快速跑通协作、暂不维护流水线 | 默认已生效，执行任务的 Agent 跑项目脚本并发布 PR 预览 |
| **代码平台 CI**（如 GitHub Actions） | 希望独立于 Agent 统一执行检查和预览 | 选平台与触发方式，把提示词交给本地 Agent 接入工作流并合入默认分支 |
| **外部 CI**（如 Jenkins） | 复用团队已有 CI 平台 | 生成仓库 CI 密钥，在现有流水线中上报结果并发布预览 |

以 **GitHub Actions** 为例：选择 **GitHub Actions**，触发方式选 **Pull request**，目标环境选 **预览**，应用目录填 `.`（根目录），点 **查看提示词** 复制后点 **保存**；把提示词交给本地 Coding Agent 创建工作流与 `NB_STUDIO_API_KEY` 密钥的 PR，合并后后续 PR 就会自动触发流水线。更多选项见[配置检查与预览](../../studio/setup/ci.md)和[配置仓库检查与 CI](../../studio/configure/checks.md)。

![检查面板提供三种检查来源，并配置触发方式、应用目录和预览环境。](/assets/guides/studio/checks.png)

每个仓库只采纳当前选定来源的结果；配置后，任务的 **代码与预览** 会集中展示检查状态、日志与预览链接。

### 确认预览隔离与运行依赖

- **预览数据隔离**：PR 预览初次部署默认加载示例数据，不含生产数据（见 [PR 预览](../../studio/release/previews.md)）。切勿在[托管环境](../../studio/admin/environments.md)的预览配置中填入生产数据库连接；需要外接测试库或必填变量时，在预览环境或预览应用的 **变量** 中补齐测试凭据。
- **运行环境依赖**：确认在线运行环境能安装该仓库依赖并运行测试脚本。

**步骤检查**：检查来源已保存（使用 CI 时工作流已合入默认分支），预览数据与生产隔离。

## 用一个小改动跑通首个 PR

### 提交任务并等待进入待验收

先用一个小改动验证端到端闭环。在项目页右上角点 **新建任务**，输入需求（使用自有项目时换成对应页面与文案）：

```prompt
在客户列表顶部加一段简短提示，说明销售只能看到自己负责或获授权共享的客户。保持现有页面样式、筛选操作和权限逻辑不变，做好后能在客户列表顶部直接看到这段提示。
```

核对 Agent 整理的任务卡片后点 **开始执行**（也可切到 **手动填写**，见[提出需求](../../studio/use/raise-a-request.md)）。任务进入 **进行中**，由调度 Agent 安排开发、检查与独立评审；若中途需要确认规则，可在左侧 **我的任务 › 等你处理** 回复。等待任务进入 **待验收** 并生成 **交付报告**。

### 核对交付结果并合并 PR

打开 **待验收** 的任务，先读 **交付报告**，再核对三项：

1. **规范生效**：点 **看改动** 查看 PR 差异，确认 Agent 遵守了仓库既有的 `AGENTS.md` 与约定。
2. **检查对应最新提交**：在 **代码与预览** 确认检查结果指向最新提交（排查见 [PR 检查与代码评审](../../studio/project/checks-and-review.md)）。
3. **预览独立且无回归**：打开 PR 预览（初始管理员凭据显示在任务页中），用测试账号确认新提示已显示，且核心页面与权限范围保持正常。

发现问题时点 **退回修改** 写明现象与预期；全部无误后点 **合并** 确认目标分支（多角色流程见[任务验收](../../studio/use/accept.md)）。关联 PR 合并后，任务自动变为 **已完成**，PR 预览随之清理。

**完成的标志**：已有仓库已接入 Studio，检查与隔离预览生效，首个小改动 PR 已验收合并且既有规范与生产不受影响。

## 小结与下一步

项目接入并跑通首个 PR 后，后续需求就可以在独立分支上经过检查、评审和预览验收后再进入默认分支。

接下来，可以继续阅读[让业务同事参与](business-colleagues.md)，将业务方的需求提出、规则确认与预览验收纳入同一个 Studio 项目。
