代码合并到默认分支不等于已经安全上线。下面假设 CRM 已合并“报价版本对比”和“客户交接”并准备发布候选版本（自有项目可替换为当前待发布功能），带你完成测试验证、打 tag 出包、备份升级生产并记录版本。

开始前，准备一个已接入 Studio 且有待发布提交的项目、在 Studio 配置好的测试[托管环境](../../studio/admin/environments.md)，以及你自己的生产服务器与发布权限。

Studio 的 **发布** 将交付分为四个环节：**预览** 验证 PR，**测试** 验证合并后的应用，**发布** 记录 Git tag 与制品，**生产** 记录团队确认的生产版本。Studio 只托管预览与测试环境，生产部署在自己的服务器上执行。

![CRM 发布页展示四个交付环节和待发布任务所在的位置（界面为示例项目展示）。](/assets/guides/studio/releases.png)

## 部署到测试环境并验证业务流程

打开 CRM 项目的 **发布** 页签，在 **测试** 卡片点 **部署指引**，填写应用 ID（如 `crm-staging`）并选择已有测试环境：点击 **复制给 Agent 的提示词**，交给本地仓库目录中的 Coding Agent 自动构建并上传制品（希望每次合并自动更新时，点 **接入 CI**；详见[检查与 CI](../../studio/configure/checks.md)）。

![测试部署指引支持 Agent 构建上传、接入 CI 和手动命令。](/assets/guides/studio/staging-guide.png)

部署完成后，在下方 **测试环境** 页签核对 `crm-staging` 运行的提交 SHA 并打开测试应用（若缺必填环境变量，在应用 **变量** 页签补齐并重启）。请业务负责人（如销售主管 Morgan）用独立测试数据走完新增功能与核心业务流程，确认已有功能未被破坏。

**步骤检查**：测试应用运行的是本次候选提交，新旧核心流程验证通过。

## 核对待发布任务

在 **发布** 页下方的 **待发布** 页签，查看已完成但尚未上线的任务。**已在测试环境** 表示改动已进入测试环境，**还没部署** 表示尚未部署。确认本次计划上线的任务均已进入候选提交，不能只看任务状态为 **已完成**；若有遗漏，先更新测试环境再重验。

## 发布版本

首次发布前，先在项目 **设置 › 代码仓库** 的 **版本线** 一行点 **编辑**，配置 tag 匹配格式（如 `v*`，见[版本与发布](../../studio/release/versions.md)）。

版本线就绪后，回到 **发布** 页，在 **发布** 卡片点 **如何发布**：

1. 选择 CRM 仓库与版本线，以及刚验证的测试环境，核对 **目标提交**。
2. 填写尚未使用的发布 tag，例如 `v1.1.0`。
3. 检查 **包含的任务** 和 **未包含的任务**，确认发布范围。
4. 点 **复制命令**，在本地 CRM 仓库先 `git fetch` 拉取最新提交，再运行命令创建并推送 tag。

![发布面板列出目标提交、包含和遗漏的任务，以及创建 tag 的命令（界面为示例项目展示）。](/assets/guides/studio/publish.png)

推送后，在下方 **发布** 页签等待 Studio 识别新 tag，并确认该版本已有可部署的压缩包或镜像制品。**tag 本身不是制品**：已配置标签触发 CI 时会自动构建上传；尚未配置时，可接入标签 CI 或让本地 Coding Agent 检出该 tag 执行 `pnpm build --tar` 并上传制品（见[检查与 CI](../../studio/configure/checks.md)）。

**步骤检查**：版本指向已验证提交、包含预期任务，且部署制品可用。

## 升级生产并记录运行版本

在 **生产** 卡片点 **部署指引**，选择 `v1.1.0` 并按服务器环境选 **Docker** 或 **安装器**。推荐复制指引交给可访问生产服务器的 Coding Agent，并在发送时明确补一句：

```prompt
服务器已经运行 CRM，请按升级处理：升级前先备份生产数据库和持久化文件，保留现有配置与业务数据，升级完成后检查登录和页面访问是否正常。
```

手动部署、迁移与回滚方式见[生产交付](../../studio/project/release.md)。升级后，在生产环境核对登录、历史业务记录、新增功能与权限边界。

验证通过后，由项目负责人在 **生产** 卡片点 **记录部署**（或在指引底部记录）登记 `v1.1.0`。记录后，**生产** 卡片更新为当前版本，该版本包含的已完成任务会自动移出 **待发布** 列表（记录本身不会触发部署）。

**完成的标志**：生产实际运行版本与 Studio 记录一致，对应任务已移出 **待发布**，新增功能可用且旧业务数据完整。

## 小结与下一步

至此，团队已经在 Studio 中跑通从接入已有仓库、业务同事协作、沉淀知识与经验、管理交付质量到发布生产的完整闭环。上线后的新反馈继续建为项目任务，即可进入下一轮迭代。

接下来，你可以按当前目标选择后续路径：

- **按业务需求继续扩展应用功能**：进入[专题实战](../core-capabilities/index.md)，按需选学数据建模、权限、审批、文件、通知、邮件等 Core 能力专题。
- **进一步完善团队发布与运维流程**：查阅 Studio 的[发布管理](../../studio/release/overview.md)细化环境与自动化制品流程，或阅读 Core 的[发布应用新版本](../../core/deployment/publish-app-release.md)了解生产升级、备份与回滚细节。
