---
title: 先写一份系统设计文档
metaDescription: 先和 Agent 聊出 ITAM 的设计文档放进仓库，之后每个需求说清五件事、写明验收标准。
---

不要一句话让 Agent 生成整个系统。“做一个 IT 资产管理系统”里有几十个没定的业务问题，Agent 只能替你猜。先和 Agent 把设计聊清楚，写成文档放进仓库，之后每个需求都以它为依据。

## 1. 和 Agent 聊设计

在 `itam-lite` 目录开启新会话：

```prompt
我要在这个应用里做一个精简的 IT 资产管理系统（ITAM），先不要写代码，先和我把设计聊清楚。
三个角色：员工、IT 支持、资产管理员。员工申请设备，需要时由资产管理员审批，IT 支持发放并登记到台账。
请先问我需要决策的问题，一次问一组，每个问题给出你建议的答案。
```

Agent 会逐组提问。这次的问答里定下了这些：

| Agent 问 | 决策 |
| --- | --- |
| 设备记哪些字段？资产编号和序列号是否唯一？ | 资产编号必填且唯一；序列号选填 |
| 哪些申请要审批？ | 笔记本、手机要审批；名下在用设备已有 2 台的人再申请也要审批。两项管理员可调 |
| 谁审批、谁发放？ | 任一资产管理员审批，不能审批自己的申请；IT 支持从在库设备里选一台发放 |
| 员工能看到什么？ | 只看自己的申请和名下设备 |
| 这一版不做什么？ | 采购、维修、盘点、报废、归还、多级审批、导入导出 |
| 有没有企业设计规范？ | 没有，沿用 NocoBase 3 内置的设计规范 |

有企业设计规范（颜色、字体、组件要求）时，把文件放进仓库，在这一步告诉 Agent。

## 2. 写成文档

```prompt
把刚才定下的设计写进 docs/design.md，包括：目标、角色、核心对象和字段规则、领用流程和规则、通知、页面、权限矩阵、设计规范、这一版做与不做、分步交付和每步的验收标准。
在 AGENTS.md 的索引里登记这份文档，写明做任何业务改动前先读它；需求改变了设计时，先更新它再改代码。
```

Agent 写出的文档见示例仓库的 [docs/design.md](https://github.com/nocobase/docs-examples-v3/blob/main/apps/itam-lite/docs/design.md)。最后一节把开发拆成三步，正好是后面三篇：

| 步骤 | 交付 | 怎样算完成 |
| --- | --- | --- |
| 1 设备台账 | 设备表、接口和页面 | 能新建、编辑、搜索设备；资产编号重复时在输入框旁提示；刷新后数据还在 |
| 2 领用与审批 | 申请、流程、通知、流程管理 | 笔记本申请经审批后由 IT 支持发放，台账里设备变为在用；显示器直接待发放；相关的人收到站内信 |
| 3 角色与权限 | 三个角色和数据范围 | 三个账号分别登录，看到和能做的与权限矩阵一致；越权调用接口被拒绝 |

读一遍文档，不对的地方直接让 Agent 改，然后提交：

```bash
git add -A && git commit -m "docs: add the system design"
```

想让这个过程更有章法，可以用 [OpenSpec](https://github.com/Fission-AI/OpenSpec)（把每次变更写成提案、设计、任务）或 [superpowers](https://github.com/obra/superpowers)（先头脑风暴、再写计划、再执行）。本教程直接用对话和一份 `docs/design.md`。

## 3. 之后每个需求说清五件事

设计文档管全局，单个需求还要说清五件事：

| 要说清的 | 说明 |
| --- | --- |
| 谁在什么地方使用 | 哪个角色，在哪个页面 |
| 希望完成什么 | 用户能看到的结果 |
| 规则和边界 | 业务规则；这次不做什么；已有数据怎么办 |
| 失败时怎么办 | 输入不对、数据冲突、没有权限时的表现 |
| 怎样判断完成 | 验收标准，人能照着点一遍 |

同一个需求，两种写法：

```prompt
设备要能归还。
```

```prompt
给设备台账增加“归还”。
IT 支持在设备台账的在用设备上点「归还」，设备状态改为在库，使用人清空，位置改为归还时填写的位置。
只有 IT 支持和资产管理员能归还；员工看不到这个按钮，直接调用接口也要被拒绝。已经在库、维修中、报废的设备不能归还。
设备已经被别人改过时，提示刷新后重试，不覆盖别人的修改。
验收：IT 支持归还一台在用设备后，台账里它变为在库、没有使用人；员工账号看不到「归还」，调用接口返回 403。
```

第一种，Agent 要自己猜谁能归还、状态怎么变、已有数据怎么办。第二种，Agent 照着做，人照着验收。

较大的需求先让 Agent 出方案，确认后再动手：

```prompt
先不要改代码。请阅读 docs/design.md 和相关实现，列出这次要改哪些部分、需要我决策的问题，以及打算怎样验证。
```

需求的写法和验收方法见 [和 Agent 一起开发](../core/developing-apps/develop-with-an-agent.md#描述需求)。

**完成的标志**：仓库里有 `docs/design.md`，`AGENTS.md` 的索引里登记了它，文档末尾有分步交付和每步的验收标准。
