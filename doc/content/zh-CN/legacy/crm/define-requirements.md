## 和 Agent 梳理业务需求

从日常工作出发，告诉 Agent 使用者和目标，暂时不要求实现：

```prompt
我想用这个 CRM 集中记录客户资料、联系人和每次沟通，方便查找客户并接着上次的沟通继续跟进。
第一版先由管理员使用。先不写代码，和我一起把需求聊清楚。
有需要我决定的问题就分组问，每个问题给出你的建议。
```

回答时用实际场景判断。例如，联系客户前要能看到联系人和历史沟通；不再跟进某个客户时，还需要保留过去的资料。不要让 Agent 仅凭“客户管理”推断这些规则。

## 明确第一版的范围与规则

当前 CRM 的第一版采用以下约定。可以据此回答 Agent，也可以按自己的业务调整；调整后，后续开发需求和验收标准也要一起改。

| 要确定的问题                 | 第一版的决定                                                                                                           |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 谁使用，能访问哪些数据？     | 先由管理员使用。未登录或没有客户访问权限的用户不能读取、修改客户；暂不按销售负责人隔离数据                             |
| 客户需要哪些资料？           | 名称、行业、网站、备注和状态；名称必填，其余资料可以以后补充                                                           |
| 如何查找和维护客户？         | 支持新建、查看、编辑、按名称搜索和按状态筛选；不提供删除                                                               |
| 状态表示什么？               | 潜在客户、正式客户、停用是客户分类，不涉及审批；停用保留已有资料                                                       |
| 联系人和沟通记录归属哪里？   | 都归属某个客户，在客户详情中查看和添加；联系人记录姓名、职位、邮箱和电话，姓名必填                                     |
| 跟进要记录什么，有哪些限制？ | 类型为电话、邮件、会面或备注，沟通内容必填，下一步安排选填；自动记录当前用户和时间，最新记录在前，保存后不能修改或删除 |
| 这一版暂不做什么？           | 销售与主管的职责划分、商机、报价、审批、自动提醒、邮件同步和导入；下一步安排只是文字，不会自动发送提醒                 |

页面沿用应用现有的组件和交互。若企业有必须遵循的颜色、字体或界面规范，把规范文件放进项目，并告诉 Agent 文件位置。

## 将需求整理成设计文档

业务范围与规则明确后，先让 Agent 将需求整理成设计文档，保存在应用仓库的 `docs/design.md`，作为生成原型和后续开发的依据：

```prompt
把刚才确认的 CRM 需求整理成一份需求文档，写清使用者、客户和联系人的资料、跟进流程、页面、访问规则，以及第一版暂不做的内容。
还没确定的问题单独列出来，不要当作已经确认的需求。
```

逐项阅读文档，特别检查“保存跟进后能否修改”“停用是否删除资料”“谁能访问客户”等规则。发现歧义时让 Agent 改清楚，再确认版本。

## 生成并确认 HTML 原型

确认 `docs/design.md` 后，让 Agent 根据文档生成原型，检查页面布局和操作流程。将原型保存到应用仓库的 `docs/prototype.html`，使用单个 HTML 文件，样式、交互脚本和演示数据都放在文件内，浏览器直接打开即可使用，无需启动应用或连接数据库。

```prompt
根据已确认的需求，做一个能在浏览器里直接打开的原型，让我体验客户列表、新建和编辑表单、客户详情，以及添加联系人和记录跟进的过程。
用英文界面和虚构数据演示，沿用应用现有的界面风格。这一步先做原型，不开发正式业务功能。
```

原型中的表单、搜索和状态筛选应能操作，方便我们检查页面之间如何衔接。界面遵循现有应用的 shadcn 组件风格；HTML 原型只模拟交互，不需要加载应用组件或调用真实接口。

在浏览器中打开生成的文件，依次检查：

1. 新建一个客户，尝试留空名称，确认必填提示清楚；填写后能进入详情并编辑资料。
2. 在详情添加联系人、记录两次跟进，确认入口容易找到、最新跟进在前，保存后没有修改或删除入口。
3. 返回列表，通过名称搜索和状态筛选找到客户，再将其停用，确认已有资料仍能查看。

发现布局或操作不顺手时，告诉 Agent 具体页面、操作和期望，让它修改 HTML 文件，再重新打开检查。如果原型暴露了业务规则中的歧义，先确认规则并更新 `docs/design.md`，再调整原型。原型确认后，让 Agent 在设计文档中补充 `docs/prototype.html` 的引用，记录各页面的用途和关键交互。

业务规则以 `docs/design.md` 为准，页面布局与交互参考 `docs/prototype.html`。两者有冲突时，先确认并调整一致，再开始开发。

在应用的 `AGENTS.md` 中登记这两份文件，约定业务改动前先阅读；需求变化时，先更新设计，涉及界面交互时同步更新原型，再修改代码。将两份文件一起保存到应用仓库的 Git 版本中，供后续开发引用。

## 拆分开发步骤与验收标准

让 Agent 将交付计划补到设计文档中，每步都应有可以操作检查的结果。页面布局、操作入口和反馈对照已确认的 HTML 原型检查，数据保存与权限在实际应用中验证：

| 步骤         | 交付内容                     | 怎样算完成                                                                                     |
| ------------ | ---------------------------- | ---------------------------------------------------------------------------------------------- |
| 客户管理     | 客户列表、表单和详情         | 能新建、搜索、筛选和编辑客户；名称为空不能保存；停用后仍保留资料；刷新后修改仍在               |
| 联系人与跟进 | 客户详情中的联系人和沟通记录 | 联系人归属正确客户；跟进显示记录人和时间，最新在前；必填内容为空不能保存，保存后不能修改或删除 |
| 测试与交付   | 自动化测试、构建和部署检查   | 测试与构建通过；实际操作能完成客户跟进流程；未授权访问被拒绝，已有数据保持完整                 |

前两步在[开发客户跟进功能](customers-and-follow-ups.md)中完成，第三步在[验收与交付应用](test-and-deliver.md)中完成。团队权限等后续功能另行确定规则，不能把写进计划当成已经实现。

## 后续需求如何说清楚

设计文档描述整体约定，每次开发请求再说清三件事：谁在用、要做什么、有哪些业务规则。例如，只说“加个跟进功能”，Agent 仍要猜记录哪些信息、能否修改；可以这样表达：

```prompt
管理员要在客户详情里记录每次沟通，能选电话、邮件、会面或备注，填写沟通内容和下一步安排。
沟通内容必填，自动记下记录人和时间，最新记录放在前面。保存后不能修改或删除。
```

较大的改动先让 Agent 给出方案，确认后再开发：

```prompt
先别改代码，说明这次需求会影响哪些现有功能，还有哪些业务问题需要我决定，以及怎样检查结果。
```

示例的[设计与原型](https://github.com/nocobase/doc-demo-crm/tree/lesson-2/docs)保存在 `docs/` 中，此阶段不增加正式业务表。

**完成的标志**：应用仓库中有经我们确认的 `docs/design.md` 和 `docs/prototype.html`。原型可直接打开并体验主要操作；设计文档包含第一版范围、业务规则、原型引用、分步交付计划和验收标准；`AGENTS.md` 已登记这两份文件。
