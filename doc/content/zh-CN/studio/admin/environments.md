管理员在「托管环境」中添加和维护环境。每个环境用于预览或测试，包含独立的应用、变量和运行策略。

![预览与测试环境的运行方式和策略](https://static-docs.nocobase.com/studio-zh-environments-20261111-normal-2x.webp)

## 添加环境

1. 点「添加环境」，填写名称与 ID，例如「测试」、`staging`。
2. 选择用途和运行方式。
3. 设置访问地址规则，例如 `https://apps.example.com/{appId}/`。使用子域名时准备对应 DNS 和证书。
4. 按需要设置应用容量、停止和休眠时间，测试连接后保存。

默认的「在 Studio 内运行」使用应用子进程，适合压缩包制品。启用 Docker 托管后，也可将测试应用运行在独立容器中；此方式使用镜像制品，并需要配置镜像仓库和拉取权限。相关开关见[配置参考](../reference/config.md)。

生产在团队自己的环境部署，不在此处创建生产托管环境。

## 管理预览应用

打开用途为「预览」的托管环境，查看其中各个 PR 的应用和运行状态。要按项目查看，在项目的「发布」中打开「预览环境」。

![查看 PR 预览及其构建状态](https://static-docs.nocobase.com/studio-zh-previews-20261111-normal-2x.webp)

Studio 内置预览环境使用以下默认策略。在托管环境中可以调整容量和闲置时间。

| 条件 | 行为 |
| --- | --- |
| 10 分钟无人访问 | 停止进程，下次访问自动启动 |
| 24 小时无人访问 | 休眠并清理解压文件，保留配置和数据 |
| PR 合并、关闭或手动销毁 | 删除预览及其数据 |

默认最多保留 20 个预览。休眠后的首次访问需要重新准备应用，可能比普通启动更久。

预览以 Studio 启动的应用子进程运行。正式使用时，为预览配置独立域名和受限的系统用户，相关配置见[配置参考](../reference/config.md)。

托管应用使用同一台主机的内存。启动前会检查可用容量；容量不足时，系统优先停止可安全回收的空闲应用。没有可回收的应用时，页面提示容量已满，可稍后重试或调整托管资源。

## 交付测试应用

在托管环境或项目的发布页添加测试应用，也可以由 CI 首次上报时创建。部署对话框提供给 Agent 的提示词、CI 配置和手动命令。

要持续部署测试应用，在部署面板选择分支推送或标签触发，指定目标测试环境和应用目录。为每个触发条件分别生成流水线配置。部署后可在应用详情中查看记录、日志，或停止、唤醒和删除应用。

## 配置应用环境变量

环境级变量供同一环境内的应用共用。只修改一个测试应用时，在该应用上设置变量。同名变量以应用的值为准。

必填变量缺失时，部署页会列出缺项。

环境开启「部署时加载示例数据」后，首次部署和重新部署都会加载尚未载入的示例。要为单个应用关闭，在应用变量中设置 `APP_SAMPLE_DATA=false`，再点「应用并重启」。

例如，把库存测试应用连接到 PostgreSQL：

1. 准备应用可访问的测试数据库，并给应用账号授予所需权限。
2. 在「发布」打开目标测试应用，进入「变量」。先核对制品声明的变量和应用支持的数据库驱动。
3. 按应用的配置填写连接参数。下例适用于读取这些变量的应用。另加 `DB_PASSWORD`，设为密钥后填写密码。

   ```dotenv
   DB_DIALECT=postgres
   DB_HOST=db.example.com
   DB_PORT=5432
   DB_DATABASE=inventory_test
   DB_USERNAME=inventory_app
   ```

4. 点「应用并重启」。打开启动日志检查数据库连接，再到测试应用中新建一条记录，刷新后确认可以读回。

   ![检查应用变量后，点「应用并重启」](https://static-docs.nocobase.com/studio-zh-app-vars-20261119-841feaef9f.webp)

这些变量只作用于测试应用。切换数据库前，需要保留的 SQLite 数据请另行迁移。

## 受保护的环境和审批

需要限制测试交付时，在环境中启用「受保护」并指定审批人。有部署权限的成员可以提交申请，由另一位审批人在收件箱核对应用与制品。审批人可以直接部署。Agent 执行部署时使用发起人的权限，审批申请须由本人处理。

## 回滚

在应用的部署记录中选择之前的版本回滚，或使用 `nb-studio app rollback`。回滚使用该环境的审批规则。

回滚不会自动恢复数据库。测试数据需要保留时，部署前先备份。回滚后的任务部署标记重新计算，任务状态不会自动改变。
