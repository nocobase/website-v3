托管环境在「发布 › 托管环境」里管理，管理员可以添加和修改，成员可以查看。每个环境有一个用途：

| 用途 | 运行什么 |
| --- | --- |
| 预览 | 每个 PR 的预览应用，见 [PR 预览](../release/previews.md)。Studio 安装后自动创建一个「预览」环境 |
| 测试 | 合并后的代码，供团队在上线前试用 |

生产不是托管环境，按 [部署到生产](../project/release.md) 部署到你自己的服务器上。每个环境有自己的一组应用，改动一个环境，不会影响别的环境里的应用。

## 两种运行方式

| 运行方式 | 应用运行在哪里 | 适合 |
| --- | --- | --- |
| 在 Studio 内运行 | Studio 所在的服务器上，不需要 Docker。首次访问时启动，无人访问时停止 | 预览 |
| Docker | Studio 所在服务器的 Docker 上，每个应用一个容器，互相隔离 | 测试 |

Docker 方式部署时，按镜像摘要拉取，先启动新容器，健康检查通过后才把访问切过去；新版本一直不健康时，旧容器继续服务，这次部署失败。

使用 Docker 方式前，要在 Studio 的 `config.yml` 里打开它，并让运行 Studio 的用户能访问 Docker：

```yaml
releases:
  docker:
    enabled: true
    host: 127.0.0.1
    port: 13200
```

Docker 应用的访问都经过这个端口，请用反向代理指向它。

## 添加环境

1. 打开「发布 › 托管环境」，点「添加环境」。
2. 填写名称和环境 ID，例如“测试”、`staging`，选择用途和运行方式。
3. 「访问地址规则」：应用在这个环境里的访问地址，用 `{appId}` 代表应用，可以放在路径里（`https://apps.example.com/{appId}/`），也可以放在域名里（`https://{appId}.apps.example.com/`，需要泛域名解析和证书）。
4. Docker 环境选择「镜像仓库」，也就是 CI 推送镜像的仓库，或者新建一个，填写地址和拉取凭据。
5. 需要审批时打开「受保护」，选择审批人，见下文。
6. 保存前点「测试连接」，确认能连通。

环境还可以设置最多容纳多少个应用，以及应用无人访问多久后停止、多久后休眠。

## 部署到测试环境

测试应用通常在第一次上传制品时自动创建，也可以在「发布」页选中项目后点「添加测试应用」。把制品部署到测试环境有三种方式，部署对话框里都给出了现成的内容：

- **交给你的 Agent**：复制提示词，它在仓库里运行 `pnpm build --tar`，再用 `nb-studio` 上传制品并部署。
- **接入 CI**：仓库的 CI 在每次合并后构建、上传并部署，触发方式选「推送到分支」，见 [连接 CI](../setup/ci.md)。
- **自己执行命令**：复制命令，在本地构建和上传。

测试应用的「更多」菜单里有部署记录与日志、变量、停止、唤醒和删除。

## 变量

应用读取的变量，可以设在环境上，环境里所有应用都能用；也可以设在单个应用上，应用自己的优先。密钥加密保存，之后不再显示。制品需要的变量没有设置时，不会部署，页面会列出缺的变量和设置的位置。修改变量后，在应用页点「应用并重启」才会生效。

## 受保护的环境和审批

打开「受保护」后，这个环境的每一次部署和回滚，不论由人还是 CI 发起，都变成一份部署申请，等审批人批准。Agent 不能部署到受保护的环境。

- 任意一位审批人批准即可，包括自己发起的申请。没有选择审批人时，由有权审批受保护部署的人决定。
- 申请出现在审批人的收件箱里，写明应用和环境、要部署的制品和它来自的提交、CI 构建时的标签或分支和日志，以及谁发起的。
- 批准时要再输入一次应用 ID。部署的就是申请里的那个制品，之后有了更新的制品，也不会顶替它。

## 回滚

在应用页的部署记录里，选之前的一个版本回滚；受保护的环境里，回滚同样要申请、批准。也可以用 `nb-studio app rollback`。

回滚后，Studio 重新核对这个环境里包含哪些任务的改动：不再包含的任务，部署标记会撤下；其中已经完成的任务，执行回滚的人会收到建议，可以把它们重新打开。任务的状态不会自动改变。

> [!WARNING] 先备份数据
> Studio 部署和回滚前不会自动备份应用的数据库。测试环境里有重要数据时，请自己备份。
