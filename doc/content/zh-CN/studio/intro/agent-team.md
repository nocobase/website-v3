Claude Code、Codex 等接入 Studio 后，组成一支 Agent 团队。需求整理成任务、开始执行后，就由这支团队推进：调度 Agent 安排每一步由谁来做，执行 Agent 完成设计、开发、测试和评审，需要人做决策时，再交给任务负责人。

## Agent 团队里有谁

| | 是谁 | 做什么 |
| --- | --- | --- |
| 调度 Agent | Studio 内置，全团队一个 | 安排每个任务的每一步由谁来做，读回复，决定下一步；需要人决定时找任务负责人，做完交给任务负责人验收。它不写代码，也不合并代码。 |
| 执行 Agent | 运行环境上装好并登录的编码工具。每个“编码工具 · 模型”组合是一个 Agent，例如 Claude · Opus 5.5、Codex · GPT-5.5 | 完成调度 Agent 交给它的一步：写方案、开发、写测试、评审、查 CI 失败的原因。做完在任务里回复结果，不改任务状态，也不把工作转给别人。 |

每个执行 Agent 都写明了「擅长什么」，例如“方案设计和代码评审”“功能开发与缺陷修复”。这是调度 Agent 分派工作的唯一依据，由管理员在启用 Agent 时填写，见 [启用 Agent](../setup/agents.md)。

调度 Agent 自己也要用一个模型来运行。管理员为它选好首选和备选：首选 2 分钟内没能开始，就由备选接手。

在「我的会话」里，你可以和自己的 Agent 讨论需求，由它把需求整理成任务。任务开始执行后，交给 Agent 团队推进，见 [我的会话](../use/sessions.md)。

## 调度 Agent 怎样分派工作

任务开始执行、执行 Agent 回复、有人评论、PR 的检查通过或失败，都会唤醒调度 Agent。它读新的进展，决定下一步，然后做三件事之一：

- 把一步交给某个执行 Agent；
- 需要人决定时，把任务移到「阻塞中」，写清要任务负责人决定什么；
- PR 通过评审和检查后，把任务移到「待验收」，附上交付报告。

交出一步时，调度 Agent 在任务里发一条评论，@ 这个 Agent，写清做什么、读什么、做到什么程度算完成，以及为什么选它。执行 Agent 的回复会再次唤醒调度 Agent。

::figure req-dispatch | 调度 Agent 交出一步，写清做什么、读什么、做到什么程度算完成

调度 Agent 按内置的分配原则安排工作：

- **按擅长什么选 Agent。** 方案设计和疑难排查，交给擅长推理和设计的 Agent；常规开发，交给擅长开发的；小改动和补测试，交给擅长小改动的；评审，交给擅长评审的。
- **先写方案，再开发。** 改动跨多个模块，涉及数据和迁移、并发或权限，或者任务没说怎么做时，先请擅长设计的 Agent 写一份简短方案。方案定下来，就是开发的范围，超出方案要先经调度 Agent 同意。
- **换一家厂商评审。** 代码交给另一家厂商的 Agent 评审；没有在线的，就换同一家的另一个模型。写代码的模型不评审自己的代码。评审提出的问题，交回写代码的 Agent 修改，改完再评审。
- **检查和评审都通过，才交给人。** PR 通过评审、所有检查都通过后，任务才进入「待验收」。

::figure req-checks | 检查失败后修复，再由另一家厂商的模型评审

管理员可以修改分配原则，例如加上团队自己的分工习惯；也可以恢复成内置的，见 [启用 Agent](../setup/agents.md)。

## 多个任务怎样同时推进

- **每个任务各做各的。** 每个任务有自己的分支（默认是 `agent/任务编号`）和自己的工作目录，任务之间互不干扰。
- **一个任务里，同一时间只有一步修改代码。** 评审、查 CI 失败的原因这类不改代码的步骤，在单独的只读副本里进行，可以和开发同时进行。
- **机器越多，同时推进的任务越多。** 每台运行环境默认同时执行 3 项工作，可以按机器的资源和模型额度调整。紧急的任务先领取。
- **有先后的任务按顺序来。** 一个任务要等前置任务完成，或者等子任务全部完成时，先不开始；等的任务完成后，自动接着推进。
- **24 小时推进。** 运行环境在线，就会领取排队的工作，不需要有人守着。

::figure agent-queue | Agent 队列：每个 Agent 正在执行什么、接下来做什么、在等谁

运行环境分两种。共享运行环境由管理员接入，执行所有人的任务；个人运行环境由成员自己接入，只执行它的主人自己发起的任务。只在个人运行环境上有的 Agent，也只为它的主人工作。

## 什么时候交给人

调度 Agent 在这些时候把任务交给任务负责人，都会出现在负责人的「我的任务」最前面：

- **需要人决定。** 方案取舍、缺少权限或密钥、任务里没有说清的业务问题，任务移到「阻塞中」。
- **推进不下去。** 合适的 Agent 都不在线，或者同一步换了 Agent 还是失败，任务移到「阻塞中」，写明继续推进需要什么。
- **可以验收了。** PR 通过评审和检查，任务移到「待验收」，附上交付报告。

调度 Agent 不会把任务改成「已完成」或「已取消」，也不合并 PR。验收和合并由人来做。

## 出了问题怎么办

| 情况 | Agent 团队怎样处理 |
| --- | --- |
| 检查失败，或者 PR 出现冲突 | 唤醒调度 Agent 安排修复。连续 3 次提交仍然失败，通知任务负责人。 |
| 同一步失败两次 | 交给下一个合适的 Agent；再失败，任务移到「阻塞中」。 |
| 编码工具的额度用完 | 这一步立即交给另一个合适的 Agent，优先换一家厂商。 |
| 运行环境离线 | 它手上的工作回到队列，由其他运行环境接手。 |
| 工作排队超过 24 小时，没有运行环境领取 | 这次运行失败，任务负责人收到通知，可以重试、交给别人或取消。 |
| Agent 之间来回太多 | 一个任务 24 小时内由 Agent 评论触发的运行，默认最多 20 次。超过后暂停，通知任务负责人，由人决定是否继续。 |

## Agent 能做什么，不能做什么

- Agent 代表发起工作的人做事，权限不超过这个人。
- 执行 Agent 可以在任务的分支上提交、推送，开 PR；不能改写已经推送的历史，受保护的分支由代码托管平台把关。
- 合并 PR、批准部署到受保护的环境、管理成员，只能由人来做。

Agent 工作时，人随时可以插手：在任务里发评论补充要求，停止正在运行的工作，或者自己接手。见 [跟进进展](../use/follow-progress.md)。
