质量管理是 Studio 企业版（EE）的功能。团队可以维护核心场景、运行项目测试、查看质量报告和指标，并把发现的问题转为跟进任务。企业版镜像及授权请[联系我们](https://www.nocobase.com/zh-CN/contact/)获取。

## 质量标准、工具、报告与后续问题

质量管理围绕四部分工作：先确定标准，使用工具和 Agent 执行检查，按证据生成报告，再把问题交给后续任务处理。

### 质量标准：内置标准，项目可以调整

内置的功能、权限、安全、性能和代码质量五个维度分别定义检查方法、指标与标准。检查方法参考 OWASP ASVS、Sonar way、RAIL 等业界规范与模型，具体预算按项目需要设定；使用这些检查不等于获得对应标准的认证。项目可以覆盖性能预算、修改维度绑定的 Skill，或添加维度。具体标准见[质量指标与标准](metrics.md)。

### 测试工具：工具实测，Agent 组织和分析

Vitest、Playwright、Lighthouse、OWASP ZAP 等工具产生原始测试结果。Agent 准备环境和测试数据、调用工具、分析结果，并补充业务界面操作与代码设计审查。量化指标来自实际运行，不由 Agent 通过阅读代码估算。

### 测试报告：原始证据形成可核对的结论

每个维度生成一份报告，再汇总为交付报告。服务端解析 JUnit、SARIF、审计 JSON、Lighthouse 等原始结果，计算指标并按相应规则判断。缺少数据、工具未完成或解析失败时，要明确保留未验证项，不能当作零问题。

### 后续问题：登记任务，修复后再验证

发现的问题按原因合并为后续任务，进入正常开发、评审和验收流程。规则不明确的地方由人决定，交付报告由人验收；测试过程不直接修改产品代码。修复合入后，通过后续测试验证结果。

打开「开发 › 质量」，选择项目。先在[设置](settings.md)中确认测试规则，再[发起测试](runs.md)。新项目默认不自动触发测试。

## 测试类型

| 类型 | 范围与触发方式 |
| --- | --- |
| 每日测试 | 定时检查最近已完成、尚未覆盖的业务任务；首次或长时间停用后最多回看近三天 |
| 发布测试 | 检查当前待发布任务，可手动发起，也可达到配置的任务数量后触发 |
| 项目测试 | 检查整个项目的核心场景，可手动、每周或每月执行 |
| 自定义测试 | 手动选择已完成的业务任务，或检查整个项目代码 |

每日测试只按计划触发。想立即检查指定任务，使用自定义测试。

## 测试与任务的关系

每次测试都会创建一项普通任务。它保留测试范围、采用的 Skill 版本和执行记录，结果通过任务的交付报告验收。

Agent 按维度执行检查，并将发现的问题关联到跟进任务。测试任务完成，不代表这些问题已经修复；在[跟进任务](runs.md#follow-ups)中继续处理，再通过后续测试核对。

仓库的 PR 检查和代码评审仍用于每次改动。项目质量测试用于持续检查更大范围，见[PR 检查与代码评审](../project/checks-and-review.md)。

## 核心场景

核心场景描述项目应持续满足的业务行为，例如“暂停合作的供应商不能新建订单”。项目测试和整个项目代码的自定义测试会使用它们。

## 检查维度

| 内置维度 | 检查内容 |
| --- | --- |
| 功能 | 业务任务和核心场景的预期行为 |
| 权限 | 账号、角色和数据访问边界 |
| 安全 | 依赖漏洞，以及安全扫描工具上报的发现 |
| 性能 | 页面加载和 API 响应。查看实测数据、测试条件和代码检查发现的风险 |
| 代码质量 | 可维护性问题，以及慢或不稳定的测试 |
