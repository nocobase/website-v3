先准备项目代码仓库、可用 Agent 和在线运行环境。自动测试还需要有效的项目负责人；执行身份必须有项目管理、任务读取和附件上传权限。

## 选择测试范围

1. 打开「质量」，选择项目。
2. 点「运行测试」，选择发布测试、项目测试或自定义测试。
3. 自定义测试选择已完成任务，或选择整个项目代码；按需要调整检查维度。
4. 确认后打开生成的测试任务。

发布测试使用当前待发布任务。没有符合条件的任务时，不会创建空测试。项目测试和整个项目代码的自定义测试使用核心场景检查项目。

创建时会固定测试范围和 Skill 版本。之后修改设置不会改变这次测试；需要使用新的范围或规则时重新发起。

## 查看进度与处理阻塞

![测试任务及各维度的执行状态](https://static-docs.nocobase.com/studio-zh-quality-runs-20261111-normal-2x.webp)

在「测试任务」查看各次测试，也可从「我的任务」进入。任务中会显示各维度的进展、用时、已检查数量和需要补充的信息。

缺少运行环境、项目权限或测试账号时，先补齐条件，再回复任务中的问题。需要业务决定时，由负责人回答，见[回答提问](../use/answer.md)。

不再需要的测试可以取消。取消会保留已有记录，尚未完成的维度显示已取消。执行结束后，[查看报告并验收](runs.md#reports)。

<h2 id="reports">查看报告与验收</h2>

从「质量 › 测试任务」打开测试。测试使用任务的交付报告，不需要到另一套报告系统验收。

![核对交付报告，验收或退回修改](https://static-docs.nocobase.com/studio-zh-quality-report-20261111-normal-2x.webp)

### 结果与证据

先核对测试范围、代码提交和采用的维度，再查看结果。点击维度可阅读详细报告及其附件。

下表说明场景和检查点的单项结果。维度汇总还区分「有问题」「部分未验证」等结论，见[维度结论与单项结果](metrics.md#维度结论与单项结果)。

| 结果 | 含义 |
| --- | --- |
| 通过 | 有证据支持预期行为 |
| 失败 | 实际行为不符合预期，需要查看问题和复现证据 |
| 未验证 | 缺少环境、账号或其他条件，不能判断是否通过 |
| 不适用 | 当前场景与该维度无关，不计为通过或失败 |

打开对应维度，按证据核对结果。功能验证分别列出自动化用例和 Agent 操作的场景。性能报告可分别查看页面和 API 的测量结果。检查权限问题时，确认报告说明了使用的角色、执行的操作和实际结果。只有代码评审记录时，还需验证相应角色的实际访问行为。

检查失败项的证据、未验证项的原因，以及关联的跟进任务。截图只是证据的一种，不能代替明确的预期与实际结果。

![查看维度报告和测试证据](https://static-docs.nocobase.com/studio-zh-quality-dimension-20261111-normal-2x.webp)

### 查看覆盖情况

结果会区分自动化用例覆盖、Agent 操作和未验证项。点击场景查看检查点、实际结果与证据。

已有自动化用例能证明某个场景时，可以复用它；覆盖不足的部分仍需要实际操作。未验证项应保留原因，环境或数据不足通过跟进工作补齐；场景和自动化用例缺口按[核心场景维护](settings.md#scenarios)安排开发更新。

### 验收或退回

确认测试范围完整、证据可核对、问题已有后续安排，再按任务页提示验收。报告有遗漏时，退回并说明缺少的场景或证据。

补充用例或更新核心场景资产时，应通过开发任务提交 PR，并与业务修复分开。质量测试负责报告发现和证据，业务修复进入[跟进任务](runs.md#follow-ups)。完成测试验收，不会自动完成这些修复任务。

<h2 id="follow-ups">跟进问题与复测</h2>

「质量 › 跟进任务」汇总测试产生的后续工作。它们使用普通任务的负责人、讨论和验收流程。

![跟进任务与来源测试的关联](https://static-docs.nocobase.com/studio-zh-quality-follow-ups-20261111-normal-2x.webp)

### 创建跟进任务

Agent 会将已确认的缺陷、待确认的业务问题、测试数据缺口、代码清理、性能优化和依赖漏洞修复登记为后续工作，并关联来源测试和检查维度。问题按原因合并；测试数据不足时，应说明缺少什么。

补充自动化用例和核心场景仍由开发任务维护。质量测试不自动创建「补用例」「补场景」任务；场景缺口写入功能维度的「场景待更新」说明，按业务变化安排开发更新。

| 后续工作 | 处理内容 |
| --- | --- |
| 缺陷 | 已确认的功能失败、越权或安全问题，保留复现证据 |
| 待确认 | 业务规则不明确，由人决定预期行为 |
| 补测试数据 | 补齐记录、身份或其他数据，使未验证项能够执行 |
| 代码清理 | 处理新增复杂函数、未使用代码等维护性问题 |
| 性能优化 | 按原因合并超出预算的项目 |
| 依赖修复 | 按有漏洞的依赖包安排修复 |

打开跟进任务，核对预期结果、实际现象、复现条件和证据，再确定负责人及优先级。同一问题已有未完成任务时，可复用或关联，避免重复修复。

业务修复在跟进任务中执行，测试任务负责记录发现和证据。需要补充业务决定时，在相应任务中回答。

### 修复与复测

1. 在跟进任务中完成修复和验收。
2. 按影响范围发起新的项目、发布或自定义测试。
3. 查看原场景或任务的新结果，确认问题不再出现。

关闭跟进任务不会改写历史测试结果。历史报告保留当时的证据，后续测试反映修复后的状态。
