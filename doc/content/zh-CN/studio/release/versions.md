在 Studio 里，**发布**的意思是在代码仓库里打一个版本 tag。打了 tag 的提交就是一个版本，Studio 自动识别，并算出这个版本包含哪些任务。版本部署到哪里，是另一件事：测试环境见 [托管环境](../admin/environments.md)，生产见 [部署到生产](../project/release.md)。

## 配置版本线

版本线说明哪些 tag 算版本。在「项目设置 › 代码仓库」里，找到仓库的「版本线」，点「修改」：

- Studio 会读取仓库最近的 tag，找出重复出现的前缀，推荐版本线，选中即可使用；也可以手动添加。
- 格式以 `*` 结尾，例如 `v*`、`release-beta/*`。名字里带 `beta`、`rc` 的 tag 同样算版本。
- 一个仓库可以有多条版本线，但它们匹配的 tag 不能重叠。
- 可以选择显示时去掉前缀，例如把 `release-beta/1.2.0` 显示为 `1.2.0`。

仓库还没有 tag 时，先打一个，例如 `v1.0.0`，再来配置。修改或删除版本线，会重新计算这条线的版本和任务关联，制品和部署记录保留。

## 发布一个版本

1. 在「发布」页选中项目，点「发布」。
2. 选择版本线和对应的分支，分支默认是仓库的默认分支，只有合并到这个分支的 PR 才算在内。
3. 选择目标提交：选一个测试应用，就用它正在运行的提交；也可以填写完整的提交 SHA。
4. Studio 对比目标提交和这条版本线的上一个版本，列出这个版本会包含的任务，以及还不在目标提交里的待发布任务。
5. 确认建议的 tag，需要时修改，复制命令在仓库里创建 tag 并推送。

tag 推送后，Studio 自动识别新版本，更新它包含的任务，并通知这个版本已发布。

> [!NOTE] 读取 tag 依赖 Git 连接
> Studio 通过代码平台的 webhook 和定期查询读取 tag。GitHub 的 webhook 失效、只靠定期查询时，打在旧提交上的新 tag 可能读不到。

## 待发布

已经合并、但还没有包含在任何已发布版本里的任务，列在「发布」页的「待发布」分页里，并标出它们是否已经部署到测试环境。准备发布前，从这里看这次会带上哪些改动。

项目里最早的待发布改动合并满 3 天时，项目负责人会收到提醒。

## 制品

版本是代码，制品是构建出来、可以部署的东西：`pnpm build --tar` 打出的压缩包，或者推送到镜像仓库的镜像。制品由 CI、你的 Agent 或你自己上传到 Studio，部署到测试环境和生产时用的都是制品。在「版本」分页里，可以看到每个版本有哪些制品，下载压缩包，或者复制版本号。
