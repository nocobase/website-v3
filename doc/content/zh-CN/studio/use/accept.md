验收是人做决策最关键的一处。Agent 团队交过来的，不只是一个 PR：交付报告写清原来的情况、改了什么、怎么验证的、还有哪些遗留问题，附上验收标准和截图，连接了 CI 时还有可以亲自试用的预览。不懂代码的业务专家，也可以据此直接拍板。

## 什么时候需要验收

调度 Agent 只在 PR 通过检查和评审之后，才把任务转为「待验收」并交给你；项目还没有接 CI 时，它会先问你是否不经 CI 直接验收。任务进入待验收后：

- 任务出现在「我的任务」的“等你处理”里，标着“等你验收”；
- 任务页顶部的“需要你”卡片写明要你确认什么；
- 下面是调度 Agent 提交的交付报告。

只有人能完成验收。调度 Agent 和执行 Agent 都不能把任务标记为完成，也不能合并 PR。

## 读交付报告

交付报告是验收的主要依据。调度 Agent 按内置的写法组织它，包括：

| 部分 | 内容 |
| --- | --- |
| 原来的情况 | 原来是什么样，问题在哪里 |
| 确定的方案 | 这次按什么方案做，范围到哪里为止 |
| 改了什么 | 用业务语言列出的变化 |
| 怎么验证的 | Agent 跑了哪些测试、在什么环境里检查过，评审的结论 |
| 遗留问题 | 这次没解决或者有风险的地方，每条附上建议 |
| 细节 | PR、提交、数据迁移等技术细节 |
| 验收标准 | 你可以对照的检查点，以及对应的截图 |

报告旁边是开发的 Agent 附的截图，点开可以放大、左右切换。

::figure req-accept | 待验收的任务：“需要你”卡片上是处理按钮，下面是交付报告

验收标准是用来对照的，不需要逐条勾选。你对结果做整体判断：通过，或者退回。

## 看改动

- 点「看改动」，在代码托管平台上打开 PR。
- 「代码与部署」页签列出任务关联的所有 PR、每个 PR 的检查结果和冲突情况。

不读代码也能验收：重点看交付报告里的验收标准和截图是否满足你的需求。有疑问时，在任务里发评论问，或者用「问 Agent」。

## 在预览里试一遍

项目连接了 CI 时，每个 PR 都有一个预览。在任务页打开预览，用初始管理员登录，按验收标准亲自操作一遍。

::figure req-preview | PR 的预览，可以亲自试一遍

- 能编辑这个任务的人，可以在任务页看到预览的初始管理员账号和密码。
- 预览用示例数据，没有企业的真实数据。
- 预览一段时间没人访问会停止、休眠，再次打开时会重新启动，稍等片刻即可。
- PR 合并或关闭后，预览自动删除。

项目还没有连接 CI 时没有预览，见 [连接 CI](../setup/ci.md)。

## 通过

**有 PR 的任务**：点「合并」。确认框会先向代码托管平台核对 PR 和检查结果，并写明：

- 合并提交的标题和合并方式，例如“压缩合并到 main”（GitHub 和 Gitee 上是压缩合并；GitLab 按项目的设置）；
- 合并后任务会变成什么状态。

::figure merge-dialog | 合并前的确认

确认后，Studio 合并你确认时的那个版本；如果这期间 PR 又有了新提交，会提示你重新确认。任务关联的 PR 全部合并后，任务自动变为「已完成」。

**没有 PR 的任务**（例如调研、文档整理）：点「验收通过」，任务变为「已完成」。

> [!NOTE] 合并以谁的身份进行
> 你在「个人设置 › Git」连接了自己的账号时，合并以你的身份进行；否则用工作区的 Git 连接。

## 检查没有通过时

下面几种情况，「合并」不可用，需要先解决：PR 有冲突、检查还在进行、PR 还是草稿，或者代码托管平台自己的规则不允许合并。

必需的检查失败，或者没有检查结果（例如项目还没有接 CI）时，确认框里的按钮是「仍然合并」，可以填写合并的原因。Studio 会把这次强制合并评论到 PR 上，并记录在任务动态里；代码托管平台自身的规则仍然生效。Agent 永远不能强制合并。

## 退回修改

结果不符合预期时：

1. 点「退回修改」。
2. 写清需要改什么。越具体越好，例如“合并后应保留最早的创建时间，现在保留的是最新的”。
3. 点「发送并退回进行中」。

任务回到「进行中」，调度 Agent 会根据你的意见安排修改，改完后再交给你验收。

## 在代码托管平台上已经合并

如果有人直接在 GitHub 或 GitLab 上合并了 PR，Studio 会通过 Webhook 或轮询发现，任务同样会自动完成。确实需要时，也可以在 Studio 里点「标记为已合并」，记录为已合并。
