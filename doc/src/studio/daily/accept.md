## 什么时候需要验收

调度 Agent 只在 PR 通过检查和评审之后，才把任务转为「待验收」并交给你。这时：

- 任务出现在「我的任务」的“等你处理”里，标着“等你验收”；
- 任务页顶部的“需要你”卡片写明要你确认什么；
- 下面是调度 Agent 提交的交付报告。

只有人能完成验收。调度 Agent 和执行 Agent 都不能把任务标记为完成，也不能合并 PR。

## 读交付报告

交付报告是验收的主要依据，通常包括：

| 部分 | 内容 |
| --- | --- |
| 改动前的情况 | 原来是什么样，问题在哪里。 |
| 约定的方案 | 这次按什么方案做，范围到哪里为止。 |
| 改了什么 | 用业务语言列出的变化。 |
| 怎么验证的 | Agent 跑了哪些测试、在什么环境里检查过。 |
| 验收标准 | 你可以逐条对照的检查点。 |

报告旁边还有 Agent 评论里附的截图，点开可以放大、左右切换。

::figure req-accept | 待验收的任务：“需要你”卡片上是处理按钮，下面是交付报告

验收标准是用来对照的，不需要逐条勾选。你对结果做整体判断：通过，或者退回。

## 看改动

- 点「看改动」，在代码托管平台上打开 PR。
- 「代码与部署」页签列出任务关联的所有 PR、每个 PR 的检查结果和冲突情况。

不读代码也能验收：重点看交付报告里的验收标准和截图是否满足你的需求。有疑问时，在任务里发评论问，或者用「问 Agent」。

> [!PENDING] 在预览中验收
> 为每个 PR 生成可以实际操作的预览环境，属于发布与部署模块，模块完善后补充。

## 通过

**有 PR 的任务**：点「合并」。确认框会先向代码托管平台核对 PR 和检查结果，并写明：

- 合并提交的标题和合并方式（GitHub 上是压缩合并；GitLab 按项目的设置）；
- 合并后任务会变成什么状态。

::figure merge-dialog | 合并前的确认

确认后，Studio 合并你确认时的那个版本；如果这期间 PR 又有了新提交，会提示你重新确认。任务关联的 PR 全部合并后，任务自动变为「已完成」。

**没有 PR 的任务**（例如调研、文档整理）：点「验收通过」，任务变为「已完成」。

> [!NOTE] 合并以谁的身份进行
> 你在「账号设置 › Git」连接了自己的账号时，合并以你的身份进行；否则用工作区的 Git 连接。

## 检查没有通过时

下面几种情况，「合并」不可用，需要先解决：PR 有冲突、检查还在进行、PR 还是草稿，或者代码托管平台自己的规则不允许合并。

必需的检查失败或缺少检查结果时，项目负责人等有相应权限的人可以选择「仍然合并」，并填写原因。这次强制合并会记录在任务动态里，并以评论的形式写到 PR 上。Agent 永远不能强制合并。

## 退回修改

结果不符合预期时：

1. 点「退回修改」。
2. 写清需要改什么。越具体越好，例如“合并后应保留最早的创建时间，现在保留的是最新的”。
3. 点「发送并退回进行中」。

任务回到「进行中」，调度 Agent 会根据你的意见安排修改，改完后再交给你验收。

## 在代码托管平台上已经合并

如果有人直接在 GitHub 或 GitLab 上合并了 PR，Studio 会通过 Webhook 或轮询发现，任务同样会自动完成。确实需要时，也可以在 Studio 里点「标记为已合并」，记录为已合并。
