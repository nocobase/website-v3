---
title: 现有文档的问题
description: 以目标用户的视角，逐项看现在的《NocoBase Studio 使用指南》缺了什么、哪里会让读者走错。
---

评审对象是 [v3.docs.nocobase.com/zh-CN/studio](https://v3.docs.nocobase.com/zh-CN/studio)（标题《NocoBase Studio 使用指南》），对照的是 Studio 仓库 `dev` 分支和 NocoBase 3 框架 `v3-develop` 分支的代码与设计文档（2026-10-22）。

## 总体判断

现在这份文档是管理员第一次把 Studio 跑起来的安装清单：部署、配置运行环境、连接 Git、建项目、配 CI、建任务、验收。步骤清楚，截图齐全，每一节都有完成标志，作为“快速开始”的底稿是合格的。

问题在于它被当成了整个 Studio 的使用手册。Studio 的目标用户是中大型企业的 IT 与数字化团队，读完这份文档能把 Studio 装起来，但不知道 Studio 是什么、团队里每个人该怎样用它，也看不出它和“直接用 Claude Code 加 GitHub”有什么不同。

## 一、只照顾了一类读者

Studio 的使用者至少有三类，关心的事情完全不同：

| 读者 | 关心什么 | 现在的文档 |
| --- | --- | --- |
| 管理员 | 部署、成员与角色、Agent 和模型、用量与费用 | 覆盖了部署和 Agent 的一部分 |
| 技术负责人 | 项目怎么建、检查规则、合并与发布怎么把关 | 只有建项目和 CI 的操作步骤 |
| 业务负责人和成员 | 怎么提需求、怎么回答 Agent 的提问、怎么验收 | 只有两三句话 |

所有内容放在一页里，按安装顺序排开。业务负责人想知道怎么验收，要先翻过 SSH、Caddy 和 GitHub Secret。

## 二、没讲 Studio 是什么，也没提 Core

全文没有一句话说明 Studio 在 NocoBase 3 里的位置：它是人与 Agent 协同开发的治理平台，开发出来的应用建在 Core 上，上线后独立运行。

- 新建项目时，代码默认用“NocoBase 应用默认模板”初始化，也就是在运行环境上执行 `pnpm create @nocobase/app`。这是“起点高”的来源，文档里只有一句“按需要选择初始化模板”。
- Studio 自己的项目、Agent、知识库能力也来自 Core 的开源插件，这一点同样没有提。
- 读者因此看不出 Studio 的价值在哪里，只看到一串配置步骤。

## 三、Studio 的大部分功能没有出现

文档截图里的侧边栏就能看到：收件箱、仪表盘、知识库、项目记忆、技能、用量、设置里的成员、角色和 API 密钥，都没有讲。其中几项对“团队治理”这个定位至关重要：

- **成员与角色。** 一份团队治理平台的文档，没有一处讲怎样邀请同事、分配角色。
- **技能、知识库和项目记忆。** 团队的做事方法和业务背景怎样交给 Agent、怎样留在团队里，没有讲。
- **仪表盘和用量。** 管理者怎样看交付进度和 Agent 的花费，没有讲。

发布与部署、质量管理两个模块还在开发中，这次的文档方案先为它们留出位置，不写正文（见 [文档结构与写作原则](02-文档结构与写作原则.md)）。

## 四、概念没有建立，操作也就只能照着点

文档里出现了 Runtime、Runner、Runner Agent、Agents、Project manager、My agents、Studio CLI、Coding tools，却没有讲它们之间的关系。几个直接影响使用效果的地方：

- **“擅长什么”没有解释。** 启用 Agent 时要填写它擅长什么，这是项目经理分派工作的唯一依据。文档只写了“点击 Fill in and enable，完成配置”。
- **没有提醒接入两家厂商的 Agent。** 项目经理的内置分配原则要求代码由另一家厂商的 Agent 评审，没有时换同一家的另一个模型，写代码的模型不评审自己的代码。只接一个 Agent，这条规则就落不了地。
- **个人和团队运行环境的区别没有讲。** 个人运行环境只执行主人自己发起的任务。
- **新建任务的“什么时候开始”没有讲。** 选“以后再说”的任务进入“待规划”，Agent 不会动，要在任务页点「开始」。新用户很可能建完任务后奇怪为什么没人动。
- **任务的六个状态、谁能改状态、“初始化项目”任务会挡住其他任务，都没有讲。**

## 五、人做决定的时刻写得最少

在 Studio 里，人主要出现在三个时刻：交代目标、回答提问、验收。这恰恰是文档最薄的部分。

- **“阻塞中”完全没有出现。** 这是 Agent 需要人做决定的时刻，任务页顶部会出现“需要你”卡片和「回复」按钮。
- **验收只有两句话。** 实际上有 PR 的任务用「合并」完成验收，合并后任务自动变为已完成；没有 PR 的用「验收通过」；不通过用「退回修改」并写明原因。
- **交付报告的结构没有介绍。** 改动前的情况、约定的方案、改了什么、怎么验证的、验收标准和截图，是验收时最重要的依据。
- **运行失败后怎么处理没有讲。** 失败的运行会给负责人一张决定卡片：重试、改派给人、不再重试。

## 六、部署章节不够企业级

部署只有一段让 Agent 以 root 身份登录服务器的提示词，而且假设服务器上已经有一套 Caddy 部署（`/root/deploy/docker-compose.yml`），看起来是我们内部环境的做法。企业 IT 需要的信息基本缺失：

- 服务器规格；网络要求（Git 托管平台的回调和 Webhook 要能访问到 Studio）。
- 数据库选择：镜像里的示例配置默认用 SQLite。
- 关键配置：`APP_PUBLIC_ORIGIN`；`SECRETS_KEYS`（它加密所有已保存的凭据，丢失后这些凭据全部无法解密）；`APP_DEFAULT_LOCALE`（决定界面默认语言和预置标签的名称）。
- `/main` 是镜像默认的 `APP_BASE_PATH`，文档只说“保留 /main”，没说这是什么、能不能改。
- 运行环境的安全提示：界面上明确写着“执行机不是安全边界：请用专用系统用户、容器或虚拟机来运行它”，文档只有一句“建议使用隔离的虚拟机”。
- 镜像仓库的 Token 从哪里获得、Studio 自身怎样升级和备份。

用 Agent 部署的提示词可以保留，它符合 Studio 的工作方式；但企业运维需要一份能审阅、能复现的标准做法，这部分放进管理员手册。

## 七、术语和语言不统一

- 中文文档通篇用英文界面名和英文截图（Agent team → Runtimes、My issues、Add runtime、Fill in and enable）。Studio 有完整的中文界面：「Agent 团队 › 运行环境」「我的任务」「我的 Agent」「收件箱」。用中文界面的读者按文档找不到入口。
- 文档写“待审查”，界面是“待验收”。
- “Runner Agent”在界面上是会话面板里切换到 Agent 团队模式的叫法，文档却拿它作“配置运行环境和启用 Agent”这一章的标题。
- Runtime、运行环境、Runner 混着用。产品界面本身也不统一，见 [命名方案](03-命名方案.md)。

## 八、没有排错和参考

常见问题都没有说明：运行环境离线；编码工具没登录导致 Agent 不出现；任务排队 24 小时没人领取会过期；同一任务 24 小时内 Agent 之间触发的运行默认上限 20 次；Webhook 收不到；GitHub App 缺权限；个人账号没有仓库推送权限。也没有状态与权限表、术语表、命令参考。
