## 术语表

文档一律用左列的词。名称的取舍见 [命名方案](03-命名方案.md)；界面改名完成之前，右边两列是界面上现在的叫法。

| 文档用词 | 中文界面（现在） | 英文界面（现在） | 说明 |
| --- | --- | --- | --- |
| 任务 | 任务 | Issue | 不用“工单”“需求单” |
| 任务负责人 | 负责人 | Owner | 对任务结果负责的人，总是人；默认是创建任务的人。讲角色时用全称，指任务页上的属性时可以写「负责人」 |
| 执行者 | 执行者 | Executor | 几乎总是调度 Agent；少数任务由成员自己执行 |
| 调度 Agent | 项目经理 | Project manager | 全局唯一的系统 Agent，拆分步骤、分派、提问、交付验收，不写代码 |
| Agent | Agent | Agent | 一个“编码工具 · 模型”组合，例如“Claude · Opus 5.5”；只有调度 Agent、执行 Agent、我的 Agent 三种角色。不用“智能体”“代理” |
| 执行 Agent | Agent | Agent | Agent 团队里完成具体步骤的 Agent；评审、开发、初始化都是它做的一步，不另起名字 |
| 编码工具 | 编码工具 | Coding tool | Claude Code、Codex、OpenCode 等；正文不写“Coding Agent”（界面上的「用本地 Coding Agent 管理 Studio」照原样引用） |
| 擅长什么 | 擅长什么 | Good at | 启用 Agent 时必填，调度 Agent 据此分派 |
| 运行环境 | 运行环境；部分页面写作“执行机”“运行器” | Runtime / Runner | 运行 `nocobase-runner` 的机器，分团队和个人两种 |
| 我的会话 | 我的 Agent | My Agent | 按会话跟进的入口 |
| 我的 Agent | 我的 Agent（会话模式） | My Agent | 你连接到 Studio、自己直接驱动的 Coding Agent |
| Agent 团队 | Agent 团队（导航）；Runner Agent（会话模式） | Agent team；Runner Agent | 团队启用的全部 Agent；作为会话模式时，由运行环境领取执行 |
| 项目负责人 | 负责人（项目成员角色） | Lead | 与任务负责人区分 |
| 工作目录 | 工作目录 | Working directory | 项目的代码位置：仓库，或运行环境上的目录 |
| 初始化项目 | 初始化项目 | Initialize project | 新项目的第一个任务，其他任务等它完成 |
| 待规划 / 进行中 / 阻塞中 / 待验收 / 已完成 / 已取消 | 同左 | Backlog / In progress / Blocked / In review / Done / Cancelled | 任务的六个固定状态；不写“待审查” |
| 需要你 | 需要你 | Needs you | 任务页顶部的卡片，写明负责人要做的决定 |
| 交付报告 | 交付报告 | Delivery report | 调度 Agent 在任务进入待验收时提交 |
| 验收通过 / 合并 / 退回修改 | 同左 | Accept / Merge / Send back | 验收时的三个动作 |
| 评论 / 备注 | 评论 / 备注 | Comment / Note | 备注只给人看，不会唤醒 Agent |
| 运行记录 | 运行记录 | Runs | Agent 每次运行的过程、用量和结果 |
| 技能 | 技能 | Skills | 做事的方法，人和 Agent 共用 |
| 知识库 | 知识库 | Knowledge | 人写和上传的资料，Agent 只读 |
| 项目记忆 | 项目记忆 | Project memory | Agent 在工作中记下的经验，存进代码仓库，由 Agent 自己读写，人不需要阅读 |
| 收件箱 | 收件箱 | Inbox | 同事的消息和任务之外的事项 |
| Pull request（PR） | Pull request | Pull request | GitLab 上叫 Merge request；文档统称 PR |

## 界面名称的写法

- 界面上的名称、按钮、菜单一律用「」括起来，与界面文字一致（按命名方案改名的除外），例如「生成安装命令」。
- 界面路径用「A › B」，例如「Agent 团队 › 运行环境」「设置 › 集成 › Git」。
- 只写中文界面的名称。需要对照英文时，放在术语表里，不在正文里中英混写。

## 语气与用词

- 用“你”称呼读者，用短句，一句话说一件事。
- 中文与英文、数字之间加一个空格：“Agent 团队”“Node.js 24”。
- 直接说明能做什么、怎么做。少用“不是……而是……”和一连串否定句。
- 避免“X 很快，企业要的是 Y”这类对仗句、“不只是快：A，B，C”这类冒号列举，以及连续排比的“要……要……”。
- 讲价值时说“长期稳定迭代”，不用“改坏”“失控”这类制造焦虑的词。
- 检查项来自应用自己的 CI（代码规范、类型、测试、构建）和评审 Agent；不写“NocoBase 检查”。
- 只写已经核实的行为。没有核实的写进“待确认事项”，不在正文里猜测。

## 角色标记

概念页和流程图里，用颜色区分人和 Agent：<span class="who human">人</span> 用琥珀色，<span class="who agent">Agent</span> 用紫色，<span class="who sys">Studio</span> 等系统动作用灰色。操作步骤里不需要角色标记。

## 提示块

| 写法 | 用途 |
| --- | --- |
| `> [!TIP] 标题` | 好的做法、省时间的办法 |
| `> [!NOTE] 标题` | 需要知道的规则或背景 |
| `> [!WARNING] 标题` | 不注意会出问题的地方（安全、数据、不可撤销的操作） |
| `> [!PENDING] 标题` | 模块还在开发、内容待补充的位置 |

一页里的提示块不超过三四个，重要的事写进正文。

## 配图

### 用 HTML 画局部，而不是整页截图

文档的配图用 HTML 画出界面的一小块，只画正在讲的那一部分，例如“需要你”卡片、「现在」一行、一条交接评论。理由：

- **读者一眼看到重点。** 整页截图里信息太多，读者要自己找；局部图只有当前在讲的东西。
- **跟着文档主题走。** 深色模式、字号、手机宽度都自动适配，截图做不到。
- **改起来容易。** 界面文字或命名调整时，改 HTML 片段里的文字即可，不用重新搭环境截图。
- **没有隐私和凭据问题。** 示例数据是写出来的，不会带出真实的令牌、邮箱和内网地址。

真实截图只在一种情况下使用：读者需要在一个复杂页面里找到某个入口，而局部图不足以说明位置时。

### 配图的写法

- 片段放在 `doc/figures/名称.html`，正文里单独一行写 `::figure 名称 | 说明`。两张并排写 `::figure 名称一+名称二 pair | 说明`。
- 组件的类名见 `assets/docs.css` 的“Studio 界面配图”一节，写法与官网 `studio-ui.css` 一致：`.sw` 窗口（`.sw-top` 顶栏、`.sw-body` 内容、`.sb` 侧栏）、`.si` 状态图标、`.st-a` Agent 标识（`cc` Claude Code、`cx` Codex、`pm` 调度 Agent）、`.st-av` 成员头像、`.st-btn` 按钮、`.st-pill` 状态胶囊、`.st-chip` 标签、`.st-li` 列表行、`.st-dh` 任务页顶栏、`.st-le` 动态、`.st-cmt` 评论框、`.needs` 需要你、`.report` 交付报告、`.sess` 与 `.linkbar` 会话和任务进度条、`.lanes` Agent 队列。图标写 `<i data-lucide="名称"></i>`。
- 界面文字与中文界面一致（按命名方案改名的除外），示例数据用统一的故事：采购团队的“供应商管理”项目，任务编号 `PUR-23` 等，人名用常见中文名。
- 每张图下面写一句说明，说清这张图要看什么。

## Markdown 约定

- 每页开头写 front matter：`title`（页面标题）、`description`（标题下的导语）、可选的 `nav`（侧边栏里的短名称）。
- 正文从二级标题开始，二级标题会进入右侧的“本页内容”。
- 页面之间的链接写 `.md` 路径，构建时会换成 `.html`。
- 流程图、结构图直接写 HTML，类名见 `assets/docs.css` 里的 `.flow`、`.map`、`.states`、`.roles`、`.pillars`。
