文档方案 · Core 与统一文档站

读者与需求

NocoBase 3 的文档写给谁：每类读者是谁、来文档想解决什么、需要在哪里找到答案。这是 Core 文档和统一文档站的出发点。

从一个事实出发

NocoBase 3 里，应用是一份代码，由 Agent 基于 Core 编写。Core 是一组 npm 包：运行时、插件、基础库、UI 组件、技能和命令行。人很少直接操作 Core，提需求、做判断、验收、上线后的管理，都隔着 Agent 和应用。

NocoBase 2 的文档围绕配置界面写，读者照着界面点就能完成。到了 3，界面由 Agent 按业务做出来，每个应用都不一样，照着点的写法失去了依据。读者需要从文档里得到的是这五件事：

  1. Core 已经有什么，哪些不用让 Agent 从头写；
  2. 怎样让 Agent 用上它，需求要说清哪些事；
  3. 怎样判断 Agent 做得对不对；
  4. 上线以后谁能调整什么：哪些在应用的管理页面里改，哪些要改代码，哪些是部署配置；
  5. 应用怎样部署、运行和升级。

后面每一类读者、每一页文档，都围绕这五件事组织。

读者是谁

读者 他是谁 来文档想解决什么
评估者 CTO、IT 负责人、架构师；为客户选型的伙伴 判断能不能用 NocoBase 3 建自己的业务系统：Core 提供什么、还要自己做什么、开源和商业的范围、能否满足企业要求（数据库、统一身份、权限、审计、私有部署、成熟度）
应用开发者 在应用目录里指挥 Agent 的人：开发者、技术负责人，也包括懂一些技术的业务专家 让 Agent 做出对的东西：有哪些现成能力，怎样提需求，怎样检查结果，怎样增减插件、升级版本。Core 文档的主要读者
业务负责人、业务专家 提需求、做判断、验收的人；用 Studio 时是任务负责人 系统能做到什么，怎样把需求说清楚，验收时看什么
应用管理员 应用上线后维护用户、角色、权限和流程参数的人，常常是企业 IT 在应用的「系统设置」里管理用户和权限，看懂权限集、数据范围、共享与限制规则，知道哪些调整不必找开发
运维 部署和维护应用的人 部署、配置、数据库、文件存储、后台任务、备份、升级和回滚、排错
NocoBase 2 用户 用过 NocoBase 2 的开发者和管理员，社区里人数最多的一群 弄清 3 变了什么：插件管理器、配置界面、工作流设计器去了哪里；用过的 2 的插件在 3 里对应什么；要不要迁、怎样迁
插件开发者、伙伴 开发可复用插件、行业应用的团队 什么时候该写插件，插件怎样构成、怎样发布，怎样给插件配技能和 UI 组件
Studio 的团队 用 Studio 带领 Agent 团队的成员和管理员 见 Studio 文档结构。他们做出的应用同样建在 Core 上，提需求和验收时也会查 Core 的能力和插件

还有一类读者不是人：Agent。它通过技能（随包发布、同步到应用 .agents/skills/ 的 SKILL.md）学习怎样用每个包写代码，也会读文档站的 llms.txt。文档和技能怎样分工，见下文。

主要读者是应用开发者

Core 的读者里，应用开发者读得最多、最细。他坐在 Agent 旁边，每天都要回答“这个能不能用现成的”“Agent 这样做对不对”。评估者和 NocoBase 2 用户读得最急，他们要在几分钟里建立对 NocoBase 3 的整体认识，然后决定是否继续。文档的入门部分优先照顾这两群人，开发应用、能力和插件目录优先照顾应用开发者。

他们会问什么

问题 谁会问 来源 新文档在哪里回答
有哪些插件？每个插件做什么、提供了什么？ 开发者、评估者、2 用户 用户反馈 插件目录，每个插件一页档案
插件都没有界面了，它怎么用、怎么工作？ 2 用户、管理员、开发者 用户反馈 插件怎样工作
新建的应用里默认有什么？我的应用用了哪些能力？ 开发者、管理员 推断 快速开始；核心概念里的「应用底座」页
这个需求 Core 有现成的吗，还是要 Agent 从头写？ 开发者、业务负责人 推断 能力总览；每项能力的“开箱即有 / Agent 实现”
需求怎样说清楚，Agent 才不会做偏？ 业务负责人、开发者 推断 和 Agent 一起开发；每项能力的“怎样提需求”
Agent 做完了，我怎么检查对不对？ 开发者、业务负责人 推断 每项能力的验收清单；测试与验收
上线后改权限、改审批人，还要找 Agent 改代码吗？ 管理员、业务负责人 推断 系统设置；每项能力的“管理员能调整什么”
工作流设计器在哪里？审批怎么配？ 2 用户 推断 工作流与审批
哪些开源，哪些要商业授权？ 评估者 推断 插件目录的标记；开源与商业
支持我们的数据库吗？支持 LDAP、企业微信、钉钉登录吗？ 评估者、运维 推断 数据建模；用户与组织；插件目录
升级 NocoBase 会不会冲掉我们的修改？ 开发者、运维 推断 升级 NocoBase
2 的应用能迁到 3 吗？ 2 用户 推断 从 NocoBase 2 来
推断的问题需要核对

前两条来自用户反馈，其余来自对产品和读者的推断。正式编写前，建议从社区论坛、客户支持和售前记录里收集真实问题，补充和修正这张表，见 待确认事项。

文档和技能的分工

两者面对的读者不同，写法也不同：

文档（给人看） 技能（给 Agent 看）
回答什么 有什么、为什么、能做到什么、怎样提需求、怎样判断结果、上线后怎样管理和运维 怎样写代码：公开接口、目录约定、不能违反的规则、验证步骤
怎么写 业务语言，配局部图和示例，标明哪些开箱即有、哪些要 Agent 实现 精确到文件、接口和命令
放在哪里 文档站 随包发布，同步到应用的 .agents/skills/

文档不复制接口说明。插件页的“开发参考”只列事实（入口、页面、数据表、配置项、命令），再链接到技能和 README，给审查 Agent 代码的开发者查阅。接口变了只改一处，文档也不会和代码脱节。

技能本身对人也有用：开发者想知道 Agent 为什么这样做，读对应的技能最直接。文档在每项能力和每个插件页上注明对应的技能名称。

按读者的阅读路径

读者 先读 再读
评估者 NocoBase 3 是什么 → Core 是什么 → 一个应用怎样做出来 能力总览 → 插件目录 → 开源与商业
应用开发者 Core 入门五篇（含快速开始） 开发应用 → 按需查能力和插件
业务负责人、业务专家 Core 是什么 → 一个应用怎样做出来 能力总览 → 相关能力的“怎样提需求”；用 Studio 时读 Studio 的日常使用
应用管理员 核心概念 系统设置 → 用户与组织 → 权限控制
运维 快速开始 部署与运维 → 配置参考
NocoBase 2 用户 从 NocoBase 2 来 → 插件怎样工作 插件目录（每页有与 2 的对应）→ 工作流与审批
插件开发者 核心概念 → 插件怎样工作 扩展开发

这张表放在 Core 首页，统一文档站的首页再按“你要做什么”给出入口，见 统一文档站。
