文档方案 · Core 与统一文档站

Core 文档的问题

以目标读者的视角，逐项看现在的 NocoBase 3 Core 文档缺了什么、哪里会让读者走错。

历史分析记录。Core 当前内容和结构已按用户决定全部替换为现有 app-docs，以 Core 文档结构与写作原则 为准。

评审对象是 v3.docs.nocobase.com/zh-CN 的 Core 部分：首页、“能力”一章（14 组、56 页）、部署指南、NocoBase 2 与 3 的区别。源文件在 NocoBase 仓库 v3-develop 分支的 docs/docs/cn/，对照的是同一提交（4d61361，2026-10-23）的包代码、应用模板、技能和 UI 组件库，以及商业插件源码。

总体判断

“能力”一章用一家物流公司 Northstar 的业务串起各项能力，每页是“业务场景 + 一段提示词 + 搭建效果截图”。它清楚地传达了一件事：在 NocoBase 3 里，向 Agent 描述需求就能接入能力。认证、文件、定时任务等页面还有“完成后如何检查”和常见问题，这些写法值得保留。

问题在于文档只回答了“可以让 Agent 做什么”。读者要建立的心智模型、要查的事实、要做的判断都没有着落：

  • 没讲 Core 是什么、一个 NocoBase 3 应用由什么构成；
  • 只按能力组织，没有插件，读者查不到“有哪些插件、每个提供什么”；
  • 读者最困惑的“插件没有界面了怎么用”，文档没有正面回答；
  • 每页不交代哪些开箱即有、哪些要 Agent 实现、管理员上线后能调整什么；
  • 能力名称沿用 NocoBase 2，和 3 的实现对不上；
  • 运维只有部署，没有参考。

用户反馈里的两个问题，“每个插件的详细信息”和“插件没有界面了怎么用、怎么工作”，正是这几处缺口的直接结果。

一、没有讲 Core 是什么，也没讲一个应用怎样构成

首页的 Markdown 只有一句部署指引，能看到的首页是一张落地页，讲的是“一条命令创建应用、和 Agent 对话开发”。全站没有一页回答这些问题：

  • 应用是什么：用 pnpm create @nocobase/app 生成的一份代码仓库，归你所有，页面、接口、数据表、流程都在里面。
  • Core 是什么：应用依赖的一组 npm 包，包括运行时（app-server、app-client）、插件（app-plugin-*）、基础库（db、lifecycle、jobs 等）、UI 组件库、技能和命令行（pnpm nocobase）。
  • 插件怎样进入应用：在 server/plugins.ts、client/plugins.ts、cli/plugins.ts 三个清单里注册，由 pnpm nocobase plugin register 维护。
  • Agent 怎样学会用插件：每个包随附技能，安装后由 pnpm nocobase skills sync 同步到 .agents/skills/。
  • 谁拥有什么：页面、接口、数据表、迁移、业务逻辑归应用；插件拥有自己的路由、服务和内部数据表；.agents/skills/ 是生成的，不能改。

没有这些，读者只能把 NocoBase 3 理解成“一个会写代码的 AI”，看不出 Core 的价值，也无法判断 Agent 写的东西是否合理。

二、只有能力，没有插件

现在的目录按能力分组，读者查不到下面这些事实。它们都能从代码里直接读出来：

读者想知道 实际情况（v3-develop）
一共有哪些插件 开源仓库 23 个 app-plugin-*，商业仓库 2 个（审批、任务中心），另有约 30 个基础库和工具包
新应用默认装了什么 默认模板注册了 16 个插件；Agents 和知识库两个插件已安装但没有注册；Agent 会话、项目、发布、Web Push、模板打印不在模板里
哪些开源、哪些商业 审批、任务中心以及达梦、人大金仓、OceanBase 的数据库方言在商业仓库；其余在开源仓库
每个插件提供什么 差别很大：「应用底座」插件自带 /foundation 页面；任务中心自带 /task-center 页面；数据库浏览插件只有接口，不带页面；模板打印插件只有技能，没有任何运行时代码
插件之间的依赖 例如 Agent 会话依赖认证和文件；项目依赖认证、权限、文件、通知和用户

插件之间的这些差别，正是读者理解“插件怎样工作”需要的材料。

三、“插件没有界面了怎么用”没有正面回答

NocoBase 2 的用户习惯在插件管理器里启用插件，再到插件的设置页配置。在 3 里，一个插件给应用带来的是这几样东西：

  1. 服务端能力：服务、接口、数据表、权限检查，在应用的服务端进程里运行；
  2. 自带的页面（少数插件有），注册后出现在应用里；
  3. UI 组件：从 UI 组件库复制进应用的源码（client/extensions/），之后归应用所有，可以改；
  4. 技能：告诉 Agent 怎样用这个插件；
  5. 命令：例如定时任务插件的 pnpm nocobase scheduler sync。

管理入口也换了地方：应用开发技能要求 Agent 在交付应用时，默认把用户管理、角色与权限、流程管理、后台任务等页面做进应用的「系统设置」，复用插件的接口和 UI 组件。默认模板还带一个「应用底座」页面，列出这个应用实际用到了哪些 Core 能力、由哪些包提供、关联哪些业务模块。

这些都是读者理解 NocoBase 3 的关键，文档里一处也没有提。读者只看到“向 Agent 描述即可”，自然会问“那插件到底在哪里”。

四、每页只有提示词和效果，没有边界

一项能力落到应用里，有四个层次，现在的页面都没有分开讲：

层次 例子
开箱即有 文件插件的上传接口、文件表结构、存储驱动
Agent 在应用里实现 订单详情里的附件区、谁能上传和删除
管理员上线后调整 角色的数据范围、共享规则；流程的审批人和金额阈值（在「流程管理」里）
部署时配置 对象存储（drive.disks）、邮件服务商、jobs 用内存还是 Redis

读者分不清这四层，就估不出工作量，也不知道验收时该看什么。几个具体的例子：

  • 定时任务：计划写在代码里（defineSchedule），后台用 jobs 配置执行；只用内存时一个进程停止，状态写回 storage/jobs，多实例要用 Redis。文档没有讲。
  • 文件：页面说“由应用开发或部署人员将存储信息配置到应用服务端”，没有说配置在哪里、叫什么。
  • 权限：页面说“应用可以提供业务化管理入口”，没有说默认模板已经带了「用户管理」「角色与权限」「默认数据范围」页面。

五、名称沿用 NocoBase 2，和 3 的实现对不上

  • 工作流：工作流插件已在 2026 年 10 月从仓库删除，“工作流”一组实际讲的是 @nocobase/lifecycle（记录生命周期：状态在记录自己的字段里，流转在代码里声明）。NocoBase 2 的用户读到“工作流”，会去找可视化设计器。开发参考页写着“当前没有拖拽设计器”，但只有读到最后一页的人才看得到。
  • AI 员工：这是 NocoBase 2 的叫法。3 的插件叫 Agents，定位文档和官网叫“业务 Agent”。
  • 数据源：一组里同时讲应用数据库和外部数据库，和产品里的“数据建模”对不上。
  • 分类和产品不一致：应用自带的「应用底座」页把 Core 能力分成 13 类（数据建模、文件管理、用户与组织、权限控制、工作流与审批、AI 与 Agent、知识库、邮件互通、消息通知、外部集成、界面与配置、操作审计、基础运维），定位文档的“底座能力”也是这 13 项。文档的 14 组少了用户与组织、外部集成、操作审计、基础运维，多出主题、多语言、模板打印几组。读者在应用里看到的分类，在文档里找不到。

六、没有照顾 NocoBase 2 的用户

“NocoBase 2 与 3 的区别”讲清了理念：业务逻辑从数据库里的配置变成仓库里的源码。但 2 的用户接下来要问的事都没有答案：

  • 我用的 2 的插件，在 3 里对应哪个包，还是由 Agent 在应用里实现，还是暂时没有？
  • 哪些 2 的能力 3 还没有？例如操作审计，「应用底座」页的说明是“尚未识别到支持的提供方”。
  • 2 的应用怎样迁到 3？已经有客户项目在做迁移，文档里没有路径。

七、运维只有部署

部署指南写得扎实（PM2、Docker、Studio 三种方式，有升级前检查）。部署之后的事没有着落：

  • config.yml 有哪些配置项：app.publicOrigin、api 的请求上限、secrets（加密所有保存的凭据，轮换要按步骤做）、database、jobs、realtime 等；
  • 支持哪些数据库：SQLite、PostgreSQL、MySQL、SQL Server、Oracle，商业版另有达梦、人大金仓、OceanBase；
  • 多实例部署时，定时任务、实时更新、队列要改用 Redis；
  • 升级 NocoBase：应用随模板升级，由 nocobase-app-upgrade 技能对照新版模板合并，不会回退应用自己的修改；
  • 备份要同时备份数据库和文件存储；
  • 日志、健康检查（/api/healthz）、排错。

八、没有参考

没有命令行参考（pnpm nocobase 有二十多个常用命令）、配置项参考、HTTP 接口说明（运行中的应用在 /api/swagger 提供 OpenAPI 文档，文档没有提）、包与版本清单、术语表。

九、和 Studio 是两套文档

  • 线上的 Studio 文档是一个单页的安装清单，新的 Studio 文档草稿是另一套站点，结构、术语和样式都不同。
  • 用词不一致：Core 文档写“Coding Agent”“AI Agent”，Studio 写“编码工具”“Agent”。
  • 故事不一致：Core 用物流公司 Northstar；Studio、应用模板首页的提示词示例、定位文档和官网用的是采购和供应商管理。
  • 两边互不链接。Studio 新建项目用的就是 Core 的默认模板，Studio 里的 Agent 读的就是 Core 的技能，Studio 自己的项目、Agent、知识库、发布也建在 Core 的开源插件上，这些衔接文档里都看不到。

十、配图

  • 中文页面引用的 81 张截图里，77 张是英文界面（文件名以 -en.png 结尾）。
  • 截图拍的是 Agent 按提示词做出来的页面。每次实现的结果不同，读者容易把它当成产品自带的界面。应用模板自带的页面（登录、「系统设置」、「应用底座」、收件箱）反而没有配图。

保留什么

  • Northstar 一章里业务场景和提示词的写法：先讲业务，再给可以直接复制的需求，最后看效果。新文档的“怎样提需求”沿用这种写法。
  • 认证、文件、定时任务、多语言等页面的“完成后如何检查”和常见问题。
  • 部署指南的全部内容，并入“部署与运维”。
  • 审批、工作流的开发参考，改为插件档案和开发参考的一部分。

新的结构见 Core 文档结构与写作原则。
