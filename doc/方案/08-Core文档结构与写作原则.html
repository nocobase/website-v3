文档方案 · Core 与统一文档站

Core 文档结构与写作原则

新的 Core 文档怎样组织：先建立心智模型，再按能力和插件两个入口查找，最后是运维、扩展和参考；每类页面按什么模板写。

从第一性原理出发

Core 文档要解决的根本问题只有一个：读者和 Core 之间隔着 Agent，读者要能指挥 Agent、判断结果、管理和运行应用。由此推出文档的结构：

  1. 先建立心智模型。 应用是你的代码，Core 是 Agent 用来搭建它的一组包；插件给应用带来服务端能力、少数自带页面、UI 组件、技能和命令；管理入口做在应用的「系统设置」里。这一层不讲清，后面每一页读者都会问“那插件在哪里”。
  2. 用一个应用从创建到上线再到升级作为主线。 概念都挂在这条线上：模板、插件、技能、系统设置、应用底座、部署、升级。
  3. 能力和插件两个入口，互相链接。 能力回答“我要做 X，用什么、要说清什么、怎样验收”，按业务组织；插件回答“这个包是什么、提供了什么”，按包组织。读者从业务出发查能力，从代码或 NocoBase 2 的经验出发查插件。
  4. 每项能力分四层讲： 开箱即有 / Agent 在应用里实现 / 管理员上线后调整 / 部署时配置。读者据此估工作量、写需求、做验收。
  5. 文档写给人，技能写给 Agent。 开发参考只列事实并链接技能，不复制接口说明（见 读者与需求）。
  6. 事实以代码为准，能生成的就生成。 插件档案里的版本、许可、入口、自带页面、UI 组件、数据表、配置项、命令、技能，从包的 package.json、路由、迁移和配置样例生成，避免手抄过时。
  7. 分类和名称与产品一致。 能力按「应用底座」页的 13 类排列；界面名称按默认模板的中文界面写（「系统设置」「用户管理」「角色与权限」「流程管理」「应用底座」）。
  8. 照顾 NocoBase 2 的用户。 每项能力和每个插件都写“与 NocoBase 2 的对应”，另有一页“从 NocoBase 2 来”。

Studio 文档的写作原则（文档结构与写作原则、写作规范与术语）同样适用于 Core：先讲是什么再讲怎么做，每个操作写清四件事，配图只画正在讲的部分，以代码为准。

全站共用的“NocoBase 3 是什么”“开源与商业”“从 NocoBase 2 来”“术语表”放在「开始」部分，见 统一文档站。

几处取舍：

  • “快速开始”放进入门。 它是入门的最后一步，读者先有心智模型，再动手，动手时知道自己看到的是什么。
  • “开发应用”和“能力”分开。 前者讲和 Agent 协作的通用方法（怎样提需求、应用的结构、怎样验收），后者讲具体能力。通用方法只讲一次，每项能力页不再重复。
  • 运维单独成组。 部署、配置、升级是运维的事，和开发应用的读者不同；“开发应用”里的“升级 NocoBase”只讲开发者要做的合并与验证，运维步骤链接到“升级与回滚”。
  • 插件目录收录基础库。 @nocobase/lifecycle（记录生命周期）不是插件，却是“工作流”的实现，NocoBase 2 的用户一定会来找；@nocobase/db 决定支持哪些数据库。这两个单独成页，其余基础库合成一页。

入门

按陌生读者理解一个新产品的顺序：它是什么 → 一件事怎样做完 → 背后的概念 → 读者最困惑的那一点 → 动手。

  • Core 是什么：Core 提供什么（运行时、插件、基础库、UI 组件库、技能、命令行）；人、Agent、Core 的分工；什么是开箱即有、什么由 Agent 写；和 Studio、Solutions 的关系；开源与商业。
  • 一个应用怎样做出来：以采购应用为例，从创建到上线再到下一次改进，七步：创建 → 描述需求 → Agent 读技能、注册插件、写代码 → 试用和验收 → 管理员在「系统设置」里配置 → 部署上线 → 升级与改进。每一步写清人做什么、Agent 做什么、Core 提供什么。
  • 核心概念：一张图，按图从上到下讲十个概念：应用、模板、插件、基础库、UI 组件库、技能、命令行、配置、系统设置、应用底座。
  • 插件怎样工作：专门回答“插件没有界面了怎么用”。一个插件带来的五样东西；注册、同步技能、Agent 怎样用它；管理入口在哪里；怎样查看应用用了哪些插件；和 NocoBase 2 插件的对照。
  • 快速开始：约 20 分钟，安装技能 → 创建应用 → 认识首页的“内置能力” → 提第一个需求并验收 → 打开「应用底座」→ 接下来做什么。

插件目录

总览一页列出全部插件：名称、做什么、开源或商业、默认模板里的状态（已启用 / 已安装未启用 / 需要安装）、自带页面、技能。然后按能力分类，每个插件一页档案。基础库、UI 组件库、开发工具各一页。

页面模板

能力概览页

  1. 这项能力解决什么：一两段业务语言。
  2. 四层分工：一张表，开箱即有 / Agent 在应用里实现 / 管理员上线后调整 / 部署时配置。
  3. 由哪些包提供：每个包一行，标明开源或商业、默认模板里的状态，链接到插件档案。
  4. 在应用里看到什么：模板自带的页面和 UI 组件，用局部图画出来。
  5. 怎样提需求：要说清的几件事，加一段可以直接复制的示例。
  6. 怎样检查结果：验收清单。
  7. 限制与常见问题。
  8. 与 NocoBase 2 的对应。

场景页

沿用 Studio 操作类页面的模板，加上 Core 特有的两部分：

  1. 开头一两句：这一页解决什么问题。
  2. 前提：需要哪些插件、要先完成什么。
  3. 提需求：提示词，前面列出要说清的事。
  4. Agent 会做什么：注册哪个插件、读哪个技能、大致改哪些地方（数据表、接口、页面、系统设置），让读者知道该去哪里看。
  5. 查看效果：配图。Agent 做出的页面每次都不同，配图标明“示例效果”。
  6. 完成的标志：验收清单。
  7. 常见问题。

插件档案页

  1. 一句话：它做什么，什么时候用。
  2. 档案（生成）：包名、版本、开源或商业、默认模板里的状态、注册位置（服务端 / 浏览器 / 命令行）、依赖的插件、自带页面、UI 组件、数据表、技能。
  3. 它怎样工作：在服务端做什么、在浏览器里提供什么、Agent 怎样用它。
  4. 在应用里看到什么。
  5. 怎样让 Agent 使用：要说清的事和示例。
  6. 管理员能调整什么。
  7. 部署配置：config.yml 里的配置项。
  8. 限制与尚未支持。
  9. 与 NocoBase 2 的对应。
  10. 开发参考：技能、README、API 文档的链接，给审查代码的开发者。

档案部分由脚本从代码生成，其余由人写。插件页不写接口用法，那是技能的事。

写作规范的补充

在 写作规范与术语 之外，Core 文档还要遵守：

  • 四层分工必须写明。 不能只写“向 Agent 描述即可”。读者需要知道哪些已经有了、哪些要做、上线后谁来调。
  • 提示词写清要素。 谁用、在哪个页面、记录什么数据、规则是什么、谁能看谁能改、上线后谁能调整、怎样算完成。示例放在 text 代码块里，读者可以复制后修改。
  • 不写实现细节当需求。 提示词描述业务结果，不指定文件名和接口名；Agent 按技能决定怎样实现。
  • 界面名称分两种。 模板和插件自带的界面（「系统设置」「应用底座」「流程管理」）用「」照原样写；Agent 按需求做出的页面，写成“订单详情里的附件区”这样的描述，不加「」，因为每个应用不一样。
  • 代码名称只在开发参考里出现。 正文用“记录生命周期”“定时任务插件”，开发参考和档案里再写 @nocobase/lifecycle、@nocobase/app-plugin-scheduler。
  • 商业功能明确标注。 用 商业版 标记，并写明需要的授权。
  • Beta 状态明确标注。 现在所有包都是 beta 版本，档案里写出版本号；正式版之前，首页写明这一点。

发布形式

本地草稿和 Studio 一样：中文正文写在 doc/src/zh-CN/core/，node doc/build.mjs 生成到 doc/dist/zh-CN/core/。正式站点的落地方式见 统一文档站。

插件档案的生成：在 NocoBase 仓库里加一个导出脚本，读取每个包的 package.json（名称、版本、许可、入口、依赖）、client/routes.ts（自带页面）、registry.json（UI 组件）、database/（数据表）、skills/（技能）以及默认模板的三个插件清单（注册状态），输出一份 JSON，文档构建时填进档案。本轮草稿用同样的方法从 v3-develop 读取，生成了全部插件页的档案部分。
