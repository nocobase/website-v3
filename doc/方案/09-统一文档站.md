## 为什么合并

读者不按产品划分自己的问题。一位技术负责人可能先用 Core 和自己的 Agent 做出第一个应用，再上 Studio 让团队一起改；评估者要同时看懂两者的分工；Studio 的成员验收时，要查 Core 的能力和插件。两套文档各说各的，读者要在两套结构、两套用词、两个故事之间来回切换。

合并之后，一个站点、一套术语、一个故事、一种样式。

### “开始”部分

- **NocoBase 3 是什么**：一句话定位；人、Agent、NocoBase 的分工；Core、Studio、Solutions、Launch 各是什么；只用 Core 和用 Studio 有什么不同；应用上线后独立运行。内容取自《NocoBase 3 定位与产品结构》，只保留读者理解产品需要的部分。
- **开源与商业**：Community、Professional、Enterprise 各包含什么；具体到 Core 的哪些包是商业的。
- **从 NocoBase 2 来**：思路的变化；2 的功能和插件在 3 里的对应；还没有的部分；迁移路径。
- **术语表**：全站共用。Studio 的术语表并入这里，Studio 参考组里的“术语表”改为链接。

## Core 和 Studio 怎样衔接

两部分在这些地方互相链接，让读者看到同一套东西：

| 衔接点 | Core 一侧 | Studio 一侧 |
| --- | --- | --- |
| 应用从哪里来 | 快速开始：`pnpm create @nocobase/app` 用默认模板创建应用 | 创建项目：新项目用“NocoBase 应用默认模板”初始化，就是同一个模板 |
| Agent 怎样学会 Core | 插件怎样工作：每个包随附技能，同步到 `.agents/skills/` | 技能：Studio 里的 Agent 读的是同一批技能，Studio 再加上团队自己的技能 |
| 能力和插件 | 能力、插件目录 | 提需求、验收时链接到对应能力页 |
| 发布与部署 | 部署与运维：PM2、Docker 和通过 Studio 部署三种方式，现有部署指南已经这样写 | 发布与部署：在 Studio 里构建、审批、部署和回滚 |
| Studio 自己建在 Core 上 | 插件目录的“研发协作”：项目、发布插件；Agents、Agent 会话、知识库插件 | Studio 是什么：项目、Agent、知识库等能力来自 Core 的开源插件 |
| 上线后 | 应用独立运行，日常请求不经过 Studio | 同左 |

## 统一用词

[命名方案](03-命名方案.md) 和 [写作规范与术语](04-写作规范与术语.md) 为 Studio 定下的用词，全站沿用。Core 带来的新词，按同样的原则定下来：

| 文档用词 | 说明 | 不用 |
| --- | --- | --- |
| 应用 | 用 NocoBase 模板创建的一份代码仓库，部署后是一个业务系统 | 项目（Studio 里“项目”另有所指） |
| 模板 | 创建应用用的起点，默认模板和示例模板 | 脚手架 |
| 插件 | 注册进应用的 `app-plugin-*` 包 | 扩展、模块 |
| 基础库 | 应用直接使用、不需要注册的包，例如记录生命周期、数据库 | |
| UI 组件库 | NocoBase 发布的业务组件，复制进应用源码后归应用所有；单个叫“组件”或“区块” | Registry |
| 技能 | 随包发布、教 Agent 怎样用这个包的说明（`SKILL.md`）；与 Studio 的「技能」是同一个概念 | Skills（正文里） |
| 能力 | Core 提供的一类功能，按「应用底座」的 13 类划分 | 功能模块 |
| 系统设置 | 应用里的管理入口，模板中文界面的名称 | 系统管理、后台 |
| 应用底座 | 模板自带的页面，显示应用用到的 Core 能力 | |
| 记录生命周期 | `@nocobase/lifecycle`：记录的状态和流转在代码里声明 | 工作流（指机制时） |
| 工作流与审批 | 能力分类的名称，与「应用底座」一致 | |
| 流程参数 | 管理员在「流程管理」里可调整的审批人、金额阈值等 | |
| 业务 Agent | 在应用里、按权限处理业务的 Agent，由 Agents 插件接入 | AI 员工（第一次出现时注明“NocoBase 2 中称 AI 员工”） |
| Agent | AI 执行者的统称；写代码的 Agent 就叫 Agent，在 Studio 里再分调度 Agent、执行 Agent、我的 Agent | Coding Agent、AI Agent、智能体 |
| 编码工具 | Claude Code、Codex、OpenCode、Cursor 等 | Coding Agent |

“开发 Agent”只在需要和业务 Agent 对比的地方使用（例如 Core 是什么），其余地方直接写 Agent。

## 统一故事

全站用同一个企业的同一个应用做例子：**一家企业的采购团队，用 NocoBase 做采购应用**（供应商、采购订单、审批、到货）。Core 讲这个应用怎样从零做出来、用了哪些能力；Studio 讲团队怎样用 Agent 团队继续改它，例如“供应商分级”（任务 `PUR-23`）。

理由：

- 应用模板首页的提示词示例、定位文档和官网都在用采购和供应商管理；
- Studio 草稿已经用“采购团队的供应商管理项目”；
- 读者看到同一个应用在 Core 里做出来、在 Studio 里继续改，最容易理解两者的关系。

现有 Core 文档的 Northstar 物流例子逐步改写，截图同步替换，见 [待确认事项](10-Core进度与待确认事项.md)。

## 样式

- 全站同一个外壳：顶栏（Logo、版本、三个分区、GitHub 和官网链接），左侧菜单，中间正文，宽屏时右侧“本页内容”。只做浅色，配色和字体与官网一致。
- 配图沿用 Studio 的做法：用 HTML 画界面局部。Core 画的是默认模板自带的界面（首页、「系统设置」、「应用底座」、收件箱）和 UI 组件库的区块；Agent 按需求做出的页面，需要时用真实截图，标明“示例效果”，并且用中文界面。
- 结构图、流程图用同一套样式：人用琥珀色，Agent 用紫色，NocoBase 用品牌蓝。

## 正式站点怎样落地

正式站点就是 `doc/` 本身，由本仓库发布到 `docs.nocobase.com`，不再迁回 NocoBase 仓库的 Astro 站点（之前的建议已作废）。NocoBase 仓库的 v3 文档流水线已于 2026-10-25 停用，`v3.docs.nocobase.com` 整域 301 到 `docs.nocobase.com` 的同一路径，旧的 `/capabilities/...` 等地址不做逐页重定向。v2 文档迁到 `nocode.docs.nocobase.com`，`docs.nocobase.com` 上 v2 的旧一级路径和语言前缀 301 到 nocode 的同一路径。

1. **语言布局。** 英文在站点根路径，源文件在 `doc/src/`；简体中文在 `/zh-CN/`，源文件在 `doc/src/zh-CN/`。两种语言目录结构相同，页面一一对应。中文是基准，英文先放占位页（front matter 写 `status: placeholder`，页面提示读者看中文版），译好一页换一页。
2. **产物沿用 CDN 回源约定。** `node doc/build.mjs` 生成到 `doc/dist/`：每页输出成 `<路径>/index.html`，地址不带扩展名、以 / 结尾，站内链接和资源都用根路径；根目录有 `404.html`、`sitemap.xml`、`robots.txt`、`llms.txt`，每页另有去掉 front matter 的 `.md` 副本。canonical、hreflang、sitemap 用的站点域名读环境变量 `DOCS_SITE_ORIGIN`，默认 `https://docs.nocobase.com`。本地用 `node doc/serve.mjs` 预览。
3. **构建检查。** 菜单和源文件必须一一对应，正文里的站内链接必须写成相对的 `.md` 路径并指向存在的页面，否则构建失败。
4. **CI 和发布。** 本仓库是私有仓库，由 `nocobase-bot` 把 PR 和 `main` 的推送转发到 `2013xile/nocobase-ci`，用其中的 `website-v3-docs.yml` 构建 `doc/`；发布步骤上传到 OSS bucket `nocobase-docs-v3` 的时间戳目录，再切换 CDN 回源规则（逻辑取自 NocoBase 仓库的 `deploy-cdn.mjs`），直接上线 `docs.nocobase.com`。v2 旧地址的 301 写在 CDN 的 EdgeScript 里，按黑名单匹配 v2 的一级路径和语言前缀；CI 会校验黑名单和 v3 的一级路径没有冲突，免得把 v3 页面也转走。
5. **插件档案在构建时生成。** 导出脚本读取 NocoBase 仓库各包的信息，生成插件档案的 Markdown，版本号和包内容变了，档案随之更新（待实现）。

## 和产品保持同步

文档的分类和产品里的几处界面互相对应，改一边要同步另一边：

| 产品里 | 文档里 | 需要同步的 |
| --- | --- | --- |
| 默认模板首页的“内置能力”和提示词（代码注释写明按文档“能力”一章的顺序排列） | 能力总览、各能力的“怎样提需求” | 能力改为 13 类后，首页的分类和顺序随之调整；提示词与文档示例一致 |
| 「应用底座」页的 13 类能力 | 能力分组 | 名称和顺序一致；建议在每项能力的详情里加“查看文档”链接 |
| 模板的「系统设置」页面 | 系统设置、权限控制、用户与组织 | 界面名称一致 |
| 各包的技能 | 每个插件档案的“开发参考” | 技能名称和链接 |

## 推进步骤

1. 确认 [读者与需求](06-读者与需求.md)、本方案和 [Core 文档结构](08-Core文档结构与写作原则.md)，以及 [待确认事项](10-Core进度与待确认事项.md) 里的命名、故事和地址问题。
2. 统一站点外壳和 Core 的入门、能力总览、插件目录（本地草稿已完成）。
3. 写插件档案导出脚本，补全每个插件页的正文。
4. 按 13 类重写能力各组，把现有 Northstar 页面改写为采购故事。
5. 编写开发应用、部署与运维、参考。
6. 启用发布，切换 `docs.nocobase.com`，逐页补英文版。
