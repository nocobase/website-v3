《NocoBase 产品定义与标准表述》（下称“标准表述”）是产品定位和对外表述的唯一依据。官网首页、Studio 页、Core 页都已按它改写，Studio 文档也要按它改写：叙事的骨架、用词和句式与标准表述一致，读者从官网点进文档，读到的是同一个产品、同一种说法。

## 现有文档的问题

1. **叙事骨架不一致。** 文档首页和「Studio 是什么」用的是以前官网的说法：“Agent 完成执行，人只拍板”“每个人都能带领一支 Agent 团队”，再从组织、制度、流程、记录、决策五个方面讲价值。标准表述讲的是定义、标准介绍和四条核心特色。
2. **用词不一致。** “底座和流程”（标准表述是“底座和治理能力”），“通用能力”（标准表述是“基础能力”），「开始 › NocoBase 3 是什么」把 Studio 叫作“工作台”。
3. **没有从读者的问题讲起。** 标准表述里 Studio 回答两个问题：并行任务很多，人确认不过来；知识和经验难以沉淀和共享。文档开头讲的是 Studio 有什么。
4. **“各项进展一目了然”是散的。** 仪表盘放在「跟进进展」末尾，用量与费用只有占位页。
5. **产品又有变化。** 上次核对（2026-10-22，`19a3e83`）之后，Studio `dev` 又合入了 12 个提交，见下文“已核实的产品变化”。
6. **菜单里一半是占位页。** 对评估 Studio 的人来说，这会显得产品没做完。

## 读者带着什么问题来

Studio 的读者已经在用 Claude Code、Codex 开发，知道 Agent 是什么。他们来看文档时，带着标准表述里的这些问题：

| 读者的问题 | 标准表述里的回答 | 文档里的位置 |
| --- | --- | --- |
| 已经在用 Claude Code、Codex，为什么还要 Studio？ | 问题与方案、四条核心特色 | Studio 是什么 |
| 团队电脑和服务器上的 Agent 怎样接进来、分工、同时推进？ | 一支持续推进的 Agent 团队 | Agent 团队怎样工作；接入共享运行环境、启用 Agent、接入个人运行环境 |
| 我不盯着，怎样知道做到哪里了、花了多少？ | 各项进展一目了然 | 我的任务、跟进进展；项目进展、Agent 工作负荷与模型用量 |
| 什么时候要我出手？出手时手上有什么依据？ | 有理有据做决策 | 回答 Agent 的提问、验收；检查与评审、批准上线与回滚 |
| 换人、换 Agent 之后，背景和经验还在吗？ | 方法、经验、知识沉淀在团队里 | 技能、知识库、项目记忆 |
| 能私有部署吗？模型能自己选吗？ | 开源与私有部署 | Studio 是什么、安装 Studio |

同一个问题，不同角色要做的事不一样。例如“什么时候要我出手”，任务负责人要回答提问、验收，项目负责人要定检查的要求、批准上线。所以问题的答案分在几组里，见下文“文档结构”。

### Studio 解决的四个问题

标准表述的“问题与方案”里，归给 Studio 的只有两条：“并行任务很多，人确认不过来”和“知识和经验难以沉淀和共享”。只照这两条写，读者会以为 Studio 只解决两个问题，和四条核心特色对不上。

第一条其实包含了三件事，拆开后，正好对应前三条核心特色；FAQ 的“开发治理”一条补上了决策的另一面：

| 核心特色 | 问题 | 问题的出处 |
| --- | --- | --- |
| 一支持续推进的 Agent 团队 | 同时处理多个项目和任务，在多个终端和对话之间切换。Agent 分散在各自的电脑上，有人操作时才工作。 | 第一句来自“并行任务很多，人确认不过来”；第二句是新写的 |
| 各项进展一目了然 | 任务散落在不同的终端和对话里，做到哪里、卡在哪里、花了多少，都要一个个去问。 | 新写的，由“人确认不过来”展开 |
| 有理有据做决策 | Agent 交来的改动越来越多，人审不过来，往往直接接受，问题越积越多。 | FAQ 的“开发治理”，与“人看不过来，又不敢放手”是同一件事 |
| 方法、经验、知识沉淀在团队里 | 需求背景、业务资料、项目经验散落在不同电脑的不同会话里，换人、换 Agent 就很难找到。 | “知识和经验难以沉淀和共享” |

「Studio 是什么」按这张表写，每条特色先说问题，再说 Studio 怎样解决。新写的两句建议补进标准表述，见“需要更新标准表述的地方”。

## 文档结构

### 前两版的问题

第一版按四条核心特色分组，同一组里的页面是给不同的人看的。例如“Agent 团队”一组：接入运行环境是管理员做的，调度规则是项目负责人关心的，提出需求是每位成员都要会的。

第二版按角色分组，解决了这个问题，但没有按事情发生的先后组织。一家公司开始用 Studio，通常是一个人先部署，再做配置，配好一个项目，走完一个任务试一遍，然后邀请同事。按角色分组时，这个人要在“部署与管理”“管理项目”“日常使用”三组之间来回找。成员第一次进来，要先把自己的电脑接进来，这一步在第二版里没有位置。

### 按使用 Studio 的过程组织

文档主体按一家公司用起 Studio 的先后分组：一个人先搭建，同事再加入，然后是每天的使用和持续的管理。每组给一种角色看，组里的页面按这个角色做事的先后排列。

| 分组 | 给谁看 | 什么时候读 | 页面 |
| --- | --- | --- | --- |
| 入门 | 所有人，尤其是正在评估的人 | 了解 Studio 时 | Studio 是什么 · 一个需求怎样完成 · Agent 团队怎样工作 · 核心概念 |
| 搭建 Studio | 管理员 | 团队开始用之前，按顺序做一遍 | 安装 Studio · 连接 Git · 接入共享运行环境 · 启用 Agent · 新建项目 · 连接 CI · 走完第一个需求 · 邀请成员 |
| 加入团队 | 每位成员 | 第一次进入 Studio | 登录与个人设置 · 连接自己的电脑 · 在本地 Coding Agent 里使用 Studio · 接入个人运行环境 |
| 日常使用 | 任务负责人 | 每天 | 提出需求 · 我的会话 · 我的任务 · 跟进进展 · 回答 Agent 的提问 · 验收 · 收件箱与提醒 |
| 管理项目 | 项目负责人 | 项目推进过程中 | 项目设置 · 技能 · 知识库 · 检查与评审 · 项目记忆 · 批准上线与回滚 · 项目进展 · Agent 工作负荷与模型用量 |
| 系统管理 | 管理员 | 需要时 | 部署环境 · 成员与角色 · API 密钥 · 通知与推送 · 升级与备份 |
| 参考 | 需要查细节的人 | 需要时 | 任务状态与权限 · nb-studio 命令 · 配置项 · 常见问题与排错 |

角色和权限以 Studio 的内置角色为准：「成员」「管理员」「所有者」三个系统角色，加上每个项目的项目负责人、每个任务的负责人。

### 两条上手路径

**团队开始用 Studio。** 一个人（通常是管理员）把“搭建 Studio”从上到下做一遍：

1. 安装 Studio，用初始管理员登录。
2. 连接 Git：在「设置 › 集成 › Git」连接团队的 GitHub 或 GitLab。
3. 接入共享运行环境：在一台装好编码工具的服务器上安装运行环境，团队所有人的任务都可以在上面执行。
4. 启用 Agent：运行环境上报编码工具和模型后，写好每个 Agent「擅长什么」，启用；再为调度 Agent 选好首选和备选模型。
5. 新建项目：新建或选择代码仓库，用 NocoBase 应用模板初始化。
6. 连接 CI：需要 PR 预览、部署到各个环境时做。
7. 走完第一个需求：提出一个小需求，看调度 Agent 分派、检查和评审，回答提问，验收合并；连接了 CI 时，再在预览里试一遍，看它部署到预发布环境。
8. 邀请成员。

“走完第一个需求”是一篇引导，每一步只写最少的操作和完成的标志，详细说明链接到“日常使用”里的页面。原来的「快速开始」并入这一组，不再单独保留。

**成员加入团队。** 每位成员第一次进来时，把“加入团队”做一遍：

1. 接受邀请，登录；在「个人设置 › Git」连接自己的 GitHub 或 GitLab 账号，Agent 为你开的 PR 以你的身份进行。
2. 连接自己的电脑，在「我的会话」里和自己电脑上的编码工具讨论。
3. 在本地 Coding Agent 里使用 Studio：让自己常用的 Claude Code、Codex 通过 `nb-studio` 查询项目、创建任务。
4. 接入个人运行环境（可选）：把自己的电脑或服务器接成个人运行环境，只执行你自己发起的任务，用你自己的编码工具和订阅。

运行环境分两种，已对照代码核实：共享运行环境由管理员接入，执行所有人的任务；个人运行环境每位成员都可以接入，只执行它的主人自己发起的任务。两页各写各的角色要做的部分，系统要求和排错写在「接入共享运行环境」里，个人那页链接过去。

### 四条核心特色在哪里讲

四条核心特色在「Studio 是什么」里讲：每条先说问题，再说 Studio 怎样解决，然后链接到各组里的页面。

| 核心特色 | 对应的页面 |
| --- | --- |
| 一支持续推进的 Agent 团队 | 入门 › Agent 团队怎样工作；搭建 Studio › 接入共享运行环境、启用 Agent；加入团队 › 接入个人运行环境；日常使用 › 提出需求 |
| 各项进展一目了然 | 日常使用 › 我的任务、跟进进展；管理项目 › 项目进展、Agent 工作负荷与模型用量 |
| 有理有据做决策 | 日常使用 › 回答 Agent 的提问、验收；管理项目 › 检查与评审、批准上线与回滚 |
| 方法、经验、知识沉淀在团队里 | 管理项目 › 技能、知识库、项目记忆 |

### 一件事涉及几种角色时

各组只写这个角色要做的部分，再链接到别的组。以预览为例：

- 日常使用 › 验收：在任务页打开预览，用初始管理员登录，试一遍。
- 搭建 Studio › 连接 CI：连接代码仓库的 CI 之后，每个 PR 才有预览。
- 系统管理 › 部署环境：预览环境最多同时运行多少个预览，多久不用就停止、休眠。

日常使用一组不写 CI、分支、配置项，不写代码的业务专家也能照着做。需要先设置的，写一句由谁设置，链接到对应的页面。

## 每页怎样写

- **管理项目一组的页面**，先说这项设置让 Agent 团队怎样做，再写怎样设置。
- **操作页**依次写：这一页解决什么；前提；步骤；之后会发生什么；完成的标志；常见问题。不需要的部分省略。
- **入门页**先给结论，再给例子。一个需求怎样完成，用统一的故事：采购团队的“供应商管理”项目，任务 `PUR-23` “供应商评分与分级”，任务负责人是采购主管周航。官网 Studio 页的“业务专家”一节讲的是同一个故事。
- **例子符合真实的工作顺序。** 业务规则在提出需求、和 Agent 讨论时就确认；做的过程中向人提问的，是开工后才发现的事，例如写方案时发现和现有规则冲突。不能开发完、跑完 CI 才回头问需求阶段就该问的问题。
- **以代码为准。** 行为描述对照 Studio `dev` 分支的代码和设计文档核实；没核实的不写。

## 写给谁

Studio 文档的读者是已经在用 AI 开发或者 Vibe Coding 的企业：评估 Studio 的技术负责人，每天用 Claude Code、Codex 写代码的开发者，以及提出需求、验收结果的业务专家。他们熟悉编码工具，不需要解释 Agent 是什么；他们关心的是 Studio 用起来是什么样，能替团队省掉哪些麻烦，自己要做什么。

NocoBase 的目标用户是团队，不是个人。讲问题和场景时从团队的角度写：团队里每个人都在用 Agent，任务散落在每个人的终端和对话里，经验散落在每个人的电脑上。

所以文档从读者遇到的情况写起，用读者自己的话说。标准表述的原文要融进自然的句子里，不能为了和标准表述的条目一一对应，写出“四项核心特色分别解决这四个问题”这样生硬的话。

## 措辞规范

标准表述的写法就是文档的写法。下面的规则从标准表述里总结出来，和 [写作规范与术语](04-写作规范与术语.md) 一起使用；两者冲突时，以本节为准。

### 引用标准表述

- 讲定位、定义、价值和特色时，引用标准表述原文，或者在原文基础上缩写、扩写，不改逻辑，不换用词。
- 首页导语用定义；「Studio 是什么」用标准介绍、核心特色和它们对应的问题。
- 讲 Studio 解决的问题时，按四条核心特色讲四个问题，问题句尽量照搬标准表述，例如“人审不过来，往往直接接受”。
- 讲 NocoBase 和 Vibe Coding 的关系时，用 FAQ 的说法：Vibe Coding 让软件开发更加高效；NocoBase 在它之上补齐底座和治理能力。不把 Vibe Coding 写成反面。
- 不写重复的口号和附带说明。品牌表达用在官网标题上，文档不再作导语重复；“部署在企业自己的服务器上，在商业版中提供”只在「Studio 是什么」的“私有部署”一节讲一次。

### 编码工具

- Studio 支持 18 种编码工具：Claude Code、Codex、Gemini CLI、GitHub Copilot、Cursor、OpenCode、Qwen Code、Kimi CLI、CodeBuddy Code、Qoder CLI、Goose、Auggie、Factory Droid、Kilo Code、Cline、Amp、Mistral Vibe 和 Pi（`@nocobase/acp-bridge` 的工具目录加上运行环境原生支持的工具）。
- 引用标准表述原文时保留“Claude Code、Codex 等”。自己展开写时，多举几种常见的工具，例如“Claude Code、Codex、Gemini CLI、Cursor、OpenCode 等常见编码工具”，不要让读者以为只支持两种。
- 完整的列表放在「接入共享运行环境」，随产品更新。

### 固定用词

| 用 | 不用 |
| --- | --- |
| 治理平台（Studio 是什么） | 工作台、管理平台、协作工具 |
| 应用底座、底座（Core 是什么） | 平台底层、框架 |
| 基础能力 | 通用能力、核心能力、内置能力 |
| 底座和治理能力 | 底座和流程、底座和工作流程 |
| 人与 Agent 协同开发 | 人机协作、AI 协同 |
| 团队（只指人）；指 Agent 时说“Agent 团队” | 用“团队”指 Agent |
| 提出需求（人提出的是需求；需求在 Studio 里整理成任务，由 Agent 团队推进） | 交出任务、提出任务、把任务交给 Agent 团队 |
| 自主推进 | 自动推进 |
| 任务负责人、项目负责人、管理员（Studio 里的角色） | 技术负责人、业务负责人（作为 Studio 里的角色时） |
| Agent 团队 | Agent 集群、智能体团队 |
| 接入（Agent 接入 Studio） | 挂载、注册（`nocobase-runner` 的命令说明除外） |

### 句式

- **定义句**：“X 是 Y 的 Z。”一句话说清是什么，例如“NocoBase Studio 是人与 Agent 协同开发的治理平台。”
- **分工句**：主语是 Agent、人或 Studio，动作具体。例如“Agent 写代码、做执行，人来做决策”“Studio 组织多个 Agent 协同完成设计、开发、测试和评审”。
- **动作链**：按事情发生的顺序写，例如“接入后，组成一支 Agent 团队，由调度 Agent 分派设计、开发、测试、评审工作”。
- **结果句**：写读者能看到的结果，例如“每个任务做到哪里、下一步做什么，都一目了然”。
- **决策句**：先说 Agent 附上什么，再说人做什么，例如“需要人做决策时，Agent 会附上报告、清单、截图和建议，由人来拍板”。
- 有真实数字时写数字：“24 小时”“默认 20 次”“20 多项基础能力”。

### 不这样写

- 不写对仗句、排比句和“不是……而是……”。引用标准表述原文时除外。
- 不写“赋能”“无缝”“革命性”“重新定义”这类词，不写“智能体”。
- 不用破折号；一句话说一件事，用逗号、分号和句号。
- 不写讲文档自身的话，例如“本页介绍”“下面我们来看”“以下四项分别对应”；首页不写“关于这份文档”。
- 不写没有核实的能力，也不提前写还没上线的功能。

### 界面名称

- 界面上的名称、按钮写在「」里，路径写成「A › B」，与中文界面一致。
- 文档按标准表述写“调度 Agent”，界面上也全部用「调度 Agent」（2026-10-25 定）。截至 `dev` `c8b3c349`，界面上还叫「项目经理」，文档不再迁就，等界面改名。
- 侧边栏的分组现在叫「Agent 管理」，路径照界面写，例如「Agent 管理 › 运行环境」；正文讲的是“Agent 团队”，与标准表述一致。
