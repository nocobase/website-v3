# Website

`homepage/` is the source of www.nocobase.com. It is an Astro site and one package of the pnpm workspace at the repository root (the other is `packages/shared/`: the header, footer, styles, fonts, language table and Astro integration that the website and, later, the docs site share). Directory layout: `content/` holds the content sources (page bodies, translations, blog data, the sources of the NocoReach figures); `src/` is the Astro app (`pages/` routes, `layouts/`, `lib/` translation lookup, link rewriting and build checks, `styles/`, `scripts/` browser scripts); `public/` holds files that are copied as they are (favicon); `scripts/` holds the maintenance scripts (Node.js). `dist/` and `node_modules/` are not committed: change only the sources, and leave the build output to CI to generate and publish.

## Local development

You need Node 24 and pnpm 11 (the version is the `packageManager` field of the root `package.json`; use `corepack enable` or install it yourself). From the repository root:

```bash
pnpm install              # install the dependencies of the whole workspace
pnpm homepage:dev         # Astro dev server, reloads when a source changes
pnpm homepage:build       # generate homepage/dist/; fails on a broken link or a translation error
pnpm homepage:preview     # local preview at http://localhost:4322/ (PORT changes it), maps URLs the way the CDN rules do; build first
```

Inside `homepage/` the same commands work directly as `pnpm dev`, `pnpm build`, `pnpm preview`, `pnpm test`, `pnpm figs`, `pnpm i18n:extract` and `pnpm i18n:check` (the root `homepage:*` scripts only forward to them).

After changing a source, run `pnpm homepage:build` again and reload the preview. The preview server behaves like production: `/core` and `/core/` both read `core/index.html`, `/en/…` is treated as the root, and an address that is not found returns the root `404.html` with status 404. Other commands: `pnpm homepage:test` (vitest; tests the website and the shared package `packages/shared/`), `pnpm homepage:i18n:extract` and `pnpm homepage:i18n:check` (translations, see `content/i18n/README.md`), `pnpm homepage:figs` (regenerate the interface illustrations), and, inside `homepage/`, `pnpm cms:import` (import the CMS blog posts) and `pnpm fonts` (download the fonts again). Environment variables: `SITE_ORIGIN` (the site origin used for canonical, hreflang and the sitemap; default `https://www.nocobase.com`), `SITE_OUT_DIR` (another output directory) and `GITHUB_STARS` (the GitHub star count in the header, a raw number; see "Header and footer" below).

## Output and URLs

Every page is written to `<path>/index.html`; URLs have no extension and end with `/`, and links and assets inside the site use root-relative paths (CSS, scripts and fonts are bundled by Astro into `/_astro/` with hashed file names). The CDN's back-to-origin rules (`REWRITE_RULES` in `scripts/deploy-cdn/deploy-cdn.mjs`) depend on this layout; changing it takes the whole live site down with 404s.

- Language directories: English is at the root (`/`, `/core/`) and the other languages are under `/<directory>/`, named like the language files of the NocoBase 3 plugins: `zh-CN zh-TW ja-JP ko-KR es-ES fr-FR de-DE pt-BR ru-RU id-ID vi-VN`. `<html lang>` and hreflang use `en` for English and the directory name for the others, and `x-default` points at English. Do not generate an `/en/` directory (the CDN maps `/en/…` to the root). The language table (12 languages, code, directory, name) is in `packages/shared/src/languages.mjs`.
- The home page, Core, Studio, the Solution overview, NocoCRM, NocoITAM, Pricing, Become a Partner, Find a Partner and Contact Us exist in 12 languages. NocoReach, the blog (`/blog/`, `/blog/<slug>/`), customer stories (`/customers/`, `/customers/<slug>/`) and the changelog (`/changelog/`) exist only in English and `/zh-CN/`; in the language menu the other languages link to the English version.
- The root also has `404.html` (English; at publish time it is uploaded to the bucket root as well, and it is returned for an address of any depth), `sitemap-index.xml` and `sitemap-0.xml` (generated by `@astrojs/sitemap`; each address carries the hreflang links of all languages of the page and an `x-default` that points at English; noindex pages are left out; configured in `astro.config.ts`, with the `x-default` and filter logic in `packages/shared/src/sitemap.mjs`) and `robots.txt` (written by the shared package's Astro integration `packages/shared/src/integration.mjs`, pointing at `sitemap-index.xml`; the docs site's `llms.txt` and per-page `.md` copies will be added to the same integration later). The site origin comes from the environment variable `SITE_ORIGIN`, which canonical, hreflang and the sitemap all use.
- There is no redirect by browser language; switching language is an ordinary link. Each language is a separate page, and `window.__lang` in the page scripts is the language code written at build time (`zh`, `en`, `de`, …).

Build checks (the `astro:build:done` hook; the logic is in `src/lib/checks.mjs`; the build fails if one does not pass): every page and file an internal link points at exists, the translations are well-formed, every language has the same number of pages, and the output root has no `en` or `api` (the CDN maps `/en/…` to the root and passes `/api/ai/…` through; any other name in the output root, such as `_astro` or `favicon`, is allowed). A missing translation shows English, and a missing Traditional Chinese interface text shows Simplified Chinese; both only print a warning. Broken relative links inside blog posts (which come from the CMS) also only print a warning; fix them in the CMS.

## Which files to change for a page

- **Sub-page bodies**: `content/pages/<name>.body.html`, written in Chinese and English (`<t-zh>…</t-zh><t-en>…</t-en>`, `.zh-only` / `.en-only`, `data-ph-zh` / `data-ph-en` on forms). The meta lines at the top (`page`, `title_zh`, `title_en`, `desc_zh`, `desc_en`, `i18n`, `langs`, `noindex`) are described at the top of `src/lib/pages.mjs`. A body can start with a `<style>` block (it goes into the head), and what follows `<!-- AFTER-MAIN -->` is the page's own script. `{{SNIP:name:width}}` in a body pulls in an interface illustration from `content/pages/snips/`, and `{{DOCS}}` is the docs site `https://docs.nocobase.com/`. After changing the Chinese or English copy, update the other languages as described in `content/i18n/README.md`.
- **Internal links**: always write the source file name, such as `core.html`, `index.html`, `contact.html#contact` or `blog/<slug>.html`; the build replaces it with the address in each language (the English address when the page has no such language). Links to the docs site are written with the English address, and the build adds `zh-CN/` on Chinese pages.
- **Home page**: the first two lines of `content/pages/home.html` are the `<title>` and `<meta name="description">` with `data-zh` / `data-en`, then comes `<main id="top">…</main>` (the body, handled per language like a sub-page), then the video dialog and the home page's own script (placed after the footer). The home page has no navigation or footer of its own: like every page it uses the shared `Header.astro` and `Footer.astro`. Its own styles are in `src/styles/home.css` (only what differs from `site.css`; the home page loads `site.css` too), and it does not load `site.js` (its own script includes the sheet scaling). Routes: `src/pages/index.astro` (English) and `src/pages/[lang]/index.astro` (the other languages) for the home page, `src/pages/[...path].astro` for sub-pages, the blog and so on, and `src/pages/404.astro` for the 404 page; the shell is `src/layouts/Base.astro`. In the script, interface text uses `L(zh, en)` and marketing copy that needs translation uses `M(zh, en)`. An inline `<script>` (one without `src`) on a page runs after the page is parsed (`DOMContentLoaded`), because the bundled scripts (the icon library and so on) are deferred.
- **Header and footer**: the content (Chinese and English text, the menu structure, which item is highlighted) is in `src/lib/nav.mjs` and is shared by the home page and every sub-page. It is rendered by `packages/shared/src/Header.astro` and `Footer.astro`, styled by `packages/shared/src/styles/shell.css`, and the mobile menu and language select behave as written in `packages/shared/src/shell.js` (the mobile menu closes when a link in it is clicked). The Changelog entry under Resources has no published v3 release yet, so it is greyed out (`.soon`); once there is content, turn the menu and footer entries back into links in `nav.mjs`. The default GitHub star count in the header (`24.6K`) is in `packages/shared/src/config.mjs`, and the build uses the environment variable `GITHUB_STARS` when it is set; before the build, `site.yml` in CI reads the GitHub API with a plain `curl` without a token and falls back to the default when that fails. The browser never requests GitHub.
- **404 page**: `content/pages/404.body.html` (English only, `noindex`).
- **Blog, customer stories, changelog**: the data is in `content/blog/` (`posts.json`, `cs-posts.json`, `releases.json`), the page structure is in `src/lib/blog.mjs` and `src/lib/changelog.mjs`, and `getStaticPaths` in `src/pages/[...path].astro` generates each page from the data. `content/blog/cms/articles/` is a mirror of the CMS (cms.aliyun.nocobase.com); `pnpm cms:import` (inside `homepage/`) merges it into `posts.json` and `releases.json` (the display rules are at the top of `scripts/cms-import.mjs`). On import, old addresses of the v2 docs become `nocode.docs.nocobase.com`, and addresses in the posts that point at the old website (the NocoBase 2 era www.nocobase.com, which has moved as a whole to `nocode.nocobase.com`) become new addresses: old blog posts that exist on the new site become `/blog/<slug>/` or `/customers/<slug>/` (under `/zh-CN/` for Chinese), `/en` and `/cn` become the new home page, plugin pages become the plugin list of the v2 docs site, and the other old pages (those starting with an old language prefix and the old `.html` pages) become the same path on `nocode.nocobase.com`. The import also handles the hand-scraped posts and `cs-posts.json`. The rules are `legacySiteLinks` in `src/lib/links.mjs` (tested in `src/lib/links.test.mjs`), and the build applies the same rules again when it generates the blog, customer story and changelog pages. The Sungrow customer story currently has only a title and a summary (`SUNGROW` in `src/lib/blog.mjs`). The changelog of v2 and earlier is on the old website, and the changelog page links to it at the top.
- **Shared styles and scripts**: the color and font variables and the base styles are in `packages/shared/src/styles/tokens.css`, the header and footer in `shell.css`, and the rest of the website's shared styles in `src/styles/site.css` (the home-only `home.css` is described above). Scripts: `src/scripts/site.js` (sheet scaling, the Core figure interaction and so on; it does not handle language and the home page does not load it), `src/scripts/public-form.js` (the forms of the Contact and Partner pages, submitted to a NocoBase 2 public form; `site.js` loads it dynamically when the page has a form with `data-public-form-zh`) and `src/scripts/lucide.js` (the icon library: the npm package `lucide`, pinned to 0.460.0; pages write `<i data-lucide="name">`, and it is also exposed as `window.lucide`). Astro bundles all of these. Language-specific CSS uses the page's `<html lang>`, such as `html[lang="zh-CN"]` and `html[lang="ja-JP"]`.
- **Analytics**: the IDs of Google Analytics 4, Baidu Tongji and Microsoft Clarity are `ANALYTICS` in `src/lib/nav.mjs`, and the shared component `packages/shared/src/Analytics.astro` writes them into the head of every page (including the home and 404 pages); each site passes its own IDs, and the docs site will write its own in its own config. The IDs are the same as the old website nocode.nocobase.com, so the data goes into the same accounts, and reports tell the old and new websites apart by hostname.
- **Interface illustrations**: generated by the scripts in `scripts/figs/`. To change an illustration, change its script, then run `pnpm homepage:figs` and `pnpm homepage:build`. The fragments in `content/pages/snips/` and what the scripts write between the markers of `home.html` and `src/styles/site.css` are the scripts' output; do not edit them directly. CI runs `pnpm homepage:figs` again and fails if the result differs from what is committed.
  - `product-figs.mjs`: the Core first screen (`coreStack`, the same figure as `coreFig()` on the home page, so change the data in both places), Core "A unified architecture and conventions for agents" (`coreRepo`, based on `AGENTS.md` and `.agents/skills/` of the NocoBase 3 app template) and Studio "Progress at a glance" (`studioDash`, based on the dev branch of the nocobase-studio repository); it also syncs `content/pages/product-pages.css` into `src/styles/site.css` between the `/* PRODUCT-PAGES */` markers.
  - `studio-figs.mjs`: the Studio interface figures drawn in the style of real Studio screenshots (the Studio first screen `studioHero` and so on); it syncs `content/pages/studio-ui.css` into `src/styles/site.css` between the `/* STUDIO-UI */` markers (the home page loads `site.css` too and has no copy of its own).
  - `home-studio.mjs`: one figure for each of the four core features in the home page's Studio section, written into `home.html` between the `<!-- STUDIOTPL -->` markers; the same set is also written to `snips/stv*.html` for the Studio page. The styles are in `src/styles/site.css` between the `/* HOME-STUDIO */` markers.
  - `home-sol.mjs`: one figure for each of the six apps in the home page's Solutions section, written into `home.html` between the `<!-- SOLTPL -->` markers; the same set is also written to `snips/sol*.html` for the Solution page. The NocoCRM, NocoITAM and NocoReach figures are taken from the most central figure in each inner page's body, so run it after changing an inner page's figure. The one-line description and the "Learn more →" link of each app on the left are in `getAPPS()` in the home page script, and the Solution page's left side uses the same wording.
  - Most of the interface figures of the NocoCRM, NocoITAM and NocoReach inner pages are written directly in their own `.body.html`.
- **NocoReach product screenshots**: `content/reach/` (`figs.html` loads the product's own stylesheet `product.css`, `figs.js` follows the structure of the product pages, and the data is the Acme example from the promo video). After changing a figure, run `node scripts/reach-shoot.mjs [figure…]` (needs Chrome and cwebp); it writes to `homepage/.reach-shots/` (neither committed nor published). Upload the images to the root of static-docs.nocobase.com, and the pages reference the CDN addresses; when an image's size changes, change the width and height of the `<img>` too.
- **Images, videos, fonts**: images, videos and the favicon live at the root of static-docs.nocobase.com, pages write the full address, and a new image is uploaded before it is referenced. The fonts are in the shared package, `packages/shared/src/fonts/` (`pnpm fonts` inside `homepage/` downloads them from Google Fonts; to change a font or weight, change `SETS` in `scripts/fonts.mjs`; Astro bundles the font files that the CSS references into `/_astro/`). Chinese, Japanese and Korean use system fonts, and Russian uses Inter (`inter.css` is loaded together with the styles, and the browser downloads Inter only when a Russian page actually uses it). The icon library Lucide is an npm package; see `src/scripts/lucide.js` above.

## Content conventions

- The three product pages Core, Studio and Solution follow "NocoBase Product Definition and Messaging" (in the [nocobase/nocobase-v3-standard](https://github.com/nocobase/nocobase-v3-standard) repository): the brand statement is the H1, the definition is the lead, and each core feature gets a section in the order of the standard (the heading is the feature's original wording; the lead states the matching problem from "Problem and solution" first and then the solution, and a problem sentence must read as a difficulty at once; the Studio section "An agent team that keeps moving" keeps only the solution), followed by Open Source and Private Deployment and Get Started. The comparison with Vibe Coding appears only in the home page FAQ. To change copy, change the standard first and then excerpt from it.
- The split between open source and commercial on the pricing page follows the "Open Source and Private Deployment" section of "NocoBase Product Definition and Messaging".
- The business inquiry entry of the blog and customer story lists and detail pages points at the Contact page (`contact.html#contact`), and the button stays "Book a Pilot" (in Chinese 预约实战验证).

## Publishing

`.github/workflows/site.yml`: a pull request, or a push to `main`, that changes `homepage/`, `packages/shared/`, the root `package.json`, `pnpm-lock.yaml` or `pnpm-workspace.yaml`, this workflow or `scripts/deploy-cdn/` runs `Site build`: `pnpm install --frozen-lockfile` at the root, `pnpm homepage:test`, `pnpm homepage:figs` (which must not change any committed file), reading the GitHub star count and `pnpm homepage:build`. It checks that `index.html`, `zh-CN/index.html`, `404.html`, `sitemap-index.xml`, `robots.txt` and so on exist, and uploads `homepage/dist/` as an artifact. Only runs on `main` go on to `Site publish`: it uploads to a timestamped directory in OSS, switches the CDN back-to-origin rules according to `SITE_CDN_DOMAINS`, refreshes the cache, and keeps the newest 3 versions (see "CI and publishing" in the root `AGENTS.md`). A push to `main` changes the live www.nocobase.com directly.
