NocoBase Studio人与 Agent 协作Humans + Agents

带领一支 Agent 团队，每个人推进更多项目。Lead a team of agents. Everyone runs more projects.

开发中的绝大部分工作，已经可以交给 Agent。NocoBase Studio 是人带领 Agent 团队开发和改进应用的工作台：接入并统一调度大量 Agent，提供做事的方法和基础设施。规划、编码、测试、评审与部署由 Agent 完成，你只在需要判断时出场：回答提问、预览验收、批准上线。Most of the work in software delivery can now go to agents. NocoBase Studio is where people lead agent teams to build and evolve apps: it connects and schedules many agents and gives them a method and the infrastructure to work. Agents plan, code, test, review, and deploy. You step in only for the calls: answer questions, verify previews, approve releases.

分工Division of Labor

Agent 完成执行，Agents do the work. 人只拍板。People make the calls.

任务交给 Agent 团队后，由项目经理 Agent 编排：拆成步骤，交给最合适的 Agent 开发、测试、评审和修复；需要决定时向你提问，并写清要你做什么；做完后附上验收清单、截图和预览交给你。Once a task goes to the agent team, a project manager agent runs it: it splits the work into steps and hands each to the best-suited agent to build, test, review, and fix. When it needs a decision, it asks you and says exactly what it needs. When it’s done, it hands you an acceptance list, screenshots, and a preview.

  1. 01

    交代目标Set the goal

    一段话、一份资料，或一次讨论的结论都可以。在「我的 Agent」里把事情想清楚、建好任务，点开始。A sentence, a document, or the outcome of a discussion. Think it through in My Agent, create the task, and press Start.

  2. 02

    回答提问Answer questions

    方案取舍、业务规则和例外情况由你决定。任务进入「阻塞中」，写清需要你回答什么。Trade-offs, business rules, and exceptions are yours. The task goes to Blocked with exactly what it needs from you.

  3. 03

    验收与批准Accept and approve

    在独立预览环境里按验收清单走一遍。通过就合并上线；退回时说明原因，Agent 接着改。Walk through the acceptance list in an isolated preview. Accept to merge and ship; send it back with a reason and the agents keep going.

规划与开发Plan & Build

项目经理 Agent 拆分任务，把每一步交给最擅长的 Agent：梳理需求、提出方案、调用 Core 底座能力编写代码并互相评审。The project manager splits the work and hands each step to the best-suited agent: specs, code on Core, and peer review.

你敲定业务规则、交付边界与关键方案。You decide business rules, scope, and key approaches.

测试与验收Test & Verify

Agent 对照验收标准逐项检查功能、权限、数据迁移与回归场景，遇到报错自行修复重测。Agents test features, permissions, migrations, and regressions—fixing issues automatically.

你对照验收清单，在独立预览环境里亲手走查。You follow the acceptance list and walk through the live preview.

发布与运维Deploy & Operate

Agent 准备发布包与迁移脚本，执行上线前检查、数据备份，并在授权后完成发布。Agents prep releases, run checks, back up data, and deploy once approved.

你把控发版时机、变更范围与应急回滚预案。You control release timing, scope, and rollback plans.

受控上线Controlled Release

放手的前提：What makes letting go safe: 每次变更都经过检查。every change is checked.

Agent 做得越多，越需要可靠的检查。每次变更走同样的路：分支开发、自动检查、预览验收、人批准后上线，出了问题可以回滚。The more agents do, the more checks matter. Every change takes the same path: a branch, automated checks, preview verification, and human approval before release—with rollback if needed.

  1. 1

    分支开发Branch

    一个任务一个分支、一个 PR。One branch and PR per task.

  2. 2

    自动检查Check

    CI 跑代码检查、类型检查和测试，再换一家模型评审。CI runs lint, types, and tests; a different model reviews.

  3. 3

    预览验收Preview

    每个 PR 一个预览环境，人在里面验收。Each PR gets its own preview for acceptance.

  4. 4

    合并发布Merge

    验收后合并，按授权发布，发布前备份。Merge on acceptance; deploy as authorized, backup first.

  5. 5

    可以回滚Roll back

    出了问题，恢复到上一版。If something breaks, restore the last version.

每个 PR 一个预览A preview per PR

CI 随 PR 自动创建预览环境，带示例数据和独立的管理员账号；没人访问就休眠，合并或关闭后连同数据删除。CI creates a preview for each PR, with sample data and its own admin account. It sleeps when idle and is removed with its data on merge or close.

逐级推进，同一份构建Promote, don’t rebuild

预发验证过的版本推进到生产，按镜像摘要部署，每个环境跑的是完全相同的字节。Promote a verified staging release to production by image digest, so every environment runs exactly the same bytes.

受保护的环境要审批Protected environments need approval

指定审批人；不论是人、CI 还是 Agent 发起，部署都会变成发布请求。Agent 永远不能直接改动受保护的环境。Name the approvers. Whether a person, CI, or an agent deploys, it becomes a release request. Agents can never change a protected environment directly.

任务知道自己发到了哪Tasks know where they’ve shipped

任务上标着“预发 ✓ a1b2c3d”“生产 ✓ 1.8.0”；项目概览列出已合并、还没上生产的任务，回滚后标记自动撤回。Tasks are marked “Staging ✓ a1b2c3d” or “Production ✓ 1.8.0”; the project overview lists merged work not yet in production, and marks are withdrawn on rollback.

变量与密钥按环境管理Variables and secrets per environment

每个环境、每个应用各自的变量和密钥，页面上只显示“已设置”；版本列表写明还缺几个变量，缺了就不发。Each environment and app has its own variables and secrets, shown only as “Set”. Releases list any missing variables, and won’t ship without them.

选触发方式和目标环境，Studio 写好工作流和仓库密钥，或交给 Agent 开一个 PR；密钥到期前自动轮换。也可以接入你已有的流水线。Pick the trigger and target environment; Studio writes the workflow and repo secret, or hands it to an agent as a PR. Keys rotate before they expire. Or connect your existing pipeline.

上线后有人盯着Watched after release

运维 Agent 对照上线前后的错误和日志，发现异常就带着依据建议回滚，并提出要重新打开哪些任务。The ops agent compares errors and logs before and after release; if something’s off, it recommends a rollback with evidence and which tasks to reopen.

任意版本一键回滚Roll back to any release

每次部署都留记录：哪个版本、哪次提交、谁发起、谁批准。回滚就是重新部署一个旧版本，同样要经过审批。Every deployment is recorded: which release, which commit, who asked, who approved. A rollback redeploys an earlier release and goes through the same approval.

在你的环境里运行Runs where you choose

应用跑在 Studio 自带的应用主机上，或你自己的 Docker 服务器；镜像存在你选的仓库里。发布后应用独立运行，日常请求不经过 Studio。Apps run on Studio’s built-in app host or your own Docker servers, with images in a registry you choose. Once live, apps run independently—daily traffic never touches Studio.
