分工Division of Labor

从提需求到上线，From request to release, 人只在三个时刻出场。people step in only three times.

任务交给 Agent 团队后，项目经理 Agent 自动拆解步骤，分派给最合适的 Agent 开发、测试、评审和修复；拿不准时向你提问，完成后附上验收清单、截图与预览交给你。Once you hand off a task, a project manager agent breaks it into steps and assigns the right agents to build, test, review, and fix. It asks when a decision is needed, and delivers an acceptance checklist, screenshots, and a live preview when done.

  1. 01

    交代目标Set the goal

    一段话、一份文档或一次讨论结论都可以。在「我的 Agent」里聊清楚、建好任务，点开始。Start from a prompt, a doc, or a quick chat. Scope it in My Agent, create the task, and hit Start.

  2. 02

    回答提问Answer questions

    方案取舍、业务规则和例外情况由你决定。任务挂起时会明确列出需要你确认的问题。You decide trade-offs, business rules, and edge cases. Blocked tasks clearly state what they need from you.

  3. 03

    验收与批准Accept and approve

    在独立预览环境里对照清单走查。通过即合并，发布到生产由审批人批准；退回时写明原因，Agent 接着改。Walk through the checklist in an isolated preview. Approve to merge, with production releases approved by your approvers, or send it back with notes for the agents to revise.

规划与开发Plan & Build

项目经理 Agent 拆分步骤，安排合适的 Agent 梳理需求、调用 Core 编写代码并交叉评审。The PM agent breaks down work and assigns agents to write specs, build on Core, and peer-review.

你敲定业务规则、交付边界与关键方案。You decide business rules, scope, and key approaches.

测试与验收Test & Verify

Agent 按验收场景编写和运行测试，另一家模型评审缺陷与安全；CI 报错时自动修复重测。Agents write and run tests for each acceptance scenario, another vendor’s model reviews for defects and security, and CI failures are fixed and rerun automatically.

你对照验收清单，在独立预览环境里走查。You walk through the checklist in the live preview.

发布Release

CI 构建版本，部署到测试环境；发布到受保护环境时提交申请，获批后才部署。CI builds the release and deploys it to staging; for protected environments it files a request and deploys only once approved.

你把控发版时机、变更范围与回滚决策。You control release timing, scope, and rollbacks.

实时显示哪个 Agent 在做哪一步、改了哪些文件、过了多少测试。随时查看运行记录或直接接手。See which agent is on which step, what files changed, and how many tests pass. Inspect any run or step in anytime.

项目经理统一编排PM agent orchestration

项目经理按专长分配每一步。它本身不写代码、不合并 PR、不擅自结项，最终验收始终由人拍板。The PM agent assigns each step by strength. It never writes code, merges PRs, or marks tasks done; humans always sign off.

独立副本，并行不冲突Isolated repo checkouts

每一步在独立仓库副本中开发、测试、推分支、提 PR，几十个任务同时跑也互不干扰。Every step runs in an isolated checkout to build, test, push, and open a PR, so dozens of tasks run in parallel without conflict.

算力按需扩容Scale capacity on demand

加服务器即可增加并行槽位。成员电脑也能为本人的任务提供算力，只运行主人自己的任务。Add servers to add parallel slots. Member machines can lend capacity too, and run only their owner’s tasks.

跨项目统一排队Shared across all projects

同一支 Agent 团队服务所有业务项目，统一排队、并行执行、按序交付。One agent pool serves all your apps (CRM, support, HR, assets, growth), queued and delivered from one place.

集中管理权限与用量Centralized governance

Agent 代表发起任务的人工作，权限不超过这个人；接入的 Agent、API 密钥与用量费用集中管理，可随时停止运行或接手，每次运行全程留痕。Agents act for the person who started the task, never beyond that person’s rights. Agents, API keys, usage, and cost are managed in one place; stop a run or take over anytime, with every run on record.

业务专家Domain Experts

懂业务的人，也能主导系统开发。Know the business? You can lead the build.

非技术背景的业务专家用 AI 做项目，难的不是讲清需求，而是搭环境、管分支、写测试和发版。在 Studio 里，这些工程杂事全部由工作台、技能与基建代劳。For domain experts who don’t code, the barrier isn’t describing requirements; it’s managing environments, branches, tests, and deploys. Studio handles the engineering plumbing.

  • 技能：Skills: Agent 按官方规范写代码，产出遵循统一验收标准。agents follow official NocoBase coding standards and shared acceptance criteria.
  • 基础设施：Infrastructure: 运行环境、独立预览、测试与评审、发布审批全部就位。runtimes, isolated previews, tests and review, and release approval are built in.

技术负责人定规则、把关上线；业务专家定需求、负责验收。Tech leads set the rules and approve releases; domain experts drive requirements and sign-off.

受控上线Controlled Release

放心放手的前提：Why you can delegate with confidence: 每次变更都经过检查。every change is verified.

Agent 干得越多，质量把关越关键。每次改动都走完整闭环：分支开发、测试与评审、预览验收、人工批准上线，出问题可以回滚。检查项由团队定义，Studio 负责把关：通过检查才交给人验收，经人批准才进入生产。The more agents build, the more guardrails matter. Every change follows the same path: branch, tests and review, preview verification, human approval, and rollback when needed. Your team defines the checks and Studio enforces the path: work goes to a person once it passes, and to production once a person approves.

  1. 1

    分支开发Branch

    一任务一分支、一 PR。One branch and PR per task.

  2. 2

    测试与评审Check

    CI 跑语法、类型与测试，再换另一家模型交叉评审。CI runs lint, types, and tests; a second model cross-reviews.

  3. 3

    预览验收Preview

    每个 PR 独立预览环境，供人实测验收。Each PR spins up an isolated preview for human sign-off.

  4. 4

    合并发布Merge

    验收通过后合并，生产发布由人批准。Merge after sign-off; production releases need approval.

  5. 5

    一键回滚Roll back

    遇到问题，退回上一版本。Redeploy the previous release if anything breaks.

按 NocoBase 的规范评审Reviewed to NocoBase standards评审由另一家模型完成，结果附在任务与 PR 上；有必须修复的问题，就不能合并Another vendor’s model reviews every change; findings attach to the task and PR, and must-fix findings block the merge

缺陷Defects

是否做到了任务要求；迁移是否自包含，有没有改动已合并的迁移。Does it do what the task asks? Are migrations self-contained, with merged ones left untouched?

安全Security

权限检查是否缺失或放错位置，输入是否校验，密钥有没有外泄。Missing or misplaced permission checks, unvalidated input, leaked secrets.

用对底座Built on Core

平台已有的能力不重写，业务代码不修改 Core。Nothing Core already provides is rebuilt, and domain code leaves Core untouched.

测试Tests

测试是否证明了行为，有没有拖慢 CI。Do the tests prove the behavior without slowing CI?

多应用独立演进Multiple apps, independent cadences

同时管理多个应用，各自拥有独立仓库与环境，开发与发版互不阻塞；也可直接接入现有代码仓库与 CI 流水线。Manage multiple apps with separate repos and environments so builds and deploys never block each other, or plug in your existing repos and CI.

平滑跟进 Core 升级Core upgrades as tasks

Core 发布新版本时，把升级作为一个任务交给 Agent：按变更说明适配业务代码、提交 PR，经测试、评审、预览与审批后上线。When Core updates, hand the upgrade to agents as a task: they adapt your code to the release notes and open a PR that goes through the same tests, review, preview, and approval.

每个 PR 独立预览Preview per PR

CI 随 PR 自动拉起带样本数据的预览环境；空闲自动休眠，PR 合并或关闭后自动销毁。CI spins up an isolated preview with sample data for every PR. It sleeps when idle and cleans up on merge or close.

一次构建，逐级推进Build once, promote everywhere

预发验证通过的镜像按摘要直接推进到生产，确保各环境运行完全一致的构建产物。Promote verified staging images to production by digest, guaranteeing identical builds across environments.

受保护环境强制审批Approval gates on production

无论由人、CI 还是 Agent 发起，向受保护环境部署均须指定责任人审批，Agent 无法直接发版。Deploys to protected environments always require designated human approval. Agents can request, never deploy directly.

清晰追踪发布去向Release tracking per task

任务直接标注「预发 ✓」「生产 ✓ 1.8.0」；哪些已合并但未上生产一目了然，回滚后状态自动更新。Every task shows whether it’s on staging or live in production, and updates automatically if a release is rolled back.

环境变量与密钥隔离Per-environment secrets

按应用与环境独立管理变量和密钥，界面脱敏显示；发版前自动校验缺失变量，缺项不予发布。Variables and secrets are scoped per app and environment. Releases check for missing variables before deploying.

一键配置 CI 流水线One-click CI setup

选定触发方式与目标环境，自动生成工作流配置与轮换密钥；也可直接对接企业既有流水线。Auto-generate workflow files and rotating repo secrets, or plug right into your existing CI/CD pipeline.

回滚后自动对账Rollbacks reconcile tasks

回滚或部署旧版本后，任务上的上线标记自动更新，并为被撤下的改动生成重新打开任务的计划。After a rollback or an older release, each task’s release marks update on their own, with a plan to reopen the work that was withdrawn.

任意版本一键回滚One-click rollback

完整记录每次发布的版本、提交、发起人与审批人；经审批即可一键切回任意历史版本。Every deploy logs the version, commit, requester, and approver, making it easy to redeploy any prior release.

生产环境独立运行Standalone production runtime

应用可部署在 Studio 主机或自有 Docker 服务器上；上线后独立运行，日常业务流量不经过 Studio。Run apps on Studio’s host or your own Docker servers. In production, apps run standalone; live traffic never passes through Studio.
